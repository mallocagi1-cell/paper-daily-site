Today's retrieval papers put text, images, pages, and video into one servable multi-vector index, and also spend limited compute on the evidence that is actually worth it in relevance and long context. Some models barely lose accuracy after compression, and can locate a hit to a page or a video interval. Some relevance models distill reasoning into classification heads, so serving no longer generates tokens autoregressively. Video retrievers begin to teach time without giving up general retrieval, and search agents use a faster estimate to cut how often they rerank. Long videos allocate a token budget by diminishing value, and long tables first decide whether to compute statistics or fetch rows. When a gallery changes encoders, old and new vectors can be queried in one backfill pass. Answer lists from generative search are unstable, so visibility reports should say which items appear and which come first. A search engine can also query files that still live in object storage.

1. OmniEVIE: Evidence-Vector-Informed Embedding for Multi-modal Retrieval

Tencent

Multimodal retrieval has to match dense pages, fine-grained entities, ordered video, and agent tools. Single-vector embeddings lose local evidence, cross-encoders reread every recalled item online, and uncompressed late interaction is too large to serve. OmniEVIE is a 4.5-billion-parameter multi-vector model that covers text, images, visual documents, video, and tools with one compressed index and a three-stage retriever. Each record stores at most 128 int8 vectors of dimension 64, about 8.82 GiB per million records, and can locate a hit to a page region or a video interval. On the 190 tasks of MMEB-V3, the full sequence scores 60.68 and the compressed index still scores 60.06, almost no drop. A single-thread query over a million records takes 54.2 milliseconds. Video is encoded directly from frames, without a separate parsing model.

2. LARF: Learning-aligned Reasoning Framework for Search Relevance

WSDM 2027TencentSouthwest University

AI-native search has to judge whether a document meets a complex, multi-dimensional information need, and applying a large language model directly is not easy. Ordinary fine-tuning gives little supervision for domain-specific rationales, trajectory-level reinforcement learning may not separate adjacent relevance grades, and chain-of-thought reasoning is often too slow at serving time. LARF first does cold-start fine-tuning on multi-agent chain-of-thought samples, then uses discriminative reinforcement learning with a margin loss on the terminal relevance token, and finally distills the teacher into a student that keeps only classification heads for non-autoregressive inference. On a human-annotated web relevance benchmark with about 300 thousand training and 16 thousand test examples, LARF-8B raises six-class accuracy by 5.78 points and NDCG by 5.05 points. The classification-only serving path cuts inference latency by 82.9%.

3. Teaching Time Without Losing General Retrieval: Adapting Multimodal Embeddings for Time-Sensitive Video Retrieval

University of TokyoNNational Institute of InformaticsUUniversity of Augsburg

In text-to-video retrieval, multimodal embedding models do well when the text describes the scene, but poorly when it describes actions and their direction. Prior fine-tuning on temporal hard negatives improves time-sensitive retrieval but hurts general retrieval. The new method keeps one model and one vector per clip, and aims to hold on to both kinds of retrieval. It finds that a clip and its reversed copy often sit too close in video embedding space, so it widens that gap along the difference of their two text embeddings, and trains LoRA only in the middle layers where temporal information peaks. General R@1 stays at 58.4, while R@1 with each clip's reversed copy in the gallery rises from 55.5 to 63.2. Those LoRA parameters are only 0.15% of all weights, and on most time-sensitive benchmarks they nearly match training every weight.

4. SOARS: System One Assisted Reranking for Agentic Search

University of WaterlooThomson ReutersUniversity of Guelph

Deep search agents retrieve and reason over many steps, and the relevance of the evidence shapes later answers, but calling a reranker throughout the trajectory adds substantial latency and cost. SOARS needs no extra training. It uses a faster System One model for calibrated relevance estimates. At each step, a single call selects query-relevant passages from long documents and reranks candidates, taking into account both the original question and the agent's sub-query. Across six LLM backbones on BrowseComp-Plus and WebShaper, it raises answer accuracy and evidence recall while cutting search calls, end-to-end latency, and inference cost. On BrowseComp-Plus, GPT-5.4 Mini's accuracy rises from 73.9% to 84.7%. Search calls fall from 23 to 14. In other words, deep search need not call an expensive reranker at every step; a calibrated fast estimate can already cut how often it searches and what it spends.

5. Efficient Video Retrieval Augmented Generation via Token Allocation

University of Illinois Urbana-Champaign

Long-video understanding has to find the relevant evidence without sending too many tokens through a vision-language model. Existing video retrieval-augmented methods mostly select frames and compress tokens, but they rarely ask how much one more token is worth. Lembas treats the problem as allocating tokens to frames and subtitles under a shared budget. Its key observation is that a token is worth less inside the same item, and worth still less once similar evidence already has more tokens. It captures both effects in one objective and solves it with an iterative water-filling algorithm that has a convergence guarantee. In multi-turn conversations, it reuses tokens from earlier turns and refines relevance with the model's attention at no extra cost. Accuracy improves by up to 7.2 points over strong baselines at comparable compute. On multi-turn video understanding, accuracy is up to 1.5 points higher, using 1.7 times to 17.3 times fewer floating-point operations.

6. TableRouter: Query-Aware Evidence Construction for Long-Table Question Answering

Language models can reason over tables, but when a table outgrows the context budget, retrieving relevant rows is only part of the solution. A retrieved subset may omit what an exact aggregate needs, and even complete evidence can still be hard for the model to use. TableRouter needs no extra training. It analyzes the query and then chooses a route: one derives question-conditioned statistics from the full table, the other retrieves relevant rows and column summaries, and the chosen context is passed to a frozen language model in one call. Across three models and three large-table benchmarks, it outperforms the strongest of six single-call baselines in all nine settings. Explicitly providing computed statistics improves accuracy by up to 40.0 points, even when every answer-determining row is already in context. On long tables from databases not used in earlier experiments, it reaches 35.8% accuracy with Qwen2.5-7B, compared with 16.4% for the strongest external baseline.

7. RELAY: Learning Compatible Representations One Encoder at a Time

Alibaba

When a gallery switches to a new document encoder, old and new embeddings coexist during backfill, and a query vector often cannot score both document versions fairly. RELAY first trains a new query encoder with a learned projection against the original gallery, then freezes both and trains the new document encoder. The same query vector can score both document versions throughout a single re-encoding pass. After backfill, optional query refinement drops the projection and reuses the stored document vectors. Across three text-to-image upgrades on COCO and Flickr30K, it raises Recall@1 on galleries that have not yet been updated by 8.66 to 10.23 points over the original systems. After refinement, final Recall@1 is within 0.97 points of conventional joint training. An encoder upgrade therefore need not wait for the whole gallery to be rewritten before it can be used.

8. Ask Again: Answer-List Instability in Generative Engines

Visibility in generative search engines is measured by which entities appear in answers, and in what order. Ask the same question twice and the list can change: a different order, or different items altogether. Across 60,000 responses, answers to the same prompt name a different first item 32% of the time, and even two answers with the same items can disagree on which comes first. The first position is a measurement target of its own. A clear leader often emerges after seven or eight runs, which are the budgets recommended for brand and source monitoring, but a close leader appears only about half the time. Even after 25 runs, a close leader is identified only 60% of the time. Differences between engines are larger than those inside one engine. Visibility reports should say, for each engine, which items appear and how often each comes first, each with its own uncertainty.

9. Data Auctions for Retrieval Augmented Generation

NeurIPS 2026

When data is sold for retrieval-augmented generation, a buyer's value for a dataset rises as more relevant points are included that would help answer anticipated queries. If each data point can be licensed exclusively to only one buyer, welfare maximization is already NP-hard with two bidders. The authors give a polynomial-time algorithm that attains a (1-1/e) approximation for any number of bidders, but this efficient allocation is not incentive compatible on its own. The key patch is a post-processing step that burns some of the data: it keeps the same approximation factor and makes the mechanism incentive compatible. The same guarantee can be turned into a revenue-maximizing auction through virtual valuations. On synthetic data and on real image and text datasets, the method also works better than common baselines for combinatorial auctions.

10. No pipeline, no second copy: Querying Amazon S3 from Elasticsearch with ES|QL

Elastic

Retrieving historical logs or tables that already live in object storage usually means building a pipeline and keeping a second copy in the cluster, which is costly and slow. Elasticsearch's ES|QL Data Federation lets you register an Amazon S3 bucket as a data source and query Parquet, CSV, TSV, and NDJSON files with the same FROM syntax used for an index, without copying the data into the cluster. The schema comes from the file itself, so there is no ingest pipeline or mapping to build first. Filters and column selection push down into the Parquet reader, so a query reads only the columns it needs from S3. Federated identity keeps AWS credentials out of Elasticsearch. A single query can cover a hot index and cold objects that still live in the bucket. The feature is still in technical preview, so it is better treated as exploratory than as a wholesale move of production search.
