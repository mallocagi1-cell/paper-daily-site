ATTUNE: Agentic Throughput Tuning for LLM Training

Leo Fan, Hongyang Wang, Wenbo Chen, Jingguo Liu, Xian Li, Xuan Wang, Ruochen Wen, Yiming Yan, Hao Wu, Yichuan Li, Qian Qu, Zheshen Wang, Benoit Dumoulin
27 minread4.45score

Move the same model to a different GPU or framework version, and the training recipe that was tuned for it may no longer be the fastest. ATTUNE, from Amazon, hands recipe tuning to a coding agent. Starting from any working recipe, it searches unattended within a GPU-hour budget the user sets, changing one lever at a time. What makes the result usable is a correctness gate outside the agent: any argument that changes the training objective is refused before launch. Amazon's production post-training SFT recipes on H100, H200 and B200 get 1.7× faster on average and up to 3.9×. On four of NVIDIA's own AutoModel benchmark recipes, ATTUNE beats NVIDIA's published throughput by 6–17%. On MiniMax-M2, a model held out from development, throughput rises 2.6×.

1. The problem: throughput fixed knobs cannot reach, and "it runs" is not "it is unchanged"

A training recipe covers how the model is split across GPUs (TP, PP, EP, CP, DP), how much recomputation trades for memory, which kernels run and how communication overlaps. Existing automated tuners come in two kinds. Parallelization planners and vendor autoconfigurators search a fixed space with a cost model or a sweep. Black-box search such as Bayesian optimization needs no system model but many costly trial runs. Recent LLM-agent tuners such as OptiCo read profiles, but they too can change only a fixed list of knobs.

Two observations drive the design. First, the throughput a recipe misses lies partly in levers that only pay off when changed together, and partly in levers a fixed list does not include at all, such as virtual pipeline stages or a different expert dispatcher. Second, some configurations quietly change what is trained while the job still completes. The MoE expert capacity factor is a standard throughput argument, but it drops tokens that overflow an expert. --grad-reduce-in-bf16 reads like a communication flag, but it also disables FP32 gradient accumulation. A tuner that only checks whether a job runs could ship either as an optimization.

2. Method: one agent searches, deterministic code judges

Measurement. One tuning session is a campaign: one model, one cluster, a fixed GPU count. Across candidates, the model, data, sequence length, global batch, precision and GPU count stay fixed, and every run reads the same rows in the same order. Each run lasts a fixed number of steps. The first steps absorb startup and compilation and are not scored; the remaining window W is scored by aggregate throughput:

Summing before dividing keeps short steps from weighing too much. The baseline runs at least five times on different node allocations; its mean is the denominator, and the noise band is max(3%,3σ). A candidate replaces the leader only if it beats it by more than the band.

Search discipline. The agent uses ordinary tools: file search and reading (including the framework source in the training image), a shell and the cluster API. The skill sets six rules. State a hypothesis before each launch (which bottleneck shrinks, the mechanism, the expected gain). Change one lever, or one coupled set of parallelism degrees, per candidate. Before using a flag, read its implementation in the running image, including what it asserts and which flags it silently overrides, and record the code location in the ledger. Rule out a lever only after measuring two of its values or reaching its feasible limit, and call topology exhausted only after probing all five parallelism degrees. When trying a new layout, start without the leader's memory savings and add them back if it runs out of memory. Once the layout settles, re-test flags that won on earlier layouts.

Diagnosis. The agent mainly reads step time, per-stage memory and step-time variance within the window. When the bottleneck is unclear it profiles a run, tracing one rank per pipeline stage, and a deterministic trace analyzer splits each step into compute, communication, host-side and idle time.

Control plane and budget. To launch a candidate, a run generator copies the baseline job and changes only the flags and allowlisted environment variables under test. An accounting script charges GPU-hours from scheduler admission to release, including failed runs and correctness checks, and admits a launch only if it fits the remaining budget. The control plane also refuses to relaunch a recipe that failed, forcing the agent to diagnose and change it.

Correctness gate. The gate has two steps. Before launch, a configuration check compares the candidate's resolved arguments and environment with the baseline's (resolved values, because one flag can silently change others) and classifies each change in a registry no tuner can edit. "Known invalid" changes alter what is trained (data, batch, optimizer or its schedule, a loss term, routing, precision format) or trigger a known stack defect, and they are refused. "Known valid" changes alter only how the computation runs (placement, packing, or a same-math swap such as a fused kernel that matches an FP32 reference on identical inputs), and they pass. Everything else is "unknown": it goes on to the loss check and is listed in the report for review. After the run, the loss check requires the step-0 loss to be within 5% of the baseline's and every logged loss to be finite. Step 0 applies the same weights to the same first batch before any update, so a legitimate change moves it only through floating-point evaluation order, while wrong weight loading or sharding moves it by multiples.

Unattended operation. The harness builds on Claude Code's persistent-goal feature. A stop hook keeps the agent from ending its turn until the budget is spent or a stop is recorded with evidence. A pre-tool hook turns any question to the user into "take the default and record the assumption", and blocks unrecognized destructive shell commands. An append-only ledger is the single source of truth, so a fresh session can rebuild the campaign. At the end, the agent writes a summary and lessons, which enter the skill after human review.

3. Core contribution

The main contribution is the split of responsibilities: an open action space for the agent, and the verdicts kept in deterministic code. The agent may change any argument the framework exposes unless the gate marks it as objective-changing. Which measurements count, which candidate leads and which recipe ships are all decided by scripts the agent cannot edit. The authors also release OpenRecipes, a leaderboard of more than 60 recipes for more than 20 models, measured under one protocol (8,192-token SFT rows, global batch 128, BF16). Each entry lists tokens/s/GPU and cost per million tokens, and has passed Megatron-Bridge's convergence check.

4. Experiments

Against the strongest public recipes. There are two sets. The reproduced set is NVIDIA's four AutoModel benchmark recipes, run unchanged in NVIDIA's container on the H100s they target; three come within 2% of the published figures. The ported set is four models held out from development, trained on real text on slime and Megatron-LM.

The size of the gain depends on how far the original recipe is from the current setting. MiniMax-M2's recipe was written for RL on 128 GPUs with optimizer state in CPU memory; all three campaigns turned CPU offload off and deepened the pipeline. GLM-4.5's recipe was written for H100; on B200 it was diagnosed as bound by communication and kernel launches, so the expert all-to-all moved inside a node, and the fastest campaign also dropped TP to 1. Llama-3.1-70B dropped context parallelism and switched to FlashAttention-3, reaching a step that is 98.5% compute. The Mixtral and 405B recipes are vendor benchmarks for the same hardware and leave little room; Mixtral's best candidate stayed within the noise band, so the original recipe was kept.

Against other tuners on the same budget. Every tuner gets 30× the cost of one baseline run in GPU-hours, the same gate and the same shipping rule, with three campaigns per model. On GLM-4.5, ATTUNE averages +33.9% using 669 GPU-hours and 6.4 hours; OptiCo gets 0.0% (1,407 GPU-hours), random search +7.8% (1,688), BO +1.8%, and BO with a memory pre-filter +3.9%. On MiniMax-M2, ATTUNE reaches +164.2% against +55.5% for the best rival, BO with the pre-filter. Notably, ATTUNE's fastest GLM-4.5 layout (minus virtual stages) lies inside OptiCo's 11-knob schema and is within 2% of ATTUNE's recipe, but OptiCo never reached it: it tried TP=1 only with shallower pipelines and with EP still crossing nodes. The black-box searches had every winning lever in their space but no diagnosis to guide them; most draws ran out of memory or were pruned as slower than the leader.

Ablations. On GLM-4.7-Flash and Nemotron-3-Nano (8×H200, five campaigns per arm): without the skill, mean gain falls from +88.0% to +66.9% and from +49.4% to +42.9%, and failed launches rise to 50%. Restricted to OptiCo's knobs, GLM-4.7-Flash gets only +18.1%, because its biggest win is turning off CPU optimizer offload, which is not on the list. Without logs and profiles, gains are slightly lower but not significantly (p = 0.24 and 0.14).

The gate itself. On runs with a known answer, all 460 legitimate runs pass, and every configuration fault is refused before launch. Of six code faults, the two that change the forward pass raise the step-0 loss by more than 150% and are caught. Faults that act only through the update (such as skipping one gradient bucket's reduction) are invisible at step 0, and a loss mask shifted by one token moves the loss by only 2.0%, about as much as the largest legitimate change; these pass. In real campaigns, the configuration check refused 19 uneven pipeline splits on Nemotron-3-Nano. One of them was the fastest run: it loaded another layer's weights into the Mamba layers, with a step-0 loss 215–768% above baseline.

5. Limitations

The authors list three. The gate sees only the configuration and step 0, so faults acting only through optimizer updates go undetected, and a full training run is still needed before production. The lever catalog comes from past campaigns, and GLM-4.5 shares a family with the development model GLM-5.2, so some gain may come from priors; however, without the catalog GLM-4.5 lands within the same noise band as full ATTUNE. ATTUNE tunes only what the framework and image expose, not kernels or code, and does not cover RL rollout. The lessons also need curation: on review, about a fifth of the catalog entries were wrong, and some held only on the workload where they were measured.

6. What it means in practice

For training-platform teams, the gate and the accounting are worth borrowing more than the agent itself. Whether tuning is done by people or by an agent, you can build a check that diffs resolved arguments, uses a non-editable valid/invalid registry and compares step-0 loss, so that flags like capacity factor or bf16 gradient reduction, which quietly change the objective, are stopped before launch. Charge the budget from scheduler admission to release, failed runs included. Automated tuning pays most when a recipe was ported from other hardware or another task (such as RL). With a vendor benchmark recipe tuned for the same hardware, expect much less; such recipes gained 0–26% in the paper. Review the lesson library against the raw records periodically, and keep only entries the model does not already know or that correct its wrong intuitions.
