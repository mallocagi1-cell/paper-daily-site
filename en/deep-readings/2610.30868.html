uGDS: A User-Space Development Kit for High-Performance GPU Direct Storage

Jing Wei, Guanyi Chen, Qi Chen, Chuyu Zhang, Zheng Zhou, Chutian Wang, Jian Zhang
26 minread4.40score

When LMCache reads KV cache back from SSD through NVIDIA GPU Direct Storage (GDS), a single asynchronous stream reaches only 2.36 GiB/s, less than half (40.8%) of GDS's synchronous read bandwidth, and profiling shows 99.6% of wall-clock time spent inside submission calls. This paper, from Sun Yat-sen University, HKUST (Guangzhou) and others, open-sources uGDS, a user-space GPU Direct Storage library. The whole NVMe command lifecycle runs in user space on the CPU, and the kernel module handles only one-time privileged setup, while data still moves SSD-to-GPU by PCIe peer-to-peer DMA. On an A100 with a Samsung 990 PRO, uGDS reaches up to 12.12× GDS's batch-read bandwidth and 30.69× its batch-write bandwidth, saturates the device on a single stream (5.49 GiB/s), and inside LMCache cuts median time to first token (TTFT) by up to 62.7% while raising serving goodput 2.63×.

1. The problem: the data no longer detours, but control still does

GDS fixed the data path: the SSD reads and writes GPU memory directly through PCIe P2P DMA, with no staging in host memory. But its control path still enters the kernel on every I/O. Each cuFile call traverses VFS, the filesystem, the block layer and the kernel NVMe driver, and the nvidia-fs module intercepts each request's DMA mapping to translate every 4-KiB shadow page into a cached GPU bus address. Large transfers amortize this fixed cost; for the small, latency-sensitive requests common in KV-cache offloading and vector-index lookups, it becomes the main cost.

The authors identify two more gaps. One is over-strict ordering: cuFile's stream-ordered APIs inherit CUDA stream FIFO semantics, so every request is ordered after the previous one. Yet when LMCache restores a prefix, its chunks need no order among themselves; only the attention kernel must wait for all of them. Applications end up spreading I/O over many streams, doing the library's scheduling themselves. The other is opacity: the nvidia-fs kernel module is open source, but libcufile, which implements batch submission, worker threads and stream integration, ships only as a binary, so stalls can be neither inspected nor fixed by changing the scheduling policy. Earlier user-space prototypes such as libnvm/ssd-gpu-dma showed the approach is feasible, but they support only NVIDIA, assume a single submitter in their queue primitives, and do not track in-flight commands, so a buffer can be freed while the SSD is still writing into it.

2. Method: the CPU orchestrates, the SSD transfers, the GPU computes

Three separated paths. At setup, the application talks to ugds_drv.ko through a character device (open, mmap, ioctl): it claims the NVMe PCI device, maps the BAR0 controller registers and queue memory into the process, pins GPU memory across vendors, and optionally sets up an MSI-X interrupt bridge. During steady-state I/O the kernel module is not involved at all: libugds.so fills 64-byte NVMe submission entries (SQEs) in user space, builds PRP page lists, writes the mapped doorbell registers directly, and polls the completion queue (CQEs). Data flows only between SSD and GPU memory. The cost is that the SSD must be unbound from the kernel NVMe driver, and applications see block-device offsets rather than POSIX files. The authors argue this fits storage engines such as LMCache and Mooncake, which manage their own chunk pools; a user-space filesystem can sit on top when file semantics are needed.

Request translation. With logical block size B, a request must satisfy offsetmodB=0 and sizemodB=0, and the command fields are LBA=offset/B and NLB=size/B−1. A contiguous chunk of size C needs P=⌈C/S⌉ page descriptors (S is the controller page size): one page uses PRP1, two use PRP1+PRP2, and beyond that PRP2 points to a host-side page list. The synchronous path pre-maps one PRP-list page per queue pair (QP); larger requests are split by MDTS, or conservatively at 128 KiB when the controller advertises no MDTS. Memory fences before the doorbell write make sure the PRPs and SQE are visible to PCIe.

Cross-vendor GPU memory registration. uGDSBufRegister() translates CUDA or HIP virtual pointers into a vendor-neutral array of controller-visible page addresses, recorded in a process-wide buffer registry; on NVIDIA, physical page tables come from the peer-memory API at 64-KiB granularity. Registered buffers can also be exported as DMA-bufs for RDMA NICs.

Queue partitioning. QPs are statically split into two domains: a general pool for synchronous and stream-ordered requests, and one dedicated deep queue for batch I/O only, so bursty batch submissions do not inflate synchronous queueing delay. Within the general pool, an atomic round-robin counter picks a QP, and a request holds that QP's lock from submission until its final CQE, so ring indices and doorbells need no extra atomics. The batch path coalesces many commands into one doorbell write to amortize MMIO cost. Stream-ordered requests attach a host callback via cudaLaunchHostFunc, and the callback calls the same user-space engine as synchronous reads and writes.

DMA-safe lifetimes. This is where user-space drivers most often go wrong. Before each I/O, the library atomically takes in-flight references on the device handle and target buffers; releasing a handle or buffer with transfers still in flight returns -EBUSY. Each registration carries a monotonically increasing generation token, so a stale request cannot unpin a new buffer that reuses a just-freed virtual address. On a command timeout, the handle is marked wedged, all further submissions are refused, and the affected QPs and memory are quarantined; forced reclamation is allowed only after an external controller reset (such as a PCIe Secondary Bus Reset) has stopped the DMA engine.

Choice of completion mode. The default is busy polling. MSI-X interrupts are also available: the kernel interrupt handler only signals an eventfd, and CQEs are still reaped in user space.

3. Core contribution

uGDS's value is not the idea of kernel bypass itself; user-space NVMe (such as SPDK) has existed for years. Its contribution is turning that idea into a GPU storage library that matches cuFile's interface semantics and can replace it in production: synchronous, batch and stream-ordered APIs; one address abstraction shared by CUDA and HIP; DMA safety completed by in-flight references, generation tokens and fail-stop quarantine; and a fully open stack from kernel module to user-space engine, so performance anomalies can be traced command by command. The most practical point is that a single stream saturates bandwidth, so applications no longer need to fan I/O out over a dozen streams to get it.

4. Experiments

The testbed is 2× Xeon 8368Q, an A100-SXM4-40GB and a Samsung 990 PRO 1TB (PCIe Gen4×4, IOMMU disabled), compared with GDS 1.9 / libcufile 2.12.

Setup. uGDS's median setup time is 42.00 ms against 114.56 ms for GDS, 63.3% faster. GDS spends 111.83 ms in cuFileDriverOpen (opening the nvidia-fs session, loading configuration, discovering PCIe topology); uGDS spends its time registering the handle and configuring the controller and queues. This matters for elastic serving that frequently spawns and recycles workers.

Small synchronous I/O. The largest gain is at two threads and 4-KiB writes: bandwidth rises from 161 to 1003 MiB/s (6.23×) and mean latency falls from 48.36 to 7.69 μs (84.1% lower); 4-KiB reads rise from 111 to 543 MiB/s. With more threads and larger requests the bottleneck moves to the SSD and PCIe and the gap narrows: at 16 threads and 64 KiB, writes are 6264 vs 4542 MiB/s (1.38×) and reads 4616 vs 3855 MiB/s (1.20×). On AMD against hipFile, 64-thread 4-KiB writes rise from 2176 to 2596 MiB/s (1.19×).

Batch I/O. uGDS wins all 36 parameter combinations, with 2.12–12.12× GDS's read bandwidth and 2.33–30.69× its write bandwidth.

The authors chase an anomaly: with 128-KiB requests, GDS write throughput falls from 2373 to 502 MiB/s as the batch grows. The cause is the first batch. At batch size 128, GDS's first batch takes 90.84 ms for reads and 117.65 ms for writes, 87.7% and 92.2% of the whole 64-MiB transfer. nvidia-fs does not create the P2P mapping at registration but calls nvidia_p2p_dma_map_pages() on the first I/O; the authors suspect cuFile also lazily allocates batch state sized to the first submission. uGDS does all of this during setup, so its first batch matches later ones (2.46 vs 2.45 ms for reads). Excluding the first batch, at 4 KiB and batch size 128 uGDS is still 8.8× (reads) and 23.8× (writes) faster than GDS.

Streams and pipelining. In a serialized loop that synchronizes after every asynchronous read, uGDS is 4.10× faster than GDS at 4 KiB and 4.58× at 1 MiB. For sixteen pairs of "1-MiB write + identical GPU compute" under full pipelining, uGDS takes 3.03 ms and GDS 15.35 ms.

Polling or interrupts. For 4-KiB requests, polling cuts latency from 21.0 to 8.97 μs at the cost of one fully busy CPU core. For 1-MiB requests, MSI-X interrupts cut issuing-thread CPU use from 100% to 4.15% with only 5.5% more latency (245.3 vs 232.6 μs).

5. Limitations

uGDS must unbind the whole SSD from the kernel driver and gives up the filesystem, POSIX locks and page-cache coherence, so the drive cannot serve other processes as a normal disk. Each handle currently drives one local SSD; multi-SSD striping and NVMe-oF are on the roadmap. Synchronous requests get QPs round-robin and hold them until completion, so a large request can delay small requests on the same QP; the authors plan a load-aware scheduler. The experiments use one consumer 990 PRO, one A100 and IOMMU disabled, and the end-to-end test uses only the small Qwen3-0.6B; behavior with datacenter SSDs or many GPUs behind a shared PCIe switch remains to be shown.

6. What it means in practice

If you are building KV-cache tiering (HBM→DRAM→SSD) or GPU vector search on a dedicated local SSD, uGDS is worth testing as a GDS replacement, especially for small, frequent, single-stream reads, exactly where GDS suffers most. Before deploying, confirm three things: the SSD can be owned exclusively and unbound from the kernel driver; the layer above already manages its own block allocation (as LMCache and Mooncake do); and your IOMMU policy permits P2P. Choose completion mode per workload: busy polling for latency-sensitive inference nodes, MSI-X for throughput-bound or CPU-constrained pipelines. Even without switching libraries, the paper's analysis of GDS's lazy first-batch initialization and single-stream submission blocking is directly usable: warm up each buffer–device pair first, then spread critical reads over several streams.
