ForkPilot: Self-Evolving Policy for Retrospective Search in Long-Horizon Agents

Xinyue Zeng, Shivam Shandilya, Guilherme Potje, Leonardo Nunes, Rakshanda Agarwal, Ranveer Chandra, Emre Kiciman, Dawei Zhou, Tusher Chakraborty
30 minread4.15score

Long-horizon agent tasks call tools dozens of times in a row, and when one early judgment is wrong, the later steps keep working on top of the wrong premise. Retrospective search repairs this as follows: after a task fails, the agent reviews the whole trajectory, finds a recoverable earlier state, keeps the correct actions before it, and forks a new execution from there. The problem is that this search is expensive, and it is hard to decide in advance when to fork, how many times to fork and which trajectory to keep searching. With GPT-5.6 Sol on AutomationBench, a single agent run scores 43.7, and full Retrospective Tree Search (RTS) reaches 77.0, but its inference cost per task is also clearly higher. ForkPilot, from Microsoft and Virginia Tech, learns an allocation policy: at each moment where a fork is possible, it predicts whether "the extra score from this fork minus the extra token cost" is above zero, and it forks only if it is. On 6 benchmarks and 4 open-source models, compared with RTS it uses 36.2% fewer raw tokens on average while scoring 0.23 points higher on average. It only changes how much compute goes into retrospection; how the agent itself acts at each step is left unchanged, so it can wrap around an existing agent.

Below, I first explain why retrospective search is hard to allocate, then what each of ForkPilot's two stages does, and then three main experiments and two check experiments.

1. The problem: whether a fork was worth it is only known when the task ends

Retrospective search in long-horizon tasks has two concrete difficulties, and the authors gave each a name.

The first is Attribution Complexity. The effect of a fork only becomes visible after all later tool calls have run and the final reward arrives, and the final reward is shaped both by this fork and by every action after it. Making the same kind of fork from the same state produces final-score differences that vary widely, because sampling randomness and environment feedback differ. Estimating the average value of a fork accurately therefore needs many pairs of finished samples.

The second is Adaptation Complexity. New observations and search results change the current state, and the live environment itself changes too. What was learned on the previous batch of tasks, "forking pays off in this situation", may no longer hold on a new task.

The authors write the quantity to be estimated as a paired comparison. At decision point t, a candidate allocation u specifies the number of forks and the maximum depth of each branch, and u0 means no fork, continuing the current execution. Starting from the same restored state, the system runs to the end of the task once under u and once under u0:
Gt​(u)=E[R(x,τtu​)−R(x,τt0​)−λ(C(τtu​)−C(τt0​))​zt​]
Here R is the task reward (0 to 1), C is the token cost, including the generation and evaluation cost of branches that were not selected, λ converts cost into reward units, and zt​ is the summary of what the controller can see at that moment: the actions and observations so far, the branches already explored and their outcomes, and the remaining budget. Intuitively, Gt​(u)>0 means the extra score from this fork exceeds the extra cost. The authors call this characterization Search Value Dynamics (SVD). The paper also gives a bound showing that when an estimate fitted on old tasks is applied to a new state, the error comes from three parts: sampling error from too few samples, the change in the input state, and the change in the reward distribution itself. The authors state explicitly that this bound only explains why the two difficulties exist and provides no guarantee for the deployed controller.

2. Method: learn scores offline, decide by the lower bound online

ForkPilot has two stages. The first stage updates parameters between tasks; the second stage makes decisions inside a single task with the parameters fixed.

Stage I: build labels from finished trajectories. At a source-task state where a fork is possible, the system runs both "fork under u" and "no fork" to the end, obtaining a score difference Y~ and a normalized cost difference D~. Each pair labels only the allocation that was selected, and no human labels of the form "fork this many times here" are needed. The model is an encoder that turns zt​ into a vector, followed by M prediction heads trained on task bootstrap samples; each head takes the vector and a candidate allocation and outputs a predicted score difference and cost difference. Averaging the heads gives the net-value estimate G^t​(u).

A point estimate alone is not enough, because the two difficulties in Section 1 make the estimate inaccurate. ForkPilot trains an additional error model that predicts an upper quantile β^​t​(u) of the net-value estimation error; its inputs include the disagreement among the prediction heads, how close the current state is to the training data, and residuals on held-out samples, and it is calibrated on a separate set of source data. This gives a lower bound Lt​(u)=G^t​(u)−β^​t​(u) and an upper bound Ut​(u)=G^t​(u)+β^​t​(u). The authors stress that these two values are only decision scores, not coverage guarantees.

Stage II: closed-loop decisions inside a task. At every moment where a fork is possible, the controller scores all candidate allocations using the current zt​, with three tiers of rules:

  1. If some allocation has a lower bound above zero, fork with the one whose lower bound is largest.
  2. If no lower bound is above zero but some "small probe" allocation has an upper bound above zero, pick, among these probes, the one with the smallest predicted cost difference. The probes' fork count and depth caps are set in advance and are stricter than the limits the system allows.
  3. Otherwise, skip this round and continue the current execution.

The second tier spends a little to try when the outcome is uncertain but may pay off, and the new observations from the probe update zt​, so the next decision has more information. After a task ends, its decisions, branches, outcomes and costs are added to the experience pool, and Stage I refits the parameters on the enlarged pool; this is the "self-evolving" in the title.

An illustrative example (numbers are illustrative): at some moment, the candidate allocation "fork 2 branches, at most 5 steps each" has a predicted net value of 0.06 and an error upper quantile of 0.10, so its lower bound is negative and its upper bound positive; the probe allocation "fork 1 branch, at most 2 steps" has a positive upper bound and the lowest predicted cost. The controller picks this probe; it neither gives up outright nor launches a large search directly.

3. Core contributions

  • It formulates retrospective search in long-horizon tasks as an allocation problem defined by "score difference minus cost difference", and splits the difficulty into two kinds, attribution and adaptation.
  • It trains the allocation policy with labels built automatically from paired replay, with no human labels of the optimal allocation and no need for paired replay at every step during deployment.
  • It handles estimation uncertainty with three tiers of rules, lower bound, probe and skip, and updates parameters with new trajectories after every task.

4. Experiments

The experiments compare 9 baselines in three groups: test-time search (BoN-5, which samples 5 times and keeps the best; full Retrospective Tree Search RTS; Retrospective Depth Search RDS, which continues only from the last resumable node of the first trajectory), experience-based methods (ACE, ReasoningBank, Reflexion, GEPA and Trace2Skill, which use past trajectories to produce reflections, memories or skills), and GitHub Copilot's agent harness GHCP. The 6 benchmarks cover workflow automation (AutomationBench), tool-user interaction (τ³-Bench), software engineering (SWE-bench Verified), multimodal tool use (MM-ToolSandbox), web interaction (WorkArena++) and general interactive tasks (VitaBench). The metrics are task score S (0–100), plus the ratio of raw tokens R and the ratio of uncached tokens U relative to RTS; lower R and U mean more savings.

Experiment 1: does it save tokens consistently across benchmarks? The method is to compare ForkPilot with all baselines on the 6 benchmarks on 4 open-source models (DeepSeek-V4-Flash, Kimi-K3, DeepSeek-R1-671B, Qwen3.8-27B). The result is that, relative to RTS, raw tokens fall by 36.2% on average, uncached tokens by 30.3% on average, and task score rises by 0.23 points on average; raw-token savings per benchmark range from 31.8% on SWE-bench to 39.8% on AutomationBench. What it saves is the part of RTS's search that does not pay off, so the score does not drop with it.

Experiment 2: does the gain hold as model size changes? The method is to repeat the experiment at four Qwen3.5 sizes, 4B, 9B, 27B and 122B-A10B. The result is that raw-token savings rise from 28.5% at 4B to 33.7% at 9B and 37.0% at 27B, and are 35.8% at 122B-A10B; the score changes relative to RTS at the four sizes are +0.27, +0.27, +0.30 and +0.23 points. The authors read this as the gain saturating at the largest size.

The result is that ForkPilot used 58.8–77.8% of RTS's raw tokens and 40.8–76.3% of its uncached tokens; the "up to 59.2% savings" in the abstract refers to the uncached-token saving here. The scores deserve a close look: on both Sol benchmarks and on Opus AutomationBench, ForkPilot is below RTS (69.00 vs 71.83, 64.43 vs 67.53, 66.67 vs 70.83), and only on Opus τ³-Bench is it higher (48.31 vs 44.67). So on closed models it trades part of the score for cost. Compared with RDS, ForkPilot scores higher in all four settings with 53.1–78.9% lower raw cost, which shows that the gain comes from choosing the right place to fork; simply searching deeper along one trajectory cannot achieve it.

Check 1: does the gain come from leaked evaluator feedback? The prompt given to the agent during retrospection contains evaluator feedback, and the authors were concerned that the model might use it to "peek at the answer". The method is to remove the feedback and keep only the execution history (masked), or to shuffle the feedback across tasks (shuffled). The result is that on AutomationBench, Qwen3.5-9B scores 14.5 original, 14.4 masked and 13.0 shuffled; Qwen3.5-27B scores 25.6, 25.5 and 23.2. Removing the feedback barely changes the score, which shows that the gain does not come from answer cues in the feedback.

Check 2: how much experience is needed to learn well? The method is to learn the policy on AutomationBench with only part of the training data and compute what fraction of the full-training improvement is recovered.

The result is that with only 25% of the training split (13.3% of all data), it recovers 81–85% of the full improvement, and the remaining 75% of the data contributes only another 15–19%.

5. Limitations

The authors state that the theoretical bound only explains the two difficulties, attribution and adaptation, and provides no guarantee for the learned error estimate or the deployed controller; the upper and lower error bounds are only decision scores. Two facts to add: first, the method requires the host system to be able to restore earlier environment states, so forking is unavailable for real operations that cannot be rolled back (for example, a request that has already been sent); second, on closed models 3 of the 4 settings score below RTS, so the token savings come at the price of a small amount of score.

6. Practical takeaways

  • If your agent already uses retries or tree search, ForkPilot's approach can be borrowed directly: record "score difference minus cost difference" for each extra search as a training label and learn a scorer that decides whether to keep searching, with no retraining of the agent itself.
  • The three-tier decision rule (search big only when the lower bound is positive, probe small first when the upper bound is positive, skip otherwise) can be used on its own, and suits settings with a fixed compute budget where you do not want to miss searches that might pay off.
