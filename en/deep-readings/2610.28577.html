Cache Engineering for Agents

Tianyu Fu, Ruoxi Wang, Zihan Min, Zhongqi Ren, Zhihao Li, Tengxuan Liu, Shengxu Mu, Hanling Zhang, Yu Wang
27 minread4.30score

Once an agent runs for hundreds of rounds, the dominant cost is no longer generation but repeatedly reading the historical KV cache: by the paper's count, KV cache reads account for 82.4% of total API cost. The usual remedy is context engineering, trimming or summarizing old messages, but editing the prefix invalidates every later cached state and forces a re-prefill. A Tsinghua team proposes cache engineering: leave the text trajectory untouched, drop selected entries directly from the active KV cache, and reuse what remains as is. With its serving system AKV, a simple tool-response rolling-drop policy across three models and four agent benchmarks raises average scores by 1.7 points and cuts average cost by 27.7% relative to conventional threshold-triggered summarization, with 1.18× output throughput and a 1.51× speedup in P95 request latency.

1. The problem: re-prefill cost versus accuracy

Longer agent trajectories cause two KV-cache problems. On cost, retaining and repeatedly reading accumulated cache incurs heavy storage and I/O overhead. On accuracy, performance drops sharply once the number of attended KV states or their positional range exceeds what the model handles reliably.

Context engineering shrinks the cache by trimming or summarizing old messages, but the earlier the edit, the longer the suffix that must be re-prefilled. Common harnesses therefore wait until the active context hits a threshold, then trim or summarize most of the trajectory at once and keep only the last few rounds so recomputation stays short. Such abrupt cuts tend to lose useful information from intermediate rounds. The authors test GPT-OSS-120B on the first 100 BrowseComp-Plus (BCP) tasks (four trials each, at most 100 rounds): trim-based context engineering that keeps only the latest 12 tool responses costs 1.85× the full-context baseline, and summarization at a 48K threshold cuts cost by about 7% but loses 5 points of accuracy. Dropping older tool-response cache directly improves accuracy and reduces cost at the same time.

2. Method: three cache operations

Cache engineering separates two lengths: the trajectory's logical token length and the size of the active cache that takes part in later attention. Context engineering edits the logical sequence; cache engineering edits only the active cache. The paper defines three operations:

  • append: the standard cache update; it processes a new token, appends its KV entry and advances the position index by one.
  • drop(P): excludes the KV entries at indices P from later attention while leaving retained states, their position encodings and the logical sequence unchanged. Drop does not change the position index used by later appends.
  • repos: re-indexes the r retained entries to positions 0,…,r−1 in logical order, and the next token starts at r. For RoPE, moving a key from position p to q is just K←R(q)R(p)−1K; values are untouched and nothing is recomputed.

Repos is needed because drop does not reset the position index. Even with a small cache, indices keep growing with the logical trajectory and eventually hit the model's position limit.

To choose what to keep, the authors look at attention patterns: older tokens get less attention than recent ones, and at similar relative positions tool responses get less attention than assistant messages. The main policy is therefore tool-response rolling drop: keep all reasoning and the latest K tool responses ($K=12$ in the experiments), and progressively drop older tool-response cache.

3. The core challenge: cache state depends on history

With standard KV caching, the token prefix uniquely determines the cached state, so prefix matching suffices for reuse. Cache engineering breaks this: the same token sequence under different operation sequences yields different cache states.

Take the example: all three trajectories retain B and C, but in ① C was computed while A was visible, in ② C cannot see A, and in ③ B itself has no prefix. C's KV therefore differs in all three. The paper uses a cache operation sequence o1:m​ to describe state precisely: for a fixed model, starting from an empty cache, this sequence uniquely determines the current cache. The serving system must track both token history and operation history to reuse correctly.

4. The AKV serving system

AKV follows the principle of a stateless interface with stateful serving. The interface keeps the standard chat API: the messages field gives the full logical sequence as usual (each message implies an append), and a new optional cache field specifies drop and reposition with an "operate after message i" grammar. Clients need not know which KV states remain on the server; each round they simply extend the messages and operations as they normally would.

Internally, cache management preserves three properties: reuse only when states are equivalent; reclaim unused cache without breaking request isolation; restore evicted states in one prefill pass. Three mechanisms provide them:

  • Extended radix tree (reuse): when a request drops cache, a drop node recording the dropped indices is inserted at the trigger point on its path. Prefix matching compares both tokens and operations, so ① and ② share the A–B prefix but each keep their own C because they drop A at different times. Repos creates a new positional version by copying cache and rotating keys, forming a new branch with a reposition node; matching position indices allow direct reuse, differing ones require key rotation.
  • Drop-aware eviction: an entry becomes evictable only when no ongoing computation or restoration needs it. For example, once both ① and ② have dropped A, its cache can be freed before the requests finish. Dropped cache is evicted before cache from completed requests, which is more likely to be reused next round. Positional versions are evicted independently.
  • Segment-batch attention (restore): ordinary causal prefill cannot reproduce states shaped by drop and repos, and replaying them step by step needs many forward passes. At each layer, AKV splits queries at drop and repos trigger points; each segment attends causally to its own tokens and to cache from earlier segments that is still active, while dropped cache stays visible to the earlier segments that originally used it. Only attention is segmented; the FFN still processes the whole batch once, avoiding repeated FFN weight reads per segment. Segments needing different positions get temporary KV versions built by rotating keys and copying values.

5. Experiments

The baselines are two summarization-based context-engineering schemes. Standard uses a higher, model-specific threshold (96K for GPT-OSS-120B and MiniMax-M2.7, 192K for MiroThinker-1.7-Mini); Text Engineering uses the same policy with a 48K threshold for all models. AKV uses rolling drop that keeps the latest 12 tool responses, with the repos threshold equal to Standard's summarization threshold. Benchmarks are BCP, xbench-DeepSearch-2510, the 103-task text-only GAIA validation subset and SWE-bench Verified. Cost is computed from active input and generated tokens; to be conservative, every repositioned token is also charged at the cache-hit rate, deliberately overestimating key-rotation cost.

AKV has the highest average score on all three models, 1.3–2.1 points above Standard and 0.9–8.7 above Text Engineering, and its average cost is 27.7% below Standard and 21.9% below Text Engineering. It does not win every cell: on MiniMax-M2.7, Text Engineering is higher on BCP (62.3 vs 58.9) and Standard is higher on SWE-Verified (75.2 vs 74.4).

Where the accuracy gain comes from: on the first 100 BCP tasks with GPT-OSS-120B, all three methods are comparable below 48K logical tokens; Text Engineering is lowest in the 48–96K range and Standard is lowest above 96K, matching their respective summarization thresholds. This fits the explanation that abrupt cuts lose information, whereas rolling drop removes older tool responses gradually.

Serving efficiency (eight A800-80GB GPUs, four for prefill and four for decode, TP=4, Top-80 SWE-Verified): at each method's peak-throughput setting, AKV (concurrency 14) achieves 1.36× and 1.51× speedups in mean and P95 latency over Standard (concurrency 12), with 1.53× input and 1.18× output throughput. At concurrency 14 and 16, KV pressure increases Standard's re-prefill work, and its P95 latency reaches 229.90 s at concurrency 16 against 30.63 s for AKV. The latency breakdown shows the decode speedup comes mainly from less full-attention time: a shorter active context means fewer KV reads and less attention compute per step.

Ablations and policy exploration (GPT-OSS-120B, first 100 tasks per benchmark): dropping tool responses without repos gives 55.0 on BCP; adding repos raises it to 62.0, because exploration can continue instead of halting at the position limit. With repos enabled, dropping reasoning cache, alone or together with tool responses, is worse on both benchmarks than dropping tool responses alone; on SWE they score 36.5 and 34.5 against 41.0. Recursive self-improvement (RSI) uses MiniMax-M2.7 to refine policies on 20 BCP tasks and evaluates them on 100 held-out tasks; the policies from iterations 3 and 6 keep Standard's accuracy while cutting per-task cost by 15.6% and 17.8% relative to Standard. When cache management is exposed as a tool for the agent to decide, GPT-OSS-120B and MiniMax-M2.7 reach 61.0% and 64.0% on a BCP subset; cost falls from 13.4 to 12.1 cents for the former and rises from 5.4 to 5.9 cents for the latter, which runs more turns.

6. Limitations and what it means in practice

The authors list as future work further exploration of cache-engineering strategies, training agents under this scheme, and serving support for linear-attention models. A few more points are worth noting. The main policy is a hand-designed fixed rule (keep the latest 12 tool responses), and the best K may differ by task. The influence of dropped tokens persists in KV computed afterwards; the paper presents this as a benefit, but it also means results depend on operation order, so debugging and reproduction need the full operation sequence logged. Experiments ran in BF16 on A800, without native MXFP4.

For teams building agent platforms and inference services, the paper's value is moving context compression from the text layer to the cache layer. If your agents produce many tool responses (retrieval results, web pages, code-execution output) and you currently control length with threshold summarization, first measure how attention splits between tool responses and reasoning on your own trajectories, then try rolling drop of old tool responses plus repos, the most robust combination in the paper. The prerequisite is a serving stack that distinguishes operation histories: if the server matches only token prefixes, different drop timings under the same prefix will be reused incorrectly. AKV is built on SGLang, its code is open source, and its interface is compatible with the standard chat API, so clients only need to pass an extra cache field.
