The generative recommendation track has 10 papers today, 4 with deep dives, and the common thread is running generative recommenders in production. Kuaishou's GR4AD-X prunes ad candidates by revenue rather than generation probability. Alibaba's PFA has all beams share one ranking of important behaviors when decoding long histories, which saves most of the attention compute. Taobao's UGR generates the final list directly from about a thousand cross-business candidates, skipping separate per-business ranking followed by blending. RoFiGR uses collaborative signals to keep the first SID codes pointed in the right direction. Other papers train a query generator from retrieval results, make SFT tree-shaped, federate recommender agents and build a generative user embedding at DoorDash, and one audit shows that LLM recommendations shift with candidate order. Teams working on ad retrieval can start with GR4AD-X and PFA Teams working on blended feeds can start with UGR.

5. R2QRec: Learning Recommendation Queries from Retrieval Feedback

One way to use an LLM for recommendation is to have it write a few search queries from the user's history and pass them to an existing retrieval system. The catch is that logs record what the user clicked, not what query should have been written. The common fix imitates the clicked item's text, but such a query may not actually retrieve that item. R2QRec checks queries with a fixed retriever instead. It first generates many candidate queries and keeps only those that really retrieve the clicked item as SFT targets. The model then writes a set of queries, each retrieves a list, RRF merges the lists into one recommendation list, and GRPO rewards the set by where the clicked item lands in it. Only the query generator is trained; the retriever and item index stay fixed. On MovieTV, removing the retrieval check drops NDCG@10 from 5.07% to 4.03%.

6. Statistical Detection of Positional Bias in LLM-Based Recommender Systems: Methodologies and Empirical Evidence

Put candidate products into a prompt and ask an LLM to recommend one, and the order of the candidates by itself changes the pick. The authors built a RAG recommendation testbed on a real product catalog, shuffled the candidate order repeatedly for each query, and tested 8 models. Statistical tests confirmed that the recommendation depends on position for every model. The direction differs by model: GPT-OSS favors items listed first, while LLaMA 4 Scout avoids the first slot. It gets worse with more candidates. With 20 candidates, merely shuffling the order makes 58.1% of DeepSeek R1 7B's recommendations differ from the product it most often gives for the same query. The bias comes from the model itself and does not go away with a different temperature, so teams using LLMs for recommendation should randomize candidate order and audit for this regularly.

7. Merge and Branch: Efficient Tree-Structured Supervised Fine-Tuning of LLMs for Recommendation

In LLM generative recommendation, the input is a long, text-heavy history while the output is an SID of just a few tokens. Training spends a lot of compute reading a whole history and then usually learns only one target item from it. Merge and Branch first squeezes each history item into a handful of tokens. The item's per-level SID embeddings are combined into one anchor vector. A few learned offset vectors are each added to the anchor to form queries, which attend over the item's SID and text tokens. What each query picks up is added back onto the anchor vector to form one token. Second, the compressed history predicts several targets at once: the next item, later items and items a teacher model recommends. The targets share the same history like branches of a tree and cannot see each other. Beams share one history KV cache at decoding time. The history is computed once and every branch still sends gradients back. At a history length of 512, beam search uses 61.8% less memory and runs about a tenth faster.

8. Federated Recommender Agents

LLM recommender agents face a choice: pooling every user's memories raises privacy concerns, while isolated agents cannot learn from each other. FedRecAgent lets each client-side agent upload only experiences written in natural language, with no interaction logs and no model parameter updates. Each experience has three parts: what situation the user was in, how the next choice went (staying with the current interest, returning to an earlier one, or trying something new), and why. Specific items and personal preferences are stripped out. The server uses text similarity to group experiences with similar situations, merges those in a group whose choices are also alike, and keeps different choices apart. At recommendation time the next choice is unknown, so each client finds the group closest to its current situation, uses its local memories of preferences and choice habits to shortlist the best-matching experiences in that group, and lets the model pick one to guide ranking. Across six datasets, the best variant beats the strongest baseline on NDCG@10 by 1.54% to 9.19%.

9. PALATE: Pretrained Autoregressive LATent Embeddings

CIKM 2026 WorkshopDoorDash

Ads ranking on food-delivery and local-commerce marketplaces needs strong personalization, yet user histories are sparse and there are hundreds of thousands of stores. DoorDash's ranker used to rely on hand-built count features and order-free pooled history, with no learned representation of a user's sequence. PALATE trains a GPT-style model to predict which stores a user will engage with next from their behavior sequence, and takes the hidden state at the last position as the user embedding. It is refreshed daily and fed to the ranker of every ad surface as an ordinary feature. Because repeat orders dominate, training gives more weight to stores new to the user, pretrains on clicks and then fine-tunes on orders. Offline it is the largest single-feature AUC gain. Online it shipped inside bundled ranker retrains, and on search ads revenue rose 0.94% and conversion rate rose 1.50%.

10. Category-Anchored Large Language Models for Next POI Recommendation

ICDE 2027

When predicting a user's next point of interest (POI), asking an LLM to generate the POI ID directly is unreliable: POIs are numerous, scattered and long-tailed, and their names carry little meaning. ANCHOR changes the order. The LLM first predicts what category of place the user wants next, which is easier because categories are few and stable. Candidates are then gathered from three sources: places in that category, places the user has visited, and places in the categories the user favors over the long term, recently and at that time of day. Finally a reranker that looks at the user's past trajectories picks the specific place. Guessing the category first and then the place is steadier than guessing the place outright. On check-in datasets from New York, Tokyo and California, ANCHOR beats the strongest LLM baseline, Think2Go, on Acc@1 by 7.56%, 11.21% and 1.94%.
