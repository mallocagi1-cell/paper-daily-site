Infra — Paper Daily, 2026-10-25

Today's infrastructure theme is the cost of training and inference. Amazon has a coding agent edit training recipes directly, and uGDS moves the control path of GPU direct storage into user space. Several other papers cut the cost of long-context and agent workloads by compressing attention dimensions, using stratified sparse attention and managing the lifecycle of the KV cache.

LEAD STORY · Amazon

1. ATTUNE: Agentic Throughput Tuning for LLM Training

Amazon

Amazon engineers trained MiniMax-M2 on 64 B200 GPUs, starting from a recipe ported from a reinforcement-learning setup written for 128 GPUs that kept optimizer state in CPU memory. A coding agent asked to tune it turned that offload off and deepened the pipeline, and across three tuning runs throughput rose by 164.2% on average. Run for 1,000 steps, the tuned recipe stayed 2.66 times as fast as the public one, with loss differences within normal run-to-run noise. The agent reads framework code and run logs, finds the bottleneck, changes one setting or one group of related parallelism settings at a time, and keeps measuring within a fixed GPU-hour budget. Separate fixed checks block changes that alter the training objective and compare the first-step loss. On Amazon's real post-training jobs the tuned recipes were 1.7 times faster on average and up to 3.9 times faster. Training recipes hide a lot of untuned speed, and letting an agent search for it under strict correctness checks works.

2. uGDS: A User-Space Development Kit for High-Performance GPU Direct Storage

Running Qwen3-0.6B with vLLM and LMCache on an A100 GPU, the authors turned off in-memory prefix caching so reusable attention caches could only be read back from a Samsung SSD. For an already cached prompt of 32,768 tokens, NVIDIA's own GDS took 1915 ms to produce the first token; the paper's uGDS took 715 ms. GDS is the technology that lets an SSD send data straight into GPU memory without passing through host memory. After a one-time privileged setup, uGDS has the CPU issue storage commands and handle completions directly in user space, cutting out the middle layers. In a test with small 4 KiB reads and writes, its read bandwidth was 3302 MiB/s against 276 MiB/s for GDS. When LLM serving keeps caches on SSD, the software path for reading them back can itself be the biggest source of delay.

3. RACE: RoPE-Aligned Attention Compression Based on Query-Key Activation Energies

Running Llama-3.2-3B-Instruct on one H100 with a 256K-token prompt, 128 generated tokens and only half of the attention (KV) cache kept, overall throughput reached 1.79 times that of the uncompressed model. Total compute fell by 47.75% and allocated GPU memory by 28.06%. The paper also shortens each cached vector itself. Rotary position encoding rotates the dimensions of a vector in pairs, so dimensions can only be kept a pair at a time. On calibration text, the authors add up the squared activations of queries and keys in each pair as that pair's energy and keep only the highest-energy pairs, leaving their rotary encoding unchanged. These changes are folded into the model weights, so attention runs on shorter vectors without rebuilding the dropped dimensions. The cost is visible too, since adding this compression on Qwen2.5 7B cut average zero-shot accuracy from 0.706 to 0.604. Shortening cached vectors saves a lot on long contexts, but the harder you compress, the more accuracy drops.

4. Cache Engineering for Agents

Running GPT-OSS-120B on BrowseComp-Plus research tasks, dropping the cache for older tool responses while keeping the most recent 12 tool responses and the reasoning gave a pass rate of 55%. The kept tokens can also be renumbered consecutively from 0 in their original order, with the next new token continuing after them. This needs no recomputation, because rotary encoding just rotates vectors by position, so each kept key is rotated by the difference between its old and new numbers. That raised the pass rate to 62%, because the agent no longer hit its position limit and had to stop. None of this rewrites the conversation; it only stops the model from looking directly at the old tool responses. The serving system records these operations so it can correctly reuse or restore the cache later. Replaying 80 SWE-bench Verified code-repair tasks with the longest contexts on 8 GPUs, output throughput was 1.18 times that of the standard approach. Averaged over all tested models and tasks, inference cost fell by 27.7%. Most of an agent's old tool output can be dropped from the cache, saving money while letting it explore further.

5. Stratified Sparse Attention: Reducing the Sparse-to-Dense Gap at Extreme Sparsity

Qwen3.5-9B solved AIME 2025 problems with up to 32K generated tokens each, while reading only one fiftieth of its attention cache for every token. The paper's method, SSA, had a mean accuracy of 59.8%, against 36.7% for PQCache at the same sparsity. The reading budget is split in two, 3 to 2 in the paper's analysis. The first part keeps the highest-scoring cache entries by cheap approximate scores, computed by table lookup from a 16-byte code each key is compressed into. The second part samples randomly from the rest, and a higher approximate score makes an entry more likely to be picked. Exact attention is computed only for the chosen entries, and sampled ones are reweighted by their chance of being picked. That lets lower-ranked information still shape the next token without reading the whole cache. On one H200 with a context of 1M tokens, decode attention was up to 2.96 times faster than FlashInfer; this is the attention layer's speed, not a whole application's. At extreme sparsity, keeping only the top scores loses information, and a little probability-weighted sampling wins back much of the accuracy.

6. Scaling NVIDIA TensorRT Performance Optimization Beyond a Single Build Route with the Global Performance Tuner, Part 2

NVIDIA

NVIDIA compared TensorRT's default build route with the best route its global tuner found on ten workloads, and tuning made them 1.14 to 1.63 times faster end to end, with large differences between models. The reason is that the better optimization depends on the model. One compiler pass can fuse horizontally, merging several independent side-by-side operations into one GPU kernel, or vertically, merging consecutive operations into one, and which is faster depends on the model, tensor shapes and target GPU. Quantization is similar: the post imagines a network with 4 places for quantization nodes, giving 16 combinations, where quantizing everything may be fastest but may miss the accuracy target. So the TensorRT global tuner turns compiler options into combinable switches, builds and measures each engine, drops those that crash or miss accuracy, and keeps the fastest. One optimization looking good does not mean the whole engine gets faster, and the reliable way is to build the candidates and measure them.

7. When PTQ Calibration Helps or Hurts: Dose-Driven Collapse and Validation-Gated Abstention in Quantized Text Embedders

The researchers compressed every linear layer of the text embedding model EmbeddingGemma-300m to 4 bits, froze the weights, and calibrated only the quantizer settings using labeled queries from retrieval data such as MS MARCO, then tested ranking on separate queries. Changing nothing but the learning rate turned a gain of 1.47 points in the ranking metric NDCG@10 into a collapse of 71.53 points. The paper finds that collapse depends mainly on how far calibration pushes the vectors from where they started; even with no relevance labels, just pulling them toward the full-precision vectors also collapses if pushed too far. So the authors propose a rule: check each calibration result on held-out queries and adopt it only if it is statistically better, otherwise keep the uncalibrated version. Over 30 decisions the rule never picked a harmful result, at the cost of keeping only 8 of 11 useful updates. Calibration after quantization can help or wreck a model, so gate it on held-out data before shipping and skip it when unsure.

8. Gandalf: Flash Shall Not Die! Increasing Flash Storage Lifetime for KV Cache Offloading in LLM Serving

The authors replay a Claude Code agent trace with Qwen3.5-27B, using 100GB of DRAM and a 1TB SSD to hold conversation caches. The common LRU-K policy, which decides what to keep by when each cache was last accessed a few times, wrote 153TB to the SSD while Gandalf wrote only 92TB. At that rate the SSD is projected to last 98 days instead of 59, with nearly the same cache miss ratio, 0.099 versus 0.098. SSD lifetime depends on how much is written, and many conversation caches have already been used up in memory, so writing them to SSD is pure waste. Gandalf places caches by the kind of attention layer they come from. Linear-attention states are usually used up quickly and stay in memory, while full-attention caches are reused by later turns again and again and go to SSD. Across all tested traces, projected SSD lifetime grew 7.3 times on average. When offloading caches to flash, count not only the hit rate but also how much the writes wear it out.

9. Lychee: Certified Screening of Inverted Lists for High-Recall Vector Search

The paper traces one MS MARCO query that must find a relevant passage among 500 inverted lists holding 1,086,390 passages in total. Screening keeps only 914 candidates, and reading the full vectors of just 32 of them is enough to put the relevant passage first. Each list keeps one vector at fixed intervals as an anchor, and the method first computes exact distances from the query to these anchors. Since the anchors sit in the lists, the k-th smallest of these distances is an upper limit, because k vectors in the lists are already no farther, so the true k-th nearest neighbour can only be closer. Each passage also stores its projection onto the data's main directions plus the length of what lies outside them. From these, GPU tensor cores compute how far it must at least be from the query, a value the paper proves never exceeds the true distance. Passages whose lower bound exceeds the limit cannot make the results. The rest are checked against their full vectors in order of their distance bounds until no unchecked candidate could improve the answer. At equal recall with 200 lists searched, Lychee is 9.7 to 117 times faster than cuVS IVF-Flat. High-recall vector search need not read every candidate; it can safely skip any it can prove will not make the results.

10. Scaling NVIDIA TensorRT Performance Optimization Beyond a Single Build Route with the Global Performance Tuner, Part 1

NVIDIA

When TensorRT builds an engine, it times candidate GPU kernels on their own, yet during real inference each kernel runs inside the full graph alongside others. The post notes that a kernel timed alone and the same kernel inside the full graph do not run in quite the same environment. So adding up per-kernel timings may not match the whole engine's real runtime. On that basis, the first part of this NVIDIA series proposes trying many compiler configurations instead of one fixed build route, checking each built engine's outputs against the accuracy requirement, timing the full engine, and keeping the fastest one that passes. This part only lays out the idea and gives no measured results, and the speedups are in part two. Compiler tuning cannot rely on local wins, and what counts is the measured speed of the whole engine.
