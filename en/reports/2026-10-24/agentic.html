1. ForkPilot: Self-Evolving Policy for Retrospective Search in Long-Horizon Agents

Microsoft

In long-horizon agent tasks, one failed tool call early on makes the later steps fail with it. Retrospective search repairs this by going back to a recoverable earlier state in the failed trajectory, keeping the correct actions before it, and forking a new run from there. The hard part is deciding when to fork and how many times: the reward only arrives when the task ends, and every fork costs extra tokens. ForkPilot builds labels from trajectories that have already finished: from the same state, it runs one continuation with a fork and one without to the end, and uses the difference in final score minus the difference in token cost as the label for whether that fork was worth it; it then trains a predictor that scores candidate fork options. At deployment it forks only when the lower bound of the predicted gain is above zero, and after each finished task it adds the new trajectories to the training set and refits. What it learns is whether this step is worth extra compute; the agent's own action policy stays untouched. On 6 benchmarks and 4 open-source models, compared with full Retrospective Tree Search (RTS), it uses 36.2% fewer raw tokens on average while scoring 0.23 points higher on average.

2. Web Search on TokenHub, Tencent Cloud's Model Serving Platform

Tencent

This is the web-search API documentation for TokenHub, Tencent Cloud's model serving platform. With web search turned on, the model decides by itself whether to search and which keywords to search for while answering, and then generates the answer from the search results. There are two ways to integrate: the Responses API declares a web_search tool in the tools field and returns cited sources in structured annotations; the Chat Completions API turns search on with web_search_options and returns cited sources in search_results. It currently supports Hy3 and the DeepSeek V4 model family, search is priced in two tiers, lite and standard, the limit is 5 QPS, and it is only available in the Guangzhou region. For search teams, the reference value is the interface shape: search is packaged as a tool the model calls by itself, and cited sources come back together with the answer, so an in-house RAG service can align with these fields and make a later switch easier.

3. TeleTune: Evolving Agent Skills From Offline Telemetry

MicrosoftUUNCUUT Austin

Computer-use agents need to know how people actually use software. User activity logs (telemetry) are plentiful, but they have three problems: the logs do not record the goal behind each action, past activity cannot be replayed to check whether a skill is good, and several tasks are interleaved in the same log. TeleTune uses the logs themselves as the exam: it has the agent predict the next action on recorded trajectories, proposes edits to a textual skill library based on where the predictions were wrong, and keeps only the edits that raise action-prediction accuracy on held-out trajectories. Action-prediction accuracy can be computed offline, so it replaces task success rate, which cannot be measured without replay, as the optimization signal. At test time the agent receives the learned skill library plus demonstration trajectories retrieved by workflow. On WorkArena and Online-Mind2Web its average success rates are 77.1% and 80.6%, 6.7% and 7.7% above the strongest baseline on each benchmark.

4. Subagents vs Agent Skills: Executing Reusable Knowledge for Long-Horizon Agentic Tasks

MicrosoftCornell

An agent skill package is a multi-file bundle of instructions, scripts and resources, and the usual way to use one is to load the skill instructions into the main agent's context and let the agent follow them. As tasks get longer, the context keeps piling up and reasoning quality drops. This paper compares another execution mode: invoking the skill package as a subagent, so that each subtask is solved in a fresh context window of its own. On SkillsBench, with the original human-curated skill packages, loading them directly into the context matches or beats subagents; with the authors' synthesized packages that spell out input-output contracts, subagents pull ahead, and the smaller the model, the larger the gain. Subagents pay off only when a skill has a clear input-output interface, because the main agent must be able to hand off a subtask completely and then take the result back. The cost is a clear increase in total tokens, because each subagent has to be given the context it needs all over again.

5. What Is Agentic RAG: How Agents Enhance Retrieval-Augmented Generation

Alibaba

This is an explainer article on the Alibaba Cloud developer community about what Agentic RAG is. Traditional RAG follows one fixed "retrieve first, then generate" pipeline; Agentic RAG brings an agent into it, which first works out what material the question needs, then decides how to search, whether to search again, and whether to call other tools, and finally composes the answer. The article groups the core mechanisms into five kinds: agent collaboration, external tool calls, reasoning enhancement, query refinement and iterative interaction, and names complex knowledge-base QA, document summarization and multi-step analysis as the use cases. The article contains no experiments or numbers, so it is better suited to explaining the concept to business stakeholders; to judge how well a specific approach works, you need the paper or evaluation of the corresponding system.

6. Code Understanding is a Bottleneck for Coding Agents

Microsoft

Repository-level benchmarks for coding agents, such as SWE-bench, often assume that the more lines of code are edited, the harder the task; but these datasets control code and task types poorly, so they cannot show which ability actually causes an agent's errors. CABRA builds tasks from scratch: each task is one transformation of a function call graph, and a single task-size parameter scales difficulty along four directions: traversing functions along the call chain, search, runtime resolution and instruction following. The authors ran 8 LLMs and 6 coding agents on 6,840 CABRA tasks. As tasks grow, plain LLM accuracy falls, while agents offload the work to tools such as grep and stay near-perfect, but their tool calls for reading and analyzing code increase. On SWE-bench Verified trajectories, these tool-call counts predict whether an agent succeeds better than the number of lines edited in the final solution. For agents, the difficulty lies more in understanding the code to be changed; making the edit itself is not the bottleneck.
