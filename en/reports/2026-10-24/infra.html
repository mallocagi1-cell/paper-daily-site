Six of today's 8 papers are about LLM inference serving. llm-d 1.0 handles agent traffic with prefix-cache-aware routing and separate prefill and decode. FastLLM and Superfluid are local inference servers that can place weights in CPU memory or even on disk. Dell compares the latency trade-offs of tensor and pipeline parallelism, and Amazon's TorchNeuron runs PyTorch code on Trainium with a one-line configuration change. The other two cover vector search infrastructure: SweepANN keeps half a billion molecule vectors in GPU memory and scans them directly, and Tair builds a vector engine into Redis.

LEAD STORY · Google

1. llm-d 1.0, an open source stack for distributed inference

Google

Agent requests come in many steps, share long prefixes and arrive in bursts. Behind a plain round-robin load balancer, replicas recompute the same prompts and fill memory with duplicate KV cache. llm-d 1.0, released by Google with Red Hat, IBM and others, is an open-source distributed inference stack on Kubernetes that organizes a set of vLLM and SGLang servers into one serving pool. Its router tracks which replicas hold each cached prefix and picks a replica with load in mind, and when GPU memory is full it moves KV cache to host memory and SSD. On a coding-agent workload on Ironwood TPUs, median time to first token falls by more than 85% and total throughput is 2.4 times that of a plain Kubernetes Service. The gain comes mainly from sending a session's requests back to the replica that already holds its context.

2. SweepANN: A GPU-Accelerated Large-K Approximate Vector Search for Drug Discovery

DrugCLIP encodes protein pockets and small molecules into one vector space, turning early drug screening into vector search. One screen queries half a billion molecules with more than twenty thousand pockets and keeps half a million candidates per pocket. With results this large, an inverted index must probe almost every list and a graph index must track huge candidate sets, so an index has little left to skip. SweepANN scans directly instead: INT8-compressed molecule vectors stay resident in the memory of four GPUs, each data block is read once for a whole batch of pockets, and a score threshold estimated from samples filters out most rows. It finishes all pockets in about 61 seconds with an average recall of 99.6%. When the result set is too large for an index to skip much, a direct scan is faster.

3. llm-d 1.0 hardens open-source AI inference for production

IBM

This IBM Research article on llm-d 1.0 focuses on day-to-day operations after launch. Prefix-cache-aware routing, tiered KV cache offloading and the split between prefill and decode are not new in 1.0. What changed is that they are integrated to the point of long-term operability, with stable APIs, several tenants sharing the same hardware by priority, and upgrades without downtime. In a coding-agent load test, prefix-aware routing reused 97% of the reusable cache. IBM and Red Hat run 3,000 software engineering agents at once on their own deployment, at a tenth to a fifth of the cost of buying the same open model as a service. Agents keep returning to the same code and instructions, so pinning a session to one replica pays off more than in chat.

4. Amazon targets Trainium gains with new TorchNeuron developer tool

Amazon

Amazon released TorchNeuron, which lets existing PyTorch code run on AWS Trainium chips by changing one line of configuration, open-sourced under Apache 2.0. Amazon says the same training script learns the same things at the same speed on conventional chips and on Trainium, and testing, debugging and scaling tools need no changes. Voice AI company Cartesia says its team only hand-writes NKI kernels for the layers that are called repeatedly and decide end-to-end latency, while other operators use the native path. The article gives no performance comparison between Trainium and GPUs. For inference teams, it lowers the cost of rewriting and revalidating code when switching hardware.

5. FastLLM: a C++ LLM inference engine

HHysen Labs

FastLLM is an LLM inference engine written in C++ that does not depend on PyTorch, reads Hugging Face weights directly, and offers interfaces compatible with OpenAI and Anthropic. Its core design does not require all weights to fit in GPU memory: regular layers and MoE expert layers can be placed on the GPU, in CPU memory or on disk in proportions the user sets. The author says full-precision DeepSeek reaches 20 tokens per second for a single request on a dual-socket server with one GPU, but the repository has no benchmark data to verify it. It targets machines whose GPU memory cannot hold the model but which have plenty of host memory and SSD.

6. Choosing a Vector Retrieval Database: The Built-in Vector Engine of Tair (Redis Enterprise Edition)

Alibaba

This Alibaba Cloud developer community article on database selection introduces TairVector, the vector engine built into Tair (the enterprise edition of Redis). It supports HNSW and FLAT indexes and hybrid search that combines vector search with BM25 full-text search. The article argues that RAG setups no longer need a separate Milvus or Qdrant, since one Tair deployment can handle caching, vector search and state, and it claims 510 thousand QPS on a single node. It does not say which vector dimension, data size or recall that figure refers to, so teams should retest on their own data. The main selling point is one less standalone vector database to maintain.

7. Scaling LLM Inference via Parallelism: Throughput-Latency Trade-off

This measurement paper from Dell's Office of the CTO studies how to choose parallelism for LLM inference. Prefill sets time to first token (TTFT), and decode sets the latency between consecutive tokens (ITL). The authors run Qwen2.5-14B with vLLM on 8 H200s and compare tensor parallelism (TP), pipeline parallelism (PP) and mixes of the two. The more prefill-heavy the load, the stricter the TTFT target and the longer the context, the better PP-heavy setups do, while TP-heavy setups win on throughput once latency targets relax. The best parallelism shifts with load, latency targets and context length, so it should be a runtime setting.

8. Introducing Superfluid: the local-AI native LLM server for multi-agent inference

BBaseCompute

Superfluid is an open-source local LLM server from BaseCompute for machines running several agents at once, compatible with the OpenAI, Anthropic and Ollama interfaces. Interactive requests preempt running batch jobs at the next scheduling cycle. Every token is written to a log before it is returned, so a session resumes where it stopped after a worker crash, and requests sharing one system prompt are prefilled only once. On an Apple M5 Pro with 8 agents working in the background, a chat request's time to first token is 1.5 seconds, against 291 seconds with llama-server. The gap comes from priority preemption: with the same model and runtime, chat no longer waits behind batch jobs.
