Infra — Paper Daily, 2026-10-24

Six of today's 8 papers are about LLM inference serving. llm-d 1.0 handles agent traffic with prefix-cache-aware routing and separate prefill and decode. FastLLM and Superfluid are local inference servers that can place weights in CPU memory or even on disk. Dell compares the latency trade-offs of tensor and pipeline parallelism, and Amazon's TorchNeuron runs PyTorch code on Trainium with a one-line configuration change. The other two cover vector search infrastructure: SweepANN keeps half a billion molecule vectors in GPU memory and scans them directly, and Tair builds a vector engine into Redis.

1. llm-d 1.0, an open source stack for distributed inference

Google

On an agentic coding workload on Ironwood TPU, llm-d cut the median wait for the first token by more than 85% compared with spreading requests through a plain Kubernetes Service. On the same workload, total throughput was 2.4 times higher. It does two things. First, its router looks at each model server's load and at whether the server already holds the prompt prefix this request shares, and sends the request there if so, which avoids recomputing it. Second, when accelerator memory fills up, it moves cached context into host memory and other storage so it can be reused later. Google's post also says that a synthetic-data company using the same routing now generates more than 4 times as many tokens per day on the same TPU allocation. Agent workloads repeat long prompts, so sending requests to machines that already hold the cache pays off more than adding machines.

2. SweepANN: A GPU-Accelerated Large-K Approximate Vector Search for Drug Discovery

A drug-screening campaign needs, for each of 26,562 protein pockets, the 500 thousand best-matching molecules from a library of 500 million. On 4 RTX PRO 6000 Blackwell GPUs, SweepANN finished the search in 61.04 seconds once the library was in GPU memory. Compared with exact FP32 search, its mean recall was 99.63%. Ordinary approximate vector search returns a few dozen results, while here every pocket needs hundreds of thousands, so the approach differs. The authors compress the molecule vectors and split them across the GPUs, and each GPU scans every molecule while scoring a batch of pockets at once. Instead of sorting after every block, it selects once per group of blocks and records the current 500-thousandth score as a cutoff. Molecules below the cutoff are no longer kept, the GPUs exchange the cutoff only once, and the results are merged at the end. Loading and compressing the library takes about 500 more seconds, which that time leaves out. When you need very many results per query, a full scan with a score cutoff suits better than an index.

3. llm-d 1.0 hardens open-source AI inference for production

IBM

IBM and Red Hat ran 3,000 coding agents at the same time on a cluster they operate themselves, at 5 to 10 times less than buying a hosted service for the same open model. In another agentic coding test, of all the cache that could have been reused, the llm-d router actually reused 97%. llm-d is an open-source inference stack built by Google, IBM and Red Hat, and it has just reached version 1.0. It sends requests that come back with the same context to the server that already holds that context, and lets the cache move between GPU, CPU and storage so that more of it is reused. It also manages requests that compete for resources and runs prompt reading and answer generation on separate machines. The post does not say which model, hardware or tasks the tests used. Agent requests share a lot of context, so self-hosted inference that reuses the cache well can cost far less than a hosted service.

4. Amazon targets Trainium gains with new TorchNeuron developer tool

Amazon

Amazon's engineers ran the same training script on a conventional chip and on Amazon's own Trainium chip, changing only the setting that tells the code which chip to use, and the model learned the same things at the same rate. Voice company Cartesia says its standard inference pipeline ran on Trainium with almost no changes to its PyTorch code, small operators were fast enough through native support, and only the few frequently called layers that drive latency needed hand-written kernels. This rests on the new tool TorchNeuron, which lets existing PyTorch code run on Trainium after changing a single line of configuration. Moving to a new chip used to mean rewriting and revalidating code, and Amazon says 85% of AI researchers and developers write their code in PyTorch. The article gives no performance comparison. TorchNeuron will be released as open source under the Apache 2.0 license. Most of the cost of switching chips is changing code, and native framework support can shrink it to one line of configuration.

5. FastLLM: a C++ LLM inference engine

HHysen Labs

FastLLM's repository description says it can run an unpruned, full DeepSeek on any GPU with more than 10 GB of memory, without saying which DeepSeek version. On a dual AMD EPYC 9004 or 9005 server it can generate 20 tokens per second at full precision while handling one request at a time. This review points out that the repository contains no benchmark data to check these numbers against. FastLLM is an inference engine written in C++ that does not depend on PyTorch, reads weights from Hugging Face directly, and serves endpoints compatible with OpenAI and Anthropic. Its unusual feature is that the weights need not fit in GPU memory, because users can place ordinary layers and MoE expert layers separately in GPU memory, CPU memory or even on disk, mixing hardware in proportions they choose. Its use case is narrow, mainly machines with far more host memory or SSD than GPU memory that need to run MoE models. When GPU memory is short, spreading weights by layer over memory and disk is a practical way to run a large MoE model on a small machine.

6. Choosing a Vector Retrieval Database: The Built-in Vector Engine of Tair (Redis Enterprise Edition)

Alibaba

Alibaba Cloud says Tair, its enterprise edition of Redis, reaches 510 thousand QPS on a single node, and recommends it on that basis as the vector database for RAG applications. The summary does not say which operation, hardware or data size that number measures. The idea is to skip a separate Milvus or Qdrant deployment and use the TairVector engine built into Tair. It supports HNSW and FLAT indexes, mixes vector search with BM25 full-text search, and keeps search latency at the millisecond level. One Tair deployment then handles caching, vector search and session state, so the system has one component fewer. This is a product-selection article, and we could read only its summary because the body requires a login. If a RAG system already caches in Redis, using its vector engine saves maintaining a second database.

7. Scaling LLM Inference via Parallelism: Throughput-Latency Trade-off

The authors ran Qwen2.5-14B-Instruct on H200 GPUs with 1200 input tokens and 2800 output tokens per request and 256 requests at a time. When the first token had to arrive within 5 or 10 seconds, pipeline parallelism, which gives consecutive layers to different GPUs, completed the most requests on time. When the deadline was relaxed to 20 or 25 seconds, the advantage shifted first to hybrid setups that use some of each, and then to tensor parallelism, which splits each layer across several GPUs. The authors measured time to first token, the gap between tokens and requests completed per second, and multiplied throughput by the share of requests whose first token met the deadline to get the useful throughput. In experiments with ever longer inputs, pipeline-heavy setups kept a higher on-time share and eventually overtook tensor-heavy setups in useful throughput. Choose the parallelism by how tight the first-token deadline is, not by throughput alone.

8. Introducing Superfluid: the local-AI native LLM server for multi-agent inference

BBaseCompute

Eight agents on one Mac are working through 7.5k-token documents when, 2 seconds later, the user asks a question in the chat box. Superfluid answers in 0.36 seconds, while llama-server takes more than 10 seconds with the same model on the same machine, about 30 times slower. The reason is scheduling. Servers like llama-server are built for throughput, so a new chat request waits behind batch work. Superfluid lets the interactive request jump the queue at the next scheduler tick and resumes the agents' work afterwards. In another example, 32 requests share one system prompt, and it prefills that prompt once for all of them. These numbers come from demos in the launch post, not from an independent benchmark. When several local agents share a machine, the scheduler should put the request a person is waiting for first.
