Towards Reliable, Scalable, and Value-Aligned Generative Recommendation for Large-Scale Advertising

Kuaishou made three changes to GR4AD, its deployed generative ad retrieval system, and the result, GR4AD-X, raises online ad revenue by a cumulative 3.07% over GR4AD. All three target the same mismatch: the model picks ads by generation probability, while the platform cares about revenue. Kuaishou measured it. The top ten ads by generation probability and the top ten by eCPM barely overlap, with a hit rate of only about 0.02, and this holds at every level of the SID. The first change is to the SID: the first level keeps the two nearest cluster centers, so an ad has two paths and is not lost when one prefix is pruned. The second adds capacity: not a bigger backbone, but more input signals, a larger encoder, a larger embedding for the SID vocabulary and so on. The third teaches generation about revenue: each SID prefix takes the mean revenue of the ads beneath it as its value, and a value head at each level is trained to predict it. Pruning first keeps twice as many candidates. It then cuts them with RRF, which combines each prefix's positions in the probability ranking and in the value ranking into one score, and a final step reranks by value. The changes were stacked one at a time in online tests, and the value-alignment group contributes 1.07 points of the total.

What problem is it solving?

Generative retrieval encodes each ad as a 3-code SID and runs beam search level by level: the first code picks a coarse category, the second refines it, and the third is a hash of the ad's own features that separates ads within the same fine cluster.

The table shows the mismatch: the model picks prefixes by generation probability, while the platform wants the ads that earn the most. Ad C has the highest eCPM, but it sits under a category whose generation probability ranks only 9th. When the beam keeps just the top 5 categories, that category is pruned at the first level, the next two codes are never generated, and ad C is gone for good.

The paper measures this mismatch with HitRate@10. For each online request, it takes the top 10 ads by generation score and the top 10 by eCPM and checks what share of them overlap. The generation score can be computed from the first code only, the first 2 codes, or all 3 codes. Under these three options, the base model's hit rate is only 0.017, 0.019 and 0.021. Every level is about equally bad, so the problem is not confined to one level. GR4AD already optimized revenue over the whole sequence, but whether to keep each prefix at each level still depends almost entirely on generation probability.

Two more things make it harder. First, when an ad's SID is built, the first level assigns the ad to its single nearest coarse category. The authors counted 7.556 million ads: nearly 30% of them are less than 5.3% farther from their second-nearest coarse centroid than from their nearest one, so which side they land on is close to chance, and once only one side is kept, the other path can never be reached.

Second, serving compute is tight: in Figure 1, scaling the model from 0.03B to 0.50B cuts throughput to 18% of the original, while the revenue gain slows clearly after 0.16B.

Two SID paths per ad

Standard RQ-KMeans picks only the nearest centroid at each level. Over 7.556M ad embeddings and 16,384 first-level centroids, 29.31% of ads have a second-nearest centroid at most 5.26% farther than the nearest. Multi-Path SID changes only the first level: it keeps the m nearest centroids (m=2 in production), runs a normal residual quantization from each, and shares the final hash code across paths. Each ad gets 2 full SIDs rather than a tree of paths.

Training uses both paths as targets, weighting their next-token losses. Both are packed into one forward pass with a block mask so each path sees only the user context and its own earlier codes, and the user context is computed once. At inference, results are deduplicated per ad, keeping the higher-scoring path. First-level top-1 hit rate goes from 14.38% to 17.58%, and online revenue rises 0.58% with the same beam width and latency.

Capacity without a bigger backbone

The authors add a little capacity in five directions, each chosen for low serving cost. Input: 20+ profile and context features from the ranking system, with sequence length unchanged: the existing sequence positions are reallocated by feature importance, so more important features get more positions. The paper says only this, not how many positions each feature gets or how the new features fill them. Encoder: key embeddings widened from 16 to 64 dimensions and a SwiGLU FFN. Vocabulary (PCGM): each decoder layer gets its own SID memory table, plus memory entries for 1-, 2- and 3-code prefixes located by hashing; the first code is predicted without PCGM, the second uses the first code's memory, the third uses the memory of the first two, and the full SID's memory is used in the rerank step. The looked-up vector replaces the FFN gate projection. This step takes parameters from 0.20B to 0.46B while QPS (relative to the 0.16B multi-path model) recovers from 90% to 95%, because part of the matrix math becomes a table lookup. Residual streams: the hidden state is copied into 4 parallel streams that are mixed by learned scalar gates, with attention and FFN still computed once. First-code reasoning: a small learned network maps the BOS hidden state to a continuous vector that is fed to the decoder between BOS and the first code. The decoder's state at that slot predicts the first code, needs no target ad at inference, is shared by both SID paths, and is supervised to predict which of 256 coarse clusters the ad belongs to.

Teaching generation about revenue

A sequence-level reward is not enough, because the reward lives only at the leaves: a wrong third code penalizes a good first-level prefix too. PV-RSPO pushes rewards up the tree. For a user, the model rolls out a batch of ads, each rewarded with an eCPM-style revenue value. Most of these ads were never actually shown in the logs, so the reward has to be an estimate: the appendix only mentions that the production system includes reward estimation, with no word on which model scores the newly sampled ads or how. A prefix's value is the mean reward of the sampled ads under it. A light value head per level takes the prefix's own lookup embedding, which does not depend on the user, cross-attends from it to the backbone's user memory, and is trained with GR4AD's listwise RSPO loss (a ranking loss that makes the predicted values of a group of prefixes order the same way as their true values). The user memory M_u is the representation the backbone computes once from this user's context; it is reused, without recomputation, for every prefix and candidate it scores, and which layer's output it is goes unspecified. UniVGD's contribution is letting generation know mid-way which direction earns more. Decode a batch of ads for a user; two are sampled under a prefix with estimated rewards 3 and 5, so the prefix's value target is 4. The value head's only input is the prefix's looked-up vector, the same for every user; it uses that vector to read the memory the backbone computed for this user, which makes the prediction user-specific. Source: illustrative example of the paper's PV-RSPO description

PV-BeamSearch gives that head a second vote during decoding. From level 2 on, it keeps 2k candidates by probability (k=512), ranks them by value, merges the two rankings with RRF, and keeps the top k. Ranks are merged instead of scores because log probability and value are on different scales. Level 1 is left alone: in the authors' experiments, fusing there let the value head pick coarse codes with few valid ads beneath them.

Finally, the discriminative rerank builds a rank token from each candidate's SID embedding and ad features, including eCPM signals, and runs one extra step of the same network, reusing the user representation. The paper says only that these ad features include the eCPM-related signals used by the rank step; it does not say whether they are stored features, scores already computed in the request, or a fresh estimate per retrieved ad, so the extra compute of this step cannot be judged from the paper. One head learns eCPM order with a LambdaLoss, another models how deep the conversion chain goes, and RRF merges the two.

Results

Each variant got 5% of traffic for 7 days, with changes stacked cumulatively against GR4AD.

Change addedCumulative revenue lift
+ Multi-Path SID+0.58%
+ Input and encoder scaling+0.96%
+ Vocabulary scaling (PCGM)+1.43%
+ Residual streams+1.72%
+ First-code reasoning+2.00%
+ PV-RSPO+2.28%
+ PV-BeamSearch+2.49%
+ Discriminative rerank+3.07%

The scaling group alone takes parameters from 0.16B to 0.49B for +1.41% revenue at 85% QPS, while enlarging the backbone to 0.50B gives +0.53% at 33% QPS. Full-depth HR@10 rises from 0.021 to 0.298. Level-1 HR@10 also rises from 0.017 to 0.145 even though beam fusion skips level 1, so that part comes from PV-RSPO training. Training-time value supervision and decode-time value pruning cover different stages and do not replace each other.

Limitations

The value group keeps 75% of the scaled model's QPS, and the scaled model itself runs at 85% of the 0.16B baseline; multiplying the two gives a rough end-to-end figure of a bit over 60%. Every gain is measured on top of all earlier changes, so the table cannot say what PV-BeamSearch adds without PV-RSPO. Rewards are defined at the eCPM and revenue level; content feeds that optimize watch time would need a new prefix value definition.

How a team could try it

First measure your own boundary problem: the share of items whose distance ratio to the two nearest first-level centroids is close to 1. If it is high, Multi-Path SID is cheap and leaves the model unchanged. Then measure the top-K overlap between generation score and business value in your logs. If it is low, start with the discriminative rerank, which is local and gave the largest single gain here, and add prefix value heads and beam fusion later, leaving level 1 untouched.

Bottom line

To align generative retrieval with business value, consider giving every prefix level a value estimate instead of relying only on a final rerank, while keeping the first level's coarse choice protected from the value head. The paper measured these steps stacked together and never tested a rerank-only variant, so it has not shown that each step is strictly necessary.
