LoopGR: Parameter-Efficient Scaling for Generative Recommendation via Recurrent Depth

Huizhe Zhang, Yudong Li, Liang Chen, Chengxiang Zhuo, Zang Li
30 minread4.00scoreNo. 410-28 Generative issue
Original paper ↗
SHARE

To make a generative recommender stronger, teams usually add layers, which means adding parameters and memory. Tencent's LoopGR (a generative recommendation backbone that reuses one decoder in a loop) takes another route. It runs the same decoder several times, and between passes a very small GRU module rewrites the representation of the user's history based on the decoder's current prediction state, then hands it to the next pass. Computational depth is thus decoupled from parameter count. At the same budget of about 0.5 GFLOPs, it uses only 1.3M parameters and still beats a 2.7M-parameter encoder-decoder. On Tencent's industrial data its Recall@10 is 0.6458, above TIGER's 0.6125 and the production model BARGE's 0.6277. To control latency, the authors distill the 16-loop model into a 4-loop one, cutting single-request latency from 211 ms to 50 ms with almost no loss in quality.

Teams that care about the serving cost of generative recommendation should read this. It answers a practical question: when the parameter and memory budget is fixed, where else can quality come from? The core idea in one sentence: the decoder keeps revising its prediction of the target SID, and the updater makes the user history change along with that prediction. The evidence comes mostly from small datasets with ten to sixty thousand items and models at the million-parameter scale, and there is no online A/B on the industrial data, which limits how far the conclusions can be pushed.

What problem is it actually solving?

SID-based generative recommendation encodes each item as a few levels of discrete tokens. The model reads the user's history and generates the SID of the next item level by level. Compute is spent in two places: understanding the history and generating the target SID. Existing backbones split this differently.

All three share one property: once the history is encoded, it stays fixed during generation. An illustrative scenario shows why this matters:

The other problem is that depth is tied to parameters. To refine the history a few more times, you need more layers, and recommender memory and latency budgets are far tighter than those of large language models. LoopGR tries to solve both: let the history evolve during generation, and add rounds of compute without adding parameters.

Overall structure: one encoder, one shared decoder, one small updater

ComponentWhat it doesHow many times it runs
Encoderencodes the SID tokens of every history item into the initial history representationonce
Decoderreads the current history and its own hidden state from the previous pass, and predicts the next SID tokenfor every SID level, one loop: one pass in each of TH​ rounds, plus one final pass, all sharing parameters
Updaterrewrites the history using the decoder's current stateTL​ times after each decoding pass, sharing parameters

The authors call the decoder loop the high-level cycle, with count TH​, and the updater loop the low-level cycle, with count TL​. The whole flow is: encode once, then treat "decode once, update TL​ times" as one round, repeat it TH​ times, and finally decode once more on the rewritten history. For example, with TH​=2 and TL​=1 the order is encode, decode, update, decode, update, decode, so the decoder runs 3 times and the updater twice.

The updater: letting the history follow the prediction

Why is an updater needed? If the history stays the same between passes, every decoding pass reads the same history, and repeated decoding can correct very little. The authors tested this: replacing the updater with an identity that does nothing lowers quality by about 8% on average. So the gain comes mainly from the history changing, not from the decoder simply running more times.

The updater rewrites the current history representation, one vector per history SID token. It reads two extra signals. The first is the hidden state at the decoder's BOS position. The BOS position reads the whole history through cross-attention and inherits the state of the previous pass, so the authors use it as the model's overall judgement of the target item; an MLP turns it into a query vector. The second is the current high-level round, low-level round and SID level, turned into a condition vector by an embedding and an MLP. Both vectors are added to every history position. The updater then pools the tokens of each item into one item vector, runs a light GRU along the item order, and broadcasts the result back to the tokens.

The nesting matters. The target SID is still generated level by level. For each level the whole loop runs first, its final prediction fixes that level's token, and the model moves on to the next level with the generated prefix. Inside the loop, each decoding pass takes the hidden states it produced in the previous pass (BOS plus prefix positions) plus the round vector, so the prediction is revised pass after pass rather than recomputed from scratch.

One detail is key: after each rewrite, the result is added back to the original history representation and normalized. Every round is a correction on the original history, not a drift away from the previous round. This anchor makes multi-round loops easier to train.

Walk through the illustrative example. After the first pass the BOS state leans to "sports". The updater reads it and makes the shoes and protein powder stand out. The second pass continues from its previous state on this new history, and the first-level SID distribution becomes sharper. This per-item change is an illustration of the mechanism.

The authors also compared updaters: the default GRU; token mixing, an MLP that blends vectors along the sequence; linear attention; and vanilla attention. All four perform similarly, and token mixing is even slightly better on Sports, so what matters is having a module that rewrites the history, not which operator it uses.

What each loop level does

The authors fix both encoder and decoder to one layer and vary only TH​ and TL​.

Removing the low-level loop, TL​=0, clearly hurts; one or two updates bring Recall@5 and NDCG@5 back. Larger TH​ generally helps but stops rising monotonically at greater depths. On the larger Sports set, deepening both gives more. The two levels therefore have clear jobs: the high level revises the prediction repeatedly, and the low level adjusts the history between revisions.

The parameter-efficiency comparison is direct. At about 0.5 GFLOPs, LoopGR uses 1.3M parameters against 2.7M for the encoder-decoder, with higher NDCG@5. That pair is the "up to 52% fewer parameters" in the abstract.

Recurrent trajectory self-distillation: from 16 passes to 4

Loops add no parameters but do add latency, because passes run in sequence. The 16-loop model needs 211 ms per request, too slow for serving. The authors' fix is RTSD (recurrent trajectory self-distillation). They train a teacher with all 16 passes, initialize a 4- or 8-pass student from the teacher's weights, and make the student imitate the teacher's whole prediction trajectory.

Why not just take the output after pass 4? The authors tried common ways to save compute: supervising every pass, a gated early exit, and ILSD, the intra-loop self-distillation of Goyal et al. (2026), where shallower loops of the same model imitate deeper ones. Averaged over 8 metrics, they fall 9.7%, 13.2% and 9.4% below the full-budget model; RTSD falls only 3.2%. The authors explain that supervising every pass makes intermediate representations stall early, so later passes barely change and the loop budget is wasted.

The RTSD loss has two terms. The first aligns the student's distribution at each pass with the teacher's distribution at the matching pass, where student pass s maps to teacher pass ⌈sTHtr​/THstu​⌉:
LTraj​=THstu​H1​s=1∑THstu​​h=1∑H​DKL​(ptr(a(s),h)​∥pstu(s,h)​)
Here p is the predicted distribution for SID level h at a given pass. With a 16-pass teacher and a 4-pass student, a(s)=⌈4s⌉: student pass 1 matches teacher pass 4 and student pass 4 matches teacher pass 16, so each student step stands for four teacher steps. Pass s means the decoding after round s of updates, so pass TH​ is the final output, and the student's final distribution is pulled toward the teacher's final distribution. The second term aligns direction: the change in log-probabilities between two consecutive student passes should point the same way as the change between the matching teacher passes, measured by cosine distance. The 4-pass student runs at about a quarter of the latency, beats the teacher on all four Sports metrics and ties it on Beauty. Projecting the students' intermediate states to 2D, the authors find the student does not just cut the teacher's trajectory short: it takes one large step in the first pass and then converges in small steps to an endpoint near the teacher's.

Comparison with existing methods

The public data are the Beauty, Sports and CDs (music CDs and vinyl) categories of Amazon 2014. Baselines include classic sequential recommenders such as SASRec and generative recommenders TIGER and HSTU, plus ActionPiece and RPG, which improve the item encoding. The industrial data come from Tencent's production recommender, with TIGER, a lazy decoder-only model modeled on OneRec V2, and BARGE, a generative model in production at Tencent.

On public data LoopGR is best on 8 of 12 metrics and slightly behind ActionPiece on CDs. Since it uses plain RQ-VAE codes rather than a specially designed SID, this suggests the gain comes from the backbone itself. On industrial data it leads everywhere, and its margin over TIGER grows with the cutoff, which means the loop mainly helps recall deeper in the list.

Limitations as I see them

First, the public data are small. Beauty has about 12,000 items and an average history of 8.88, and the models have only millions of parameters. Halving parameters at this scale means something very different from industrial models with billions of parameters, and the paper's evidence does not reach the question of whether the loop keeps its parameter efficiency at that size.

Second, read the industrial result with care. The best industrial variant uses token mixing as the updater, and Table 2 reports that variant, while the public main results use the GRU; the updater appears to have been chosen on the same industrial data. And there is only offline recall, no online A/B.

Third, latency is still high. Even at 4 passes a request takes about 50 ms, measured at batch size 1, and the loop is inherently sequential, so it cannot be amortized by parallelism the way a wider network can.

How a recommendation or search team could try it

  1. Start with the cheapest control: on an existing SID generative model, make the decoder share parameters and loop 2 to 3 times without an updater. Per the paper the gain is limited, which makes it a good baseline.
  2. Add the updater, rewriting the history from the BOS state and keeping the anchor back to the original history. If this clearly beats step 1, "history follows prediction" holds on your data.
  3. Train a teacher with many loops, distill it with RTSD into a 2- to 4-pass student, and compare latency and metrics. Compare against per-pass supervision to confirm distillation beats simple truncation.
  4. Finally run an A/B where parameters are constrained, such as a memory-bound retrieval service, comparing against the current backbone at equal parameter count.

Verdict

In recommender systems bound by parameters and memory, trading loops for depth is a viable path, and the key is to update the user history along with the prediction inside the loop rather than letting the decoder spin on a fixed input.
