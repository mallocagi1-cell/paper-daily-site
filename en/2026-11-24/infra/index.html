Today's infrastructure track follows the execution path of model serving. In hybrid inference, whether an expert sits on the CPU or the GPU should not change the output, while reinforcement learning tries to co-locate sampling and learning on the same device. Agent serving has to drop history already superseded by later tool results under KV cache pressure, and MoE megakernels under expert parallelism need runtime warp scheduling that tracks routing. Speculative decoding splits into two lines: one fixes sampling randomness before drafting, and another adapts the draft tree to request rate and request characteristics. Prefix caches must both decide what to keep from user intent and hide hits that should not be shared in request timing. Concurrent kernels stop launching communication at the first opportunity, and analytical queries can hand DuckDB plans to the GPU. Overall, today's concern is filling cache, scheduling, and overlap without changing correct results.

1. IsoMoE: Placement-Invariant Hybrid CPU-GPU MoE Inference with Lossless 12-bit Experts

USTC

Hybrid serving offloads some experts to the CPU so a single GPU can run a MoE model larger than its memory. Greedy decoding outputs from existing engines often change with where those experts sit and when they are swapped in, because the two devices use different arithmetic. A GPU expert kernel that bitwise replays the CPU arithmetic, a memory layout that lets the CPU compute lossless 12-bit experts with AVX-512 dot products, and a dual micro-batch pipeline that overlaps the two devices without changing outputs make placement affect only speed. Across several MoE models, outputs stay bitwise identical under different expert placements, and decoding throughput averages 1.26 times the fastest baseline, peaking at 1.54 times. Where an expert is placed should change only how fast the run is, not the tokens produced for the same request.

2. CTRL: Concurrent Training and Rollout for LLM Reinforcement Learning via GPU Co-Residency

HKUST (Guangzhou)

Reinforcement learning post-training for large language models has to run two workloads at once: memory-heavy rollout decoding, whose batch shrinks as responses finish, and a dense learner update. Current systems either time-share every GPU between the two phases or split the devices into whole-GPU pools. Every GPU can host a learner rank beside a persistent rollout engine under CUDA MPS. Optimizer state stays on the host, policy weights stream layer by layer through a bounded GPU window, and a publication gate overlaps complete updates with later sampling under a dropless staleness bound, so both sides make progress on the full allocation. On H100, A800, and similar platforms, with the staleness limit set to two steps, throughput reaches 1.11 to 2.24 times that of the stronger asynchronous baseline. Running complementary sampling and learning on the same GPU avoids paying for a hard device split or for serial phase switching.

3. Contexture: Runtime Context Eviction for High-Throughput Agent Serving

NNTU SingaporeA*STARMicrosoftSSuperMem

Agent serving repeatedly resends a growing execution history, and the shared KV cache quickly becomes the throughput bottleneck. Existing context-reduction methods cannot see global cache state, while runtime KV managers cannot use tool-execution information. Tracing tokens back to the tool operations that produced them shows that later operations often supersede earlier outputs and their turns, marking 64% of tokens in recorded final histories as removal candidates. Separating the harness's full conversation history from the model's execution context, selecting those superseded spans, and committing removals only when shared KV pressure and prefix residency make it worthwhile cuts later cache demand. Across combinations of models, harnesses, and benchmarks, throughput under the SLO is 20% to 73% higher than the strongest baseline. What should be evicted is history already replaced by later tool results, not whatever happens to cross a length cutoff.

4. Weave: Routing-Adaptive Runtime Warp Scheduling for MoE Megakernels

SJTUNUSFudan UniversityAlibabaTTokMach

Under expert parallelism, leading systems fuse each MoE layer into a persistent megakernel, but each GPU's communication and computation volumes shift with the routing result. Prior designs either fix the resource split between communication and computation at compile time, or adapt only at the granularity of whole SMs, leaving Tensor Cores idle once an SM is handed to communication. Allocating resources at both SM and warp granularity to match each GPU's load, switching warp roles as a layer runs, and jointly choosing both schedules at launch from a fused cost model and routing statistics can follow that dynamism. On SM103, the MoE layer is 1.30 times faster than the strongest DeepGEMM-MegaMoE baseline in the geometric mean, and up to 1.97 times faster. When routing changes, the on-device split between communication and computation should change with it, rather than keeping a compile-time partition.

5. Speculative Decoding Is Less Speculative Than You Think

CMU

Speculative decoding drafts candidate continuations before the target model verifies them, and its efficiency depends on whether limited drafting compute can anticipate the path the target will actually follow. That path has two sources of uncertainty: the target model's predictions, and the randomness of sampling. The first requires a target forward pass, but the second can be drawn before drafting and reused at verification. Combining those known draws with predictions from an existing drafter steers tree construction and asynchronous prefetching toward the continuations this sampling run will actually use. With no extra drafter training and no change to the target sampling distribution, decoding throughput rises by up to 24.6% over strong baselines, and by up to 13.7% in asynchronous prefetching. Sampling randomness need not be treated as unknown: fix it first, and the drafting budget can be spent on the candidates this run will use.

6. Isonomy: Isolating Every Request from Timing Side Channels at Nearly Full-Sharing Throughput in Multi-Instance LLM Prefill

Johns Hopkins University

Long prompts often share a prefix, and reusing cached keys and values saves prefill work, but a cache hit makes the first token arrive earlier and can reveal that another request used the same prefix. Providers usually share the cache only within an account, yet under least privilege even permission to send and pay for requests should not expose other prompts in that account. Isolating every request by default, while still keeping one cache across accounts, hides hits on prefixes cached outside a request's group in that request's own timing: routing uses only visible hits, and the first token is released on the schedule of a miss twin. At saturation on a session workload, the prediction mode retains 0.984 of unprotected sharing's throughput, compared with 0.945 for isolation by account; when more reuse crosses accounts, isolation by account falls to 0.802. Isolation need not mean giving up reuse, as long as hits that should stay hidden are concealed in the request's own timing.

7. AdaTree: Serving-Aware Adaptive Tree Construction for Speculative Decoding

NeurIPS 2026

Tree-based speculative decoding can raise generation throughput for large language models, but in a live serving system the tree configuration that performs best changes with the request rate and with per-request characteristics. A fixed tree or a chain-style drafter therefore often sits at odds with current serving conditions. A plug-in component for the serving stack can predict model execution time and acceptance length under different tree configurations and then pick the one that maximizes speculative decoding efficiency, so the tree can follow the load. To capture the nonlinear relationship between tree configuration and execution time, it uses decision trees as its core modeling primitive. In the reported evaluation, it consistently outperforms both chain-based and static tree-based speculative decoding across diverse serving conditions. A speculative tree should not be frozen before launch; the shape itself should change with request rate and request characteristics.

8. Contention-Aware Flexible Execution for Machine Learning Workloads

University of Central FloridaAMD

In both training and inference, compute and communication kernels often run concurrently and then contend for the same cores, caches, and memory bandwidth, so concurrency is often slower than running each kernel alone. A characterization on datacenter AMD Instinct MI300X GPUs shows that the slowdown depends on whether the kernels are compute-bound or memory-bound, and on whether they are large or small. Frameworks today usually launch communication as early as they can, and that choice is not always best. Using the flexibility already present in the ML dataflow about which operators can overlap and how resources can be split, simple heuristics can retune overlap anchors and resource allocation without rewriting kernels. Across inference prefill, decode, and training, end-to-end speedups reach 13%, and about 5% in training. Communication need not start at the first opportunity; hiding it behind a compute operator that tolerates contention is often the better schedule.

9. Intent-Aware Caching for Efficient LLM Serving

NeurIPS 2026

Serving systems for multi-turn chats cache the key-value states of conversation prefixes so later turns can reuse them and skip redundant prefill, but a hit depends on whether the conversation continues and how soon the next turn arrives. Even when a follow-up comes, delays vary widely as users read, think, or write, and a later hit still needs earlier prefixes to remain in the cache. In real logs, different intents show different continuation probabilities and inter-turn delays. Classifying requests by intent, learning lightweight reuse statistics from recent serving logs, and using those statistics to guide an eviction policy that follows an oracle-style rule puts that signal to work. On ShareChat, the cache hit rate reaches 34.6%, above 18.8% for the previous learning-based method and 12.2% for LRU. TTFT falls by up to 46.1% compared with LRU. Whether a prefix should be kept depends on how often that intent continues and how long the gap usually is, not only on whether the entry was used recently.

10. Get Started with GPU-Accelerated DuckDB Analytics Using the Sirius Core Extension

NVIDIA

Analytical queries slow down as datasets grow, which holds back exploration, pipelines, and the applications on top of them. NVIDIA and DuckLabs released a GPU-native SQL engine as a DuckDB core extension: once it is installed and loaded, supported analytical queries can run on NVIDIA GPUs without rewriting SQL or changing schemas. DuckDB still parses and optimizes the SQL, the extension executes the resulting plans, and queries with unsupported features fall back to DuckDB's CPU engine, so existing scripts and interfaces can stay as they are. In cold-run comparisons on TPC-H-derived queries stored in Amazon S3, at scale factors up to 10 TB, a tuned two-GPU configuration was 3.25 to 5.50 times faster than the best tested CPU-based DuckDB setup. Query-time compute cost fell by as much as about 79%. At small scale a single GPU had the lower cost, while at the largest scale the tuned two-GPU setup was better on both runtime and cost. The familiar SQL workflow can stay in DuckDB, while supported query plans are handed to the GPU.
