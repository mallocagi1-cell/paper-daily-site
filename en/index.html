1. How Language Models Learn Taste: Brand Preference in LLMs

Ask LLMs to "name a running shoe brand" and they will most likely say Nike; ask them to "recommend a running shoe brand" and they are more likely to say Brooks. The paper measures this effect across 102 models and 42 categories. In 26 categories the answer changes this way, and the models move together to the same brand: Chrome becomes Firefox, Google becomes DuckDuckGo. The brands named off the cuff are mostly market leaders; the brands picked after some thought are mostly niche or specialist ones. Tracing back through the training stages, the author finds the key step is preference training, even though the training data for that step hardly mentions brands.

2. A Cue's Hidden Price: Auditing Seller Influence on AI Shoppers

Two headphone listings are identical in price, star rating and specs, except that one adds the line “Our best-selling model, chosen by over 10,000 customers.” Across six such pairs, GPT-4o picked the listing with that line in all 144 trials. Raise that listing's price step by step, and it has to cost about 13% more before the model starts to waver. With a plain product description instead, the advantage is gone at only about 2% more. By choice rate the two lines look identical, but in money they differ sixfold. The authors want to use this method to put a price on every line a seller writes.

LEAD STORY · LinkedIn

1. PAIR: Preference-Aligned Intent Retrieval for Premium People Recommendation at LinkedIn

LinkedIn

On LinkedIn, a software engineer who starts looking for a job usually wants to open the profiles of recruiters, hiring managers and HR, not other engineers. In professional networking, who should be recommended is often complementary, not similar. Yet most recommender systems assume that the more alike two profiles are, the more one should be recommended, so they keep showing him his peers. PAIR changes the training goal: instead of learning who resembles whom, it learns from real logs which of the people shown the user clicked. In a live comparison experiment, clicks on recommendations rose 7.5%, paid-member renewals rose 2.1%, and pages did not get slower.

2. Ranking Bandits for Carousel Interfaces with Observable Browsing Depth

A recommender places a film in a row of items, and the user does not click it. Should the system record that the user doesn't like it? If the user never swiped far enough to see it, that record is wrong. Most online learning-to-rank algorithms cannot tell these two cases apart and have to guess: first estimate roughly how many people see each position, then scale click counts by that proportion. In a carousel interface that scrolls sideways, no guessing is needed, because the client can already record the furthest position the user reached this time. The authors use this signal in ranking algorithms and learn only from positions the user actually saw. In a simulated environment built from real users' eye-tracking data, the new algorithm does as well as a rival that knows in advance how likely each position is to be seen, while it does not need those probabilities itself.

LEAD STORY · Adobe

1. When Agentic Retrieval Fails Silently: Framework and Production Evidence from a Creative AI Assistant

Adobe

In Adobe Express's AI assistant, retrieval metrics that assume the user saw a ranked list and acted on it stop working. The chat entry point has a reformulation rate of 44.4%, higher than the template gallery search served by the same retrieval system, at 33.1%. The reason is that reformulation means different things on the two sides. In the gallery, a user reformulates because the results were irrelevant and they try other words. In chat, most reformulations come after the user sees a generated result and wants to tweak it. More surprising still, the assistant actually called retrieval on only 0.31% of prompts. The paper's evaluation framework measures in three layers: it scores the returned results against relevance labels when retrieval fires, then checks whether the returned assets were used, and finally whether the user exported. Four log fields record the retrieval ID, the full returned list, which asset each action used, and which retrieval that asset came from, linking every use and export back to that retrieval.

2. AutoSim: A Self-Improving User Simulator for Conversational Search Evaluation

Ask a strong LLM to play a search user, and a discriminator that never saw the training data recognizes its utterances with AUC 0.88. The conversational search user simulator AutoSim is in exactly this state: the order in which it ranks retrieval systems by retrieval quality matches the official NIST evaluation, yet the way it talks is far from human. The authors have the simulator improve itself toward real users. For prompts, another model writes edits aimed at the measured gaps to human behavior, and an edit is kept only if its score on a calibration set does not drop. The scores come from evaluators that each check one gap type, such as utterances that are too long and polite or that fail to lean on earlier turns. For weights, the model is first fine-tuned on real user utterances, then repeatedly fine-tuned on the generated utterances the discriminator finds most human. Changing only the prompt cannot push discriminator AUC below 0.85; changing the model weights brings AUC down to 0.45. Sounding human changes evaluation conclusions: where real users retrieve poorly, a prompt-driven simulator overestimates nDCG by 0.136.

LEAD STORY · Amazon

1. ATTUNE: Agentic Throughput Tuning for LLM Training

Amazon

Move a large model to a different GPU or framework version, and the training recipe that used to be fastest often no longer is. The recipe settles how the model is split across GPUs, which low-level routines to use, and how GPU data transfers overlap with computation. ATTUNE lets an AI agent able to write code and run commands tune recipes, given a recipe that runs and a budget of GPU-hours; it tries things and analyses bottlenecks on its own. But the real point of the paper lies outside the agent, in a correctness gate run by fixed code the agent cannot change. The model, data, batch size and numeric precision are locked, and any change that would quietly alter what is being trained, such as dropping overflow tokens, is rejected before launch. After fine-tuning jobs for three models switched to the tuned recipes, training ran on average 1.7 times as fast as before, and up to 3.9 times.

2. uGDS: A User-Space Development Kit for High-Performance GPU Direct Storage

When NVIDIA's GDS reads data from SSD straight into GPU memory, the authors measured that 99.6% of the time for asynchronous reads was stuck at the step of submitting requests. Large-model inference services store the KV cache they have already computed on SSDs, so that the next request with the same opening can read it back instead of recomputing, and the speed of this read feeds directly into time-to-first-token. uGDS moves the job of telling the SSD what to do out of the operating-system kernel and into an ordinary program. Data still goes straight from SSD to GPU; what changes is who gives the orders. uGDS's batched reads are up to 12 times as fast as GDS, and plugged into an open-source cache system, the median time-to-first-token for long prompts fell from 1.9 seconds to 0.7 seconds.
