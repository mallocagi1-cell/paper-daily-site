1. A Framework for Value-Aligned Modeling and Robust Experimentation

RecSys 2026

Google's Discover Ads team found that the offline Poisson Loss of its conversion model (pConvs) correlated only 0.1 with online advertiser value (Delivered Value: conversions per click times the advertiser's target cost per acquisition, tCPA, summed over clicks), so models that improved offline often did not gain once launched. The authors weight each click in the loss by its tCPA, and pair every low-traffic experiment with a retrained production model serving at the same traffic as its control. With tCPA weighting, the offline loss measures exactly the conversions advertisers are willing to pay for. Offline-to-online correlation rose to 0.65, and low-to-high-traffic experiment correlation rose from 0.53 to 0.93.

2. scikit-rec: A Unified, Extensible Recommendation Library with scikit-rec-agent, a Conversational Interface

RecSys 2026Intuit

Recommendation teams often use a different library for ranking, contextual bandits, uplift and sequential recommendation, each with its own offline evaluation interface. Intuit's open-source scikit-rec splits business logic, scoring strategy and the underlying model into three layers (Recommender, Scorer, Estimator), and five recommendation paradigms share one evaluate() interface, which includes six off-policy evaluators such as IPS, SNIPS and DR whose results match Open Bandit Pipeline within floating-point error. On the same logged data, a bandit policy and a ranking model can be compared directly with the same evaluators. An internal version has powered 15 use cases in TurboTax and QuickBooks for more than three years under a sub-100 ms latency requirement.

1. UniRec: A Unified Expressive-Aligned Generative Recommendation Framework for E-commerce

RecSys 2026

The Shopee authors measured three-level semantic IDs (SIDs) built by standard RQ-KMeans: the top 10% most-exposed full codes took 89.62% of exposure, so a generative recommender's probability mass concentrates on a few popular codes. UniRec has the model first generate the item's level-2 and level-3 category tokens and only then the three SID levels, and when building SIDs it gives every code an exposure-weighted capacity limit. Once the category is generated, each later SID level only has to choose within that category. Offline HR@50 is 22.6% higher (relative) than OneRec-V2; online, against the old multi-stage pipeline, orders rose 4.76% and GMV 5.60%.

2. GenPage: Towards End-to-End Generative Homepage Construction at Netflix

RecSys 2026Netflix

The Netflix homepage consists of rows, each with a theme and a set of titles, and it used to be assembled by several stages such as a row model and an entity model. GenPage encodes the user's viewing history, device, time of day and so on as tokens forming a prompt, and a ~200M-parameter decoder-only Transformer generates row and title tokens one by one, left to right and top to bottom. Every row and every title is a single token, so business rules can be written directly as a candidate mask at each step. In an online A/B test the core metric used for launch decisions rose 0.24% and end-to-end latency fell 20%; offline, enriching the prompt reduced the loss more than scaling the model from 120M to 900M parameters.

1. The Fusion Tax: A Diagnostic Analysis of When Hybrid Retrieval Hurts

Hybrid retrieval fuses BM25 and dense retrieval into one ranking, and most search engine and RAG framework docs default to reciprocal rank fusion (RRF). The authors keep a per-query ledger on 7 BEIR datasets: the best fusion method, score interpolation with weight 0.7 on the dense score, beats dense-only retrieval on mean nDCG@10 on every dataset, yet still ranks 8–21% of queries worse than dense-only. These losses concentrate on queries where only one retriever finds a relevant document; the other retriever then contributes only noise, and fusion pushes relevant documents that were already ranked high back down. Scaling the dense encoder from 22M to 596M parameters does not remove this loss. RRF beats dense-only only on datasets where the two retrievers are roughly equal, so the fusion method should be chosen from the measured gap between the two retrievers on the target corpus.

2. Chunk Recomputation under Real Document Revisions: Measuring Update Cost and Retrieval Quality of Fixed, Recursive, and Content-Defined Chunking

RAG chunking schemes are usually compared on one static corpus, but knowledge bases keep changing. Each chunk is embedded on its own, so when an edit moves a chunk boundary, unchanged text must be re-embedded too. The authors measure this on 120 pairs of adjacent Chinese and English Wikipedia revisions, reusing an old vector only when a chunk's embedding input is byte-identical: non-overlapping fixed-size chunking recomputes 57–68% of the new version's embedding input, paragraph-first recursive chunking 38–56%, and content-defined chunking (CDC, which picks cut points from local text fingerprints) 43–54%, while evidence recall under a 2048-token retrieval budget differs by less than 2 percentage points among the three. When 1% of text is inserted at the start of an article, fixed-size chunking recomputes everything, because every window after the insertion point shifts, so no chunk matches the old version. For knowledge bases that change often, a chunker's recompute fraction should be reported alongside its retrieval quality.

1. ForkPilot: Self-Evolving Policy for Retrospective Search in Long-Horizon Agents

Microsoft

In long-horizon agent tasks, one failed tool call early on makes the later steps fail with it. Retrospective search repairs this by going back to a recoverable earlier state in the failed trajectory, keeping the correct actions before it, and forking a new run from there. The hard part is deciding when to fork and how many times: the reward only arrives when the task ends, and every fork costs extra tokens. ForkPilot builds labels from trajectories that have already finished: from the same state, it runs one continuation with a fork and one without to the end, and uses the difference in final score minus the difference in token cost as the label for whether that fork was worth it; it then trains a predictor that scores candidate fork options. At deployment it forks only when the lower bound of the predicted gain is above zero, and after each finished task it adds the new trajectories to the training set and refits. What it learns is whether this step is worth extra compute; the agent's own action policy stays untouched. On 6 benchmarks and 4 open-source models, compared with full Retrospective Tree Search (RTS), it uses 36.2% fewer raw tokens on average while scoring 0.23 points higher on average.

2. Web Search on TokenHub, Tencent Cloud's Model Serving Platform

Tencent

This is the web-search API documentation for TokenHub, Tencent Cloud's model serving platform. With web search turned on, the model decides by itself whether to search and which keywords to search for while answering, and then generates the answer from the search results. There are two ways to integrate: the Responses API declares a web_search tool in the tools field and returns cited sources in structured annotations; the Chat Completions API turns search on with web_search_options and returns cited sources in search_results. It currently supports Hy3 and the DeepSeek V4 model family, search is priced in two tiers, lite and standard, the limit is 5 QPS, and it is only available in the Guangzhou region. For search teams, the reference value is the interface shape: search is packaged as a tool the model calls by itself, and cited sources come back together with the answer, so an in-house RAG service can align with these fields and make a later switch easier.

LEAD STORY · Google

1. llm-d 1.0, an open source stack for distributed inference

Google

Agent traffic is multi-step, shares long prefixes and arrives in bursts. Behind an ordinary round-robin load balancer, replicas recompute the same prompts and accelerator memory fills up with duplicate KV cache. llm-d 1.0, released at the PyTorch Conference by Google together with Red Hat, IBM and others, is an open-source distributed inference stack that runs on Kubernetes and organizes a set of vLLM and SGLang model servers into one serving pool: the router tracks which replicas hold each cached prefix and picks a replica using load and predicted latency; when accelerator memory fills up, KV cache is moved first to host memory and then to SSD; prefill and decode are split into two pools. Version 1.0 adds flow control that queues requests by priority and fairness, and rolling upgrades that do not interrupt sessions. On an agentic coding workload on Ironwood TPU, prefix-aware routing plus host-memory offload cut median time-to-first-token by more than 85% and delivered 2.4x the total throughput of a plain Kubernetes Service. The gain comes mainly from sending a session's requests back to the replica that already holds its context, which removes repeated prefill.

2. From VDBBench to the Top of MMEB: Full-Stack Optimization of Alibaba Cloud AI Search, from Engine to Model

Alibaba

This is an article on the Alibaba Cloud developer community about full-stack optimization of AI Search, from the retrieval engine to the embedding model. The authors' starting point is that once agents go into production, search has to keep supplying the model with high-quality context, and the pipeline covers model understanding, vector and full-text recall, hybrid retrieval, fusion reranking and engine execution. The article says AI Search achieved breakthroughs on VDBBench vector retrieval, Big5 and Tantivy traditional retrieval, and MMEB multimodal document retrieval, backed by FalconSeek, an in-house Elasticsearch engine, and a multimodal embedding model. Its reference value is that it breaks an AI search pipeline into stages that can be optimized separately; the article summary gives no specific scores, so for a selection decision the raw results need to be checked on each leaderboard.
