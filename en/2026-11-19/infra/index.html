Today's systems track is less about whether the model itself is fast enough, and more about repeated work, idle time, and skew on the serving path. Wide-beam generative retrieval folds identifier constraints into a model-native output path, and closed-loop throughput can be several times a custom processor baseline. Multi-vector retrieval uses one data-aware graph index to approximate MaxSim mainly on CPU. Recommender user profiles are stored as reusable KV cache so ranking calls need not re-prefill every time, and skewed event streams are resplit at checkpoints so the busiest worker no longer runs far above the mean. Gains from speculative decoding change with hardware, concurrency, and modality, which calls for hardware-aware search, visual head routing, and preemption that waits until a request is nearly done. Reinforcement-learning rollout still needs migration and early stop to cut tail bubbles, and token-level routing needs a serving system that can actually carry the algorithmic gain, just as a public backend on new chips needs the runtime and cache hierarchy first.

1. Efficient Wide-Beam Generative Retrieval with Model-Native Trie Decoding and Shared-Context Attention

LinkedIn📖 Deep dive →

Generative retrieval maps requests to catalog entries as short semantic IDs, and trie-constrained beam search keeps those IDs valid, but wide beams create two serving costs: vocabulary-wide score tensors that are mostly discarded, and repeated attention over the same prompt. A model-native output interface stores the identifier trie as validated GPU tensors, avoiding Python constraint callbacks and vocabulary-wide candidate buffers.

3. KVUse: Reusable-KV User Memory for Efficient LLM Recommenders

Meta📖 Deep dive →

Memory-augmented recommenders built on large models keep a natural-language profile for each user, then splice it into the prompt and recompute its key-value cache during prefill for every ranking call. Those calls are prefill-heavy, decode-short, and frequent, and prefix caching cannot help because the text before the profile changes from call to call, so repeated prefills dominate serving.

4. CheckCo: Checkpoint-Coordinated Load Balancing for Skewed Event Streams at Scale

KKing

Event streams are rarely uniform: a few dominant keys can generate orders of magnitude more events than the rest, overloading the workers that receive them and capping throughput. A checkpoint-coordinated load balancer needs no prior statistics. It estimates per-key frequencies from the live stream: workers count events locally, the counts are merged at each checkpoint barrier, and a partitioning function splits keys in rough proportion to those frequencies, packs the splits onto workers, and routes the next checkpoint window. On a production pipeline processing more than 100 billion events a day, the most loaded worker receives only 9.8% more events than the average over a day, an imbalance ratio of 1.10, against 8.03 for key-based routing in simulation. Shifts in the key distribution are reflected in routing from the next checkpoint, and the load stays balanced through job restarts.

5. SGLang-Neuron v0.1.0: SGLang's Serving Stack on AWS Trainium

AWS

Serving large language and diffusion models on AWS Trainium inside one stack has lacked a public SGLang backend. The first public preview is a PyTorch-native plugin, co-developed by the SGLang team and Annapurna Labs, and supported during the preview through an AWS Deep Learning Container. Every supported language model shares one fully asynchronous runtime, so chips can run decode steps back to back, and megakernels can run every decoder layer of a step in a single kernel call. Kimi-K3 runs prefill-decode disaggregation across Trainium3 nodes, and GLM-5.2 can serve a million-token context for agentic coding workloads. On GPT-OSS-120B, a host-memory tier for evicted prefixes delivers 72% to 75% more output throughput.

6. SpecSearch: Towards Hardware-Aware Efficient Speculative Decoding

UIUC

Speculative decoding can speed up large-model inference, but the best configuration depends jointly on the workload, the GPU, and available memory. On an RTX 5090, for example, the strong drafter DFlash reaches 3.50 times the throughput of autoregressive decoding at low concurrency, but only 0.76 times at high concurrency with short outputs. A hardware-aware search engine jointly chooses decoding strategy, draft length, and precision for each workload-GPU pair, using an analytical cost model to narrow the feasible set before calibration measurements on multiple GPUs. Across the RTX 5090, H100, L40, and AMD MI300X, full calibration reaches on average 2.01 times the throughput of autoregressive decoding and 1.36 times that of speculative decoding, both served by vLLM. A parameter-efficient predictor closely matches this search on unseen GPUs without requiring calibration on the deployment card.

7. VisHead-Spec: Head-Routed Visual Attention for Multimodal Speculative Decoding

Meta

Speculative decoding can speed up vision-language models while preserving the target model's outputs, but the gain shrinks under high-concurrency serving as the system becomes compute-bound, and long image tokens in the prompt make draft prediction more expensive. Block-diffusion drafters often add only modest speedup for these models at high concurrency. Looking at information flow from the target to the draft model shows a sparse visual-attention pattern: only a small set of draft key-value heads need to read image features, and only from the target model's top layers. A head-routing method therefore lets a fixed subset of heads attend to those top-level image features, and restricts the rest to text. On Qwen3-VL-8B, accepted length stays within 0.3% of the block-diffusion baseline. At a larger batch size, throughput over autoregressive decoding rises to 16.0%, compared with 9.5% for the baseline drafter.

8. TAILROLL: Tail-Aware Rollout Acceleration for RL-Based LLM Post-Training

ÉÉTSHuaweiRRBC BorealisUniversity of Melbourne

Reinforcement-learning post-training of large models is often bottlenecked by rollout: heavy-tailed responses leave engines idle while each step waits for the longest sequence. Asynchronous training can mask idle time but does not remove it, and tail length, not average load, often sets the step bound. An online scheduler combines stateless in-flight migration with ending a response once enough samples are in. It moves decode requests between engines at chunk boundaries and resumes them with one re-prefill, and it stops a response once its group has enough completed samples for advantage estimation, masking the partial output from the training loss. In end-to-end training, rollout time drops by 24% to 34%, and generation throughput rises by up to 33%, with comparable or higher final reward.

9. TokenRouter: Efficient Serving System for Token-Level LLM Routing

NeurIPS 2026Tsinghua UniversityCMU

Routing spreads inference work across different models and can push the cost-quality frontier of serving. Coarse routing at the session or query level is already common in production, and algorithmic work shows that token-level routing can add substantial efficiency and quality gains, but existing serving systems struggle to run it well. Built on single-model assumptions, they suffer step desynchronization and batch-admission delays under token-level routing, and they impose high implementation complexity. A serving system designed for this setting lets developers describe routing logic from the perspective of a single request, while the runtime launches a subserver for each model and dispatches requests asynchronously. Each subserver uses delayed batching whose hyperparameters come from a mathematical throughput model. Across routing algorithms, workloads, and model pairs, decoding throughput is 2.01 to 64.15 times higher than on existing systems, which finally makes token-level routing practical at the serving layer.

10. Keep or Preempt? Termination-Aware Scheduling for LLM Serving with Speculative Decoding

NeurIPS 2026

Interactive large-model serving is shaped by both time-to-first-token and end-to-end latency. Speculative decoding reduces latency with a lightweight draft and parallel verification, but it also makes classic SRPT scheduling from output-length estimates less reliable: remaining service time also depends on draft acceptance and the number of verification rounds. A termination-aware scheduler first uses a lightweight predictor built from runtime draft-and-verify states to identify requests that will finish within the next few decode steps. It then applies a switching-aware online policy to decide whether preemption is worthwhile, so the running set is not rewritten too often. On an open-source vLLM serving system, it cuts mean time-to-first-token by up to 3.83 times versus the default schedulers, and still achieves up to 2.0 times lower mean time-to-first-token against an oracle length-based preemption baseline.
