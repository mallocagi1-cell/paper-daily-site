Today's infrastructure papers ask how serving can wait less on the busiest rank, and how prefill chunk size can stop dictating both compute and communication. Another line makes speculative drafters cheaper, or lets the drafter read worked examples and simulate the target instead of solving the same hard problem. Others let the model decide when to compact its own context, or bring the existing PyTorch and JAX stack to Tenstorrent chips. Some systems balance expert parallelism with different objectives in prefill and decode, some cut energy by serving many precisions, including half-bit steps, from one checkpoint, and some speed up low-bit attention on consumer GPUs by recycling registers. Silent bugs in distributed training are being hunted by aligning intermediate tensors, rather than by watching the loss curve alone.

4.47

1. RankCast: Phase-Aware Rank Balancing in MoE Serving

In MoE inference, expert parallelism makes every layer wait for the busiest rank. Prefill is compute-bound, so the bottleneck is the token count on that rank; at moderate batch sizes, decode is memory-bound, and the bottleneck becomes how many experts are active on each rank. Even if training used load balancing, a frozen router at serving time still sees batch variation and domain drift, and what stalls latency is the instantaneous load on each rank. RankCast keeps each token's predicted top experts and assigns the remaining slots from a larger candidate set to lighter ranks: it steers flexible work toward less loaded ranks in prefill, and closes some experts on the busiest ranks in decode. The extra kernels can overlap with model execution. On Qwen3-235B and Qwen3.5-397B, it removes more than 75% of the busiest rank's excess prefill load, raises prefill input throughput by up to 19%, and cuts decode time per output token by up to 10%, with a quality cost below one percentage point.

2. PipeAxes: Decoupling Compute and Communication Granularities for Pipeline-Parallel LLM Serving

When pipeline parallelism serves long-context models on PCIe servers or heterogeneous GPUs, existing engines often split prefill into token chunks, and that chunk size also sets the GPU batch width and the size of activation transfers between stages. Small chunks reload weights too often, while large chunks can stall interactive requests. PipeAxes runs wide prefill batches a few layers at a time so decodes can slip in between slices, sends compressed activations in independently sized row groups, and uses latency slack to choose batch width, slice depth, and row-group size. The measure of success is how many requests meet time-to-first-token, time-per-output-token, and tail-interval targets together. In a four-stage MoE pipeline, it serves requests within their latency targets at 23.3 times the rate of calibrated Revisit-PP. In a mixed long-context workload, high-percentile time to first token for short requests fell from 129.8 seconds with native vLLM to 512 milliseconds.

3. Any-Rate: Half-Bit Multi-Precision LLM Quantization with Coded Bit-Planes

On-device deployment often has to switch precision under changing memory and energy budgets, but if a single checkpoint can only be read at integer bit widths, the gaps between adjacent precisions stay large and accuracy drops sharply at two bits. When several precisions share leading bit-planes while chasing different targets, they often lose still more accuracy. Any-Rate serves many precisions from one checkpoint, from two to eight bits, with half-bit steps between two and four bits. It restricts some bit-planes to short codewords, shares one lookup table per row across precisions, and encodes each precision against its own target, which reduces the loss from sharing leading planes. Across four language models, the two-bit mode still keeps 69% of FP16 accuracy, leading other multi-precision methods, and it decodes about as fast as existing kernels. An LPDDR energy model estimates up to 27% less energy at equal accuracy.

4. DFly2: Turbocharging Long-Context Speculative Decoding by Sharing the Target&#39;s Sparsity

Natively sparse long-context models already select positions for each target query, yet speculative drafters still often keep their own context cache, or else read the whole prompt or a recent window. A private cache costs memory, slows prefill, and crowds out concurrency, and computing a fresh selection per query would grow with context length. DFly2 reuses the cache and the selection the target has already paid for: each draft layer reads only the positions its paired target layer cached and its indexer chose, and it runs no scoring pass and keeps no cache of its own. The selection stays a fixed size but can land anywhere in the context, so a long prompt does not mean a larger read. At high concurrency and matched per-user decode speed, it delivers 62% and 81% more throughput on long-context and agentic sets when serving DS-V4.1-Flash.

5. How to Optimize NVFP4 Attention on NVIDIA RTX Blackwell Through Register Recycling

NVIDIA

When serving world models, long sequences often make attention a clear bottleneck. On NVIDIA RTX Blackwell, NVFP4 can raise throughput with four-bit matrix multiplies, but dependencies among softmax, data movement, and intermediate storage can leave Tensor Cores idle. On these consumer cards, attention is often bound by matrix multiplies rather than by softmax. A register-recycling schedule splits each score tile into two narrower slots and, after softmax quantization, immediately reuses the registers for the next tile's work, so the kernel need not allocate a second full score buffer. Registers are nearly full, so there is little room to hold a second score tile at the same time. On an RTX PRO 6000 Blackwell, this speeds up the NVFP4 attention kernel by up to 1.64 times. Reactor integrated the optimized kernel into its production serving stack for world models, cutting end-to-end inference latency by up to 15.34% on workloads such as LongLive, Helios, OmniDreams, and Cosmos 3 Nano. The schedule has been merged into the FlashInfer main branch.

6. Asymmetric Speculative Decoding: Unlocking In-Context Learning in Draft Models

Practical speedups from speculative decoding often fall far short of theoretical bounds, especially on reasoning tasks. The usual cause is that the draft and target models receive the same prompt, so a much weaker drafter is forced to solve the problem itself, and high rejection rates wipe out the benefit of parallel verification. Even when the drafter reaches a correct answer, it may get there by a trajectory the target rejects. Acceptance rates rise steadily during generation, which shows that the drafter is doing in-context learning from already verified tokens and gradually aligning with the target distribution. AsymSpec stops giving both sides the same prompt: it supplies the drafter with task-relevant worked solutions, so the job becomes simulation rather than problem solving, and it needs no retraining. On reasoning, code generation, and summarization, it speeds up autoregressive decoding by 2.29 to 4.95 times and also outperforms standard speculative decoding.

7. Looped Models are Fast Multi-Token Predictors

Looped language models can change how much computation they spend on a token by adjusting the number of loops, without a matching increase in unique parameters. Shallow loops are often used as a fast drafter, with deep loops as the verifier, because drafting still uses the full set of parameters. Those shallow loops can also predict several future tokens at once. Floodgates appends a block of mask tokens at the end of the sequence and, with a low-rank adaptation, learns to draft those positions in parallel, while remaining lossless. The speedup also depends on training the looped model at all depths, so the shallow drafter can use the deep prefix cache already computed during verification. Across seven models, five benchmarks, and a range of batch sizes and decoding modes, it is the fastest lossless method in most cases, reaching up to 7.5 times speedup. On shallow four-loop models, a single drafting loop is up to 5.1 times faster on average; the higher figure appears on deeper models with elastic drafting.

8. Libtt: A Compiler and Runtime for Tenstorrent Processors

Running existing PyTorch and JAX programs on Tenstorrent chips depends on speaking the same interface those frameworks already use to drive TPUs. Libtt implements that interface, so JAX runs directly, PyTorch runs through TorchTPU, and software written for TPUs carries over with no changes except replacing custom kernels. It ships the compiler and the multi-chip runtime as one shared library, fixes many upstream issues, and adds compiler optimizations so existing code is more likely to run out of the box. It passes most of the JAX and TorchTPU test suites and runs SGLang, TorchTitan, and Miles, covering serving, fine-tuning, and reinforcement learning. On four chips, it can follow TorchTitan's TPU training path without changing the trainer's source. In small checks, starting losses on the chips agree with a CPU run to three decimal digits. With fused attention and a fused loss, training throughput for Qwen3-8B rose from 287 to 435 tokens per second per chip.

9. Letting Models Manage Their Own Context: Where We Stand

Today's agent harnesses usually manage context for the model: when the window fills, the harness triggers a compaction that summarizes the history. The alternative is to let the model decide, through a context API, when and what to compact. The comparison was run in NOOA, NVIDIA's open-source agent harness, on document research and machine-learning engineering tasks, with context budgets from tight to very wide. Models that use the API well reach higher accuracy, often with fewer input tokens, especially under tight budgets: GPT 6.1 nearly triples its score on OfficeQA Pro v2, from 21% to 56%. Models differ widely in how often they call the API, how aggressively they compact, and when they start, and prompt changes shift that timing. If an inference engine reuses the KV cache of the unchanged suffix after an edit, prefill compute per request falls by up to 15%, with no measurable change in accuracy.

10. nnTrace: Detecting and Localizing Silent Bugs in Distributed Training

Distributed training spreads work across thousands of GPUs, and as the implementation gets more complex, it becomes prone to silent bugs that raise no explicit error yet still produce incorrect training outcomes. Watching the training-loss or gradient-norm curve is often slow, sometimes misses the bug entirely, and does little to localize it. nnTrace detects and localizes these bugs with differential testing: it aligns intermediate tensors from distributed training with those from a trusted reference implementation, then compares the floating-point values in corresponding tensors. The tolerance cannot be set arbitrarily; a mathematical analysis provides a guideline that separates bug-induced errors from ordinary numerical error. That way, a check is less likely to treat rounding differences as bugs, or to let a truly silent fault slip through. For people training at scale, being able to point to the layer or tensor that went wrong is much more useful than noticing only that a curve later looks off.
