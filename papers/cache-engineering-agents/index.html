Cache Engineering for Agents

一个智能体做一道复杂任务，往往要和搜索、网页、代码执行等工具来回几百轮。每一轮，模型都要把之前所有内容的 KV cache 重新读一遍。论文统计，读这些旧缓存占了总调用费用的 82.4%，比生成新内容贵得多。常见的省钱办法是删掉或摘要旧消息，但只要改动了前面的文字，后面所有缓存都作废，得从改动处重新算一遍。清华大学团队提出换个层面来做：文字记录一个字不动，只在缓存里把选中的部分丢掉，留下的部分原样接着用。他们为此做了一个推理服务系统 AKV。在三个模型、四个智能体测试上，一个简单的策略“只保留最近 12 次工具返回的缓存”，和常用的“到长度上限就摘要”相比，平均得分高 1.7 分，平均费用低 27.7%。

1. 问题：重算太贵，一刀切又会丢信息

智能体的对话越长，缓存带来两个问题。一是费用：缓存越积越多，每轮都要读一遍，存储和读取开销很大。二是准确率：模型一次能可靠处理的长度有限，参与计算的内容超过这个范围，效果会明显变差。

现在的通行办法是改文字，也叫“上下文工程”：把旧消息删掉或换成摘要。但大模型的缓存是按顺序算出来的，每个词的缓存都依赖它前面的所有内容。改动越靠前，后面需要重算的部分就越长。所以常见的智能体框架会一直等到长度到了某个上限，再一次性把大部分历史摘要掉，只留最近几轮，这样重算的次数少一些。可这样一刀切，很容易把中间几轮的有用信息也丢了。

作者先做了一个对比。用 GPT-OSS-120B 做 BrowseComp-Plus（一个需要多轮搜索才能回答的问答测试）的前 100 题，每题做 4 次、最多 100 轮。只保留最近 12 次工具返回、每轮删文字的做法，因为反复重算，费用是不做任何处理时的 1.85 倍。到 4.8 万词元才摘要一次的做法，费用只降了约 7%，准确率却掉了 5 个百分点。而直接在缓存里丢掉旧的工具返回，准确率和费用能同时变好。

2. 方法：对缓存的三种操作

作者先区分两个长度。一个是对话记录在文字上有多长；另一个是真正参与后续计算的缓存有多长，论文叫“活跃缓存”。改文字的做法改的是前者，改缓存的做法只改后者。

在这个框架下，论文定义了三种操作：

  • 追加：这是平常的做法，读进新的词，把它的缓存接在后面，位置编号加一。
  • 丢弃：把指定的缓存条目排除在之后的计算之外。留下的条目原封不动，文字记录也不变，之后新词的位置编号照常往后数。
  • 重排位置：把留下的条目按原来的先后顺序，重新编号为 0、1、2……，下一个新词接着往后编。

为什么需要第三种操作？丢弃不会让编号变小，缓存虽然少了，编号还是一路往上涨，迟早超过模型能处理的最大位置。重排位置就是把编号压回去。对用 RoPE 的模型，这一步很便宜：把一个条目从第 p 位挪到第 q 位，只要把它的 key 再旋转 q−p 对应的角度，value 不用动，也不用重新计算。

丢哪些？作者看了模型的 attention 分布，发现两个规律：越旧的内容被关注得越少；距离差不多时，工具返回的内容又比模型自己的推理内容被关注得少。所以主策略是滚动丢弃旧的工具返回：保留所有推理内容和最近 12 次工具返回，更早的工具返回的缓存逐步丢掉。

3. 难点：同一段文字，缓存可能不一样

平常的推理服务里，只要文字开头相同，缓存就相同，所以可以按“开头相同”来复用缓存。改缓存打破了这一点：同样的文字，经过不同的操作顺序，会得到不同的缓存。

用图里的例子说明。三条路径最后都只留下 B 和 C。但 ① 里 C 是在还能看到 A 的时候算出来的，带着 A 的影响；② 里算 C 时 A 已经被丢了；③ 里连 B 自己算出来时前面都没有 A。所以三条路径里 C 的缓存各不一样。论文因此用“从空缓存开始做过的全部操作”来描述缓存状态：对同一个模型，这串操作唯一决定了当前的缓存。推理服务必须同时记住文字历史和操作历史，才能正确复用。

4. AKV：怎么把它做成一个推理服务

AKV 的接口和标准的对话接口几乎一样。客户端照常发送完整的消息列表，只多一个可选字段，写明“在第几条消息之后丢掉哪些、在哪里重排位置”。客户端不需要知道服务端还存着哪些缓存，每轮照常追加消息和操作就行。

服务内部有三个机制。

第一是复用。推理服务一般用前缀树（radix tree）做 prefix caching，前缀相同的请求共用一段缓存。AKV 在树上加了“丢弃”和“重排位置”两种节点，查找时既比文字也比操作。所以图里的 ① 和 ② 能共用 A–B 这一段，但因为丢 A 的时间不同，C 各存一份。

第二是回收。一个缓存条目只有在没有任何正在进行的计算还需要它时，才能被释放。比如 ① 和 ② 都丢掉 A 之后，A 的缓存不用等请求结束就能释放。显存紧张时，先回收已经被丢弃的缓存，再回收已结束请求的缓存，因为后者下一轮更可能被用到。

第三是恢复。缓存被挤出显存后，下次要用时得重新算出来。可普通的从头计算只能得到“什么都没丢过”的缓存，而一步步重放每个操作又要算很多遍。AKV 的做法是在每一层把要重算的内容按丢弃和重排的时间点切成几段，每段只看自己和前面各段在当时还保留着的缓存，所有段一次性算完。这样一次计算就能复原出经过丢弃和重排的准确状态。

5. 实验结果

对照组是两种“到上限就摘要”的做法。“标准”做法用模型自带的较高上限（GPT-OSS-120B 和 MiniMax-M2.7 为 9.6 万词元，MiroThinker-1.7-Mini 为 19.2 万）。“改文字”做法用同样的摘要方式，但上限统一降到 4.8 万。AKV 用“保留最近 12 次工具返回”的滚动丢弃。测试集有四个：两个多轮搜索问答（BrowseComp-Plus、xbench-DeepSearch）、GAIA 的 103 道纯文字题，以及修真实代码库漏洞的 SWE-bench Verified。费用按实际读入和生成的词元计价。为了不偏袒自己，作者让重排位置涉及的每个词元也按读缓存的价格收费，有意高估了这一步的成本。

四个测试的平均结果（得分为通过率 %，费用为每题美分）：

模型标准做法改文字AKV
MiniMax-M2.752.4 分 / 5.0 美分52.8 / 5.753.7 / 4.4
GPT-OSS-120B51.0 / 11.248.3 / 10.253.1 / 7.3
MiroThinker-1.7-Mini44.1 / 20.437.1 / 18.145.8 / 14.8

三个模型上，AKV 的平均分都最高，平均费用比标准做法低 27.7%，比改文字低 21.9%。不过不是每一项都赢：MiniMax-M2.7 上，BrowseComp-Plus 是改文字更高，SWE-bench 是标准做法略高。

准确率为什么会提升？作者按对话长度拆开看。4.8 万词元以内，三种做法差不多；4.8 万到 9.6 万之间，改文字最差；9.6 万以上，标准做法最差。这正好对应两者各自触发摘要的位置，说明掉分来自“一刀切”丢掉的信息。滚动丢弃是一点点地去掉最旧的工具返回，就没有这个问题。

速度上，作者用 8 张 A800 显卡，在 SWE-bench 上测服务效率。在各自能承受的最大并发下，AKV 的平均延迟快 1.36 倍，最慢那 5% 请求的延迟快 1.51 倍，输出吞吐是标准做法的 1.18 倍。并发再往上加时差别更明显：标准做法因为显存不够，频繁把缓存挤出去再重算，并发 16 时最慢那 5% 的请求要等 230 秒，AKV 只要 31 秒。

几个对比实验也有参考价值。只丢弃、不重排位置时，BrowseComp-Plus 得 55.0 分；加上重排位置升到 62.0 分，因为智能体能继续搜下去，不会撞到位置上限而被迫结束。丢掉推理内容的缓存，不管单独丢还是和工具返回一起丢，都不如只丢工具返回。作者还试了把“丢哪些”交给智能体自己决定，两个模型在 BrowseComp-Plus 的子集上分别做到 61.0% 和 64.0%，说明策略本身还有很大的探索空间。

6. 局限与实践意义

作者列出的局限是：丢哪些、什么时候丢，还需要更多探索；还没有在这套机制下专门训练智能体；对线性注意力这类新架构的模型还不支持。另外有几点值得注意。实验用的主策略是手工定的固定规则，最佳的“保留几次”可能因任务而异。被丢掉的内容仍然会通过之后算出的缓存间接留下影响，作者把这看作优点，但这也意味着结果依赖操作顺序，调试和复现时要记下完整的操作序列。

对做智能体平台和推理服务的团队，这篇论文的价值在于把“压缩上下文”从文字层挪到了缓存层。如果你的智能体有大量工具返回，比如检索结果、网页、代码运行输出，而现在靠“到上限就摘要”控制长度，可以先在自己的轨迹上看看模型对工具返回和推理内容的关注度差多少，再试“滚动丢弃旧工具返回 + 重排位置”，这是论文里最稳的组合。落地的前提是推理服务能区分操作历史：如果服务端只按“文字开头相同”复用缓存，同一段文字下不同的丢弃时间会被错误地混用。AKV 基于 SGLang 实现，代码已公开，客户端接入时只需多传一个字段。
