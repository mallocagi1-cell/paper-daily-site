RecoGEM: A Serving System for Production-Scale Generative Recommendation

RecoGEM 这篇论文的判断是：生成式推荐只是长得像 LLM 解码，压力却倒了过来，落在海量短注意力行和每一步的大 K 选择上。

先看一个请求要做什么。生成式推荐（generative recommendation，GR）不给现成候选打分，而是逐位生成物品的 Semantic ID（SID，用一串短 token 表示一个物品）。快手的一种配置里，一个请求保留 W=512 条 beam，每条扩展 C=8192 个续写。下一步开始之前，要从这约 420 万个分数里精确选出下一轮的 beam。

注意力这边同样夸张。32 个请求拼成一批，就是 16384 条候选前缀，再乘 64 个 head，约一百万条注意力行，每行只看几个 SID 位置。

RecoGEM 按这个形状专门优化之后，OneModel 在单实例 batch 32 下做到 1,053 QPS、P99 30.8 ms，吞吐是自家对照配置的 2.88 倍。这套系统已在快手线上跑了九个多月，服务 4 亿日活。

同样逐 token 生成，相邻两步却不是同一种计算

LLM 解码的每一步几乎在重复同一件事：读当前序列，从同一张词表里预测下一个 token，接上去，再来一轮。GR 的步数短而固定，每一位有自己的词表，靠前的位置做粗分，靠后的位置逐步细化。论文的直觉例子是先选「智能手机」，再细到「iPhone 18」。

麻烦出在步与步之间。第 t+1 步的输入并不是第 t 步的输出，中间隔着一次 beam search 选择，以及幸存候选的状态准备：前缀、累计分，还有从父序列继承的 KV cache。假设「智能手机」前缀有「iOS」和「Android」两个续写活下来，它们都继承父前缀的 KV cache，各自往后走。没有续写幸存的前缀，缓存直接丢弃。 Hoot 说▾

于是输入输出的序列数在一步之内就不同，跨步也不同。好在这些形状可以预测：步数固定，部署配置一定，每步的前缀长度、保留 beam 宽和候选宽都事先确定，只有请求数随流量变。

注意力的压力从序列长度挪到了行数

形状既然提前知道，先看哪个维度变了。LLM 的注意力压力常在 KV 长度 S_kv 上，一条序列要看很长的 prompt 和生成历史。GR 要看的前缀只是已生成的几位 SID，S_kv 很小，压力挪到了 batch：请求数 B_req 乘 beam 宽 W，得到 B 条候选前缀。论文把这叫作注意力维度倒置。

大 batch 听上去对现有 kernel 有利，实际相反。标准 kernel 靠长序列 tile 摊薄开销，这里每行只有几次点积和一个很小的 softmax，开销摊不掉。把行拼成一条长序列也不行，每个候选的 softmax 必须各自独立。

RecoGEM 的 row-tiled attention 换了切分方向，每个 tile 装 R 条完整的短行。每行很短，整行注意力能在片上算完，中间结果不写回，只写输出。每行的 softmax 在本 tile 内结束，tile 之间不共享状态，所以可以一边算 tile k，一边加载 tile k+1。 Hoot 说▾

Hoot 说合装一个 tile，不等于合做一次注意力收起 ✕
多条短行一起装，每行仍各算各的注意力。tile 分摊开销，softmax 的边界还在每一行。
  • 一次 softmax 的归一化范围
  1. 为什么不能拼（示意数字）：设 A 行三个位置的 exp 分数是 6、1、1，B 行是 3、2、1。各算各的，A 第一位的权重是 6/8=0.75，B 第一位是 3/6=0.5。拼成一次 softmax 后分母都变成 14，两者降到 0.43 和 0.21，B 行的权重总和只剩 0.43，本该是 1。
  2. 装块省的是什么：论文最大的设置里 16384×64 约一百万行，早期路径每行一个独立工作单元。每 tile 装 64 行后只剩 16384 个 tile，block 调度和 pipeline 准备的开销由这些行分摊。

单看这个 kernel，在上面那个约一百万行的设置下，S_kv 到 8 都低于 0.85 ms。S_kv≤4 时，它比他们早期的逐行路径快 7.2–9.4 倍，这段差距说明把多行装进一个 tile 确实摊掉了开销。相比 SDPA 最高快 154.4 倍，这是该测试环境里的最大值，所以只能当单算子上的峰值来读。

每步形状已知，就别编一份覆盖所有步的计划

row-tiled attention 解决的是一步之内的问题，跨步还有一笔浪费。LLM 引擎每步调用同一接口，只能编一个对所有位置都成立的宽泛计划。GR 这几步明明各有确定的形状，引擎看到的却只是动态变化。

RecoGEM 的 step-granular planning 分三段走。先建一张宽泛的计算图，再在编译期对 t=1..L 逐步 dry run，推出每一步的张量形状，最后生成按步特化的计算图。一个宽泛的动态 profile 会逼引擎为所有步出现过的维度的并集做优化，按步的 profile 则把每一步收窄到它实际的形状。于是每一步绑定与自身 S_kv 匹配的 row-tiled attention 变体，tiny-softmax 长度和 K/V 暂存范围都按记录的 S_kv 定，避开 attention 关键路径上宽泛的动态内循环。候选选择也按该步的候选宽度和保留 beam 宽度特化。batch 这类随流量变的维度仍然是动态的，同一份产物照样能接不同大小的 batch。

420 万个分数装不进线程块，那就先按行切一刀

形状的账算完，还剩每步结尾那次选择。LLM 通常只选 K<10，GR 的 beam update 每步选 K>128，Top-K 实现因此变得敏感，bitonic 和 radix 的延迟能差好几倍。

最直接的做法是把一个请求的 W×C 分数矩阵展平，跑一次大 Top-K。C=8192、W=512 时展平后约 420 万个候选，FP16 下占 8 MiB，远超线程块的本地内存。

RecoGEM 分两段：先在每条 beam 行里取局部 top K，再在 W×K 个幸存者上做请求级选择。结果和全局 top-K 完全相同。一个候选如果在本行连前 K 都进不去，同行已有 K 个候选压过它，它不可能进全局前 K。若 K 也取 512，第二段的输入就从约 420 万降到约 26 万。

单算子测试里，batch 32、beam 512 耗时 0.618 ms，比 ATen 快 2.08 倍，比标准 radix 快 1.70 倍，说明保留 beam 行的边界本身就有收益。Bitonic 在 K=1024 时要慢 20.6–26.6 倍，所以 K 越大，算法选错的代价越高。

把延迟拆到每一步，收益各有归属

三件事合起来的效果，先看 batch 32 的端到端结果。GeneralGen 是同一系统的对照配置，用同质的形状 profile 和朴素 GPU kernel，其余模块不变。

所以 2.88 倍度量的是形状特化和专用 kernel 的价值，并非对外部系统的领先。OneRec-v2 在整个 batch 扫描中 P99 都低于生产 100 ms 目标。外部对照 TRT-LLM 是改造过的 TensorRT-LLM，只有曲线趋势：延迟随 batch 急升，QPS 很快到平台。论文给出的原因之一，是它在 CPU 上做 beam search，再按选中的 beam 重排 KV cache，开销随存活 beam 数增长。

总账背后是哪一步在省？作者用 nsys 拆解 OneModel 在 batch 32 下的延迟。HomoGen 只去掉按步规划、保留专用 kernel，平均解码延迟从 30.4 ms 升到 39.5 ms，前三步高出 40% 以上。GeneralGen 连专用 kernel 也去掉，最后一步从 13.8 ms 涨到 54.0 ms，多出来的主要是候选选择。

按步规划的收益集中在前几步，专用 kernel 的收益集中在后几步。

读 54.0 ms 时要收窄结论。这近 4 倍对比的是朴素路径，前面的单算子测试里，对 ATen 和标准 radix 的优势约为 2 倍和 1.7 倍。它说明选择路径选错的代价很高，并不说明两段式比一个像样的 Top-K 快近四倍。

每分钟 107 次 refit，步边界还得有人守

这些优化都要求引擎看得见步边界，步与步之间的状态和线上更新就得有人接手。RecoGEM 的做法是 runtime–engine 解耦：engine 只做张量计算，runtime 管步间转移和在线更新。两者靠一份 deployment contract 连接，它由模型图加服务策略自动生成，runtime 加载时据此校验编译好的 engine。

状态管理正好对应前面的 beam 淘汰。cross-KV 编码一次，整个请求固定复用。self-KV 跟着候选行走，beam search 剪掉一部分行后，缓冲区就变稀疏了。runtime 用幸存索引把对应片段 gather-copy 到备用缓冲，下一步看到的是紧凑前缀。

更新的压力来自线上频率。生产集群的权重 refit 峰值达到每分钟 107 次，最忙时 FP32 refit 流量为每台服务器每小时 346 GB。SID 词表刷新还会改变 token 的含义，飞行中的请求必须留在同一版本。生产里也试过约 20 种 beam search 策略变体。

RecoGEM 的规则很简单。新版本先过 contract 校验，切换时短暂停止接新请求，已发出的请求在旧版本跑完，然后原子切换 engine 指针，contract 变了就一起切。每个请求因此只看到一致的模型、词表和策略版本。

早期实现是整体重建 engine 再直接推到实例，更新期间的 P99 尖峰大 2–3 倍。现在这条路径在线上 trace 里没有可见的 SLA 违约。这 24 小时内流量从约 5,000 到超过 50,000 QPS，P99 一直低于 80 ms，集群历史峰值是 60,000 QPS。这里是集群线上的端到端 P99，不能和前面单实例的 30.8 ms 直接比。

先改造 LLM 框架，是他们自己认定的错误边界

团队最初也是去改造 LLM 推理框架，后来认为这是错误的系统边界：改动侵入性大，还要和旧的推荐基础设施共存。

瓶颈的迁移也印证了这一点。DLRM 服务里稀疏 embedding 查找常超过 50% 的延迟，在他们的 GR 部署里不到 10%。xGR 报告候选选择占 40% 以上的服务时间，他们优化后降到 10% 以下，压力回到稠密解码。

我的理解是，这篇最值得带走的是一个顺序：先看清每一步真实的张量形状，再决定哪些边界交给系统，哪些交给 kernel。海量短行和大 K 选择这两笔账算清之后，下一笔账又回到了稠密解码本身。
