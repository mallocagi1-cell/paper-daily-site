LLM-Based Generative Retrieval for Snapchat Content Recommendation

1. 问题与动机

SnapLGR 研究的不是离线榜单上的一般推荐，而是把预训练 LLM 真正接入 Snapchat 短视频召回链路时出现的三类耦合问题。第一，生成式召回需要让模型直接生成物品的 Semantic ID SID，但这些离散 token 不在语言模型原始词表中；如果只在点击序列上从零学习，新 token 很难继承预训练模型已有的视觉和文本知识。第二，SID 既要压缩海量视频，又要避免大量不同视频落入同一编码桶；纯内容 RQ-VAE 容易忽略协同行为，碰撞又会把后续生成精度消耗在物化阶段。第三，工业召回使用宽 beam、频繁增量训练和大规模批量推理，标准 Python beam search 的实际 GPU 解码只占总耗时 12%–15%，其余时间被 beam 计分、KV cache 分叉、调度和 I/O 吞掉。

论文以 TIGER 式、从零训练的 13M 参数 T5 encoder-decoder 为线上旧基线，追问预训练 decoder-only LLM 的真实增益来自哪里。作者指出，既有 PLUM 已经展示 SID、持续预训练和任务微调的组合，但没有系统回答 Snapchat 规模下的碰撞、词表落地、吞吐和线上收益如何共同解决。因此本文的核心动机是端到端协同设计，而不是单点替换 backbone。

2. 方法详解

完整系统有四层：视频到 SID 的 tokenizer、CPT/SFT 两阶段 LLM 训练、SID 到具体视频的物化，以及离线批生成加在线索引服务。

SID 构造。 每条视频先由 Gemini 2.5 Flash 生成文本描述，再输入 Qwen3-VL-Embedding-8B 获得多模态向量。作者利用其 Matryoshka 表征性质，只取 4096 维向量的前 1024 维。RQ-VAE 使用三层码本，宽度依次为 1024、512、256；每一层对当前残差与码本向量计算余弦相似度，选最大者作为该层 token，再从残差中减去被选向量。前向保持硬离散选择，反向通过对全码本 softmax 的 straight-through surrogate 传梯度，避免长期未被选中的 code 失活。码本正交初始化并做 L2 归一化，输入和量化和均配合 LayerNorm。

Tokenizer 总损失可写成 L = L_rec + λ_commit L_commit + λ_co L_co。前两项负责重构与残差/码本承诺，第三项注入协同行为：作者在用户—视频二部图上，从每个视频的二跳邻域计算 Personalized PageRank，保留高于全体 P75 阈值的共参与视频对作为正样本，并用 batch 内其他视频作负样本做 InfoNCE 式对比学习。PPR 的重启项让相似性围绕当前视频局部邻域，而不被全局热门节点牵走。

词表落地与任务训练。 Backbone 是 Qwen3-0.6B。新增 SID token 的向量按原词表均值和协方差随机初始化。CPT 阶段冻结整个 LLM，只训练 SID embedding：输入一个 SID 序列，让模型生成该视频的文本描述，从而把新 token 锚定到已有语言语义空间。CPT 使用截至 SFT 日期一周前、覆盖一个月的视频语料，只在初始基座训练时执行一次。随后 SFT 用 ChatML 形式把用户按时间排序的历史 SID 放在 user prompt，把未来参与的 SID 放在 assistant target，并只对 assistant token 计算自回归损失；生产中按小时用新交互增量更新。离线实验的 SFT 数据窗口为 1 天，评估紧接着的 1 小时，每个请求最多取 10 个未来物品作标签。参考 checkpoint 为 Qwen3-0.6B、约 600k step；单次完整观测约 345.6B token。论文给出缩放实验学习率：13M、60M、220M 分别为 1e-3、3.4e-4、2.6e-4，但没有披露主训练的优化器、全局 batch size 或精确生产训练时长。吞吐实验使用单机 8×A100-80GB，最终软件栈也在 8×H100 上测试。

推理与物化。 模型每天离线用 beam width 32 生成用户未来 SID。每个 SID 桶保留固定数量视频，再以多目标线性价值函数 V(i)=Σ w_m S_m(i)，按各类参与率预测加权排序，写入用户到视频的低延迟索引；在线请求只读预物化候选并交给下游排序。训练侧依次加入 torch.compile、FlashAttention-2 变长 kernel 和动态 sequence packing。推理侧把 Python beam search 迁到 TensorRT-LLM CUDA runtime，再将中央调度改成各 worker 自主领取 Parquet shard，最后用后台 row-group 预取、异步写盘和去除无用 CPU 指标计算重叠 I/O。分布式实验使用 64×A100。

3. 核心技术贡献

  1. 把内容语义与协同行为同时写入 SID。 相比只做重构的 RQ-VAE，PPR 正样本对刻画真实共参与关系，又通过局部重启抑制热门偏置；这让码本利用率从无行为监督时的 31.8% 提至 49.1%，唯一 SID 比例从 16.8% 提至 32.1%，Gini 从 0.551 降至 0.424。机制上的价值是减少 mega-collision 桶，使生成结果更容易稳定物化为具体视频。
  1. 显式拆开新词表学习与行为任务学习。 CPT 冻结基座、只训练 SID embedding，避免一开始就让稀疏点击监督同时承担词义学习和推荐学习。随机初始化的文本语义 RSA 只有 0.016，CPT 后升到 0.322；随后 SFT 虽把它拉回 0.167，但 CPT 仍让 Recall@32 从 10.98% 增至 11.11%。这说明语义落地不是最大增益，却能提供稳定的优化起点。
  1. 证明 decoder-only 结构本身比单纯堆参数更重要。 在相同 tokenizer、数据和随机初始化条件下，13M Qwen3 的 Pass@32 是 23.07%，几乎等于 220M T5 的 23.03%；同规模下 Qwen3 在 13M 处将 Pass@32 和 Recall@32 分别提高 1.51 倍和 1.50 倍。
  1. 给出可上线的宽 beam 系统路径。 TensorRT-LLM 单卡先带来 9.3 倍吞吐，64 卡去中心化 worker-loop 累计到 30.7 倍，I/O 重叠后达到 45.7 倍。它把模型方法与系统瓶颈放在同一实验中验证，而非假定高离线 Recall 可以直接服务。

4. 实验结果分析

主要离线对比在固定 Qwen3-VL SID、相同训练数据和 beam width 32 下进行。Pass@k 表示 top-k SID 中至少命中一个未来目标，Recall@k 是命中未来目标集合的比例。

这个差距不是只由模型规模造成。结构消融显示 decoder-only 在 13M、60M、220M 都优于匹配规模的 T5，且 T5 从 60M 扩到 220M 的 Pass@32 只增加 4.4%，Qwen3 同区间仍增加 14.3%。预训练初始化将 P@10 从 20.88% 提至 21.60%、R@10 从 6.106% 提至 6.341%；再加 CPT 后分别为 21.78% 与 6.437%，说明架构和预训练是主效应，CPT 是小而一致的增益。Tokenizer 消融也更克制：Qwen3-VL SID 的 SID Recall@32 为 10.98%，旧 MM 为 10.58%、MM+ 为 10.30%；对应 video Recall@32 是 2.765%、2.720%、2.616%。值得注意的是 MM 碰撞分布比 MM+ 更差，却有更高召回，作者据此明确承认碰撞指标不是端到端质量的充分条件。

数据缩放从 69.1B token 增至 345.6B token 时，Recall@32 从 8.85% 单调升至 10.98%，但最后 0.2 epoch 只增加 0.149 个百分点，收益已开始递减。beam width 从 32 提至 96 能把 Recall@32 从 10.98% 提至 12.25%，相对 +11.56%，代价却是 A100 吞吐下降 45.0%，因此生产选择 32 是质量和预算的折中。

系统消融同样清楚：A100 上 torch.compile、FA2 变长 attention、优化 packing 累计把训练吞吐提升到 1.78 倍，换 H100 后到 3.63 倍。在线 7 天 A/B 中，SnapLGR 相对旧 T5 系统的 View Time +0.37%±0.27%（p=0.007）、Time Spent +0.09%±0.09%（p=0.048）、Deep Sessions +0.18%±0.16%（p=0.027）、Deep Sessions Unique User +0.11%±0.09%（p=0.017）。四项均显著为正，尤其 Deep Session 指标说明不只是单次观看变长。不过线上实验同时更换 tokenizer、backbone 和 serving stack，只能证明整套系统有效，不能将 +0.37% 单独归因于某个建模组件。

5. 局限与未来方向

作者明确报告了三项边界。其一，线上 A/B 是整套系统替换，组件因果只能依靠离线固定条件消融；线上收益不能直接归因于 PPR、CPT 或 decoder-only 中任何一个。其二，SID 碰撞质量与最终召回并非完全相关，说明尚缺少能同时预测编码分布、物化质量和用户价值的 tokenizer 目标。其三，CPT 把 RSA 提到 0.322，但行为 SFT 后降到 0.167，文本语义大多被协同目标覆盖；作者仅观察到小幅下游收益，尚未解释怎样长期保持两类语义。未来工作计划扩大 LLM backbone，以利用更多预训练知识。

论文未充分讨论的限制包括：数据、流量规模和绝对 GPU 成本均为内部口径，主训练优化器与 batch size 未公开，外部团队无法完整复现成本曲线；离线主要评估 SID 命中而非下游 nDCG、CTR 或内容安全，新鲜视频和极冷用户的单独结果也未给出。预物化候选虽降低在线延迟，却可能产生时效性陈旧；SID 桶内多目标价值函数的权重与公平性影响未披露。实验只来自单一短视频平台，迁移到社区文本搜索、电商或长尾专业内容仍需重新验证。

6. 工业实践意义

对搜索/推荐团队，最可行动的结论是采用分阶段改造。第一阶段先固定下游排序和 serving，只比较 decoder-only 与现有 encoder-decoder 生成召回；论文表明结构收益可能大于盲目扩大旧模型。第二阶段建设内容+行为 SID：社区 UGC 可把标题、正文、图像/视频向量与点击、停留、收藏图的局部 PPR 结合，并同时监控利用率、唯一率、Gini、SID Recall 和物化后的 item Recall，不能把低碰撞当成唯一目标。第三阶段为新 SID 增加轻量 CPT，再做小时级行为 SFT，以解决新增内容 token 与用户兴趣漂移。

部署上，应优先剖析 beam 管理和 I/O，而不是只盯 kernel。若 GPU decoding 占比像论文一样只有 12%–15%，迁移 CUDA beam search、去中心化 shard 调度和异步读写会比扩大模型更划算。beam 32→96 的 11.56% Recall@32 增益对应 45% 吞吐损失，适合只对高价值、长尾或探索请求动态放宽，而不是全流量升级。预物化索引适合推荐 feed 或可容忍分钟/小时级新鲜度的社区场景；对突发热点搜索，应保留实时 ANN/倒排召回与新内容旁路，避免日更生成列表错过热点。

评估应沿着 SID 质量→离线召回→物化后召回→影子流量→小流量 A/B 逐层推进，并给每层设回退开关。线上至少同时看 CTR、有效停留、深度会话、内容多样性、新内容曝光和安全违规率；论文的 +0.09% Time Spent 已接近显著性边界，说明单一参与指标不足以支撑全面替换。总体上，SnapLGR 最值得复制的是端到端协同方法：让表示、训练、生成、物化和 serving 共享一套可诊断指标，而不是把生成式推荐当作一个可直接替换的模型组件。
