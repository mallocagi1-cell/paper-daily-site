OxygenREC 值得做生成式推荐的团队细读，因为它把一个大家都想做、但很少有人讲清楚的事拆成了能落地的几步：让 LLM 的推理影响推荐结果，同时线上一次 LLM 都不调。这篇来自京东，做法是让 LLM 在近线把用户意图写成文本指令，编码成 embedding 存起来；线上的 encoder–decoder 生成模型只读这个 embedding，用它挑选长期历史、引导 Semantic ID 的逐位生成。同一套模型靠"场景指令"服务首页、频道 feed、加购弹层、结算页等多个场景。不过要先说清楚：训练时这个推理指令只有搜索数据里才有真实文本（用改写后的 query 充当），推荐场景训练时用的是一个可学习的默认 embedding；线上推荐场景读到的却是近线 LLM 写的指令。这两者之间的差距，论文没有单独做实验。

核心想法一句话：把"慢的推理"挪到近线，把结果压成一个 token 交给"快的生成"，再用同一个 token 区分场景。

几个关键数字：

  • 统一模型对比各场景单独 SFT 的模型，六个场景 HR@1 全部更高，比如场景 1 从 6.39% 到 15.39%；但单独 SFT 的基线在场景 3 只有 1.12%，基线本身偏弱。
  • 后训练阶段，作者提出的 SA-GCPO 对比 GRPO，HR@1 从 23.85% 到 25.58%，HR@10 从 62.15% 到 65.95%。
  • 线上 A/B 里六个场景的订单量都涨了，最高是频道 feed 的 +8.03%，说明收益不只来自点击；延迟控制在 50–80ms，意味着这套结构能放进首页这类高流量位置。

1. 一个贯穿全文的例子

下面用一个示意例子（不是论文数据）串起各个部件。用户小王，北方城市，冬至前一周，最近搜过"wine gi"（被截断的输入），加购过一个手机。现在他在首页点了一个手机壳商品，进入频道 feed。

  • 近线：LLM 根据时间地点写出"冬至，北方，饺子相关食品"；改写模型把"wine gi"补全成"wine gift box"；意图模型根据加购记录写出"在配手机周边，原因是刚加购了新手机"。这些文本再由一个 adapter 文本编码服务在近线转成 embedding，按用户 ID 存进 Redis 这类低延迟 KV。三路文本是先拼成一条再编码，还是各自编码后合并，论文没说。
  • 线上请求：场景信息是"频道 feed"，触发商品是那个手机壳，两者融合成一个场景指令；从 KV 读出推理指令 embedding。
  • 模型用指令去小王上千条长期历史里挑最相关的 K 条（比如他过去买过的数据线、贴膜），连同画像、短期行为送进 encoder；decoder 从 BOS 和指令 token 开始，逐位生成 3 位 Semantic ID。

2. 整体结构

整套系统分四块：商品 Semantic ID、近线推理指令、带指令的 encoder–decoder 预训练、多场景强化学习后训练。线上服务部分用 xLLM 推理引擎，beam size 256–512，用 Trie 做前缀约束解码，保证只生成当前场景商品池里存在的 ID。

3. 机制拆解

3.1 商品 Semantic ID

生成式推荐要逐 token 输出商品，商品必须先变成离散码。码的质量决定了同一个码前缀下的商品是否相似。

做法是：文本特征（Qwen3）和图像特征（CLIP）经 Q-Former 和 MLP 融合成 256 维 embedding，用对比学习训练，正样本来自三类信号：query 和商品的关联（Q2I）、Swing 算法挖出的行为共现商品对、同一 query 同一类目下的语义相近商品。然后用 RQ-KMeans 量化成 3 层、每层 8192 个码。

手算一下：3 层 × 8192 可表示 81923≈5.5×1011 个组合，远多于商品数，所以真正的问题是码的使用是否均匀。论文的冲突指标是先数每个完整三位码下有多少商品，再取这个分布的 99.9 分位（P999）：V4 是 35，V1 纯文本版本是 419。覆盖率按联合路径算，第 3 层的分母是 81923 种组合，V2（用 MiniCPM-V-8B 编码图文、只用 Swing 共现对做对比学习的版本）在这一层只有 0.013%，作者认为是深层码本部分塌缩。既然一个完整码下可能有几十个商品，decoder 生成出码之后怎么落到具体商品，论文没说。

这说明：V4 就是上面那套 Qwen3+CLIP、三类正样本的版本，多源信号主要改善了码的均匀度和类目纯度。类目纯度的算法是：对每个码，看它下面的商品里占比最大的一级类目占多少，再对所有码取平均；V4 是 92.80%。作者还说多模态设计比 OneRec 风格的做法 HR@1 相对提升超过 30%，但没有给出这组对比的完整表格。

3.2 近线推理指令

模型只看行为序列时，遇到"冬至+北方"这种少见组合很难推出需求；而线上调 LLM 太慢。

做法是：三路并行（见下图）。时空和画像这一路用 JoyAI LLM 生成，按"时间–地点–人群"三元组分层存储，线上按索引直接取；query 改写用 SFT 过的 Qwen3-0.6B，人工评测通过率 95.33%，高于直接用 DeepSeek-R1 的 88.67%；意图推理也是 Qwen3-0.6B，训练标签由 Qwen3-32B 清洗行为序列、DeepSeek-R1 生成理由得到，人工评测可用率 72%。每天对所有日活用户全量重算一次；用户有搜索、加购、购买等高价值行为时触发增量更新，5 分钟左右的窗口内合并成一次写入。

这说明：72% 的可用率意味着大约每 4 条意图指令就有 1 条不可用，论文没说不可用的指令在线上如何过滤，也没有给出"有无近线指令"的线上对比。

3.3 指令 token 放在哪

同一个模型要服务多个场景，必须告诉 decoder "现在是哪个场景、由哪个商品触发"。

做法是：场景指令 Is​ = 场景信息 + 可选触发商品（没有时用默认值）；推理指令 Ir​ = 文本指令经 adapter 投影出的 embedding。两者组成一个指令 token 放在 decoder 输入的 BOS 右边，后面接 sid0、sid1、sid2。论文对融合只说了一句：把场景和触发商品的特征拼起来，投影成一个统一表示后再放进序列；投影用什么网络、Ir​ 是和 Is​ 一起投影还是另加，论文没说。

手算一下：按 Table 5，没有指令 token 时 HR@1 是 2.78%，放在 BOS 右边是 3.53%，相对提升 (3.53−2.78)/2.78≈27%；直接替换 BOS 只有 3.30%。把场景和触发商品融合成 1 个 token（3.60%）略好于拼成 2 个 token（3.53%）。

这说明：位置之间的差距在 0.2 个点左右，最大的收益来自"有没有"指令。这组消融用的是全量数据的一个子集。

3.4 IGR 和 Q2I 损失

长期历史动辄上千条，大多和当前意图无关，全部放进 encoder 既慢又干扰生成。

做法是：查询向量 q 由两部分拼接后过投影网络 ψq​ 得到，一部分是场景和触发商品的 embedding，一部分是推理指令文本经文本编码器得到的向量（线上这部分直接读 KV 里近线算好的 embedding；论文把近线服务称为 adapter 文本编码器，公式里则写成与商品标题共享的编码器，论文没说两者是否同一个模型，也没说如果不是，线上向量怎样和训练时的输入对齐；复现时最稳妥的做法是近线直接用训练里那个编码器，这是我的建议，不是论文的做法），所以场景、触发商品和近线意图都会影响历史筛选。推荐场景训练时推理指令是默认 embedding，此时 q 主要由场景和触发商品决定。商品一侧把商品 ID embedding、类目等附加特征和标题文本向量拼起来，再过另一个投影 ψi​；目标商品的文本编码器可训练，历史商品的文本编码器冻结。ψi​ 通过目标商品这一支得到训练，同一个 ψi​ 也用来投影历史商品。线上是否缓存历史商品的投影结果，论文没说。训练时加一项 Q2I 损失，让 q 和目标商品向量 t 的点积变大，另加方差项和去相关项防止向量塌缩。推理时用 q 在历史中按点积取 top-K（IGR，Instruction-Guided Retrieval）。论文的方法部分只把 top-K 筛选写在推理阶段，训练时送进 encoder 的长期历史是否也用 q 筛选，论文没说。长期历史这一支不回传梯度，文本编码器是冻结的。总损失是按行为加权的 NTP（购买 > 加购 > 点击）加上 λ 倍 Q2I。

手算一下：假设 q=(1,0)，历史里数据线向量 (0.9,0.1)、羽绒服 (0.1,0.9)，点积分别为 0.9 和 0.1，K=1 时只保留数据线。K 的取值论文没说。

这说明：Table 7 在搜索为主的场景里，基线 HR@1 3.76%，加 IGR 到 4.02%，再加 Q2I 到 4.19%。IGR 单独使用已经有效，加上 Q2I 把查询和商品放进同一空间后效果最好。

3.5 后训练：SA-GCPO

推荐场景的真实反馈稀疏，直接拿线上反馈做强化学习容易被奖励钻空子。

做法是：用历史用户画像加策略模型生成的候选，交给统一的列表式排序模型打分，得到合成训练数据。奖励由四项按场景加权：格式奖励惩罚无效的 Semantic ID，相关性奖励看生成商品和当前查询在 Q2I 空间是否接近，排序奖励来自排序模型对 GMV、转化率等业务目标的打分，多样性奖励评估同一组生成商品的多样性，具体用什么特征、怎么算，论文没说。排序服务按请求的商品和用户信息给每个候选返回一个分数；各项奖励的具体算法和权重，论文没说。SA-GCPO 在 GRPO 的组内归一化优势上改了两处：一是如果某个生成商品优势为正、但奖励低于用户真实交互商品的奖励 Rg∗​，就把优势置 0，不鼓励"比组内平均好但不如真实答案"的样本（论文只说 Rg∗​ 是这一组对应的真实目标商品的奖励，没说它和候选是否同一批打分）；二是在每个 Semantic ID token 上算新旧策略的概率比 r=πθ​/πold​，用 sigmoid 软门控 f=σ(τ(r−1))⋅4/τ 代替 PPO 式的硬截断，目标函数里 f(r) 乘以处理后的优势。记 p=σ(τ(r−1))，它的梯度权重是 4p(1−p)，在 r=1 时 p=0.5、权重最大为 1，r 偏离越远衰减越多；正负优势用不同温度 τ。

手算一下：组内 4 个候选奖励 0.2、0.4、0.6、0.8，均值 0.5，奖励 0.6 的候选优势为正；若真实商品奖励 Rg∗​=0.7，它的优势被置 0，只有 0.8 那个得到正向更新。

这说明：Table 10 在 0.7B 模型、33% 合成数据下，SA-GCPO 比 GSPO（在整条 Semantic ID 序列上算重要性采样比的 GRPO 变体）高 1.45 个点 HR@1。但 Table 11 里同样设置（τ 都是 1.0）的 HR@1 是 25.48%，和 Table 10 的 25.58% 对不上；正负温度的三组结果相差不到 0.2 个点，"更稳定"的结论证据偏弱。

5. 局限

  1. 推理指令的训练–线上差距：训练时推荐场景的 Ir​ 是默认 embedding，线上读到的是 LLM 写的文本指令，模型在推荐场景从没见过这类输入。论文没有做"有无近线指令"的线上或离线对比，所以 LLM 推理到底贡献了多少，论文没说。
  2. 基线和表格问题：单独 SFT 的基线在部分场景 HR@1 只有 1% 左右，统一模型的大幅领先部分来自基线弱；文中写"五个场景"而表里有六个，Table 9 与 Table 8、Table 10 与 Table 11 的数字也有对不上的地方。
  3. 成本没有完整披露：训练用 128 张 H800、MFU 40%，但每天对全部日活用户重算指令的 LLM 成本、KV 存储规模都没给。

6. 怎么试

  1. 先只做场景指令：在现有生成式召回的 decoder 中，把场景 ID 和触发商品融合成一个 token 放在 BOS 右边，对比"每场景一个模型"和"一个模型 + 场景 token"。
  2. 用搜索日志里改写后的 query 作为推理指令训练 Q2I 和 IGR，先在搜索流量上看长期历史筛选是否有效，并调 K。
  3. 用一个小模型离线生成意图指令，抽样人工评估可用率，再做离线消融：同一批用户有无指令的 HR 差距。这一步补的正是论文缺的那组对比。
  4. 后训练时先复现"优势为正但奖励低于真实商品则置 0"这一条规则，它实现成本最低，再决定是否换软门控。

7. 评价

维度评价
问题重要性高：多场景统一和低延迟用上 LLM 推理是生成式推荐落地的核心问题
方法创新性中：各部件多为已有做法的组合，指令 token 与 IGR 的配合较有新意
实验证据中偏弱：线上 A/B 完整，但缺少近线指令的单独消融，几张表数字不一致
工程成本高：需要近线 LLM 管线、KV 存储、定制推理引擎和排序模型做奖励
是否值得尝试场景指令和 IGR 值得先试；近线 LLM 指令等有了自己的消融再决定
