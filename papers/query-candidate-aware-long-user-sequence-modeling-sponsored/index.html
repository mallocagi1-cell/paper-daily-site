在 Wayfair 这篇论文里，搜索广告该翻哪段长期历史，取决于用户这次搜了什么和正在打分的是哪件商品；而影响最大的一环，仍是把候选商品拼进每条历史 token。

先看一个示意的例子（我编的，不是论文数据）。用户搜「户外餐桌椅」，排序模型正在给一张柚木桌打分。几个月前这位用户看过遮阳伞，也看过别的柚木家具。遮阳伞和这次搜索有关，和这张桌子并不像；柚木家具则和这张桌子很像。只按候选去翻历史，遮阳伞那条很可能翻不出来。

Wayfair 的做法是按候选、按查询各取 50 条最相近的旧行为，接在最近 100 条后面。相对线上基线，下单 AUC（order-7d AUC）在只按候选时 +1.35%，只按查询时 +1.16%，两路一起 +2.19%。作者据此认为两路检索提供了互补的视角。

在两路检索的完整模型上关掉 early fusion，下单 AUC 反而比线上基线低 6.06%，幅度比检索带来的增益大得多。

最近 100 条翻不到几个月前的遮阳伞

Wayfair 的 sponsored-product ranker 是一个多任务深度网络，线上已经有 TransAct-style 序列模块，读用户最近的 100 条行为。窗口只有这么长，几个月前的遮阳伞很可能早已掉出去了。

把窗口直接拉长行不通。原始历史可以有几万条，竞价时的延迟预算读不完，而且对某一次打分来说，大部分行为都无关。所以得先挑一小批，再细读。

挑的依据，搜索场景比别处多一条线索：查询直接说出了这次请求的意图。作者的论点是，只按候选检索，会漏掉和查询高度相关、和候选只有间接关系的行为，遮阳伞正是这一类。

下面讨论的改动，都发生在图里黄色的 Sequence module 内部。

每路 50 条，是线上算得起的预算

既然一路检索会漏，就让查询和候选各检索一次。每次打分时，模型拿到三份历史。第一份是最近 100 条，原样保留。

其余行为进入检索池，回看一年，量级上千条。第二份是池子里商品与候选最相近的 50 条，第三份是池子里商品与查询最相关的 50 条。同一条行为被两路同时选中时，按 event ID 只留一次，所以序列最长 200 条，有重叠时更短。

检索用的 query 和 SKU（商品编号）表示来自 Wayfair 内部的 semantic-search 模型，对 ranker 是固定的，不跟着排序目标更新。候选这一路用 32 维 SKU embedding，为的是压住 ANN 查询和内存开销。

100 条沿用线上配置，50/50 是为了把总长控制在 serving 预算内。作者自己把这组数称为生产工作点，并不认为它是全局最优。

候选要进两个地方

历史取回来之后，模型还得知道它们和这次请求是什么关系。Transformer 的输入最前面放两个 context token，一个代表查询，一个代表候选。

后面每条历史 token 由动作类型、历史商品、候选商品、两者的 metadata 和交互 surface 经 MLP 合成，再加上时间和角色 embedding。候选在每条历史 token 里都出现一次，这就是论文说的 early fusion。 Hoot 说▾

第一层 c token 只看自己和 q token。只遮历史之间的 attention 不够：它能看到未来动作，下一层再传回更早的历史。

示意：用户搜「户外餐桌椅」，两件候选都是假设。c 进了 token 的 MLP，所以同一条旧行为遇到新候选也要重算；只有不含 c 的 embedding（动作、历史商品、surface、时间）能复用。示意成本：一次请求 30 个候选、序列都取满 200 条，token MLP 共 30×200=6000 次。如果历史 token 不含候选，最近 100 条和查询 50 条共 150 条只算一次，总数降到 150+30×50=1650 次（不计去重）。但序列里还有 c token 和候选 50 条，两层 Transformer 仍要每个候选各跑一遍。 出处: 论文 §3.2 历史 token 公式（c 进入 MLP_token）与 context token；§3.3 混合 attention；§4 序列配置与消融；候选、30 个候选和成本都是示意，依赖关系按 token 公式推出

我的理解是两者分工不同。early fusion 让模型在每一条行为上直接比较「当时看过的东西」和「正在打分的东西」。context token 则让查询和候选各占一个位置，和整段历史做 attention。从 token 的公式看，查询只走 context token 这条路，并不进入每条历史 token。

全局 token 让 causal mask 漏了一个口子

这个结构还带一个辅助目标 NAL（auxiliary next-action loss），也就是用历史去预测下一个商品。它只算在连续的最近序列上，用同 batch 里其他样本的下一个商品当负例，权重 0.05。

预测下一步就不能看到未来，而普通的 causal mask 在这里不够用。context token 是全局的，第一层可以看到未来的目标动作，第二层再把信息传回更早的历史 token。

解法是把两层分开。编码器一共 2 层 Transformer，第一层里历史之间仍是 causal，历史可以看两个 context token，context token 只能看自己和彼此，NAL 就在这一层的输出上计算。第二层完全双向，只服务排序 loss。

两路多赚多少，拆掉哪块掉多少

每一块到底值多少？Wayfair 在同一套架构、同一份一个月的留出测试集上做了消融。基线就是线上模型：只读最近行为，没有 context token，有 early fusion，没有 NAL。

第一行说明，没有长期历史时，context token 和 NAL 单独用并不够，作者认为主要提升来自翻出相关的长期行为。

中间三行是主线。两路一起时，下单 AUC 比最好的单路多 0.84 个百分点，点击 AUC 只多 0.21。作者的解读是两路提供了互补的视角。

这批离线实验的不确定性估计没有保留，作者提醒小差异要谨慎看。所以 0.84 我只当作方向，0.21 不必多读。这些增量都是在 Wayfair 同一架构内量出来的，作者明确不声称和 TWIN、TransAct V2 做过同条件比较。

再看去掉 context token 那一行。两路检索之上，点击增益从 1.37% 降到 0.45%，下单增益从 2.19% 降到 0.28%。作者的读法是，context token 和 NAL 与相关长期行为结合时收益最强；第一行同时改了这两者，点击 AUC 仍有 +0.46%。

去掉 NAL 后两项增益降到 1.11% 和 1.46%，作者读作较小的正向贡献。不过下单上这 0.73 个百分点和第二路检索的 0.84 差不多，没有误差条时我不敢排先后。

影响最大的是最后一行，而它拆的是基线本来就有的东西。

所以这 6.06% 不能算成新模型的贡献。作者的解释是，没有 token 级的候选条件，模型只能靠全局候选 token 和后续 self-attention 间接恢复候选与历史的匹配，这条路在生产任务上不够。他们也检查了训练和验证曲线，这一组优化过程正常，所以把差距归因于结构。

离线涨两个点，线上点击和转化都动了

离线 AUC 能换来什么，要到线上才知道。Wayfair 在 sponsored-product 搜索流量上跑了五周 A/B，按用户随机，实验组用新模型，对照组是现有生产模型。

相对对照组，CTR +6.0%，attributed CVR +5.2%，每次曝光的订单 +11.5%，三项都在 α=0.05 下显著。1.060 × 1.052 ≈ 1.115，所以如果 attributed CVR 按每次点击计，+11.5% 基本就是前两段相乘的结果，算不上第三个独立的提升。

同一实验里 CPC −1.3%，广告总花费 +0.8%，也都显著，说明更多的点击和订单并没有靠抬高单次点击价格换来。作者认为这组结果与匹配变好、转化量变高相符。

代价是端到端 serving latency 增加约 12%，仍在现有延迟预算之内。新增部分主要来自 candidate-NN 拉取和更长的序列，整体延迟的大头还是拉取上游模型的输出。

回到那张柚木桌。最近 100 条负责当下的兴趣，两路检索把遮阳伞和柚木家具都翻出来，每条历史里又带着这张桌子，模型才有机会比出它们的关系。作者接下来想让检索预算随查询具体程度、候选新旧等因素自适应，也想改进现在固定不动的检索表示。
