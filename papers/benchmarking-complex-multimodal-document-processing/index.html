1. 问题与动机

论文针对企业文档 AI 评测中的一个被严重忽视的问题：现有 benchmark 几乎全部聚焦在单一阶段——解析（OCR/Layout）、检索（BEIR/MTEB）、生成（RAGAS/RAGBench）——但企业落地的"解析→索引→检索→生成"完整流水线缺乏跨阶段的端到端评测。作者直白地写道："Most existing benchmarks pick one stage and assume the rest works"，这种假设在真实企业语料上崩溃：表格、图、多列布局、扫描 PDF 的小解析错误"sometimes break retrieval"，但又不会立刻显式暴露。

更关键的动机来自他们对实际后果的观察：单点指标提升不必然带来端到端质量提升，但企业团队又只能拿单点指标做选型决策，造成"采购评测被局部优化指标误导"。论文要回答的核心问题是：当四个阶段的评测同时进行时，阶段之间的相关性到底有多强？某一阶段的得分能否预测系统级表现？ 这是直接关系到企业 AI 工程化路线图的实证问题，比"再发一个新的 retriever"更具方法学意义。先前 RAGBench 等工作只评检索-生成两段，且依赖合成 query；EnterpriseDocBench 在五个真实领域语料上同时跑全四个轴，是首批严肃做这件事的尝试。

2. 方法详解

评测语料：1,459 篇文档 / 1,169 测试集（10/10/80 train/val/test 切分），覆盖 General(47%)、Healthcare(22%)、Tech(17%)、Finance(8%)、Legal(3%) 五个领域，全部来自公开许可源（SEC EDGAR、CUAD、PubMedQA、PMC Open Access、ArXiv）。500 query 用于 pipeline 比较，800 examples 用于四轴评估，QA 半自动生成且经 2 标注者验证（目标 Cohen κ≥0.85）。

四个评测轴及其内部加权：

  1. Parsing Fidelity = 0.40·TIS + 0.30·TEA + 0.15·FCQ + 0.15·LF：

- TIS（Text Integrity Score）：字符级 edit distance 准确率
- TEA（Table Extraction Accuracy）：DOM 树编辑距离
- FCQ（Figure Caption Quality）：BERTScore F1
- LF（Layout Faithfulness）：章节序列归一化编辑距离

  1. Indexing Efficiency：吞吐（pages/sec）、延迟、存储、$/page/year 成本模型
  1. Retrieval Relevance：P@k、R@k、nDCG@k、MRR，按 query modality 分层
  1. Generation Groundedness = 0.30·FA + 0.25·SAP + 0.15·SAR + 0.20·(1−HR) + 0.10·AC：

- FA（Factual Accuracy）基于 entailment 的 claim-level 支持验证
- SAP/SAR（Source Attribution Precision/Recall）
- HR（Hallucination Rate）按 extrinsic/intrinsic/fabrication 三类细分
- AC（Answer Completeness）四点 LLM 评分

对比的三条流水线（共享 GPT-5 生成器，温度 0.7，max tokens 512）：

  • BM25：经典 TF-IDF（k₁=1.5, b=0.75），512 token chunk，64 token overlap
  • Dense：E5-large 1024 维 embedding，余弦相似度，相同 chunking
  • Hybrid：0.5·BM25 + 0.5·dense 的线性融合

另有 ColPali v1.2 + ColBERT 重排、ColQwen2 v1.0、agentic 复杂度路由（query 特征 logistic 回归）作为参考架构但未端到端跑通，列入 future work。

3. 核心技术贡献

  1. 首个跨四阶段、跨领域、跨模态的统一评测框架：贡献不是"又一个 metric"，而是把解析—索引—检索—生成的 metric 用统一权重聚合（Q 系列），并提供原始拆解。这让"系统级"质量 Q 可以与"局部"质量同图比较，是后续做归因分析的前提。
  1. 通过控制变量直接测量"阶段间相关性"：固定解析、固定生成器，仅替换检索 backbone，跑 1,169 文档计算 r 与 r²，得到经验证据——而非靠直觉断言。这是论文最有价值的贡献，下文详述。
  1. 细粒度幻觉分类法（extrinsic / intrinsic / fabrication）+ 按文档长度分桶报告：把"幻觉率"从单一数字打散成可决策信息，比 RAGAS 的总体 score 更适合做工程取舍。
  1. 公开、许可清洁的多领域语料 + κ 校准的半自动 QA 生成 pipeline：使其他团队可在自己的领域复制这套评测；即使不直接采用 EnterpriseDocBench，方法学也可借鉴。

Hybrid 仅以 0.01 nDCG 的边际优势胜过纯 BM25，并未显著超越，但二者均显著强于 Dense（−0.08/−0.09）。作者结论："dense retrieval is probably not worth the cost on this corpus"——这与社区对纯稠密的浪漫认知相反。

生成端 800 例（GPT-5）：FA 85.5%、SAP/SAR 各 61%、HR 14.5%、AC 0.40、聚合 G=0.71。值得关注的是 SAP/SAR 同步只有 61%，意味着即便答案对了，约四成情况下引用归因不可靠——这才是工程上更难解决的痛点。

最重要的发现：跨阶段相关性几乎为零：

  • 解析 → 检索：r=0.14, r²=0.019
  • 解析 → 生成：r=0.17, r²=0.028
  • 检索 → 生成：r=0.02, r²<0.001

作者原文强调："Parsing quality explains under 2% of retrieval variance and under 3% of generation variance. Retrieval quality explains essentially none of generation variance." 这是颠覆性的实证：单看 parsing benchmark 上 +5% 的提升，几乎不会传导到下游；retrieval 端任何调优在该实验设定下对生成端几乎无影响。注意这是在控制实验下得到，背后原因可能是 GPT-5 太强补偿了下游差距，但对工程团队的指导意义仍然成立——只看局部 metric 选型会被严重误导。

幻觉率的 U 型曲线：

  • Short (<400 chars)：28.1% [16.0%–44.6%, n=35]
  • Medium (400–1K)：9.2% [5.6%–14.7%, n=158]
  • Long (1K–3K)：14.4% [10.6%–19.3%, n=250]
  • Very Long (3K+)：23.8% [10.6%–45.1%, n=21]

短文档与超长文档双双高幻觉率，中等文档最稳健。作者诚实承认 Short 和 Very Long 的 n 较小，但区间已能给出方向性判断：评测必须按长度桶分层报告。

领域差异：解析保真度 General 0.92、Legal 0.90、Healthcare 0.62、Finance 0.41——表格密集的财务文件解析远未解决。

5. 局限与未来方向

作者在论文中明确列出的局限：

  • 设计层面抑制相关性：解析对三条流水线相同、生成器相同、metric 都是自动化代理而非人评，"any of those can suppress correlations"。即跨阶段相关性结论需要在更多变 baseline 下复现。
  • 领域不平衡：General 占 47%，Manufacturing 因 n=4 被排除，Legal n=46 统计功率不足。
  • 英语单语种：跨语种泛化未验证。
  • 自动化幻觉检测的标注一致性 κ=0.73——尚未达到 Q&A 标注的 0.85 目标。
  • 解析评测被部分弱化：三条流水线共享同一预提取文本，导致解析得分都是 0.82；要差异化需在 Phase 2 接入 ColPali/Docling/Tesseract 在原始 PDF 上跑。
  • query 分布偏学术摘要："neither is representative of typical enterprise workflows like compliance extraction"——这是个不容回避的代表性问题。

未来工作：端到端实现 ColPali/ColQwen2/agentic 路由；用更大平衡样本验证 U 型幻觉曲线；50–100 例人评的级联效应研究；接入专用解析工具；query 分布向真实企业任务再平衡；跨语种扩展；因果干预实验。

6. 工业实践意义

  1. 混合检索（lexical + dense）依旧是默认配置：在企业混合文档场景下，纯稠密在长尾术语、公司缩写、命名实体上掉点严重。社区搜索的实践直接受益——保留 BM25 + 稠密的双轨并以学习排序融合，比 all-in dense 稳健。
  1. 不要把"局部 metric +X%"当成投产决策依据：这是论文给所有 RAG/搜索团队最锋利的提醒。检索 nDCG 单独提升 5 个点，生成端体验可能无变化。建议在落地前建好端到端评测——哪怕只跑一千 query 一遍，一次性看到 retrieval+generation+attribution 三联表，比追单点指标更省力。
  1. 按文档长度桶差异化策略：U 型幻觉曲线意味着——对短文档（如标题、问题）和超长文档（如长帖、专栏）需要不同的 chunking、不同的检索 top-k、甚至不同的生成约束。社区搜索可以直接借鉴：短文本场景增强长尾术语精确匹配；超长帖采用证据片段抽取再 RAG 而非整篇 embedding。
  1. 答案 source attribution 比 factual accuracy 更难：FA 85.5% 而 SAP/SAR 仅 61%，意味着"答对但引用混乱"是 RAG 的常态。社区搜索若开放生成式答案，必须把"原帖卡片回链"作为强制约束，否则用户和监管都将对系统失去信任。
  1. 部署考量：BM25 在该 benchmark 上呈 Pareto 最优——单 CPU 索引 + 内存倒排，吞吐与成本远优于稠密 GPU 索引。社区搜索若资源紧张，应先把 BM25 baseline 工程化做扎实，再叠加稠密重排；而不是一上来就投入向量数据库改造。
  1. 该 benchmark 可被局部复用：即使不接入 EnterpriseDocBench 整套数据，其四轴评测设计、按长度分桶的幻觉报告格式、跨阶段相关性分析方法都可以直接迁移到自家语料——这是工程团队最容易立刻拿走的"礼物"。
