IsoMoE: Placement-Invariant Hybrid CPU-GPU MoE Inference with Lossless 12-bit Experts

混合部署把部分专家放到 CPU 上，好让单卡跑下超过显存的 MoE，但专家放在哪块设备、何时换入，现有引擎的贪心解码结果往往会跟着变，因为两端算术并不相同。解码又常被 CPU 内存带宽卡住：无损压缩能少搬数据，可熵编码在 CPU 上解得太慢，跟不上内存读取。把 GPU 专家 kernel 做成对 CPU 算术的按位重放，再用便于 AVX-512 点积的内存布局计算无损的 12 bit 专家，并配上不改变输出的双微批流水线，就能让放置只影响速度。在多个 MoE 模型上，不同专家放置下的输出按位一致，也与全部专家都在 CPU 上时相同，解码吞吐平均比最快基线高 1.26 倍，最高 1.54 倍。专家放在哪只应改变快慢，不应改变同一条指令的生成结果。

CTRL: Concurrent Training and Rollout for LLM Reinforcement Learning via GPU Co-Residency

HKUST (Guangzhou)

大模型强化学习后训练要同时跑两类负载：访存为主、批次还会随回复结束而缩小的 rollout，以及稠密的学习更新。现有系统要么让每张 GPU 轮流切换两个阶段，要么把卡按整卡切成两组。若让每张 GPU 在 CUDA MPS 下同时驻留一个学习进程和一个常驻 rollout 引擎，把优化器状态留在主机、权重按层流入有限的 GPU 窗口，并用发布门控在无丢弃的滞后约束内重叠更新与采样，就可以在全卡上同时推进。在 H100、A800 等平台的多组负载上，滞后上限为两步时，吞吐达到更强异步基线的 1.11 至 2.24 倍。把互补的采样和学习放在同一张卡上一起跑，就不必再为整卡切分或串行切换付代价。

Ruijia Yang, Ruikai Li, Zeyi Wen

03 4.10

Contexture: Runtime Context Eviction for High-Throughput Agent Serving

NNTU SingaporeA*STARMicrosoftSSuperMem

智能体服务会把不断变长的执行历史反复送回模型，共享的 KV cache 很快成为吞吐瓶颈。已有的上下文压缩看不到全局缓存状态，运行时的 KV 管理又用不上工具执行信息。沿 token 追溯到产生它的工具操作会发现，后面的操作常常已经替代了更早的输出和相关轮次，记录会话终态历史里有 64% 的 token 可视为删除候选。把完整会话历史和模型执行上下文分开，按这种替代关系选出可删片段，再结合共享 KV 压力和前缀是否仍驻留来决定何时真删。在多种模型、框架和基准组合下，满足 SLO 的吞吐比最强基线高 20% 到 73%。该删的是已被后续工具结果替代的历史，而不是到了长度再一刀切。

Weave: Routing-Adaptive Runtime Warp Scheduling for MoE Megakernels

SJTUNUSFudan UniversityAlibabaTTokMach

专家并行下，主流系统常把一层 MoE 融进常驻的大 kernel，但各卡的通信和计算量会随路由结果变化。先前方案要么在编译期写死通信和计算的资源划分，要么只在整块 SM 粒度上调整，把整块 SM 交给通信后 Tensor Core 就闲着。按每张卡的负载在 SM 和线程束粒度上分配资源，并在一层执行过程中切换线程束角色，开头和收尾把全部线程束都用上，再把输出散布交给已经空闲的通信线程束。启动时用融合代价模型根据路由统计同时选定这两套日程，就能对上这种动态负载。在 SM103 上，MoE 层比最强的 DeepGEMM-MegaMoE 基线几何平均快 1.30 倍，最高 1.97 倍。路由变了，卡内通信和计算的占用就该一起变，而不是沿用编译期的固定划分。

Ziyu Huang, Yangjie Zhou, Chenhao Zhu, Hongzhe Yan, Tianwei Qiao, Sicheng He, Zihan Liu, Peng Yu 等 19 人

Speculative Decoding Is Less Speculative Than You Think

CMU

投机解码要先起草候选再交给目标模型验证，效率取决于有限算力能否对上目标真正会走的路径。这条路径有两处不确定：目标模型的预测，以及采样本身的随机性。前者必须等目标模型前向，后者却可以在起草前就抽好并在验证时复用。把这些已知随机数和现有起草模型的预测合在一起选节点，树的构造和异步预取都会偏向当前这次采样真正会用到的续写。无需额外训练起草模型，也不改变目标采样分布，解码吞吐比强基线最高提升 24.6%，异步预取中最高提升 13.7%。采样随机性不必当成未知数，先把它固定下来，有限的起草预算才能花在这次会用到的候选上。

Guanning Zeng, Andrea Zanette

Isonomy: Isolating Every Request from Timing Side Channels at Nearly Full-Sharing Throughput in Multi-Instance LLM Prefill

Johns Hopkins University

长提示常常共享前缀，复用已缓存的 KV 能省掉预填充计算，但缓存命中会让首 token 更早到达，从而暴露别人用过同一前缀。服务商通常只在同一账号内共享缓存，可在最小权限下，即便同账号、只是获准发请求并付费，也不应看到该账号里其他请求的提示。默认按请求隔离，仍保留跨账号的同一块缓存，只把组外前缀的命中藏进这条请求自己的时序：按可见命中做路由，再按未命中时的孪生进度决定何时放出首 token。在饱和的会话负载上，预测模式仍保有无保护共享吞吐的 0.984，按账号隔离则是 0.945；在更多复用发生在账号之间时，按账号隔离会降到 0.802。隔离不必以放弃复用为代价，只要把不该被看见的命中从时序里藏掉。

Bowen Sun, Chaowei Xiao

AdaTree: Serving-Aware Adaptive Tree Construction for Speculative Decoding

已录用 NeurIPS 2026

树状投机解码能提高大模型生成吞吐，但在真实服务里，能使性能最高的树形配置会随请求率和各请求自身特点一起变。如果沿用固定树或链式起草，就会和服务条件错位。把一个可插拔组件接到服务系统里，预测不同树形配置下的模型执行时间和接受长度，再选出投机效率最高的那一种，就能跟着负载调整。为了刻画树形配置和执行时间之间的非线性关系，这一组件用决策树作为核心建模单元。评测显示，它在多样的服务条件下都优于链式投机解码，也优于静态树形方案。投机树不该在上线前就钉死，树形本身就应该跟着请求率和请求特点一起改。

Soohyun Cha, Jungi Lee, Jaewoong Sim

Contention-Aware Flexible Execution for Machine Learning Workloads

University of Central FloridaAMD

训练和推理里，计算和通信 kernel 经常并发，却要争用同一批计算单元、缓存和显存带宽，于是并发往往比单独跑更慢。在面向数据中心的 AMD Instinct MI300X 上刻画后会看到，变慢的程度随计算或访存瓶颈、以及 kernel 大小而不同。现有框架通常一有机会就尽早启动通信，这个选择并不总是最好的。利用数据流里哪些算子可以重叠、资源如何分配的灵活性，用简单启发式调整重叠锚点和资源配比，不必改写 kernel。在推理预填充和解码以及训练等多种场景下，端到端最高可加快 13%，训练中也可加快约 5%。通信不必见缝就插，选更耐挤的计算算子来隐藏它，往往更划算。

Marco Kurzynski, Shaizeen Aga, Di Wu

Intent-Aware Caching for Efficient LLM Serving

已录用 NeurIPS 2026

多轮对话的服务系统会缓存历史前缀的 KV，好在下一轮复用、少做预填充，但命中取决于对话会不会继续、以及下一轮何时到来。即便会继续，用户阅读、思考和撰写下一条的间隔也相差很大，而且后面一轮要命中，前面各轮拼成的前缀都得还在。真实日志里，不同意图的继续概率和轮间间隔并不一样。按意图给请求分类，从近期服务日志里学习轻量的复用统计，再用这些统计去做接近最优的淘汰，就能把这个信号用上。在 ShareChat 上，缓存命中率达到 34.6%，高于先前学习方法的 18.8%，也高于 LRU 的 12.2%。TTFT 最多比 LRU 降低 46.1%。前缀该不该留，要看这类意图通常会不会续上、以及隔多久才续，而不是只看最近用过没有。

Kazi Hasan Ibn Arif, JinYi Yoon, Dimitrios S. Nikolopoulos, Hans Vandierendonck, Deepu John, Bo Ji

Get Started with GPU-Accelerated DuckDB Analytics Using the Sirius Core Extension

NVIDIA

分析查询会随着数据变大而变慢，拖累探索、流水线和上层应用。NVIDIA 与 DuckLabs 把 GPU 原生的 SQL 引擎做成 DuckDB 的核心扩展：装好并加载后，受支持的分析查询可以在 NVIDIA GPU 上执行，不必改写 SQL，也不用改表结构。DuckDB 仍负责解析和优化，扩展执行生成的查询计划；遇到还不支持的特性会回退到 CPU 引擎，现有脚本和接口也不用换。用存放在 Amazon S3 上、规模最大到 10 TB 的 TPC-H 派生查询做冷启动对比，调优后的双 GPU 配置比测试中最好的 CPU 版 DuckDB 快 3.25 倍到 5.50 倍。查询期计算成本最高可降低约 79%。小规模时单卡成本更低，到最大规模则是调优后的双卡在时延和成本上都更好。熟悉的 SQL 工作流可以留在 DuckDB 里，把支持的查询计划交给 GPU 去跑。
