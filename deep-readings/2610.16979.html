WeGR: Unified Generative Retrieval for Industrial Search Systems in WeChat

对社区短文本搜索，优先借鉴 query–内容协同监督及从短前缀逐步扩展到完整 ID 的训练课程。奖励只更新已验证的前缀位置，并用多正例监督稳定训练；上线时同时观察 nDCG、CTR 与候选数，分清模型收益和缩减精排工作量带来的成本变化。

1. 问题与动机

WeGR 研究工业搜索的生成式召回，核心不是让通用 LLM 输出推荐说明，而是根据 query 和用户上下文直接生成物品的层级语义 ID。传统搜索通常依赖多路召回、粗排、精排，候选数和多阶段维护带来成本。生成召回有机会合并候选生成接口，但前提是 ID 既保留相关性和协同行为，又能用真实反馈稳定优化。正文把这两个问题分别落在 tokenizer 与策略训练上。

第一类困难是语义与协同信息的保真。RQ-Kmeans 可以控制聚类分配，但行为监督先进入连续向量，再经过量化可能损失；RQ-VAE 能联合学习，却容易把分配集中到少量码字。第二类困难来自 RL 的精确 ID 奖励：只有整串码与点击或订单目标完全一致才有奖励，有限 rollout 可能全部为零，组内优势也随之消失。扩大采样预算会增加成本，使用额外排序器又可能把旧候选分布的偏置带到生成器探索的长尾区域。

对社区 UGC 搜索，query–帖子协同监督、持续更新内容和有限服务预算都与本文相近。但电商订单是特定业务目标，不能直接代替社区内容相关性或满意度。最值得借鉴的是把语义码质量、反馈学习与下游候选开销分别验证。

2. 方法详解

CoCo-VAE 是三层残差量化 tokenizer。Q2I 与 I2I 对比学习将查询—物品和物品—物品协同信号引入编码器的连续表示，正文强调不直接在离散码空间强迫协同物品共用 ID，以避免语义不同的物品挤到相同码上。训练目标将重构、协同对比与保真抗塌缩正则组合，而不是只追求均匀码本。

第一层采用 Codebook Refresh：以指数滑动平均统计每个码字的使用次数，低于阈值就从活跃码字重新初始化，并叠加标准差 0.01 的高斯扰动。作者只对第一层这样做，因为深层频繁重置可能破坏残差分解。深层由 FAR 提供两类约束：样本侧选多个相近码字，以 softmax 权重加权，最小化重建残差与原残差的余弦距离；码字侧计算不同样本分配概率的内积，并惩罚平均碰撞概率。前者扩大可训练码字的梯度覆盖，后者抑制样本集中到少数热门码。

生成骨干采用 GPT-2 Small，理由是工业低延迟与计算效率。三个码本规模为 16384、128、128。重构权重为 1.0，Q2I 为 0.2，I2I 为 0.05，FAR 总权重 0.4；其内部残差保真和碰撞权重分别为 0.9 与 1.0。上述系数需要按照正文的嵌套损失使用，不能把内部与外部权重混淆为平铺的六项损失。

DHPO 将奖励视野和更新视野一起从短前缀扩大到整串码。第 n 步视野为 min(1+floor(n/300), L)，即每 300 步增加一个 token。当前 rollout 只要前 h 个码与同 session 中某个正例一致，就获得该正例对应的行为奖励；点击为 1，订单为 2，多正例共用前缀时取最高值。组大小为 8，组内奖励减均值、除标准差后形成优势，采用类似 GRPO 的逐 token 截断重要性比目标。

关键在于：短前缀命中不证明后续 token 正确，所以奖励只能更新前 h 个位置，不能给整条未验证后缀都发正向梯度。待 h 扩至 L，才恢复完整物品匹配。另加权重 0.5 的多正例 SFT，对同一 session 的全部正例 ID 做平均交叉熵，在组内奖励无差异时仍保留稳定监督。系统每天先 SFT 再 RL 更新。正文给出 31 天日志、前 30 天训练最后一天测试，但没有公开训练样本总数、完整 optimizer、batch size 或硬件配置，不能据此声称可直接复刻。

3. 核心技术贡献

一是将行为协同与量化稳定性同时处理。CoCo-VAE 的区别不是简单增加对比损失，而是连续空间承载协同、首层刷新处理死码、残差保真与碰撞正则负责后续分配。相比最强 SFT 对照 RQ-Kmeans，点击 HR@6 从 0.2641 提高至 0.2759，相对约 4.47%；订单 HR@6 从 0.4051 到 0.4103，说明不同目标受益程度并不相同。

二是课程式改变“奖励确认了多长前缀”和“哪些 token 可以被更新”，让两者严格对齐。这比仅给前缀奖励但更新全串更保守，也无需额外 reward model。对社区搜索可直接理解为：确认了主题层面的匹配，就先更新主题决策，不把这种证据误认为具体帖子已经正确。

三是多正例 SFT 与 RL 互补。对多个有效物品做监督既保留兴趣多样性，又在所有 rollout 同奖励时提供学习信号。表 3 显示 vanilla GRPO 反而损害召回，加入 MSFT 后恢复并超过 SFT，再加入动态视野继续改善。它提示工业 RL 应检查是否真正优于强监督基线，不能仅凭训练奖励上升判断成功。

4. 实验结果分析

离线数据取自 2026 年 6–7 月微信电商搜索日志，共 31 天，点击与订单测试集各 20000 条。评价包括 HR 与 MRR，截断位置为 6、50、200。SID 对照都在 SFT 下比较；RL 对照均由 CoCo-VAE 初始化，因此不能把 tokenizer 与策略两个表组当作完全不同训练起点的任意模型混排。

这些数值揭示了一个重要反例：在相同初始化下，直接 GRPO 不是“小幅无益”，而是点击、订单两侧都下降。MSFT 已挽回大部分损失，动态视野则在其上进一步提高点击 HR@6 约 0.0046、订单 HR@6 约 0.0057。DHPO 相对 SFT 的提升为点击 HR@6 约 1.85%、订单约 2.78%，不能把这部分与 tokenizer 的改善简单相加成通用收益。

Tokenizer 消融中，去掉 Q2I 后点击 HR@6 为 0.2650；去掉 I2I 为 0.2704；去掉残差保真为 0.2437；去掉抗塌缩正则为 0.2492。保真与分配正则的单独去除影响更大，说明行为监督不能替代可用的量化空间。正文没有在该表中单列首层刷新消融，不能宣称已经独立量化它的贡献。

线上表格明确实验日期为 6 月 22 日至 8 月 4 日，摘要概括为两个月，评审时应优先保留具体日期。V1.0 仅增加生成召回，订单、CTR、CVR 相对提高 1.579%、1.108%、0.520%；V1.1 删除其他召回路 60% 候选后，为 1.962%、0.884%、0.950%；V1.2 删除其他路 80% 后，为 2.539%、1.508%、1.381%。作者报告表中结果 p<0.05。这里删除比例针对其他召回路的候选，并不是整个搜索语料减少 80%。

V1.2 使进入粗排的候选减少 38.10%，CPU/GPU 用量降至基线的 74.5%/73.9%。资源减少幅度小于候选减少幅度，因为请求处理、召回等仍有固定开销。微信视频号搜索与微信搜一搜的平均服务延迟分别减少 21.7ms、15.4ms；论文没有给出同表中的绝对基线延迟，不能计算总延迟加速倍数。

细分流量也值得保留：中频 query 的订单与 CVR 变化为 -0.05%、-0.84%，CTR 为 +0.99%，前两者不显著，说明参与度改善并不必然转化为订单。低频 query 订单增益 +3.24%，中低频订单 +3.86%。独立直播搜索实验中订单和点击 HR@6 相对提高 7.07%、5.95%，这项隔离实验验证 DHPO 的迁移性，而不是完整 WeGR 已在所有业务等幅生效。

5. 局限与未来方向

正文没有独立 limitations 章节，不能编造作者自述。作者明确提醒，不同频率 query 的异质收益尚需进一步受控研究解释；直播搜索实验只隔离策略优化阶段，因此证据支持 DHPO 的迁移，而非整个 tokenizer 加服务体系的迁移。作者也讨论了辅助 ranker 对中长尾生成物品可能不可靠，这是放弃额外奖励模型的设计动机，并不构成对所有 ranker 的否定。

读者额外应关注：数据与日志属于私有工业场景，缺少公开可重算的完整训练设置及置信区间；线上候选替换和模型更新共同影响最终业务指标，无法从单表证明哪项模块贡献了全部资源收益。31 天离线切分和 6–8 月线上实验有时间交叠，需要更完整的 checkpoint 与数据时间说明才能独立审计信息泄漏。论文的持续 HR 上升是观察性曲线，不能单独证明数据积累造成了增长。

6. 工业实践意义

对社区 UGC 搜索，最可行的试验起点是固定现有检索器，先训练带 query–帖子与帖子–帖子协同监督的语义码，监控码字使用率、碰撞率、残差保真及长尾内容覆盖。社区内容生命周期短，tokenizer 更新如何影响帖子 ID、缓存和索引版本需要单独设计；论文没有提供可直接套用的全量迁移操作方案。

随后比较 SFT、GRPO、GRPO+多正例监督、动态前缀优化四组。在相同训练预算、候选数和时间切分下报告 nDCG、HR、MRR、CTR，并观察每组全零奖励比例及每层正确率。点击与订单的 1:2 权重不能直接搬到帖子场景，可用经过校准的点击、停留或满意度反馈构建业务奖励，先确认相关性没有被热度信号替代。

上线应从附加召回开始，再逐步减少旧候选，通过独立 A/B 衡量效果与成本。WeGR 的结果提示生成器价值可能体现在替代冗余候选而非无限增加候选；但缩减也可能损害罕见意图和新帖覆盖，因此必须按 query 频段、新老用户和内容年龄分层。服务成本核算应包含 tokenizer 更新、每日 RL、索引维护及粗排省下的计算，不能只引用 25% 左右在线节省而忽略新增离线训练成本。
