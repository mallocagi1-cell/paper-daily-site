Stratified Sparse Attention: Reducing the Sparse-to-Dense Gap at Extreme Sparsity

长上下文解码时，每生成一个 token 都要把整个 KV cache 从 HBM 读一遍，所以上下文越长，注意力越慢。稀疏注意力只读其中一小部分 token，但压到 50 倍稀疏时，现有方法和稠密注意力差得很远：Llama-3.1-8B 在 RULER-HARD 32K 上，稠密注意力得 88.76，PQCache 式的 top-k 只有 72.51。这篇论文提出分层稀疏注意力 SSA（Stratified Sparse Attention），思路是分数高的 token 一定保留，剩下的长尾按代理分数抽样，抽中的 token 再按“被抽中的概率”放大权重。同样 50 倍稀疏，Llama-3.1-8B 的分数回到 83.67；Qwen3.5-9B 做 AIME 2025，SSA 得 59.8，PQCache 只有 36.7。作者还写了专门的 CUDA kernel，1M 上下文时解码注意力比 FlashInfer 快 2.96 倍。

1. 问题：top-k 丢了长尾，均匀采样又浪费预算

预算是 k 个 token，现有方法分配它的方式有三种。第一种只做检索，Quest、PQCache 用代理分数挑分数最高的 k 个，Tactic 做的是 top-p。注意力集中在少数 token 上时这很好用；可一旦分布比较散，集合之外的注意力质量就全部丢了，代理分数再有一点偏差，真正重要的 token 会刚好落在边界外。第二种只做采样，MagicPig 用 LSH 近似抽样再做重要性校正，覆盖面广，但预算小时方差很大。第三种是混合，vAttention 保留 top-k，再从剩下的 token 里均匀抽样。它比前两种都好，可在激进稀疏下离稠密注意力还是有明显差距。

作者认为问题出在“均匀”。top-k 之外剩下的注意力质量分布很不均匀，均匀抽样会把同样多的预算花在几乎没贡献的 token 上。他们先做了一个小实验：同样的预算，按代理分数抽样的相对 L2​ 误差在各种预算比例和稀疏度下都低于均匀抽样（下图）。这就是 SSA 的出发点。

2. 方法：先分层，再抽样，最后按概率修正

先看采样式稀疏注意力的基本写法。记 si​=q⊤ki​/d​，wi​=exp(si​)。如果每个 token 以概率 πi​ 被选进集合 S，就给它乘上 1/πi​：
o=∑i∈S​wi​/πi​∑i∈S​(wi​/πi​)vi​​
直观地说，一个本来很难被抽中的 token 抽中了，它就要替一大片没被抽中的同类说话，所以权重要放大。SSA 在这个写法上分三步。

先决定哪些 token 一定保留。把代理分数 s~i​（实验里用 PQCache 的乘积量化分数）做 softmax 得到 qi​，再找一个 λ，让 ∑i​min{1,λqi​}=k。凡是 λqi​≥1 的 token 进入重集合 H，直接保留；剩下的预算 m=k−∣H∣ 留给其余 token（残余集合 R）去抽。这样重集合多大不用手调，由代理分布决定：分布越尖，重集合越大。

然后在残余集合里抽样。把 R 上的 qi​ 重新归一化成 pi​，有放回地抽 m 次，去重得到 S。一个残余 token 至少被抽中一次的概率是 πi​=1−(1−pi​)m，重集合里的 token 则是 πi​=1。

最后只对 H∪S 算精确的注意力分数 ℓi​，权重取 exp(ℓi​)/πi​，归一化后加权求和。重复抽中的 token 只算一次，所以实际读的 token 不会超过 k 个。

举个示意的例子（数字是假设的）。上下文 100 万 token，50 倍稀疏，预算 k=20,000。假设有 8,000 个 token 满足 λqi​≥1，它们直接保留；剩下 12,000 次抽样在大约 99 万个残余 token 里按 pi​ 进行。一个 pi​ 很小的 token 被抽中后，1/πi​ 很大，它代表的是一大片分数都低、但加起来仍有不少注意力质量的长尾。top-k 会把这片长尾整个扔掉，均匀抽样则把大部分次数花在几乎为零的 token 上。

已有的几类方法都是这个框架的特例：只有重集合，就是 top-k 或 top-p；重集合为空，就是纯采样；提议分布换成均匀分布，就是 vAttention 那种混合。

作者还证明了一个误差界，它说明预算该怎么分。记 AR​ 为残余集合里真实的注意力质量，ρ=maxi∈R​aˉi​/pi​ 表示提议分布和真实残余分布差多远（ρ≥1，两者一致时取等号）。定理 2 说，以至少 1−δ 的概率，输出误差 ∥o−o∥2​ 和 AR​ρ/m​ 同阶，去重只多一个常数因子。所以多留重 token 能降低 AR​，多留抽样预算能增大 m，两者要权衡；而代理分数一旦低估了某个重要的残余 token，ρ 就会变大，误差随之上升。

这个框架和用哪种近似检索无关。任何能给出代理分数的 top-k 方法（PQCache、Quest 等）都能直接拿来当 SSA 的提议分布，检索方法变好，SSA 也跟着变好。

3. 实现：让抽样不拖慢解码

长上下文解码受显存带宽限制，SSA 要省的是读 KV 的流量。为了跑得快，实际 kernel 没有用自适应的 λ，而是固定重集合占预算的比例 h，作者报告这样和理论版本的结果很接近。解码一步分四个阶段，前三个阶段要扫完整个上下文，但每个 token 只读几个字节。

第一阶段算代理分数。每个 key 存成 16 字节的 PQ 码（16 个子空间、256 个中心），而 head 维度 256 的 fp16 KV 对要 1 KiB，所以扫一遍 PQ 码比读 KV 便宜得多。sink 和局部 token 的掩码在同一个 kernel 里顺带处理，不用再扫一遍。

第二阶段用 radix top-k 选出重集合。返回的下标不排序，因为上面的估计量和顺序无关。

第三阶段在残余里抽样。直接在百万个 token 上建分布、抽样太慢，所以作者分层抽：每次先选一个 1024 token 的 chunk，再在里面选一个 32 token 的子块，最后在这不到 32 个 token 里选一个。重复的样本用每行一个哈希表去掉。πi​ 最小截断到 10−4，防止个别权重大到失控，代价是带进一点偏差。随机数用基于计数器的 RNG，这样能兼容 CUDA graph。

第四阶段从分页 KV cache 里取出选中的 K、V，用 online softmax 算注意力。为了多用并行度，每个 query head 拆给多个 thread block，最后用 log-sum-exp 合并。拆多少份有讲究：1M 上下文、batch 1 时，拆 64 份比 32 份快 1.58–1.71 倍，但拆到 128、256 份反而变慢，因为启动和合并的开销超过了并行带来的收益。

4. 实验：激进稀疏时优势最大，代理分数质量仍是瓶颈

对照组有三个：PQCache、vAttention（用 PQ 分数），以及 Oracle-top-k。Oracle-top-k 先算精确分数再挑 top-k，本身没法加速，只当作“确定性检索最多能做到多好”的参考。所有方法都留 128 个 sink token 和 128 个局部 token。模型有 Llama-3.1-8B、Qwen3.5-4B/9B、Ministral-3-3B/8B，LongBench 上另加 Qwen3.5-27B。

先看 RULER-HARD，50 倍稀疏。PQCache、vAttention（PQ）和 SSA 用的是同一份 PQ 分数和同样的预算，区别只在预算怎么分，所以下表的差距可以直接归到分配方式上。

SSA 在每一行都超过 PQCache 和 vAttention（PQ）。在 Ministral-3-8B 上，它在 32K 和 128K 分别保住了稠密注意力 94% 和 85% 的分数。但也要看到，128K 的两行和 Ministral-3-8B 的 32K 那行，Oracle-top-k 仍然比 SSA 高，说明代理分数本身不够准，这是 SSA 绕不开的上限。Qwen3.5 系列上所有稀疏方法都和稠密相差不到 2 分，SSA 没什么可赢的。

AIME 2025 要生成 32K token 的长推理，这里稀疏度越高，SSA 的优势越明显。Qwen3.5-9B 稠密得 66.3；50 倍稀疏时，SSA 得 59.8，而 Oracle-top-k 只有 48.3，PQCache 36.7。到 100 倍稀疏，SSA 还有 51.5，vAttention（PQ）已经掉到 3.5。反过来，只有 5 倍稀疏时 vAttention（PQ）更好，65.4 对 61.0，所以 SSA 的收益集中在激进稀疏的区间。

重集合比例 h 的消融说明两部分都不能少。h 在 0.2 到 0.8 之间，得分都在 61.0–64.0；全部预算拿去抽样（$h=0$）只有 40.2–42.5，全部给 top-k（$h=1$）是 49.4–53.8。

LOFT 和 LongBench 上看不出差别。LOFT 上 SSA 的注意力误差在所有设置下都是非 oracle 方法里最低的，但任务指标 subspan-EM 在各方法之间最多差 0.04；LongBench（Qwen3.5-27B）上所有稀疏方法都在稠密 1 分以内。也就是说，误差变小不一定变成任务分数的提升，要看任务本身对稀疏有多敏感。

速度在单张 H200 上测（16 个 query head、4 个 KV head、head 维度 256、fp16 KV）。上下文短时 SSA 反而慢，因为前三个阶段的固定开销摊不开：batch 1、128K 时，它只有 FlashInfer 速度的 0.60–0.74 倍。上下文越长越划算，到 1M 时，50 倍稀疏快 1.79 倍，20 倍快 1.39 倍，10 倍只快 1.07 倍。batch 变大收益更高，1M、batch 16、50 倍稀疏时到 2.96 倍。

kernel 优化是 batch 1 也能比稠密快的原因。不做第 3 节那些优化的参考实现，同样的算法只有 FlashInfer 的 0.37–0.47 倍，到 batch 8 才追上；优化后快了 2.95–3.80 倍。其中分层抽样比只按 chunk 抽快 1.21–3.16 倍，1M 上下文、$h=0.4$ 时抽样本身只花 0.30–1.18 ms。

5. 局限与实践意义

局限有几条。实际 kernel 用的是固定比例 h，自适应分配还没有同样高效的实现。πi​ 截断会带来少量偏差。抽样有随机性，同一个请求解码两次，注意力输出不完全一样，需要可复现时要固定随机种子。128K 以下、batch 1 时 SSA 比 FlashInfer 慢。在 Qwen3.5、LongBench 这种稀疏本来就不怎么掉点的设置下，SSA 也没有明显优势。作者打算下一步让 SSA 可验证，即用户设定近似质量，系统给出保证。

对工业界，SSA 适合的场景很明确：百万级上下文、batch 较大，而且要压到 20–50 倍以上稀疏的解码服务，比如长时程智能体的会话历史、超长文档问答、长推理链生成。如果系统里已经有 PQCache、Quest 这类 top-k 检索，接 SSA 的改动不大：检索索引原样复用，只是把一部分预算从 top-k 挪给按代理分数的抽样，再加上 1/πi​ 修正。上线前先在自己的任务上扫一遍 h，论文里 0.2–0.8 都不错，纯 top-k 和纯抽样都明显更差。如果你只需要 5–10 倍稀疏，现有的 top-k 或 vAttention 大概已经够用，SSA 的收益主要在更激进的区间。
