Efficient Listwise Reranking with Compressed Document Representations

4.30
Relevance 5 | Novelty 4 | Practical 4 | Evidence 3 | Timely 5

Summary: 针对 LLM listwise 排序计算开销过大的问题，本文提出 RRK，将每篇文档先通过 RAG 中常用的文档压缩技术编码成多 token 的固定长度 embedding，再用蒸馏方式训练 listwise reranker。8B 参数的 RRK 相比 0.6B-4B 的小型 reranker 仍可提速 3-18 倍且质量持平甚至更优；在长文档基准上优势进一步放大。

Key insight: 把“压缩 + 蒸馏 + listwise”三件套组合是 LLM 重排在 UGC 短/长文本搜索中落地的关键路径：用紧凑表示替代 token 拼接可大幅压缩输入长度，蒸馏让大模型质量迁移到推理友好的形态。社区搜索的 reranker 完全可以参考这种“先压再排”的两阶段方案，把现有 cross-encoder 替换为基于压缩 embedding 的 LLM listwise 排序，兼顾 nDCG 与延迟。

1. 问题与动机

LLM-based listwise reranker 在搜索系统中已成为提升 nDCG 的重要手段，但代价是巨大的计算开销：典型部署需要把 query 与 k 篇候选文档的全文拼接成一条长序列输入 LLM，每条 query 的注意力复杂度高达 O((|q|+k|d|)²)。常见缓解方式是用更小的 LLM (0.6B–4B) 或限制 k，但这些都让相关性指标退化。论文给出的 baseline 数字也很直白：纯文本 8B reranker (Qwen2.5-8B) 在 BeIR 上虽能拿到 nDCG@10 = 59.7，但延迟相对 RRK 慢 20 倍 (1.26s vs 0.06s/query)。作者借鉴了 RAG 中"压缩文档表示"的最新进展（PISCO 这类 multi-token compressor），把"先把文档压成固定数量的 memory token，再让 LLM 看 memory token 而非全文"的思路迁移到 listwise reranker 上。论文的核心问题是：能否同时拿到大模型的相关性和小模型的速度？

2. 方法详解

RRK 的整体架构由两个 LoRA 微调组件构成：(1) 一个文档压缩器 (基于 PISCO 初始化)，把每篇文档压成 l = 8 个 memory token (h=3584 维)，对 128-token 文档相当于 16x 压缩，对 2048-token 长文档可达 256x；(2) 一个解码式 listwise reranker (Qwen-2.5 8B-instruct + LoRA)。输入序列结构为 X = (q ; c₁ ; [SEP] ; c₂ ; [SEP] ; … ; cₖ ; [SEP] ; q)，即 query 在两端各重复一次，中间是各文档的压缩 token，[SEP] 分隔。Ranking score 来自 query 的隐藏态与每个文档对应隐藏态的余弦相似度。

训练目标是 RankNet 风格的 listwise loss，温度 τ=1/8：ℒ(q,Dₖ) = ∑_{(i,j)∈𝒫} log(1 + exp((sᵢ - sⱼ)/τ))，监督信号来自一个更大的 teacher (Qwen-32B 打分)。最关键的设计是"压缩器与 reranker 联合训练"——不冻结压缩器，让 ranking loss 反传回 PISCO，使 memory token 学到对排序最有用的语义。这相比"冻结 PISCO 压缩 + 仅训 reranker"在 BeIR 上 nDCG@10 从 55.5 → 58.4，提升非常显著。

训练设置：MS MARCO 0.5M queries × 16 docs (top-50 retriever 结果) + BGE-M3 score 标注的 0.15M queries，合计 0.65M。单 A100 训练 2 epochs (48h)，batch 2，gradient accumulation 16，learning rate 1e-4。推理 batch 128，A100 GPU 利用率 90%+。整套方案不需要新硬件，标准 LoRA 工具链可复用。

3. 核心技术贡献

(1) 联合训练的多 token 压缩器：相对前作 PE-Rank (用 1 个 token/doc 的极端压缩) 和 E2RANK (固定特征)，RRK 用 8 token/doc 保留更多语义同时压缩明显，并且让 ranking loss 端到端调整 memory token 内容。BeIR nDCG@10：PE-Rank 51.3 → RRK 58.4 (+7.1)，且延迟 RRK 比 PE-Rank 还快 7x。

(2) 解码式架构 + 余弦相似度打分：相比 cross-encoder 风格的 logits 输出，RRK 把 ranking score 表示为 query 与文档隐藏态的余弦，配合 RankNet 的 pairwise log loss，使得长 list (k=16) 也能稳定训练。该选择带来的好处在 listwise vs pointwise 对照中可见：相同骨干 RRK pointwise 0.21s/query，listwise 0.06s/query，延迟差 3.5x，nDCG@10 也从 57.5 → 58.4。

(3) 压缩-存储解耦的 pipeline：所有压缩在离线索引阶段完成，服务时只读 8 token/doc。MS MARCO 8.8M 文档 fp16 存储约 230 GB，与 ColBERT 索引 (286GB) 量级相当——对工业搜索来说意味着把 LLM reranker 引入并不要求额外的内存级技术。

(4) 长文档优势放大：在 TREC DL20 (2048-token 文档) 上 RRK nDCG@10 = 68.6，比 Jina-v3 (62.6) 高 6 个点，比 Qwen3-4B (70.0) 仅低 1.4 点，但延迟 RRK 比 Qwen3-4B 快 37x。这说明压缩越激进，RRK 的相对优势越大。

4. 实验结果分析

主对比表 (BeIR 12 数据集 nDCG@10 / 延迟比)：

  • RRK (8B): 58.4 / 1x (0.06 s/q)
  • Qwen2.5-8B 纯文本: 59.7 / 20x (1.26 s/q) — 上限
  • Qwen3 4B: 58.4 / 10x — 同分但慢 10x
  • Jina-v3 (0.6B): 57.6 / 6x
  • ModernBERT-Large: 57.2 / 2x
  • E2RANK (8B + BGE): 57.2 / 10.4x — 同源但慢 10x
  • PE-Rank (7B): 51.3 / 7x — 单 token 压缩明显劣化

ablation 关键发现：(a) 数据集组合 MS+BGE (0.65M) 比单独 MS (58.4 vs 57.7)、单独 E2RANK (55.6) 都好，说明多 teacher 的 pairwise 标签互补；(b) 压缩器从 frozen PISCO 改为 joint fine-tune，nDCG@10 从 55.5 → 58.4 是最大单项收益，强调"专门给排序训的压缩"和"通用 RAG 压缩"差距巨大；(c) 训 2 epochs 后再训没有 gain。

失败案例：在 BRIGHT 这种 query 本身很长 (接近文档长度) 的基准上，RRK 优势消失——因为减负主要来自"压短文档"，query 长就抵消了收益。作者还坦承 1-4B 的小骨干尝试都没成功，意味着"压缩 + listwise + decoder"组合对模型容量有下界。

5. 局限与未来方向

作者明确列出三点：(1) Query length sensitivity——只有 query 远短于文档时压缩才有意义，BRIGHT-style 查询无法受益；(2) 还没找到比 8B 更小的稳定骨干，进一步压缩成本/索引体积受阻；(3) 230GB 索引存储对小公司不友好，需要后续 quantization 或 product quantization。论文未提及但值得警惕的隐含限制：联合训练让压缩器与 ranker 强耦合，索引一旦升级 ranker 就要重压全库；teacher 是 Qwen-32B，跨语种、跨领域的迁移性还没验证。

6. 工业实践意义

对社区/UGC 短文本搜索 (本场景核心) 的直接启示：
(a) 直接可借鉴的两阶段方案：把目前线上的 cross-encoder reranker 替换为"PISCO-style 离线压缩 + 8B LLM listwise"。UGC 场景下文档(帖子/评论)平均长度通常在 100–500 tokens，与 RRK 实验的最佳工作区间高度吻合，预期可以拿到接近 8B 纯文本 reranker 的相关性、同时延迟落到 60ms/query 量级。
(b) 存储成本可控：UGC 索引数量级在千万到百亿，按 8 token × fp16 估算，10 亿条目约 26 TB，需要量化到 int8 (~13TB) 或 int4 (~6.5TB) 才能落地。论文已提示 quantization 是后续方向。
(c) 联合训练的工程代价：每次升级 reranker 都要重压全库，索引刷新成本高。建议在工程上准备双版本索引切换机制 + 增量重压队列。
(d) A/B 实验设计：先在长尾 query (UGC 长帖子搜索) 子集试点，因为 RRK 在长文档上 advantage 最显著 (DL20 +6 nDCG)；同时排除 query 极长的用例 (如 prompt-style 搜索)。
(e) 不要做的事：不要简单复用通用 RAG 的 PISCO 压缩 (frozen 模式) 期望同等效果——ablation 已证明 frozen 比 joint-train 差 3 个 nDCG 点，必须为搜索任务专门联合训练。
