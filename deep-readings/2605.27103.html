MuChator: Enabling Active Music Discovery via Conversational Music LLMs in Douyin Music

Jiahao Liang, Linzhi Huang, Xuannan Liu, Xukai Wang, Xuanpu Luo, Yongchun Zhu, Jingwu Chen, Feng Zhang, Xiao Yang · ByteDance · arXiv 2605.27103 · 发表 2026-05-27

对社区搜索而言这是一份难得的'LLM 即检索器'落地范本：核心做法不是用 LLM 改写 query 后接传统召回，而是直接把 LLM 训成会唱'用户偏好 × 内容理解 × 召回'三角的整合体。把音乐换成 UGC 帖子，同样的范式可以处理'有没有人讨论过 XXX 这种边角问题'这类模糊意图；其 query-音乐协同推理思路提示我们在 UGC 域要专门构造 query-帖子配对偏好数据，光靠开源对话数据 SFT 出的通用 LLM 很难直接落地搜索场景。

1. 问题与动机

抖音音乐日活上亿，但 90%+ 的播放发生在被动后台收听场景，主动发现窗口极短，用户在 App 启动早期若没有快速找到合适歌曲就会流失。Feed 流式被动推荐难以满足"下雨天通勤想听的歌"、"适合入睡的"这类模糊场景化意图——传统搜索只能处理"指定歌名/歌手"这种明确 query。但直接套通用 LLM（GPT-5.2、Gemini-3）做音乐对话发现存在三个具体失效：(1) 音乐域知识缺失：通用 LLM 不掌握平台 item 标识，Factuality 仅 49.0%–55.3%，会大量"幻觉"出平台没有的歌；(2) query-音乐协同推理弱：超出语义匹配的能力（如"早 8 打卡的怀旧粤语")需要联合推理，零 shot 大模型 Relevance 67.1%–78.7%；(3) 个性化理解浅：通用 LLM 不会读用户历史行为做偏好对齐，Personalization 仅 5.3–6.6/10。MuChator 的目标是把这三块能力压进同一个 LLM 里。

2. 方法详解

骨干模型选 Qwen3-8B，训练分四个阶段：

阶段 A — 课程式音乐预训练（共 24.1B tokens）。 分三批喂入：(1) 客观知识 3.7B token，含歌名/歌手/歌词/流派 metadata、外网百科文章、LLM 生成的歌词解读；(2) 主观知识 4.6B token，含用户/专业评论、大规模歌单共现、协同过滤关系图、知识图谱关系；(3) 个性化偏好 16B token，user profile + 行为序列。消融证明课程顺序优于混合（"Stages 1+2+3" 在 U2I personalization PPL 上比"Mixed"低，3.64 vs 4.15）。

阶段 B — Next-Behavior Prediction. 传统 next-item prediction 只在序列最后一个 token 算 loss，监督稀疏。MuChator 把用户上下文重排成 τₜ = (s₁,i₁,f₁,…,sₜ,iₜ,fₜ)，让 LLM 同时自回归预测 iₜ₊₁ 和 fₜ₊₁，相当于在序列每一步都有监督信号，密度提升一个量级。

阶段 C — UQ2I SFT. 数据合成三步：(1) Semantic Clustering 用 LLM 给每首歌生成多样化自然语言 query + 接入线上真实 query，聚成 40K 个 query cluster；(2) Candidate Retrieval：对用户每首喜爱歌曲随机抽 query → 取该 query 所在 cluster → 召回 cluster 内全部歌曲；(3) Personalization-Guided Filtering：用 fine-tune 的个性化 reward model 取 top-10 作为 list-wise label。Loss 是标准 SFT 的 maximum-likelihood。

阶段 D — GRPO 偏好对齐，最大创新点在 Hybrid Reward：相关性 reward 用 LLM judge 二值化（0/1 硬门控，强约束意图对齐），个性化 reward 用线上多目标排序模型连续打分；再叠加规则 reward（格式合法、平台 catalog 存在、避免歌手/后缀重复、不重复用户近期已播）。整体 Rhyb = Rrel · λpers·Rpers + Σλrule·Rrule，Rrel 这个乘子保证'不相关直接归零'，避免 reward hacking。GRPO 的 group size G=8，β KL 系数控制偏离 ref policy 程度。SFT 与 RL 数据严格隔离。

训练规模：512 旗舰 GPU，batch SFT=256 / RL=1024，token packing 7168，lr 2e-5 (SFT) / 1e-5 (RL)，预训练 1 epoch、SFT 2 epoch、RL 1 epoch。

3. 核心技术贡献

(a) 课程式音乐预训练：把"客观-主观-个性化"三种知识分阶段灌入，比混合训练在 U2I PPL 上低 12.3%，且不显著伤害通用能力（General Knowledge 77.1 → 74.3，仅 -3.6%）。
(b) Next-Behavior Prediction：通过把 state-item-feedback 序列化交错自回归，让模型在用户行为序列每一步都拿到监督；消融上完整加入 state+item+feedback 比只用 item 的 PPL 降低 24.3%（4.81 → 3.64）。
(c) UQ2I 合成 pipeline：40K query cluster 解决"用户日常 query 与歌曲库语义错配"问题；个性化 RM 过滤让 SFT label 同时具备相关性与偏好对齐。
(d) Hybrid Reward + 二值相关性硬门控：消融对照（Table 7）显示去掉相关性 reward 后 Relevance 从 89.1% 暴跌到 43.0%，证明二值硬门控对抑制 RL 过度优化偏好导致的'走偏歌'至关重要。

4. 实验结果分析

线上 A/B（一个月）。 相比内部传统检索+排序基线：MuChator Active Day +46.49%、Duration +77.36%、CTR +11.26%；同样底座纯 SFT 的 Qwen3-8B 在线反而 Active Day -5.81%、Duration -9.21%、CTR -2.42%——纯 SFT 上线会负向，必须走 RL+Hybrid Reward 才有正向收益，这是一个非常关键的工程信号。

离线对比（Table 3）。 Personalization 8.4（最强 baseline Qwen3-8B RAG 7.1，+18.3%）；Relevance 89.1%（最强通用大模型 Gemini-3-Pro 79.1%，+10pp 绝对）；Diversity 51.1%（vs RAG 42.2%，+8.9pp）；Factuality 99.3%（vs RAG 97.4%）。通用大模型即使加 few-shot 在 Factuality 上只能到 55%–57%，凸显"是否上 catalog 的歌"对生产可用性的卡口作用。

Ablation 全套。 预训练独占 Relevance 巨大提升（37.1% → 78.1%，+110.5%）；加 SFT 提到 87.8%；RL 再到 89.1%，但 Diversity 从 63.1% 反而回落到 51.1%——这是个性化对多样性的明显挤压，需要业务侧权衡。Reward 消融上"去掉 personalization reward"会让 Personalization 从 8.4 掉到 6.8，"去掉 rule reward"让 Factuality 从 99.3% 跌到 97.2%——每一路 reward 都是必要的。

有趣的二阶效应：MuChator 上线后，用户的"复杂 query"占比 +12.3%——产品端的能力释放反过来教育用户表达更复杂意图，这是 LLM-as-recommender 的正反馈循环证据。

5. 局限与未来方向

论文没有 dedicated Limitations 章节，但从结果可读出：(a) Diversity-Personalization 拉扯：RL 后 Diversity 51.1% < SFT 63.1%，强偏好对齐压缩探索空间，需要 reward 设计补偿；(b) 算力门槛：512 GPU + 24.1B token 预训练，中小团队难以复现；(c) 通用能力略损：full curriculum 后 General Knowledge 77.1 → 69.2（-7.9pp），如果同一 LLM 还要承担多场景，需要权衡；(d) 二值硬门控的鲁棒性：相关性 LLM judge 本身有偏，二值化进一步放大偏差风险，作者未深入讨论。未来工作可能在多目标 RL（同时拉 Diversity 和 Personalization）以及更小底座（替换 8B 到 3B/1.5B）的可行性上展开。

6. 工业实践意义

对社区搜索/UGC 短文本搜索，可直接借鉴的工程结论：

(1) "LLM 即整合体"范式可行，但纯 SFT 上线必负。 工程上必须配 RL + Hybrid Reward 才能跑赢传统检索基线，单走 SFT 路径会负向（Active Day -5.81%）。直接复制开源 SFT recipe 上线是个陷阱。

(2) "事实硬门控"是 LLM 生产化关键。 平台 catalog factuality 99.3% vs 通用大模型 49%–55% 的对比说明，要把 LLM 用在搜索召回环节，必须把"是否上目录"显式建到 reward 里，否则等同于灾难。同样可移植到 UGC 帖子检索：要把"帖子是否真实存在且未被删/未被屏蔽"作为 reward。

(3) 课程式预训练 + UQ2I 合成 pipeline 可平移。 把音乐换成 UGC 内容：阶段 1 灌"客观帖子知识"（标题/标签/正文/作者）、阶段 2 灌"主观信号"（评论、互动、收藏图谱）、阶段 3 灌"用户行为序列"。UQ2I 的 query 聚类思路应对短文本社区搜索 query 极度多样化的场景特别合适：先把线上 query 与 LLM 生成 query 联合聚类，再用个性化 RM 过滤 SFT 标签。

(4) 延迟可控。 8B 模型 TTFT 0.09s，端到端 1.87s 输出 140 token——这是生产搜索可接受的延迟边界（典型搜索整体预算 200ms-2s）。意味着 8B-级 LLM-as-retriever 在 toC 场景具备工程可行性，不需要等更小模型。

(5) 离线/线上口径要严格区分。 Qwen3-8B SFT 离线 personalization 6.8 看起来不差但线上负向，说明个性化离线 metric 与线上行为存在 gap，必须做 Hybrid Reward + RL 才能弥合。社区搜索做 LLM4Search 时，离线评估必须紧贴线上 reward 信号，否则会做出"看起来好但上线掉点"的 model。
