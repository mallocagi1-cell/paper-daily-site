Cache Engineering for Agents

Tianyu Fu, Ruoxi Wang, Zihan Min, Zhongqi Ren, Zhihao Li, Tengxuan Liu, Shengxu Mu, Hanling Zhang, Yu Wang · arXiv 2610.28577 · 发表 2026-10-20

智能体跑上几百轮之后，最贵的部分已经不是生成，而是反复读历史 KV cache：论文统计，KV cache 读取占总 API 成本的 82.4%。常见做法是上下文工程，即裁剪或摘要旧消息，但改动前缀会让后面所有缓存失效，必须重新 prefill。清华大学团队提出缓存工程（cache engineering）：文本轨迹不动，直接从活跃 KV cache 里丢掉选定的条目，保留的部分原样复用。配套的服务系统 AKV 在三个模型、四个智能体基准上，用一个简单的“工具返回滚动丢弃”策略，相比常规的阈值触发摘要，平均分高 1.7 分、平均成本低 27.7%，输出吞吐提高到 1.18 倍，P95 请求延迟加速 1.51 倍。

1. 问题：重新 prefill 成本与准确率的两难

智能体轨迹越长，KV cache 带来两个问题。成本上，保留并反复读取累积的缓存，存储和 I/O 开销很大。准确率上，参与注意力的 KV 数量或位置范围一旦超过模型能可靠处理的范围，效果会明显下降。

上下文工程通过裁剪或摘要历史消息来缩小缓存，但改动越早，需要重新 prefill 的后缀就越长。所以常见的 harness 会等到活跃上下文达到某个阈值，再一次性裁剪或摘要大部分轨迹，只保留最近几轮，好让重算的部分短一些。这样一刀切容易丢掉中间轮次的有用信息。作者在 GPT-OSS-120B 上用 BrowseComp-Plus（BCP）前 100 题测试（每题 4 次，最多 100 轮）：只保留最近 12 轮工具返回的裁剪式上下文工程，成本是全上下文基线的 1.85 倍；48K 阈值的摘要式方法成本降了约 7%，准确率却掉了 5 个百分点。直接丢弃旧工具返回的缓存，则能同时提升准确率、降低成本。

2. 方法：三个缓存操作

缓存工程区分两个长度：轨迹的逻辑 token 长度，以及实际参与后续注意力的活跃缓存长度。上下文工程改的是逻辑序列，缓存工程只改活跃缓存。论文定义了三个操作：

  • append：标准的缓存更新，处理新 token 并追加它的 KV 条目，位置编码下标加一。
  • drop(P)：把下标集合 P 里的 KV 条目排除在后续注意力之外，保留条目的状态、位置编码和逻辑序列都不变。drop 不会改变后续 append 用的位置下标。
  • repos：按逻辑顺序把保留的 r 个条目的位置重新编为 0,…,r−1，下一个 token 从 r 开始。对 RoPE，把键从位置 p 挪到 q 只需 K←R(q)R(p)−1K，value 不变，不用重算。

为什么需要 repos：drop 不重置位置下标，缓存虽小，下标却仍随逻辑轨迹增长，最终会撞上模型的位置上限。

保留哪些缓存，作者参考了注意力分布：旧 token 获得的注意力少于新 token，相近相对位置上，工具返回获得的注意力少于助手消息。因此主策略是工具返回滚动丢弃：保留所有推理内容和最近 K 个工具返回（实验里 $K=12$），更早的工具返回缓存逐步丢弃。

3. 核心挑战：缓存状态依赖历史

标准 KV caching 里，token 前缀唯一决定缓存状态，所以前缀匹配就能复用。缓存工程打破了这一点：同样的 token 序列，经过不同的操作序列，会得到不同的缓存状态。

举个例子：三条轨迹都保留 B 和 C，但 ① 里 C 是在能看到 A 的情况下算出来的，② 里 C 看不到 A，③ 里 B 本身就没有前缀。所以 C 的 KV 三者各不相同。论文因此用缓存操作序列 o1:m​ 来精确描述状态：对固定模型，从空缓存开始，这个序列唯一决定当前缓存。服务系统必须同时跟踪 token 历史和操作历史，才能正确复用。

4. AKV 服务系统

AKV 的设计原则是“无状态接口、有状态服务”。接口沿用标准 chat API：messages 字段照常给出完整的逻辑序列（每条消息隐含一个 append），新增一个可选的 cache 字段，用“在第几条消息之后执行”的语法写 drop 和 reposition。客户端不需要知道服务端还驻留着哪些 KV，每轮像平时一样追加消息和操作即可。

内部的缓存管理要保住三条性质：只在状态等价时复用；回收不用的缓存但不破坏请求隔离；被驱逐的状态能在一次 prefill 里恢复。对应三个机制：

  • 扩展基数树（复用）：请求执行 drop 时，在路径上的触发点插入 drop 节点，记录被丢弃的下标。前缀匹配同时比对 token 和操作，①② 共享 A–B 前缀，但因为丢 A 的时机不同而各有一份 C。repos 则通过复制缓存、旋转键生成新的位置版本，在树上形成新分支并记录 reposition 节点；位置下标相同直接复用，不同则做键旋转。
  • 感知 drop 的驱逐：只有当没有任何进行中的计算或恢复需要某个条目时，它才可驱逐。例如 ①② 都丢掉 A 之后，A 的缓存就能在请求结束前释放。驱逐时优先回收被丢弃的缓存，再回收已完成请求的缓存，因为后者下一轮更可能被复用。各个位置版本独立驱逐。
  • 分段批注意力（恢复）：普通的因果 prefill 复现不了经过 drop 和 repos 的状态，逐步重放又要多次前向。AKV 在每层把 query 按 drop 和 repos 的触发点切段，每段因果地关注自己的 token 和之前各段仍活跃的缓存；被丢弃的缓存对之前用过它的段依然可见。只有注意力分段，FFN 仍然整批计算一次，避免为每段重复读取 FFN 权重。需要不同位置的段，会临时旋转键、复制值生成临时 KV 版本。

5. 实验

基线是两种摘要式上下文工程：Standard 用较高的模型专属阈值（GPT-OSS-120B 和 MiniMax-M2.7 为 96K，MiroThinker-1.7-Mini 为 192K）；Text Engineering 用同样的摘要策略，阈值统一降到 48K。AKV 用保留最近 12 个工具返回的滚动丢弃策略，repos 阈值与 Standard 的摘要阈值相同。基准包括 BCP、xbench-DeepSearch-2510、GAIA 的 103 题纯文本验证集和 SWE-bench Verified。成本按活跃输入和生成 token 计价；为了保守，repos 涉及的每个 token 也按缓存命中价计费，有意高估键旋转的成本。

MiniMax-M2.752.4 / 5.052.8 / 5.753.7 / 4.4

AKV 在三个模型上平均分都是最高，相比 Standard 和 Text Engineering 分别高 1.3–2.1 和 0.9–8.7 个百分点；平均成本比 Standard 低 27.7%，比 Text Engineering 低 21.9%。不过并非每格都赢：MiniMax-M2.7 上 BCP 是 Text Engineering 更高（62.3 对 58.9），SWE-Verified 是 Standard 更高（75.2 对 74.4）。

准确率提升来自哪里：GPT-OSS-120B 的 BCP 前 100 题上，逻辑长度 48K 以下三者相当；48–96K 区间 Text Engineering 最低，96K 以上 Standard 最低，正好对应它们各自的摘要阈值。这与“一刀切丢信息”的解释一致，而滚动丢弃是逐步移除旧工具返回。

服务效率（8 张 A800-80GB，4 张 prefill、4 张 decode，TP=4，SWE-Verified Top-80）：各自吞吐峰值处，AKV（并发 14）相比 Standard（并发 12）平均延迟加速 1.36 倍、P95 延迟加速 1.51 倍，输入吞吐 1.53 倍、输出吞吐 1.18 倍。并发升到 14、16 时，Standard 因 KV 压力导致重 prefill 增多，P95 延迟在并发 16 时达到 229.90 秒，AKV 为 30.63 秒。延迟分解显示，decode 加速主要来自全注意力时间的减少：活跃上下文变短，每步读取的 KV 和注意力计算都少了。

消融与策略探索（GPT-OSS-120B，各基准前 100 题）：只丢工具返回、不用 repos 时，BCP 55.0；加上 repos 升到 62.0，因为能继续探索、不会撞上位置上限而中止。开启 repos 后，丢推理缓存（单独或与工具返回一起丢）在两个基准上都不如只丢工具返回，SWE 上分别是 36.5 和 34.5，只丢工具返回是 41.0。递归自我改进（RSI）用 MiniMax-M2.7 在 20 道 BCP 题上迭代策略，在 100 道留出题上评估，第 3、6 轮得到的策略在保持 Standard 准确率的同时，每题成本分别比 Standard 低 15.6% 和 17.8%。把缓存管理作为工具交给智能体自己决定时，BCP 子集上 GPT-OSS-120B 和 MiniMax-M2.7 分别达到 61.0% 和 64.0%，成本前者从 13.4 降到 12.1 美分，后者从 5.4 升到 5.9 美分，因为执行了更多轮。

6. 局限与工业实践意义

作者列出的局限是：缓存工程策略还需进一步探索，尚未在这套机制下训练智能体，线性注意力模型的服务支持也还没做。此外有几点值得注意：实验的主策略是手工设计的固定规则（保留最近 12 个工具返回），不同任务的最佳 K 可能不同；被丢弃 token 的影响仍残留在之后算出的 KV 里，这一点论文作为优点提出，但也意味着结果依赖操作顺序，调试和复现时要记录完整的操作序列；实验在 A800 上以 BF16 运行，没有覆盖原生 MXFP4。

对做智能体平台和推理服务的团队，这篇论文的价值在于把“压缩上下文”从文本层挪到了缓存层。如果你的智能体有大量工具返回（检索结果、网页、代码执行输出），而且现在靠阈值摘要控制长度，可以先在自己的轨迹上统计注意力在工具返回和推理内容之间的分布，再试滚动丢弃旧工具返回加 repos，这是论文里最稳的组合。落地的前提是推理服务能区分操作历史：如果服务端只做 token 前缀匹配，同一前缀下不同的 drop 时机会被错误复用。AKV 基于 SGLang 实现、代码已开源，接口兼容标准 chat API，接入时客户端只需额外传一个 cache 字段。
