ATTUNE: Agentic Throughput Tuning for LLM Training

同一个模型换一种 GPU、换一个框架版本，原来调好的训练配方（recipe）就不一定还是最快的。Amazon 这篇论文的 ATTUNE 把“调配方”交给一个编码智能体做：从一份能跑通的配方出发，在用户设定的 GPU 小时预算内无人值守地搜索，每次只改一个杠杆。真正决定能不能用的，是智能体之外的一道正确性闸门：任何会改变训练目标的参数都会在启动前被拒绝。结果是，Amazon 线上的后训练 SFT 配方在 H100、H200、B200 上平均提速 1.7 倍，最高 3.9 倍；在 NVIDIA 自己的四个 AutoModel 基准配方上，比 NVIDIA 公布的吞吐高 6%–17%；在开发阶段没见过的 MiniMax-M2 上，吞吐提升 2.6 倍。

1. 问题：固定旋钮调不到的吞吐，以及“能跑”不等于“没改坏”

一份训练配方包括模型怎么在 GPU 间切分（TP、PP、EP、CP、DP）、用多少重计算换显存、用哪些 kernel、通信怎么重叠。现有自动调优工具有两类：并行规划器、厂商的 autoconfigurator 用代价模型或扫参，在预先固定的空间里找；贝叶斯优化这类黑盒搜索不需要系统模型，但要大量昂贵的试跑；最近的 LLM 智能体调优器（如 OptiCo）会读剖析结果，但同样只能改一个固定的旋钮列表。

作者的两个观察决定了设计。第一，配方没吃到的吞吐，一部分来自必须一起改才见效的杠杆，一部分来自固定列表根本没列的杠杆，比如 virtual pipeline stage、换一种 expert dispatcher。第二，有些配置会悄悄改变训练内容，而任务照常跑完：MoE 的 expert capacity factor 是常见的吞吐参数，但它会丢掉溢出专家容量的 token；--grad-reduce-in-bf16 看着像通信参数，实际上还关掉了 FP32 梯度累加。只检查“能不能跑起来”的调优器，可能会把这两种配置都当成优化发布出去。

2. 方法：一个智能体做搜索，确定性代码做裁判

测量。 一次调优叫一个 campaign：一个模型、一个集群、固定 GPU 数。候选配方之间，模型、数据、序列长度、全局 batch、精度和 GPU 数都不变，每次运行按同样顺序读同样的数据行。每次运行跑固定步数，前几步吸收启动和编译开销、不计分，剩下的窗口 W 按聚合吞吐打分：

先求和再相除，避免短步的权重过大。baseline 至少在不同节点分配上跑 5 次，取均值做分母，噪声带取 max(3%,3σ)；候选必须超过当前最优一个噪声带以上，才能取代它。

搜索纪律。 智能体用普通工具工作：文件检索与阅读（包括训练镜像里的框架源码）、shell 和集群 API。skill 规定了 6 条规则：启动前先写假设（要缩小哪个瓶颈、机制、预期收益）；每个候选只改一个杠杆，或一组耦合的并行度；用某个参数之前，先在运行镜像里读它的实现，看它断言了什么、悄悄覆盖了哪些别的参数，并把代码位置记进账本；一个杠杆至少测过两个取值或到达可行上限才能排除，五种并行度都试过才能说拓扑已经调完；尝试新布局时先去掉原来的省显存手段，OOM 了再加回来重测；布局稳定后，把在旧布局上赢过的参数再测一遍。

诊断。 智能体主要看步时、各 stage 显存和窗口内步时方差。瓶颈不清楚时做一次剖析：每个 pipeline stage 追踪一个 rank，一个确定性的 trace 分析器把每步拆成计算、通信、host 端和空闲时间。

控制面与预算。 启动候选时，运行生成器复制 baseline 作业，只改待测参数和白名单里的环境变量。记账脚本从调度器准入到释放全程计 GPU 小时，失败的运行和正确性检查也算在内，预算不够就不放行。控制面还拒绝原样重跑失败过的配方，迫使智能体先诊断再改。

正确性闸门。 闸门有两步。启动前做配置检查：比较候选和 baseline 的解析后参数与环境（按最终值比，因为一个参数可能悄悄改掉别的），在一个调优器改不了的注册表里把每处改动分成三类。“已知无效”指改变了训练内容（数据、batch、优化器或其调度、损失项、路由、精度格式）或会触发已知的栈缺陷，直接拒绝；“已知有效”指只改了计算方式（放置、packing，或通过组件测试的同数学替换，比如融合 kernel 和 FP32 参考在相同输入上对齐），直接放行；其余为“未知”，交给损失检查，并列入报告供人复核。运行后做损失检查：第 0 步的损失要在 baseline 的 5% 以内，且所有记录的损失都是有限值。第 0 步是同一组权重作用在同一个首 batch 上、尚未更新，合法改动只会因浮点计算顺序带来极小差异，而权重加载或切分出错会让损失成倍变化。

无人值守。 harness 基于 Claude Code 的持久目标功能：stop hook 在预算没花完、也没有带证据地记录停止之前，不让智能体结束回合；pre-tool hook 把向用户提问改成“取默认值并记录假设”，并拦截未识别的破坏性 shell 命令。只追加的账本是唯一事实来源，新会话可以从账本重建 campaign。campaign 结束后，智能体写总结和经验，经人工审核后进入 skill。

3. 核心贡献

论文的主要贡献是职责划分：开放的动作空间交给智能体，裁决权留给确定性代码。智能体可以改框架暴露的任何参数，只要闸门没有把它标成改变目标；哪些测量算数、谁是当前最优、最后发布哪个配方，全部由智能体改不了的脚本决定。作者还发布了 OpenRecipes 排行榜：60 多份配方、覆盖 20 多个模型，统一用 8,192 token 的 SFT 行、全局 batch 128、BF16 测量，每条都给出 tokens/s/GPU、每百万 token 成本，并通过了 Megatron-Bridge 的收敛检查。

4. 实验

对比最强的公开配方。 实验分两组。复现组是 NVIDIA 的四个 AutoModel 基准配方，在 NVIDIA 容器、原定的 H100 上原样运行，其中三个和公布值的差距在 2% 以内；移植组是开发阶段没见过的四个模型，在 slime 和 Megatron-LM 上用真实文本训练。

收益大小取决于原配方和当前环境差多远。MiniMax-M2 的配方原本是为 128 卡强化学习写的，优化器状态放在 CPU 内存里；三个 campaign 都关掉了 CPU offload，并加深了 pipeline。GLM-4.5 的配方是为 H100 写的，在 B200 上被诊断为受通信和 kernel 启动限制，于是把 expert all-to-all 收进单节点内，最快的一次还把 TP 降到 1。Llama-3.1-70B 去掉了 context parallelism，换成 FlashAttention-3，计算占步时的比例达到 98.5%。Mixtral 和 405B 的配方本来就是厂商针对同款硬件调过的基准，可挖的空间很少，Mixtral 的最佳候选没有超出噪声带，所以保留原配方。

同预算对比其他调优器。 每个调优器都拿到 30 倍于一次 baseline 运行的 GPU 小时，共用同一道闸门和发布规则，每个模型各跑 3 个 campaign。GLM-4.5 上，ATTUNE 平均提升 +33.9%，用了 669 GPU 小时、6.4 小时；OptiCo 是 0.0%（1,407 GPU 小时），随机搜索 +7.8%（1,688），BO +1.8%，BO 加显存预过滤 +3.9%。MiniMax-M2 上，ATTUNE +164.2%，最好的对手 BO 加预过滤是 +55.5%。值得注意的是，ATTUNE 在 GLM-4.5 上找到的最快布局（去掉 virtual stage 后）其实就在 OptiCo 的 11 个旋钮范围内，和 ATTUNE 的结果只差 2%，但 OptiCo 没搜到：它只在较浅的 pipeline 上试过 TP=1，而且 EP 仍然跨节点。黑盒搜索的空间里有全部制胜杠杆，但没有诊断引导，大多数尝试要么 OOM，要么因为比当前最优慢被剪掉。

消融。 在 GLM-4.7-Flash 和 Nemotron-3-Nano 上（8×H200，每组 5 个 campaign）：去掉 skill 后，平均提升分别从 +88.0% 降到 +66.9%、从 +49.4% 降到 +42.9%，失败启动的比例升到 50%；限定只能改 OptiCo 的旋钮后，GLM-4.7-Flash 只有 +18.1%，因为它最大的收益来自关掉 CPU 优化器 offload，而这一项不在列表里；去掉日志和剖析后，提升略低，但差异不显著（p=0.24 和 0.14）。

闸门本身。 在已知答案的运行上，460 次合法运行全部放行，所有配置类故障都在启动前被拒绝。6 种代码故障里，改变前向的 2 种让第 0 步损失上升超过 150%，被抓住了；只通过参数更新生效的故障（比如跳过某个梯度桶的规约）在第 0 步看不出来，loss mask 错位一个 token 只让损失变化 2.0%，和最大的合法差异相当，这些都漏过去了。实际 campaign 里，配置检查拦下了 19 次 Nemotron-3-Nano 的不均匀 pipeline 切分，其中一次恰好是最快的运行，它把别的层的权重加载进了 Mamba 层，第 0 步损失高出 215%–768%。

5. 局限

作者列出的局限有三点。闸门只看配置和第 0 步，只通过优化器更新起作用的错误发现不了，所以上线前仍要跑一次完整训练做验证；杠杆目录来自过往 campaign，GLM-4.5 和开发模型 GLM-5.2 同属一个家族，部分收益可能来自先验，但不用目录时 GLM-4.5 的结果和完整版处在同一噪声带内；ATTUNE 只调框架和镜像暴露的配置，不改 kernel 和代码，也不覆盖 RL 的 rollout 阶段。另外，经验条目需要整理：作者回查发现，目录里约五分之一的条目是错的，有的只在测得它的那个工作负载上成立。

6. 工业实践意义

对训练平台团队，这篇论文最值得借鉴的是闸门和记账，而不是智能体本身。不管调优由人做还是由智能体做，都可以先建一个“解析后参数差异 + 不可编辑的有效/无效注册表 + 第 0 步损失比对”的检查，把 capacity factor、bf16 梯度规约这类会悄悄改变目标的参数挡在启动前；预算按调度准入到释放全程计算，失败的运行也算。如果你的配方是从别的硬件、别的任务（比如 RL）移植过来的，自动调优的回报最大；如果用的是厂商针对同款硬件调好的基准配方，预期收益要小得多，论文里这类配方的提升在 0%–26% 之间。经验库要定期按原始记录回查，只保留模型本身不知道、或者会纠正模型错误直觉的条目。
