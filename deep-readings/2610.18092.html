原文：https://arxiv.org/html/2610.18092 。本解读基于已取得的完整 HTML 正文、第 3–4 节和附录 C–E；实验是论文记录的 2026 年 8 月快照，不是今天对商业模型的重新测试。

1. 问题与动机

论文关注深度研究智能体交付的报告能否真正帮助用户做事。BrowseComp 一类短答案题便于核对，但正确命中一个实体不能证明报告覆盖了用户的所有约束。已有长报告评测又较多围绕学术主题或合成任务，真实生活和工作需求的覆盖不足。用户可能需要比较工具、核对政策、整理公司信息，也会指定截止日期、来源级别、单位和计算口径。这些条件决定报告是否可用，不能由语言流畅度代替。

作者因此把真实查询种子转为可逐项核验的研究任务，并给每个任务编写细粒度标准。203 个任务含 102 个中文和 101 个英文，专家投入超过 4,500 小时，形成 4,014 条标准。约四成标准包含明确数值、事件或命名文档，使模型必须交付具体事实。统一评测后最佳系统仍仅满足约 63.4% 的加权要求，说明高能力模型在真实研究交付上仍有明显缺口。论文不是新的检索模型，也不报告 nDCG 或 CTR；它提出的是衡量多轮搜索与证据综合质量的方法。

2. 方法详解

构建流程从众包人员写下的需求开始，依次做意图和质量过滤、领域分类、任务改写及人工筛选。过滤会剔除与搜索无关、上下文不清或默认依赖未说明近期事件的请求，但一般时间敏感任务仍可保留。任务改写移除生成本地文件等操作性要求，同时保留研究意图、时间范围和资料来源限制。这样评测结果主要反映研究交付，不被本地文件操作能力混淆。

专家随后把种子拆成通常两到四个互补子任务，类型包括查找、计算、比较和推理。能力设计通常选取搜索规划、信息综合、冲突解决和不确定性处理中的两项，并合并冗余子任务。最终再改写成自然的完整用户请求。这一步让任务保持生活化，同时把难点从泛泛的“写一篇介绍”变成有明确边界的证据工作。

每条标准记录 criterion、type、necessity、priority 和 weight。type 区分客观和主观要求，necessity 区分显式与合理隐式要求。priority 的 Must Have/Nice to Have 标签交给评审模型参考，但数值汇总直接使用专家指定的 weight；权重在 0 到 1 之间，以 0.1 为步长。不要把优先级标签机械转成固定权重。标准尽量自包含、互不冗余，明确实体、日期、单位、容差和目标事实，使评审不必再联网。

评审对每条要求输出 Pass 或 Fail。对同一任务，把通过要求的权重之和除以全部要求的权重之和，再对任务分数取等权平均。这样一条标准较多的任务不会因条数更多而支配整个基准。实现时应保留逐项结果和判定原因，以便人工追踪低分究竟来自事实错误还是遗漏。

执行层使用共享 ReAct 风格循环，每轮模型决策可以产生多个工具调用或最终报告。工具包括网页搜索、网页读取和代码执行，搜索后端为 Serper，读取为 Jina Reader。模型使用默认配置，若可配置推理强度则设为最高；每个任务独立运行三次，汇报运行级均值和样本标准差。论文没有训练新模型，所以优化器、训练批次、GPU 和训练步数不适用，不应补造这些参数。

评审器在 402 条人工标注结果上比较 11 种配置，每种重复三次。最终选择 Gemini 3.1 Pro、低推理强度、温度零，单次判定而非多数投票。这个选择是经过校准得到的局部结果，迁移到中文 UGC 场景时仍应重新抽样核验。

3. 核心技术贡献

第一项贡献是把真实信息需求和精确验收标准连接起来。任务来自真实查询种子，经过专家补全而不是随意生成。七个领域包括公司与竞品、专业文献、金融市场、政策数据、产业动态、技术工具和日常事实，避免只在学术检索上衡量能力。

第二项贡献是可定位的加权标准。平均每个任务约 19.8 条要求，既检查覆盖也检查事实、证据和推理。标准中的时间边界和数值容差让“主题大致讲到了”和“用户要求确实完成了”可以被区分。与单个短答案匹配相比，模型必须展示多项交付证据，但论文没有在相同任务上提供对旧基准的提升数字，不能宣称评分技术改善了某个百分比。

第三项贡献是分开验证评审器与智能体。先对 402 条人工标签挑选评分模型，再对 30 个任务的 210 份报告做匿名人工排序，考察最终排名是否符合整体质量判断。对应 Spearman 相关为 0.89、Kendall 为 0.81，前四名次序一致。这支持基准的排序用途，同时不意味着每一条自动判定都正确。

第四项贡献是把资源与交付质量一起记录。工具循环次数、全程输出 Token 和最终答案字符数分别统计，可以看出长报告、长轨迹和高质量之间的区别。这个设计适合工程团队避免只优化表面上的字数或调用规模。

最佳系统仍有 36.6% 的标准权重没有满足，且 203 个任务中的 41 个三次平均得分低于 50%，占 20.2%。因此总体第一并不意味着可靠完成每一种任务。GPT-5.6 Sol 和 Claude Opus 5 在七个领域都排前两位，但没有系统在任一领域超过 70%。日常事实领域只有九个任务，该领域的差异应谨慎解释。

资源方面，Claude Opus 5 和 GLM-5.3 分别输出约 48.9K 和 49.3K Token，得分却相差约 6.9 个百分点。Hy4 Preview 用 33.6K Token 达到与 GLM-5.3 相近的总体分。迭代次数和分数的 Spearman 相关为 0.76，最终报告长度和分数相关为 0.60，但模型之间的比较没有隔离“增加搜索次数”的因果作用。不能由这些相关系数推出追加若干调用必然增分。

这是一篇评测论文，没有训练模块删除式消融；可分析的是评审配置实验。Gemini 3.1 Pro 低推理、温度零的标签平均准确率为 84.25%，自一致率 98.8%，多数投票准确率 84.33%。同系列高推理默认温度准确率 84.00%，自一致率 94.5%。提高推理强度没有自动改善这个评分任务。Gemini 3.5 Flash 不推理时自一致率达到 99.0%，准确率却仅 75.62%，说明稳定重复错误仍然是错误。所有配置的多数投票增益不超过 0.42 个百分点，因此论文选择单次评分。

失败分析有三类。第一类是过早追问：自主运行没有用户回复，智能体一旦以问题结束就无法交付报告。第二类是时间范围违规：搜索到的事实可能在执行时正确，却超过用户要求的历史截止日。第三类是细节遗漏：长篇叙述仍可能缺少指定实体、单位、日期、来源或特殊条件。附录的 Dify 案例中，报告正确列举 Workflow 的 User Input 和 Trigger 起点，但没有说两者互斥，对应要求因此失败。这个例子说明关键词出现不足以证明条件完整。

5. 局限与未来方向

正文未单列限制章节，不应把通用猜测冒充作者承认的限制。作者明确提示迭代统计还包含其他工具动作，跨模型相关不能隔离额外搜索的因果效果；日常事实只有九个任务，领域比较主要是描述性的。附录 C 说明所有系统在 2026 年 8 月相隔数日内测试，因此这些数字是当时模型与网页环境的快照。

此外，人工报告排序验证仅覆盖 30 个任务、七个系统，不能视为全部 12 个系统和全部领域的逐项人工验证。评审器最佳标签准确率为 84.25%，仍有误判空间。研究者需要保留抽检和申诉复核，而不应将分差很小的系统判为绝对优劣。

本解读额外提出的工程边界是：203 个任务较适合离线比较，但不能替代大流量社区 UGC 搜索评测；用户帖子中的噪声、权限和检索结果分布与公开网页不同。未来可构建按时间冻结的社区证据集，并对搜索预算、评分模型和标准权重做控制实验。这里的建议是迁移推论，不是论文已经验证的结论。

6. 工业实践意义

社区搜索的核心线上指标是 nDCG 和 CTR，LifeSearch 的加权要求分不能与这两项直接互换。可将它作为复杂问答和深度搜索模式的补充验收：挑选需要跨帖比较、找多项证据、核对时间的真实问题，写下用户真正需要的条件，再分别评估召回证据、答案覆盖和事实正确性。普通关键词搜索仍应沿用排序指标。

落地时先保存用户请求、时间截止、原始证据、工具轨迹、最终报告与逐项评分，确保结果可回放。对历史问题，应将来源更新时间和所述事件日期分开检查，禁止用截止日之后的事实填补缺口。对无交互任务，应要求智能体在缺少非必要信息时说明假设并继续交付；关键事实缺失时要表达不确定性，而不是编造数字。

可复用专家标准的生成流程，但不能让待测智能体自己决定哪些条件算成功。先用人工样本挑选评审配置，再定期抽查争议要求，尤其是数值、单位、来源权限和时间边界。预算方面可先用单次评审而非固定三次多数投票，后者在本论文的收益很小；是否在社区语料同样成立，需要实际测量。

执行成本必须独立观察。论文最佳模型平均 86.2 次迭代、51.5K 全程输出 Token，显然不是普通搜索请求的默认时延预算。适合先把复杂查询路由到深度模式，对其他查询保留快速检索，并测量每个成功交付任务的延迟与成本。论文没有线上 A/B、服务延迟、显存或 GPU 配置报告，不能填入这些缺失数字。最终试点应同时看相关性、点击率、复杂任务完成率和用户可核验程度，再决定是否扩大流量。
