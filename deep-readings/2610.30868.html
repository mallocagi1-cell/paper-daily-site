uGDS: A User-Space Development Kit for High-Performance GPU Direct Storage

Jing Wei, Guanyi Chen, Qi Chen, Chuyu Zhang, Zheng Zhou, Chutian Wang, Jian Zhang · arXiv 2610.30868 · 发表 2026-10-22

在 LMCache 里用 NVIDIA GPU Direct Storage（GDS）从 SSD 读回 KV cache，单个异步 stream 只能跑出 2.36 GiB/s，不到它同步读带宽的一半（40.8%）；剖析显示，99.6% 的时间耗在提交调用上。来自中山大学、港科大（广州）等单位的这篇论文开源了 uGDS，一个用户态的 GPU Direct Storage 库。NVMe 命令的整个生命周期都在用户态由 CPU 完成，内核模块只负责一次性的特权初始化，数据仍然走 SSD 到 GPU 的 PCIe 点对点 DMA。在 A100 + 三星 990 PRO 上，uGDS 的批量读带宽最高是 GDS 的 12.12 倍，批量写最高 30.69 倍；单 stream 能跑满设备带宽（5.49 GiB/s）；接进 LMCache 后，首 token 延迟（TTFT）中位数最多降 62.7%，服务吞吐提升 2.63 倍。

1. 问题：数据不绕道了，控制还在绕

GDS 解决了数据路径的问题：SSD 通过 PCIe P2P DMA 直接读写 GPU 显存，不再经过主机内存中转。但它的控制路径每次 I/O 仍然要进内核：每个 cuFile 调用都要经过 VFS、文件系统、块层和内核 NVMe 驱动，nvidia-fs 模块还要拦截每个请求的 DMA 映射，把每个 4 KiB 的 shadow page 翻译成缓存好的 GPU 总线地址。大块传输能摊薄这笔固定开销；但 KV cache 卸载、向量索引查询里常见的小请求、延迟敏感请求，这笔开销就成了主要成本。

作者归纳了另外两个缺口。一是顺序语义过强：cuFile 的 stream-ordered API 继承了 CUDA stream 的 FIFO 语义，每个请求都排在前一个之后；但 LMCache 恢复一段前缀时，各个 chunk 之间并不需要顺序，只要 attention kernel 等它们全部完成就行。应用只能把 I/O 分散到很多 stream 上，相当于自己替库做调度。二是不透明：nvidia-fs 内核模块是开源的，但实现批量提交、工作线程、stream 集成的 libcufile 只发布二进制，出了卡顿既查不了，也改不了调度策略。早期的用户态原型（如 libnvm/ssd-gpu-dma）证明了这条路可行，但只支持 NVIDIA，队列原语假设单一提交者，也不跟踪在途命令，缓冲区可能在 SSD 还在往里写的时候就被释放。

2. 方法：CPU 编排、SSD 传输、GPU 计算

三条路径分离。 初始化时，应用通过字符设备（open、mmap、ioctl）和 ugds_drv.ko 交互：接管 NVMe PCI 设备，把 BAR0 控制器寄存器和队列内存映射进进程空间，跨厂商 pin 住 GPU 显存，可选地建立 MSI-X 中断桥。稳态 I/O 时，内核模块完全不参与：libugds.so 在用户态填 64 字节的 NVMe 提交项（SQE），构造 PRP 页列表，直接写映射好的 doorbell 寄存器，再轮询完成队列（CQE）。数据只在 SSD 和 GPU 显存之间流动。代价是 SSD 要从内核 NVMe 驱动上解绑，应用面对的是块设备偏移而不是 POSIX 文件。作者认为这和 LMCache、Mooncake 这类自己管理 chunk 池的存储引擎是匹配的；需要文件语义时，可以在上面再叠用户态文件系统。

请求翻译。 设逻辑块大小为 B，请求必须满足 offsetmodB=0、sizemodB=0，命令参数为 LBA=offset/B、NLB=size/B−1。一个大小为 C 的连续块需要 P=⌈C/S⌉ 个页描述符（S 是控制器页大小）：1 页用 PRP1，2 页用 PRP1+PRP2，更多页时 PRP2 指向一个主机端的页列表。同步路径为每个队列对（QP）预映射一个 PRP 列表页，超出的请求按 MDTS 切块，控制器没有声明 MDTS 时保守地按 128 KiB 切。写 doorbell 之前用内存屏障，保证 PRP 和 SQE 对 PCIe 可见。

跨厂商显存注册。 uGDSBufRegister() 把 CUDA 或 HIP 的虚拟指针翻译成一组厂商无关的、控制器可见的页地址，记在进程级的缓冲区注册表里；NVIDIA 侧通过 peer-memory API 按 64 KiB 粒度取物理页表。注册后的缓冲区还能导出为 DMA-buf，供 RDMA 网卡使用。

队列分区。 QP 静态分成两个域：一个通用池服务同步和 stream-ordered 请求，一个专用的深队列只跑批量 I/O，这样突发的批量提交不会拉高同步请求的排队延迟。通用池内用原子计数器轮询选 QP，请求从提交到收齐 CQE 一直持有该 QP 的锁，所以环形队列的下标和 doorbell 不需要额外的原子操作。批量路径把多条命令合并成一次 doorbell 写，摊薄 MMIO 开销。stream-ordered 请求通过 cudaLaunchHostFunc 挂一个主机回调，回调里调用和同步读写同一个用户态引擎。

DMA 安全的生命周期。 这是用户态驱动最容易出事故的地方。每次 I/O 前先原子地给设备句柄和目标缓冲区加在途引用；还有在途传输时释放句柄或缓冲区会直接返回 -EBUSY。每次注册附带单调递增的 generation token，防止新分配的缓冲区复用了刚释放区域的虚拟地址，被过期请求误解绑。命令超时时，句柄被标记为 wedged，后续提交全部拒绝，相关 QP 和显存被隔离；必须等外部控制器复位（比如 PCIe Secondary Bus Reset）停住 DMA 引擎之后，才允许强制回收。

完成方式可选。 默认是忙轮询；也可以走 MSI-X 中断，内核中断处理只发 eventfd 通知，收 CQE 仍在用户态完成。

3. 核心贡献

uGDS 的价值不在“绕过内核”这个想法本身，用户态 NVMe（如 SPDK）早就有了。它的贡献是把这个想法做成了一个和 cuFile 接口语义对齐、可以替换上线的 GPU 存储库：同步、批量、stream-ordered 三种 API 都有；CUDA 和 HIP 共用一套地址抽象；在途引用、generation token、fail-stop 隔离把 DMA 安全补齐；整套从内核模块到用户态引擎全部开源，性能异常可以逐条命令追踪。最实用的一点是单 stream 就能跑满带宽，应用不必再为了带宽把 I/O 拆到十几个 stream 上。

4. 实验

测试环境是 2×Xeon 8368Q、A100-SXM4-40GB、三星 990 PRO 1TB（PCIe Gen4×4，关闭 IOMMU），对比 GDS 1.9 / libcufile 2.12。

初始化。 uGDS 的初始化中位数是 42.00 ms，GDS 是 114.56 ms，快 63.3%。GDS 的 111.83 ms 几乎都花在 cuFileDriverOpen 上（打开 nvidia-fs 会话、加载配置、探测 PCIe 拓扑）；uGDS 的时间主要花在注册句柄、配置控制器和队列上。对频繁拉起、回收 worker 的弹性服务，这一点有意义。

同步小 I/O。 收益最大的点是 2 线程、4 KiB 写：带宽从 161 MiB/s 升到 1003 MiB/s（6.23 倍），平均延迟从 48.36 μs 降到 7.69 μs（降 84.1%）；4 KiB 读从 111 MiB/s 升到 543 MiB/s。线程数增加、请求变大以后，瓶颈转到 SSD 和 PCIe，差距收窄：16 线程、64 KiB 时，写 6264 对 4542 MiB/s（1.38 倍），读 4616 对 3855 MiB/s（1.20 倍）。AMD 平台上对比 hipFile，64 线程 4 KiB 写从 2176 MiB/s 提到 2596 MiB/s（1.19 倍）。

批量 I/O。 36 种参数组合下 uGDS 全部胜出，读带宽是 GDS 的 2.12–12.12 倍，写是 2.33–30.69 倍。

作者追查了一个反常现象：128 KiB 请求下，GDS 的写吞吐随 batch 增大反而从 2373 MiB/s 掉到 502 MiB/s。原因在第一个 batch：batch 为 128 时，GDS 首个 batch 读要 90.84 ms、写要 117.65 ms，占整个 64 MiB 传输时间的 87.7% 和 92.2%。nvidia-fs 不在注册时建立 P2P 映射，而是在第一次 I/O 时调用 nvidia_p2p_dma_map_pages()；作者推测 cuFile 还懒分配了按首次提交规模确定的批量状态。uGDS 在初始化阶段把这些都做完，首个 batch 和后续 batch 几乎一样（读 2.46 对 2.45 ms）。去掉首 batch 只看稳态，4 KiB、batch 128 时 uGDS 仍是 GDS 的 8.8 倍（读）和 23.8 倍（写）。

stream 与流水线。 每次异步读后都同步的串行循环里，uGDS 在 4 KiB 和 1 MiB 下分别是 GDS 的 4.10 倍和 4.58 倍。16 组“1 MiB 写 + 同样的 GPU 计算”在全流水调度下，uGDS 用 3.03 ms，GDS 用 15.35 ms。

轮询还是中断。 4 KiB 请求时，轮询把延迟从 21.0 μs 降到 8.97 μs，代价是占满一个 CPU 核；1 MiB 请求时，MSI-X 中断把发起线程的 CPU 占用从 100% 降到 4.15%，延迟只多 5.5%（245.3 对 232.6 μs）。

LMCache 端到端。 用 Qwen3-0.6B、vLLM 0.20.1，关闭 vLLM 的内存前缀缓存，强制所有 KV 命中都从 SSD 读：

5. 局限

uGDS 要把整块 SSD 从内核驱动上解绑，放弃文件系统、POSIX 锁和页缓存一致性，这块盘就不能再给其他进程当普通盘用。目前一个句柄只驱动一块本地 SSD，多盘条带化和 NVMe-oF 还在路线图上。同步请求按轮询分配 QP，且一直占用到完成，大请求会拖慢落在同一 QP 上的小请求，作者计划加一个感知负载的调度器。实验只用了一块消费级 990 PRO、一张 A100，并关闭了 IOMMU；端到端只测了 Qwen3-0.6B 这种小模型，数据中心级 SSD、多 GPU 共享 PCIe 交换机时的表现还有待验证。

6. 工业实践意义

如果你在做 KV cache 分层（HBM→DRAM→SSD）或 GPU 向量检索，并且 SSD 是专用的本地盘，uGDS 值得作为 GDS 的替代测试，尤其是小块、高频、单 stream 的读取，这正是 GDS 最吃亏的场景。上线前要确认三件事：SSD 能否独占并解绑内核驱动；上层是否已经自己管理块分配（像 LMCache、Mooncake 那样）；IOMMU 策略是否允许 P2P。部署时可以按负载选完成方式：延迟敏感的推理节点用忙轮询，吞吐型或 CPU 紧张的管线用 MSI-X。即使不换库，论文对 GDS 首 batch 懒初始化和单 stream 提交阻塞的分析也可以直接用：先预热每个“缓冲区—设备”对，再把关键读取拆到多个 stream 上。
