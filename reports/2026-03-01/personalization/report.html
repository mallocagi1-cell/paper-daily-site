Meta GEM 深度解读：广告推荐基础大模型

1. 问题与动机

Meta 的广告推荐系统面临三大核心挑战：

数据稀疏性与异构性：Meta 每天处理数十亿次用户-广告交互，但这些交互本质上是极度稀疏的——每个用户只与极少量广告发生转化行为。同时，输入数据跨越文本、图片、视频等多种模态，以及 Facebook Feed、Instagram Reels 等多个平台（surface），信号来源高度异构。

模型碎片化问题：传统做法是为每个广告场景（如 Feed 排序、Reels 推荐、Story 广告等）训练独立的 Vertical Model（VM）。这些模型各自为战，无法共享跨场景的用户行为知识。例如，用户在 Instagram 视频上的兴趣偏好无法帮助提升 Facebook Feed 广告的预测精度。

Scaling 瓶颈：传统推荐模型的架构设计限制了其从更多数据和算力中获益的能力。与 LLM 领域已验证的 scaling law 不同，推荐模型此前缺乏清晰的"加数据+加算力→持续提升效果"的路线图。

为什么重要？ 广告是 Meta 的核心商业引擎。即使 1% 的转化率提升，在 Meta 的规模下也意味着数十亿美元级别的营收增长。更关键的是，GEM 试图回答一个行业级命题：推荐系统是否也能像 LLM 一样，通过 Foundation Model 范式实现 scaling law？

2. 方法概述

GEM（Generative Ads Recommendation Model）的核心思路是：将 LLM 的 Foundation Model 训练范式迁移到广告推荐领域，构建一个统一的"中央大脑"，然后通过知识蒸馏赋能下游数百个场景化模型。

整体架构分为三层：

┌─────────────────────────────────────────┐
│           GEM Foundation Model          │  ← 跨场景统一训练，LLM-scale
│  (InterFormer + Wukong + Seq Pyramid)   │
└───────────┬──────────────┬──────────────┘
            │ Direct       │ Hierarchical
            ▼              ▼
   ┌──────────────┐  ┌──────────────────┐
   │  Vertical    │  │ Domain-specific  │
   │  Models (VM) │  │ Foundation Models│
   └──────────────┘  └───────┬──────────┘
                             │ Distillation
                             ▼
                    ┌──────────────┐
                    │ Surface VMs  │  ← 线上低延迟服务
                    └──────────────┘

训练阶段：GEM 在数千块 GPU 上进行大规模预训练，学习跨平台、跨广告类型的通用用户行为模式。

部署阶段：GEM 本身不直接上线服务（太大），而是通过知识蒸馏将学到的知识传递给数百个轻量级的 Vertical Models，这些 VM 在线上低延迟地为具体场景服务。

持续迭代：线上 VM 产生的用户交互数据回流到训练管线，GEM 周期性重训练，更新后的知识再次蒸馏到 VM，形成闭环。

3. 核心技术贡献

3.1 InterFormer：交错式特征交互架构

传统方法的问题：以往的序列推荐模型先将用户行为序列压缩为一个固定维度的 summary vector，然后再与其他特征（用户画像、广告属性等）做交叉。这相当于把一部小说压缩成一个评分——大量细节信息在压缩过程中丢失。

GEM 的方案：InterFormer 采用交错式结构，在序列学习层（自定义 Transformer）和跨特征交互层之间反复交替：

Input → [Seq Layer] → [Cross-Feature Layer] → [Seq Layer] → [Cross-Feature Layer] → ...

每一个循环中，序列学习捕获用户行为的时序模式，跨特征交互层则将序列信息与非序列特征（如广告创意、用户画像）进行深度融合。关键在于：全程保留完整的序列信息，而非先压缩再交互，实现了渐进式精炼。

3.2 增强版 Wukong：可堆叠分解机 + 跨层注意力

GEM 在非序列特征交互上增强了 Wukong 架构：

  • 可堆叠分解机（Stackable Factorization Machines）：每层发现不同复杂度的特征组合模式
  • 跨层注意力连接（Cross-layer Attention）：让深层可以选择性关注浅层发现的重要特征组合
  • 双向可扩展：垂直方向加深交互层数，水平方向扩展特征覆盖范围

这种设计让模型能自动学习"哪些特征组合最重要"，而非依赖人工特征工程。

3.3 序列金字塔（Pyramid-Parallel Structure）

挑战：用户行为序列可达数千条事件，直接用标准 Transformer 处理在计算和存储上都不现实。

方案：

        ┌──────────────┐
        │  Top: 综合理解 │
        ├──────┬───────┤
        │ 中层模式融合  │
        ├──┬───┼───┬───┤
        │ Chunk│Chunk│...│  ← 底层：并行处理行为片段
        └──┴───┴───┴───┘
  • 底层：将长序列分割为多个 chunk，并行处理
  • 中层：将 chunk 级模式融合为更宽泛的行为模式
  • 顶层：综合形成完整的用户旅程理解

这种设计兼顾了计算效率（并行处理）和信息完整性（多层融合），且存储开销极小。

3.4 知识蒸馏框架 + Student Adapter

GEM 的知识转移效率是标准蒸馏方法的 2 倍，关键创新包括：

  • 双通道转移：Direct Transfer（同域 VM 直接从 GEM 学习） + Hierarchical Transfer（先蒸馏到领域 FM，再蒸馏到场景 VM）
  • 三种蒸馏技术并用：知识蒸馏（KD）、表示学习（Representation Learning）、参数共享（Parameter Sharing）
  • Student Adapter 创新：在蒸馏训练中加入一个轻量适配器，用最新的 ground-truth 数据修正 teacher 输出，解决两个关键问题：

1. 时效性问题：FM 训练周期长，预测可能过时
2. 域偏移问题：GEM 的通用预测与特定场景目标之间存在差异

4. 实验结果分析

线上效果

场景转化率提升时间段
Instagram 广告+5%Q2 2025
Facebook Feed 广告+3%Q2 2025

效率指标

  • 单位算力产出：GEM 每单位数据和算力带来的效果增益是上一代模型的 4 倍
  • 蒸馏效率：知识转移效果是标准 KD 的 2 倍
  • Scaling 验证：Q3 通过增加数据和算力，性能收益在 Q2 基础上翻倍——这直接验证了推荐模型的 scaling law 存在性

结果的意义

  1. 5% 转化率提升在广告领域是巨大的：广告系统高度优化，通常 0.1%-0.5% 的提升就值得上线。5% 意味着 Meta 广告收入的数十亿美元增长。
  2. Scaling law 验证：Q3 "加算力→效果翻倍" 的结果表明，推荐模型确实存在类似 LLM 的 scaling 规律，这为行业指明了方向。
  3. 4x 效率提升：说明 Foundation Model 范式不仅效果好，而且更"经济"——相同投入产出更大。

5. 局限与未来方向

当前局限

  1. 部署复杂度高：GEM 无法直接在线服务，必须依赖蒸馏管线。蒸馏引入延迟（模型更新不及时）和信息损失（student 无法完全复现 teacher 能力）。Student Adapter 虽缓解了时效性问题，但增加了系统复杂度。
  1. 训练成本极高：数千块 GPU 的训练规模对绝大多数公司不可及。文章未讨论训练成本与收益的量化关系。
  1. 技术细节不完全公开：作为工程博客，缺少消融实验（ablation study）。无法量化 InterFormer、Wukong 增强、序列金字塔各自的贡献占比。
  1. 多模态能力尚在规划中：当前 GEM 主要处理行为序列和结构化特征，对广告创意内容（图片、视频）的多模态理解仍是未来方向。
  1. 冷启动问题未提及：Foundation Model 依赖丰富的行为数据，对新用户、新广告主的冷启动效果未知。

作者规划的未来方向

  • 多模态融合：同时处理文本、图片、音频、视频
  • 推理时 Scaling：动态分配计算资源给"困难"预测，类似 LLM 的 test-time compute
  • 统一排序模型：有机内容和广告共用一个排序模型
  • Agentic 自动化：智能体驱动的广告主自动化投放优化

个人认为的改进方向

  • 在线蒸馏 / 实时 FM 更新：缩短 FM 训练-蒸馏-部署的管线延迟
  • 模型稀疏化与高效推理：探索 MoE（Mixture of Experts）架构，让 FM 部分模块可直接在线服务
  • 因果推断融合：当前模型本质仍是相关性学习，融入因果推断可提升对干预效果的估计精度

6. 工业实践意义

对搜索/推荐系统的启示

1. Ranking FM 化是可行且高效的路线

GEM 最重要的信号是：Foundation Model 范式在推荐排序领域被大规模验证成功。这不是学术实验，而是在 Meta 数十亿用户的真实流量上验证了 5% 的转化提升。对于拥有足够数据和算力的公司（字节、Google、Amazon 等），Ranking 模型的 FM 化将成为主流方向。

2. "大模型训练 + 蒸馏部署" 范式值得借鉴

GEM 确立了推荐系统的 "pre-train → distill → deploy" 三段式范式，与 LLM 的 "pre-train → fine-tune → deploy" 类似但针对推荐场景做了适配。核心洞察：线上服务不需要跑大模型，只需要让大模型教会小模型。Student Adapter 的设计解决了蒸馏中 staleness 和 domain shift 两个实际痛点，这对任何采用 teacher-student 架构的系统都有参考价值。

3. InterFormer 的交错式设计可迁移到搜索排序

传统搜索排序中，query 理解和文档理解通常先独立编码再交互（如 DE 模型）。InterFormer 的"边编码边交互"思路可应用于搜索场景——让 query 序列（历史搜索）与候选文档特征在编码过程中反复交互，而非先压缩再计算相似度。

4. 序列金字塔对长行为序列建模的实用价值

工业系统中用户行为序列越来越长（数千甚至数万），标准 Transformer 的 O(n²) 复杂度不可接受。金字塔结构提供了一个工程上可行的方案——chunk 并行 + 分层融合，在保持信息完整性的同时控制计算成本。这对电商搜索的长期用户兴趣建模尤其有价值。

5. 跨场景知识共享降低冷启动成本

对于多业务线公司（如同时有搜索、推荐、广告多个场景），GEM 的 hierarchical distillation 框架提供了一种系统性的跨场景知识共享方案，新场景可以快速从成熟场景的 FM 中获取初始知识。

6. 训练基础设施的工程经验

HSDP、变长序列 GPU Kernel、FP8 量化、NCCLX 通信优化等工程实践，对任何在做大规模推荐模型训练的团队都有直接参考价值。特别是 23x 训练吞吐量提升的经验，表明工程优化本身可以带来数量级的效率收益。

总结

GEM 的核心价值不在于某个单点技术创新，而在于系统性地证明了推荐排序领域的 Foundation Model 路线可行。它回答了行业一直在探索的问题：推荐模型是否也能像 LLM 一样 scale up？答案是肯定的——而且效率还能做到 4 倍于上一代。这为整个搜索/推荐/广告行业的模型 scaling 提供了清晰的路线图。

CADET: Context-Conditioned Ads CTR Prediction With a Decoder-Only Transformer

📖 有深读 · 14 分钟

LinkedIn 提出 Decoder-Only Transformer 架构 CADET 用于广告 CTR 预估，引入上下文条件解码和自门控注意力机制。

INSIGHT将 NLP 领域成熟的 Decoder-Only Transformer 范式迁移到 CTR 预估场景。关键创新在于 context-conditioned decoding 显式建模位置等后评分信号，以及 timestamp-based position embedding 捕捉用户行为的时序模式。这表明 CTR 模型架构正在向统一 Transformer 范式收敛。

业务关联社区搜索排序模型可借鉴 CADET 的架构思路：用 decoder-only transformer 统一建模用户特征序列，通过 context-conditioned 机制引入展示位置、时间等上下文信号。自门控注意力可缓解搜索排序模型训练中的不稳定问题。

证据在 LinkedIn 广告平台上线，CTR 相比生产模型 LiRank 提升 11.04%。采用 tensor packing 和定制注意力 kernel 优化推理性能以满足线上延迟要求。

CADET：LinkedIn 用一个 decoder-only Transformer 替换整套广告 CTR 模型，线上 CTR 提升 11.04%

我的判断：做广告排序的团队值得读。它没有发明新的注意力结构，价值在于把生成式推荐搬进广告时一定会碰到的几个现实问题讲清楚了：广告位置要等打完分才知道，线上序列有延迟，训练不稳定，几百个候选要在 50 ms 内打完分。CADET（Context-Conditioned Ads Decoder-Only Transformer，按上下文分头预测的广告 Transformer）的核心思想一句话：用户历史按“曝光—动作”交替排成一条序列，交给一个 decoder-only Transformer 逐条预测点击；位置这类打分后才确定的信息不当输入，而是给每个位置档各配一个输出头。几个关键数字：线上对比原生产模型 LiRank，CTR 提升 11.04%，CPC 下降 10.9%；离线 AUC 0.8554，HSTU 基线最高 0.8505；去掉按位置分头的设计，AUC 相对下降 0.61%，是所有消融里最大的一项。

它要解决什么问题？

场景是 LinkedIn 首页信息流里的赞助内容广告（Sponsored Updates）。原来的生产模型 LiRank 是两个模型的组合：DCNv2 负责特征交叉，TransAct（一种把用户行为序列编码成向量的 Transformer 模块）负责历史序列，每条曝光是一条独立样本，带 100 多个人工特征。作者想用一个 decoder-only Transformer 把它整个换掉，像 HSTU 那样把排序写成序列预测。

难点不在模型容量，而在广告系统的几个特殊约束。最典型的是位置。用一个示意例子说明：

示意排在第 2 位排在第 8 位
广告 A 的真实点击率2.0%0.8%
广告 B 的真实点击率1.6%0.7%

同一条广告，排得越靠前越容易被点。拍卖要用预估 CTR 乘出价来决定谁排前面，可预估 CTR 本身又取决于最后排在哪里。这就是论文说的“先有鸡还是先有蛋”：打分时位置还不知道，位置是打分之后才定的。常见做法是训练时把位置当特征，线上统一填一个默认位置，或者另训一个纠偏模型。前者让训练和线上看到的输入不一致，后者多一套模型要维护。

第二个约束是线上序列有延迟。用户 10:00 看到一条广告，10:20 点了另一条，10:30 系统给他打分时，10:20 那次点击可能还没写进线上的用户序列。离线训练如果能看到它，就学会了依赖线上拿不到的信息，离线指标虚高，上线后变差。第三个是训练稳定性，第四个是推理成本：每次请求要给几百个候选打分，p99 延迟预算是 50 ms。

步骤做什么产出
1. 排序列用户静态特征，然后按时间交替放“曝光特征”和“上下文+动作”一条最长 4096 的序列
2. 编码8 层带自门控注意力的 Transformer，用时间戳做 RoPE每个曝光位置一个隐藏状态
3. 分头预测每个位置档一个 MLP 头，输出这个档下的点击 logit每条曝光 K 个预测（线上 K=2）
4. 训练遮蔽不许看一小时以内的同会话事件和线上可见信息对齐
5. 线上打分几百个候选接在用户序列后，一次前向全部打完每个候选 K 个 CTR，拍卖按位置取用

关键分工是：位置只决定用哪个头的预测，从不作为当前这条曝光的输入。下面拆开讲。

位置怎么处理：每个位置档一个输出头

作者把位置按历史点击率分成 K 个档。线上用的是 K=2：第 1–4 位一档，第 5 位以后一档。共享的 Transformer 输出接 K 个小 MLP，第 k 个头输出“如果这条广告落在第 k 档，被点击的 logit”。

训练时每条曝光的真实位置是已知的。比如某条曝光实际排在第 3 位，那就只用第 1 档那个头的输出算交叉熵，第 2 档的头这一条不参与。损失写成：
Lctx​=t=1∑L​CE(y^​kt​​,yt​)
其中 kt​ 是第 t 条曝光实际落在的档，y^​kt​​ 是那个头的输出，yt​ 是有没有点击。直觉是：每个头只用落在自己档里的样本训练，所以各自学到的是“在这一档的 CTR”。

线上一次前向同时算出两个头的值。沿用前面的示意数字，广告 A 得到“第 1–4 位约 2.0%、第 5 位以后约 0.8%”两个预估。拍卖填前四个位置时用第一个值，填后面的位置时用第二个值，不需要先排一遍、再按排出的位置重打一遍分。

为什么不直接把位置当输入特征？因为线上打分时它根本不存在，填默认值就是训练和线上不一致。分头的做法里，当前曝光的位置只用来挑选算损失的头，模型的输入里没有它。历史曝光的位置则是已知的，作者把它放进 (C, A) 那一格，和动作配对，所以模型仍能学到“这个用户在靠后位置也常点”之类的规律，又不会泄漏当前这条的位置。

图里右侧的辅助头预测点击类型、落地页停留时长和曝光时长。它们只在训练时加进损失，起正则作用，线上不算。总损失是 CTR 损失和各辅助损失的加权和，权重论文没有给。

训练时为什么要遮住最近一小时

前面 10:20 点击的例子说明了问题。作者的做法是给训练加一个按时间的 attention mask：第 i 条曝光不能看时间戳落在它之前一小时以内的任何事件。
Mi,j​=−∞if tj​>ti​−Δdelay​
这里 Δdelay​ 是线上能保证的最小可见延迟，实验里取一小时。被设成负无穷的位置在 softmax 之后权重为 0，相当于模型看不到它。论文强调这里的“会话”不是硬边界，只是“延迟窗口内的事件”。

这项设计的消融做得很讲究。验证集上始终按一小时遮蔽，模拟线上真实情况；只有训练时把延迟设成 0，让模型能看到所有更早的事件。结果 AUC 相对下降 0.31%。也就是说，训练时多看到的那一小时信息，在线上条件下不仅没用，还会让模型变差，因为模型学会了依赖一个线上拿不到的信号。很多团队评估这类泄漏时，验证集也一起泄漏，看到的是虚高的离线收益；这里的设置把这个坑避开了。

时间编码和自门控

标准 RoPE 按序列里的第几个位置旋转 query 和 key。两条相邻的曝光，可能相差 30 秒，也可能相差三周，按序号编码分不出来。CADET 把序号换成 Unix 时间戳，第 i 个二维分量的旋转角是：
αi​(t)=t⋅Δtmax​ϕmin​​⋅base2i/d
Δtmax​ 是序列的最大回看窗口（1 年），ϕmin​ 控制最慢那一维在相差整整一年时转多少（取 10−4），$base$ 控制最快那一维有多快（取 6×105）。两条事件的注意力只依赖时间差，时间越近旋转差越小。去掉时间 RoPE，AUC 相对下降 0.13%。

这里有一个和论文说法对不上的地方。代入这组参数，最快那一维在相差一年时大约转 10−4×6×105=60 弧度，相差一天约 0.16 弧度，相差一小时只有约 0.007 弧度（我按论文公式的推算）。所以这组设置主要区分的是“几天到几个月”，小时以内的差别几乎不产生旋转，和摘要里“从秒到月”的说法有距离。作者也提到，同一段密集时间里的先后顺序靠因果 mask 保留，不靠 RoPE。

自门控是为了训练稳定。门控有两处，见下图。第一处在进注意力之前：用一个线性层加 sigmoid 给每一维算一个 0 到 1 的系数，乘回原向量，压掉噪声维。示意：某一维的门控输入是 −2，sigmoid 后约 0.12，这一维的值就只剩约八分之一。第二处分别作用在投影后的 Q 和 K 上，限制点积的幅度，避免少数 token 吸走大部分注意力，也就是常说的 attention sink。

自门控没有给 AUC 数字。论文只描述了多次训练的曲线：不加门控时训练早期 AUC 会突然大跌；只加第一处门控，跌的次数和幅度变小；两处都加最稳。对生产模型来说，这一点比零点几的 AUC 更实际：一个每次重训都可能翻车的模型没法上线。

怎么在 50 ms 内打完几百个候选

线上一次请求要给几百条候选广告打分。CADET 把所有候选接在同一条用户序列后面，用特殊的 mask 让每个候选只看用户历史、互相看不见，一次前向全部打完。论文据此写了一个定制的 FlashAttention 内核，直接跳过整块被遮住的计算，注意力规模从 (L+N)2 变成 L2/2+LN，L 是历史长度，N 是候选数。

用一个示意的量级算一下：L=4096、N=500 时，前者约 2110 万个配对，后者约 1040 万，少一半。更重要的是后者对 N 是线性的，候选翻倍，增加的只是 L×N 那一项。实测这个内核比标准的融合多头注意力内核（FMHA）快 3 倍，每块 GPU 每秒 330 个请求，p99 小于 50 ms。附录特别说明，这个内核只用于线上服务，训练和离线评估都用现成的 FlexAttention（PyTorch 里支持自定义 mask 的注意力接口），所以论文里的精度结果不依赖它。

训练侧有两项数据工程。一是从“每条曝光一条样本、100 多个特征”改成“每个用户一条序列、每个 token 12 个高价值信号”，数据量减少 98%，精度没有下降。二是 packing：不把每条序列补齐到同样长度，而是把一个 batch 里的所有 token 拼成一段连续缓冲区，再记下每条序列的起止位置。用户序列长度分布严重右偏，大多数很短，所以省掉补齐之后，有效 batch 大约变成 4 倍。作者提到每个 batch 的 token 总数必须固定，否则 torch.compile 和训练稳定性都会出问题。

实验：到底赢在哪里

离线实验用一年的广告点击数据训练，最后一天验证。模型是 8 层、4 个头、隐藏维度 352、序列长 4096，规模不大。

模型AUC
HSTU-Base0.8497
HSTU-Large0.8505
CADET-HSTU（不带训练遮蔽）0.8535
CADET-Transformer（不带训练遮蔽）0.8534
完整 CADET0.8554

先看 HSTU 的两个规模：从 Base 到 Large 只涨了 0.0008，说明在这份数据上单纯加大骨干收益很小。再看两个 CADET 变体：把骨干换成 HSTU、其余设计不变，AUC 和默认的 Transformer 骨干只差 0.0001。这说明 收益来自位置分头、时间编码和门控这些设计，而不是选了哪种骨干。这两个变体都没有训练遮蔽，原因是 Meta 开源的 HSTU Triton 内核不支持这种 mask。加上遮蔽的完整 CADET 再涨约 0.002。

消融相对完整 CADET 的 AUC 变化
去掉按位置分头−0.61%
去掉时间 RoPE−0.13%
去掉训练遮蔽−0.31%

位置分头贡献最大，这和问题的性质一致：位置对点击率的影响本来就很大，模型能按位置给出不同预估，排序自然更准。

线上 A/B 在首页赞助内容上进行，对照是 LiRank，CADET 把 DCNv2 和 TransAct 两部分完全替换。CTR 提升 11.04%，统计显著。收入基本持平，CPC 下降 10.9%。这两个数要放在一起读：LinkedIn 的广告主大多用自动出价，通常会把预算花完，所以总花费不变；同样的预算换来更多点击，单次点击成本就下来了。这说明收益落在了广告主的 ROI 上，平台短期收入没有因此增加。

我认为它的局限

第一，离线和线上之间缺了一环。论文没有给 LiRank 的离线 AUC，离线表里只和 HSTU 比，线上又只和 LiRank 比。读者没法判断 11.04% 里有多少来自模型结构，有多少来自序列化数据和更长的历史。线上实验的流量比例和时长也没有披露。

第二，两张表的口径不完全一致。消融表说去掉训练遮蔽 AUC 降 0.31%，按 0.8554 算应在 0.8527 左右；对比表里不带遮蔽的 CADET-Transformer 是 0.8534，只低约 0.23%。差别不大，但说明两组实验的设置可能不同，论文没有解释。

第三，位置只分了两档，而且只处理了位置这一种打分后信息。K=2 是为了方便和下游拍卖对接。实际的卡片样式、是否首屏等因素也会影响点击，作者把多种打分后信息同时建模留给了以后。广告拍卖要用 pCTR 乘出价，校准好不好直接影响扣费，论文没有报告两个头各自的校准情况。

一个推荐或广告团队可以怎么试

  1. 先只加训练遮蔽。按线上序列的真实延迟设一个时间窗，训练时遮住窗口内的事件，验证集始终遮住。改动最小，能直接看出现有模型有没有在吃线上拿不到的信息。
  2. 再试位置分头。在现有排序模型上把位置特征从输入里拿掉，按历史 CTR 分 2–3 档各接一个头。除了 AUC，要分档看校准，确认每档样本够多。
  3. 如果在做序列模型，把 RoPE 的序号换成时间戳，同时按自己的业务算一下参数：想区分小时级差别，最快那一维在一小时内要有明显旋转。
  4. 最后才考虑整体替换。先在离线同一份数据上和现网模型比 AUC，确认结构收益，再上线 A/B，同时看 CTR、CPC、收入和 p99。

结论

一句话：生成式推荐进广告，难的不是骨干，而是把“打分时不知道的信息”和“线上看不到的信息”处理对。
