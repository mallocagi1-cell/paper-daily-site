TransRetrieval: Scaling Up Transformer-Based Retrieval for Industrial Recommendation

召回阶段一直很难像排序那样靠加大模型变好，因为召回要在几千万广告里几十毫秒内选出几千个，每个被访问的候选都要过一遍模型，算力被候选数放大。阿里展示广告的 TransRetrieval 把召回打分模型换成 Transformer，先把多值特征从求和改成加权平均来拉齐尺度，再把广告侧所有特征压成一个 token，省下的算力投到更宽更深的模型上。候选侧压成一个 token，算力花在模型本身。随着每个候选的计算量增加，Recall@2000 从 0.464 稳步升到 0.657。线上一个月平台收入提升 2.53%，延迟不变。

TransRetrieval：阿里展示广告把召回模型换成 Transformer，三处轻量改动让算力越加召回越好，线上收入 +2.53%

我的判断：做召回的团队值得读，尤其是已经在用“打分模型 + 图索引”做召回、又想把模型做大的团队。它要解决的问题是：排序阶段已经有不少“模型越大越好”的结果，召回阶段却很少，因为召回要在几千万候选里几十毫秒内选出几千个，每个候选都要过一遍模型，算力被候选数放大。核心思想一句话：先把输入特征的尺度拉齐，再把广告侧的所有特征压成一个 token 省下算力，把省下的算力投到更宽更深的 Transformer 上。几个关键数字：每个候选的计算量从约 0.14 加到 1.91 MFLOPs（百万次浮点运算），工业数据上的 Recall@2000 从 0.464 升到 0.657；线上 5% 流量跑了一个月，平台收入提升 2.53%，P99 延迟和原系统一样在 40 ms 以内。

它到底在解决什么问题？

先看一个示意场景。用户打开淘宝某个页面，展示广告系统要从 5200 万个广告里挑出 2000 个候选交给后面的排序。阿里这套召回不是双塔，而是基于模型的召回：广告预先建成一张 HNSW 图（一种分层的近邻搜索图），一个打分模型沿着图做 beam search，每次请求只真正打分约 4 万个广告，约占全库的 0.08%。

双塔只能用用户向量和广告向量的内积打分，用户和广告的特征没法细粒度交叉；基于模型的召回可以用任意复杂的打分网络，代价是每个被访问的候选都要做一次前向计算。所以这里最贵的不是用户侧，而是每个候选上的计算量，它会被 4 万倍放大。

在这种设定下想把打分模型换成更大的 Transformer，作者列了三个障碍：

障碍具体表现TransRetrieval 的对策
特征尺度不一用户侧多值特征（比如几十个历史类目）求和后，向量长度可达广告侧的 10 倍把求和改成加权平均
候选侧算力太贵每个广告的每个特征都是一个 token，算力随特征数线性增长，再乘以 4 万广告侧特征用一个 MLP 压成 1 个 token
多个业务域首页、搜索、详情页等分布不同，分开训练成本翻倍，小域数据又不够给每个域学一个向量，像位置编码那样加到所有 token 上

三处改动都只用标准算子，不需要新的基础设施。下面逐个讲为什么这样做、效果多大。

先看全景

一次请求的计算流程：

步骤做什么每次请求算几次
1. 用户侧编码用户特征和行为序列聚合成 token，加上域向量，算出各层的 KV 并缓存1 次
2. 广告侧压缩广告特征聚合后经 MLP 压成 1 个 token（可以离线算好）预先算好，特征变化时近线更新
3. 候选打分广告 token 作为查询，对缓存的用户 KV 做注意力，再过预测头约 4 万次
4. 图搜索按打分在 HNSW 图上做 beam search，选出前 2000和打分交替进行

改动一：特征聚合从求和改成平均

推荐里的一个特征字段常常包含多个值，比如“最近点击的类目”可能有几十个，每个值带一个权重。常规做法是把这些值的 embedding 按权重加起来。问题在于，加起来的向量长度会随值的数量增长。手算一下（示意）：100 个长度为 1 的 embedding，如果方向互不相关，和的长度约为 √100=10；如果方向一致，长度是 100。而广告侧很多字段只有一个值，长度就是 1。作者实测，用户侧 token 的长度最多是广告侧的 10 倍。

这为什么有害？注意力分数是查询和键的点积，键越长分数越大。设两个键和查询的方向相似度一样，原本点积都是 0.5；其中一个长度放大 10 倍，点积变成 5，softmax 后它拿到 e^5/(e^5+e^0.5)≈0.99 的权重，另一个几乎被忽略。作者认为这就是 Transformer 在推荐特征上越堆越没用的原因。

改法是除以权重之和：
ef​=∑i​vi​+ϵ∑i​vi​h(ki​)​
这样一来，不管字段有几个值，结果的长度都不会超过单个 embedding 的量级。它不需要学习参数，也不需要统计量。

消融（64D-5L 配置，工业数据 Recall@2000）：

聚合方式总体 Recall@2000
加权平均（本文）0.618
加权求和0.608
求和后再做 LayerNorm0.593
最大池化0.571

这说明平均确实最好，但比求和只高 1.0 个点。摘要把它称为“关键”，这个幅度显得偏小。另外有两点值得注意。第一，平均只保证长度有上界，没有保证各字段长度相等：100 个方向不相关的向量取平均，长度反而会缩到约 0.1，作者没讨论这种情况。第二，模型本身是 Pre-LN Transformer，每层进入注意力之前都会先做 LayerNorm，按理会把各 token 的长度拉齐，“长 token 霸占注意力”的解释和架构不完全对得上。更可能的作用途径是残差流里的尺度差异，但论文没有做这方面的分析。

改动二：广告侧压成一个 token，把省下的算力投到模型上

作者给了一次请求里所有候选打分的总计算量公式：
FLOPs≈4D⋅Ntarget​⋅Lt​⋅(4D+Lu​)⋅Nlayer​
D 是隐藏维度，Ntarget​ 是被打分的候选数，Lt​ 是每个候选的 token 数，Lu​ 是用户侧 token 数，Nlayer​ 是层数。D 和层数是想加大的，候选数已经被 HNSW 压到 0.08%，剩下能动的只有 Lt​。所以作者把广告侧所有特征拼起来，过一个三层 MLP（宽度 8D、4D、D）压成一个 D 维 token。

论文表格里报告的是每个候选的计算量，也就是这个公式去掉 Ntarget​ 后的 4D⋅Lt​⋅(4D+Lu​)⋅Nlayer​，可以用它验算。论文没有直接给 Lu​，我用 64D-3L、8 个 token、3.04 MFLOPs 反推出 Lu​ 约 240（我的推算）。代回去：

配置公式估算（MFLOPs）论文报告Recall@2000
64D-3L，8 个 token4×64×8×(256+240)×3≈3.053.040.624
64D-3L，4 个 token约 1.521.550.615
64D-3L，1 个 token约 0.380.450.603
128D-5L，1 个 token4×128×1×(512+240)×5≈1.921.910.657

公式和报告值基本吻合，1 个 token 时多出的约 0.07 应该是压缩 MLP 本身的开销。这张表说明了作者的思路：压到 1 个 token，计算量降约 85%，Recall 掉 2.1 个点；但把省下来的算力用来把模型从 64D-3L 加到 128D-5L，计算量仍比 8 个 token 的小模型低（1.91 对 3.04），Recall 反而高 3.3 个点。按每次请求 4 万个候选算，128D-5L 每次请求的候选侧计算约 76 GFLOPs（我的推算）。

另外一个好处是，这个压缩 token 本身就是固定维度的向量，可以直接用来建 HNSW 索引。广告特征变了，只需近线重算受影响广告的 token。

改动三：域信息像位置编码一样加进去

阿里展示广告服务 4 个业务域。把数据混在一起训一个模型，模型分不清请求来自哪个域；常见做法是在序列里加几个“域 token”，但每多一个 token，注意力成本就增加。作者的做法是给每个域学一个 D 维向量，直接加到每个 token 上，和位置编码一样，序列长度不变，Transformer 所有参数在各域之间完全共享。

做法（64D-3L，工业数据）总体 Recall@2000用户侧 MFLOPs
每个域单独训练0.57941.3
混合训练，不加域信息0.26541.3

混合训练，加 20 个域 token0.45249.8

这说明域信号必须足够强，混合训练才有收益：加 1 个 token 几乎没用，重复 20 次才明显好转，而加到每个 token 上效果最好、不增加计算。和各域单独训练相比，B 域从 0.539 升到 0.590，提升最大，A 域只从 0.591 到 0.593。

不过这张表有一个让人疑惑的地方：不加域信息的混合训练只有 0.265，比单域训练的 0.579 低一半以上。四个域都是同一个广告平台的流量，混在一起训练就掉到这个程度，很不寻常，论文没有解释原因。另外在公开数据 KuaiRand 上，最稀疏的 Tab 3（只占 0.13% 的交互）TransRetrieval 是 0.537，反而低于 HSTU 的 0.611，“小域靠跨域迁移受益”这个说法在公开数据上并不总成立。

工程上怎么跑进 40 ms

模型变大之后还能守住延迟，靠的是几项和模型配套的系统改动，论文给了每项的收益：

改动做法效果
用户 KV 共享通用 LLM 推理框架会给每个候选序列复制一份用户 KV，这里改成一个广播算子，不复制单次前向延迟降 30%
候选打包压缩后每个候选只有 1 个查询 token，GPU 利用率很低；把多个候选拼进一次批量计算，用掩码隔开和算子融合一起，前向延迟比朴素实现快 11 倍
图搜索上 GPU原来索引在 CPU，每轮 beam search 都要在 CPU 和 GPU 之间来回传数据；现在邻居查找、距离计算、候选选择都在 GPU 上召回延迟比 CPU 版降 89%
省显存整个图索引放进 GPU 后显存吃紧；多个请求改为共用同一份驻留在显存里的推理引擎，不再各自占一份，索引里不变的数据再做量化压缩同一块 GPU 能同时处理的请求数提高 3 倍

这些数字说明，基于模型的召回能不能换成 Transformer，一半取决于模型设计，另一半取决于推理系统。单个候选只有 1 个查询 token 的形状和 LLM 推理很不一样，直接套用现成框架会浪费大量算力。

我认为它的局限

第一，“规模定律”的证据范围有限。计算量只跨了约 14 倍（0.14 到 1.91 MFLOPs），R² 为 0.82，图上同等计算量下维度和层数的不同组合差距明显，说明不能只看计算量，形状也重要。再往上加是否还按同样斜率增长，论文没有验证。

第二，最被强调的“关键”改动收益最小。加权平均比求和只高 1.0 个点，也没有给出“用求和时规模曲线变平”的对照，所以“尺度不一导致无法扩展”这个核心论断缺少直接证据。

第三，基线的公平性存疑。所有方法共用一套为本文调好的超参数，RankMixer 原本是排序模型，被改造用于召回。HSTU 和 RankMixer 的弱表现有多少来自方法本身、多少来自调参和改造，难以区分。

一个召回团队可以怎么试

  1. 先查自己模型里各 token 的向量长度。如果多值特征字段的长度比单值字段大很多，把求和换成加权平均，成本几乎为零。
  2. 如果用的是基于模型的召回，用论文的公式算一下候选侧的计算量构成。只要候选 token 数大于 1，压缩成 1 个 token 再把算力投到维度和层数上，很可能是性价比最高的改法。
  3. 有多个业务场景共用召回时，先试把场景向量加到每个 token 上，和现有的分场景模型比较，重点看小场景。
  4. 做规模实验时固定计算量、改变宽度和深度的组合，不要只画一条“计算量—效果”曲线。

结论

一句话：召回阶段的 Transformer 也能靠加算力变好，前提是把候选侧压到一个 token，把算力花在模型本身上。

An Event is Worth One Token: Event Tokenization for Industrial-scale LLM Recommendation

📖 有深读 · 9 分钟

论文指出现有 LLM 推荐把一次交互压成文本、语义 ID 或少量类别特征，会持续丢失用户、物品、上下文与结果信号。AMBER 将完整时间快照压缩成一个可缓存的 Event Token，把“快照分辨率”变成新的扩展维度；工业排序和召回实验显示其改善计算—质量帕累托前沿，并可作为历史特征迁移到优化后的非 LLM 排序器。

INSIGHT值得借鉴的不是简单增加序列长度，而是提高每个行为事件携带的信息密度，并通过离线预计算隔离线上成本。社区推荐可把点击时的 query、内容语义、位置、停留与互动结果联合编码为事件 token，再让召回和排序共享，减少多套特征管线之间的信息损耗。

AMBER 深度解读

1. 问题与动机

工业 LLM 推荐通常用文本、Semantic ID 或少量类别字段代表一次行为，但真实曝光事件同时包含用户状态、物品属性、上下文、位置、权重和结果。作者把每个事件所保留的信息量称为 snapshot resolution，并指出信息损失会在自回归序列中复合：当前事件形成的弱查询不仅影响本次预测，还成为后续事件的上下文。直接在每次线上请求中重建几百个历史事件的全部特征又不可行，因为特征 materialization 和编码会反复发生。论文给出的排名负载分析表明，考虑全流量推理、全候选打分与低利用率后，服务计算相对保留训练样本可放大 30–100 倍；因此“训练 FLOPs 最优”可能与“训练加服务总成本最优”相反。开放词表还会周期性重训 tokenizer，导致旧事件表示漂移和缓存失效。AMBER 的目标是把高分辨率历史保留下来，同时把昂贵计算移出实时路径。

2. 方法详解

AMBER 由 Event Tokenizer 和下游 User LLM 组成。每次曝光发生后，异步服务通过现有训练数据管线收集完整异构快照；各字段先投影为 token，再送入双向 Transformer，加入可学习 [CLS]，其输出经映射成为固定维度 Event Token。实验初始化使用预训练 10 亿参数 LLM；tokenizer 可独立扩展深度 1/2/4、宽度 64/128/256/512，并把 snapshot resolution 扩到 100/200/400 个特征。Event Token 被缓存，排序时作为历史输入供端到端 User LLM 使用，也可作为现有非 LLM ranker 的即插即用历史特征；召回场景则可进入 ANN 搜索。

信息泄漏通过角色掩码控制。排序序列中每个事件使用 context token 和 label/outcome token：当前 context 只能看此前事件，label token 才能看到当前上下文，从而用 autoregressive BCE 预测反馈。模型优先采用每事件一个压缩 token，以有限上下文窗口容纳更长历史；实验显示无限上下文时两个 token 可改善 0.10% NE，但有限窗口反而恶化 0.16%，说明历史覆盖比单事件容量更重要。

训练分三阶段。预对齐阶段冻结 User LLM，只训练 Event Tokenizer，使新模态进入原有表示空间；联合阶段解冻 User LLM，端到端学习 token 表示与排序目标；循环训练阶段周期性更新以跟踪分布变化。为避免新旧 tokenizer 使同一事件编码不兼容，作者采用域对抗正则 DANN，让判别器难以区分新旧表示，并对 encoder 参数做 EMA，形成跨日稳定锚点；服务时还进行量化感知训练，以模拟 INT8 噪声并最终用 INT4 存储 token。循环训练按用户分片，只刷新部分用户并定期覆盖全量，以提高新鲜信号/训练成本比。

数据是 petabyte 级内部曝光日志，按时间切分；主实验使用全量，消融用 10% 子样本。论文没有公开 optimizer、batch size、硬件数量或总训练步数，这是复现缺口。完整流量部署的 tokenizer 有 384 万 dense 参数和约 200 GB 稀疏 embedding 表，每天为数十亿事件在线异步编码。作者以 normalized entropy（NE，越低越好）评价排序，并以 Soft Recall 评价召回；工业经验中 0.02% NE 降幅已被视为统计显著且可带来收入影响。

3. 核心技术贡献

第一，论文把“每事件输入信息量”明确为独立 scaling 轴。移除所有物品特征使 NE 恶化 6.65%，只保留 Semantic ID 与结果信号仍比完整 AMBER 差 2.40%，说明扩大下游 LLM 无法补回输入中不存在的信息。第二，异步压缩与缓存改变了系统成本结构：User LLM 每请求运行，而 tokenizer 每事件只运行一次，因此计入服务成本后，扩 tokenizer 和快照分辨率比继续扩 User LLM 更划算。第三，统一 tokenizer 在四 token 和两 token schema 下都比按实体拆分改善 0.02% NE，表明不同用户、物品和上下文实体间存在正迁移。第四，DANN 加 EMA 不仅约束向量接近，还提升跨 20 天 checkpoint 的可用性；DANN 的 cosine mean 为 0.956、kNN 区分准确率 0.856，并使 NE 再改善 0.02%，优于 MMD、CORAL 和 L2。

5. 局限与未来方向

作者明确指出，高分辨率依赖异步特征管线，尚未缓存的新事件仍有 1–5 分钟延迟；tokenizer 必须循环重训，漂移缓解只能降低而不能消除新旧表示不兼容。约 200 GB 稀疏表和每天数十亿事件编码意味着方案只在具备大规模特征平台、缓存和回填能力时现实。论文使用内部数据且未公开 optimizer、batch、硬件和绝对 NE，主要结果多用相对变化，外部复现困难；它也没有报告完整线上 A/B 收入、CTR 或延迟结果，0.06% NE 只是离线/大规模评估信号。作者提出未来可探索更灵活 token 维度而避免反复重训。额外风险包括 INT4 token 对小众行为的量化损失、缓存删除策略对长周期兴趣的伤害，以及高维快照可能放大隐私与敏感属性泄漏。

6. 工业实践意义

对社区个性化系统，最直接的启示是不要只把一次点击表示成 post ID。可把当时 query、帖子文本/多模态 embedding、位置、曝光来源、设备、用户短期状态、停留、点赞、评论和负反馈形成不可变事件快照，再离线压成 token。这样召回、粗排和精排可以共享同一历史语义，同时避免每个请求重复访问数百项特征。第一阶段不必部署 LLM：论文已证明 Event Token 加到成熟非 LLM ranker 也能带来 0.06% NE 改善，可先验证跨架构价值。

工程上应建立 token 版本、encoder checkpoint、事件时间和特征 schema 的强绑定，支持双写、回填和回滚；每天监控新旧 token 的 cosine、可分性、下游 NE 与长尾用户误差。成本评估必须包含异步编码、200 GB 级稀疏表、缓存、回填和隐私治理，而不能只算 User LLM FLOPs。有限上下文下应优先保留更长历史而非给每事件更多 token；特征选择可按 permutation importance 从 100 扩到 200/400，并用去除 item/user/outcome 组的消融判断真实贡献。若没有成熟的事件特征平台，先实现稳定、可版本化的快照日志会比直接训练 AMBER 更重要。
