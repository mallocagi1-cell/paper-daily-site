1. Stellar: Scalable Multimodal Document Retrieval for Natural Language Queries
4.10
Relevance 4 | Novelty 4 | Practical 4 | Evidence 4 | Timely 5

Summary: Stellar 针对多模态文档检索中 late interaction（多向量 token 级表示）内存开销过大、难以规模化的问题，提出把 token 级文档 embedding 存到磁盘、检索时只把候选 token embedding 调入内存。两个核心组件：LRF（Lexical Representation-based Filtering）把 MLLM 微调成稀疏编码器产出词项表示先做粗筛缩小候选集；DLI（Efficient Disk-backed Late Interaction）用平衡聚类设计磁盘上的 token embedding 存储布局，再按成本模型动态只加载必要 token。在四个真实基准外加一个新的大规模数据集上验证了效果与可扩展性。

Key insight: 多向量/late interaction（ColBERT 系）召回质量强但内存吃不消，Stellar 的解法是稀疏粗筛 + 磁盘 late interaction 两段式——先用 LRF 的 lexical 表示砍候选，再用成本模型决定哪些 token embedding 值得从磁盘读。对社区搜索做语义匹配/精排时，这套 disk-backed 方案给出了在不牺牲多向量精度的前提下控内存的可借鉴设计；LRF 把 MLLM 当稀疏编码器用，也提示了一个模型同时产出稠密+稀疏表示的统一路线。

Stellar 深度解读

1. 问题与动机

多模态文档检索（给定自然语言 query，从同时含文本和图表的文档页语料里选出相关页）是 RAG 的关键一环。当前 SOTA 走 vision-centric 多向量路线（ColPali、M3DocRAG）：把每个文档页渲染成图、用 MLLM 编码成一组 token 级 embedding，query 端也是多向量，靠 late interaction（MaxSim，Eq.1 score_mul = Σ_i max_j e_i^q·e_j^d）算细粒度相关性。效果好，但内存爆炸——论文估算 ColPali 给 240 万文档语料存 token embedding 要 >800GB 内存、AWS r7iz.32xlarge 上每月 >$8,500。量化（QColPali/PLAID）治标不治本：离线压缩阶段仍要把原始 token embedding 全 load 进内存，检索期内存随语料线性涨。Stellar 换范式：token embedding 落到便宜的磁盘，检索时只把少量候选调进内存做 late interaction。这带来两个新挑战：(I) 怎么设计轻量又高召回的一阶段过滤器把候选从全库砍到 top-k₁；(II) 候选定位后怎么压低 disk-to-memory 的 I/O 延迟（随机 I/O 是瓶颈）。

2. 方法详解

Stellar = LRF（一阶段稀疏过滤）+ DLI（二阶段磁盘 late interaction）。
LRF（Lexical Representation-based Filtering）：搭一个 siamese 稀疏双编码器，复用 MLLM 预训练的 next-token 预测头 f_head 当 lexical 投影层，把每个 token 的 last-layer hidden h_i 投到 |V|=151,936 维词表空间 w_i = f_head(h_i)（Eq.2）；对 w_i 做 ReLU 去负值，再跨 token 做 max-pooling：z_j = max_i log(1+ReLU(w_ij))（Eq.3），得到文档/query 的稀疏向量。训练用 in-batch InfoNCE（Eq.4）+ FLOPs 正则（Eq.5，λ₁=9e-5 文档 / λ₂=6e-5 query）逼稀疏。这套表示平均只有约 200 个非零维（151,936 维里），稀疏率约 99.87%，于是能建倒排索引，在线对 query 只遍历其非零维对应的 posting list 累加分数（Eq.7），过滤出 top-k₁=100 候选。
DLI（Disk-backed Late Interaction）：文档另存一份多向量 e_i = Wh_i + b（线性投影），用 pairwise contrastive loss（Eq.8，L_pw = 1/N Σ log(1+exp(s_i⁻ − s_i⁺))）微调。落盘布局靠 Balanced Clustering Algorithm（Algorithm 1）：先 k-means 出 K=⌈|D|/s_exp⌉ 簇，超过 s_exp=50 的递归拆分、小于 s_min=3 的解散重分配，同簇 token embedding 连续存成一个 block，配文档级 + block 级两级索引。在线读盘用 cost-aware loading 在 FBL（整块顺序读）和 SVL（按需随机读）间按代价模型（Eq.9/10，用顺序吞吐 R_seq 和随机吞吐 R_rand 估时）选更快的那个。最后 score 融合：score_fus = α·Z(score_spa) + Z(score_mul)（Eq.11，Z 是 z-normalization，α=0.3）。backbone 用 Qwen2-VL-2B（ViT + Qwen2-1.5B），LoRA r=32 单 epoch，τ=1，在线检索全程跑在 CPU（Intel Xeon Silver 4316 / 256GB RAM）。

3. 核心技术贡献

(1) 把 MLLM 的 LM head 复用成稀疏 lexical 编码器：不是新训一个稀疏模型，而是用预训练 f_head 初始化投影层再微调，把多模态页投到词表空间产生可建倒排的稀疏表示——99.87% 稀疏让一阶段过滤又快又省内存，且天然兼容词项倒排。
(2) 表示-存储协同设计（representation-storage co-design）：token embedding 存盘而非压缩进内存，根治了量化路线"离线压缩仍要全量 load"的内存上限问题。
(3) Balanced Clustering Algorithm：解决朴素聚类块大小不均导致的随机 I/O 抖动，保证每次 block 读不会因超大簇 stall。
(4) cost-aware loading：用一个轻量代价模型在 FBL/SVL 间动态选路，避免一刀切。消融显示这些都不是摆设：去掉 BCA（用 NCA）latency 全面变高，FBL/SVL 单用都更慢。

4. 实验结果分析

4 个公开基准（DocVQA/InfoVQA/ArXivQA/PlotQA）+ 自建 LargeDoc（40 万文档、94 query，基于 Docmatix 的 240 万 PDF 采样 + gte-Qwen2/DSE/ColPali 召回并集 + GPT-4o 清假负 + 3 名研究生人工校验）。
效果（Table II，R@1/R@10/M@10）：Stellar 在 DocVQA 84.43/97.29/89.05、InfoVQA 86.91/99.16/92.10、LargeDoc 75.53/87.23/79.47，R@1 全面拿第一，相比 SOTA 多向量 ColPali（DocVQA 82.74、LargeDoc 74.47）持平或更优；single-vector 方法（DSE/VisRet/Bi-Qwen）平均落后多向量约 15 个 R@1 点。
内存/延迟（Table III）是核心卖点：LargeDoc 上 ColPali 要 147,355MB / 42,115ms，Stellar 只要 988MB（0.96GB）/ 110ms——内存约 150× 降、延迟约 383× 降；对 QColPali（13,699MB/613ms）也是 14× 内存、5.6× 延迟。中等规模 ArXivQA/PlotQA 上 ColPali/QColPali 分别要 74.5×/9.3× 于 Stellar 的内存。注意小规模 DocVQA 上 Stellar 延迟 50.16ms 反略高于 QColPali 45.81ms，优势要到大语料才拉开。
消融：去 score fusion（Table V）LargeDoc R@1 从 75.53 掉到 70.21（−5.32）、DocVQA 84.43→82.91，证明 sparse+dense 互补；α 敏感性（Fig 8）在 0.3 处 R@10/M@10 见顶。DLI 加载策略消融（Table IV）：Stellar 的 cost-aware loading 在 DocVQA 50.16ms，优于 FBL 178.11ms、SVL 63.20ms、NCA 朴素聚类 60.33ms。LRF vs 用 DSE 做稠密一阶段过滤：DSE 在 40 万规模一阶段就要 2.3GB 内存，是 Stellar 端到端（0.96GB）的两倍多——稠密过滤本身会成内存瓶颈。

5. 局限与未来方向

论文无独立 Limitations 节，结论里点了两个方向：(1) 进一步加速 disk-to-memory loading，靠 hardware-aware prefetching 或轻量 embedding caching；(2) 把单文档检索扩展到 multi-document retrieval（答案分散在多页）。从实验也能看出几处隐含局限：小语料（DocVQA/InfoVQA）下磁盘方案的延迟优势不明显、甚至略逊量化方案，方法定位在大语料；DocVQA 高分辨率图产生更多 visual token，late interaction 延迟更高，说明 DLI 延迟仍受单文档 token 数牵制；LargeDoc 只有 94 个 query，评测规模偏小，统计稳定性存疑。

6. 工业实践意义

对做大规模检索的搜推团队，Stellar 最直接的借鉴是"多向量 late interaction 不必把 embedding 全压进内存"这条路线：当向量库大到内存放不下时，与其堆量化牺牲精度，不如把 token embedding 落盘 + 一阶段稀疏过滤 + cost-aware 读盘，在保住 ColPali 级精度的同时把内存打到 1/150。具体可拆三块复用：(1) 复用 LM head 当稀疏编码器、配 FLOPs 正则做到 ~200 非零维，直接接现有倒排基建，适合 UGC 短文本/文档的一阶段召回；(2) BCA 的"按簇连续落盘 + 限制块大小"对任何 disk-based ANN 都通用，能稳住随机 I/O；(3) sparse+dense 的 z-normalization 融合（α=0.3）是低成本提点项，LargeDoc 上 +5.32 R@1。部署上 Stellar 全程 CPU 推理、0.96GB 内存撑 40 万文档，对成本敏感、无 GPU 常驻的检索服务很友好；但甜区是大语料，小库直接用内存多向量反而更省事。代码：https://github.com/ZJU-DAILY/Stellar

2. ELVA: Exploring Ranking-Driven Universal Multimodal Retrieval
3.70
Relevance 3 | Novelty 5 | Practical 3 | Evidence 3 | Timely 5

Summary: ELVA 面向通用多模态检索（UMR），指出对比学习把样本简单当正/负二分类会导致 grain blindness——模型忽略 query 里的粒度信息、处理复杂 query 时失效。它提出一个基于规则的 RL 框架：把 RLVR（Reinforcement Learning with Verifiable Rewards）从生成任务扩展到检索，无需 reward model、也无需显式 ranking 标签，用 rule-based reward 按负样本与正样本的相似度差异做差异化排序，同时拉大正负相似度间隔。

Key insight: 把对比学习的二元正负换成按相似度分级的排序信号是这篇的关键——负样本不该一视同仁，离正样本越近越要细分。用 RLVR 替代 reward model 来训练检索/embedding 模型是个值得关注的新范式：当 query 带细粒度意图时，纯 InfoNCE 容易丢信息，引入 ranking-aware 的 reward 可能比单纯堆负样本更有效，对训练社区搜索的语义匹配模型有直接启发。

3. Closing the Calibration Gap in Semantic Caching
3.70
Relevance 3 | Novelty 4 | Practical 4 | Evidence 3 | Timely 5

Summary: 论文针对语义缓存（semantic caching，给语义相似 query 直接返回缓存结果以省 LLM 推理成本）的评估问题，指出业界常用的 PR-AUC 只衡量打分排序好坏、不管在固定阈值下是否可用，导致 PR-AUC 最高的模型上线后反而最差。提出两个 cache-aware 指标 P-CHR（Precision-Cache Hit Ratio）AUC 和 CRR（Calibration Retention Rate），并把离线-线上质量差拆成可恢复的校准分量和由数据集正例率决定的不可约结构分量。实验显示校准差距主要由训练目标决定、与数据规模关系不大，post-hoc 校准只能部分弥补。

Key insight: 论文的判断是：语义缓存的模型选型本质是校准问题，PR-AUC/AUC 这类排序指标会系统性误导固定阈值场景的上线决策。这点对社区搜索同样成立——相关性匹配模型最终要在某个分数阈值上做召回/不召回、缓存/不缓存的硬决策，光看 AUC 选模型会踩坑，应改用 P-CHR 这类带阈值利用率的指标，并把校准当作训练目标的一部分而非事后补救。

4. Query-aware Routing for Filtered Approximate Nearest Neighbors Search
3.55
Relevance 3 | Novelty 3 | Practical 4 | Evidence 4 | Timely 5

Summary: 论文系统评测了主流类别过滤 ANN（向量相似度 + 属性谓词）方法，发现在多数据集、三种谓词下没有单一方法占优，甚至同一数据集同种谓词内最优方法也随 query 而变。于是提出 query-aware 路由框架：用轻量 ML 模型预测每个候选方法在该 query 上的 recall，再查离线 benchmark 表（每个方法+参数到实测 recall/QPS 的映射）选 recall-QPS 权衡最好的方法。消融把 22 个候选特征收敛到 3 个，并用回归而非分类作为预测目标。在 6 个训练数据集训练、5 个未见验证集上取得 SOTA 的 recall-QPS 平衡，路由开销可忽略。

Key insight: 没有一个过滤 ANN 方法通吃、连同库同谓词都因 query 而异，这个实测结论本身就值得记——别迷信单一索引方案。query-aware 路由把方法选择变成一个三特征的轻量回归预测问题，对带属性过滤的社区搜索（按时间/板块/标签过滤再做向量召回）很实用：可以在线根据 query 特征动态切换召回策略而非固定一条；回归优于分类作为路由目标这点也能直接复用。

5. When Global Gating Is Enough: Admission-Time Hubness Control in Anisotropic Vector Retrieval Systems
3.50
Relevance 2 | Novelty 4 | Practical 4 | Evidence 4 | Timely 5

Summary: 论文研究向量 hubness（少数点成为大量 query 的最近邻）带来的 RAG 投毒风险——一个注入文档可能影响无关请求。现有防御靠周期性 reverse-kNN 扫描，存在暴露窗口且要反复全库计算。论文提出 admission-time 控制：在文档入库前用 sentinel queries 给候选打分、隔离类 hub 文档。在两个 10 万文档语料、五种编码器、攻防 query 不相交的设置下，全局 gate 在 embedding 空间关键点达到 recall 1.0、HotFlip 攻击下 0.91±0.07、通用文档 1% 误报；per-topic gate 无可靠收益。HNSW 上入库延迟仅增约 3.1%，打分到 10^6 向量仍平坦。

Key insight: 把 hubness 防御从周期性全库扫描前移到入库准入打分是关键设计，省掉暴露窗口和重复全库计算；各向异性导致 per-topic gate 没用、全局 gate 就够这个发现也反直觉。对运行 RAG/向量召回的社区搜索系统，这套 admission-time gating 给出了低开销（+3.1% 入库延迟）的鲁棒性方案，可借鉴用于 UGC 内容入库时过滤异常 hub 文档，防止个别内容污染大量无关 query 的召回结果。

6. MonaVec: A Training-Free Embedded Vector Search Kernel for Edge and Offline AI Systems
3.25
Relevance 2 | Novelty 4 | Practical 3 | Evidence 4 | Timely 5

Summary: MonaVec 是面向边缘/离线 AI 的确定性嵌入式向量检索内核——目标场景没有服务器、网络、训练数据，部署形态对标 SQLite（单文件、单函数调用）。其量化核心默认免训练且数据无关：用 Randomized Hadamard Transform（RHDH）把任意输入分布调向 N(0,1)，再用预计算的 Lloyd-Max 表量化到 4 bit（8x 压缩），无需学习码本、无需数据扫描。索引落成单个 .mvec 文件，内嵌 ChaCha20 旋转种子保证跨架构可复现、同构建字节级一致。在 AG News（45K×1024 维 BGE-M3，cosine）上 4-bit BruteForce 达 0.960 Recall@10、仅 27MB，召回超过 float32 FAISS-IVF 和 8-bit usearch；可选 IvfFlat/HNSW 后端支撑百万级语料，纯 Rust 实现带 Python 绑定。

Key insight: 免训练、数据无关的 4-bit 量化（RHDH 把分布调成高斯 + 固定 Lloyd-Max 表）是这篇最可借鉴的技术点——不用过库训练码本就拿到 8x 压缩且 0.960 Recall@10，比需要数据 pass 的方案省事。虽主打边缘/离线场景，但先 Hadamard 旋转再固定表量化的思路，对服务端向量检索的低成本压缩同样有参考价值；字节级确定性复现对需要可审计/可回归的检索系统也是个加分项。
