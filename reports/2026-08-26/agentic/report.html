1. Enrich-Retrieve-Rank: Scaling Capability Discovery Beyond In-Context Routing
4.85
Relevance 5 | Novelty 4 | Practical 5 | Evidence 5 | Timely 5

Summary: 论文把 Agent 生态中的能力发现重构为检索问题：先离线补全模型、Agent、工具和技能的可搜索画像，再在线执行 retrieve-then-rank，而不是把整个注册表塞进上下文。在能力规模从 10 增至 7,278 时，in-context routing 的 Match@1 从 0.85 降至 0.12，检索排序仍为 0.81 至 0.39；满规模时比 Search&Pick 高 6.5 个百分点、成本约低一半，并比 Full-Ctx 低 70 倍。

Key insight: 社区搜索 Agent 不应直接把所有工具和检索能力暴露给模型选择。可以把工具描述、输入输出和历史成功轨迹离线结构化，线上用轻量召回与重排先缩小候选空间，再交给 Agent 规划；这既减轻上下文压力，也让工具路由可以用 Match@1、调用成本和失败率持续优化。

2. Prompt-Based Abstention Fails Under Misleading Context: A Controlled Study of Small Frozen RAG Models
4.70
Relevance 5 | Novelty 4 | Practical 4 | Evidence 5 | Timely 5

Summary: 论文提出 GRAB-RAG，使用 Natural Questions 和 HotpotQA，把上下文分成支持、退化、缺失和误导四种条件，测试 3.8B–8B 冻结模型的 5 种拒答策略。模型面对缺失证据时能拒答，但面对误导证据仍有 41.6% 的问题直接作答，其中 63% 原样复述被植入的错误实体；生成侧冲突检查可将错误率降到 13.3%，代价是丢失大量正确答案。

Key insight: RAG 的安全闸门不能只问“证据够不够”，还要问“证据是否可信且彼此一致”。对 UGC 搜索 Agent，应把检索结果的来源质量、实体一致性和多证据冲突作为独立特征，在线记录误导样本；单靠 prompt 拒答或一次 NLI 校验，无法覆盖模型记忆与错误文档共同指向同一答案的情况。

3. Training a Knowledge Base: Supervised Structure Learning for Agent-Curated Document Stores
4.55
Relevance 5 | Novelty 4 | Practical 4 | Evidence 5 | Timely 5

Summary: 论文把知识库从静态文档集合改成可训练的结构：训练 Agent 根据带标准答案的问题编辑文档关系，读者 Agent 在固定动作预算下使用冻结快照回答。相对覆盖全部实体的无监督索引，它用 1,913 条链接对比 196,112 条链接，单位语料动作节省提高 1.6 倍、准确率提高 1.8 倍；训练过的问题动作数减少 31%，双 key 覆盖时未见问题 F1 还提升 0.167。

Key insight: 对社区搜索，可把高价值 query、人工审核答案和点击反馈用于训练知识结构，而不只更新向量索引。论文显示结构学习的泛化取决于 query key 覆盖度，因此应优先覆盖长尾实体、别名和跨帖子关系，并把结构编辑轨迹纳入离线评估，避免只用随机 train/test 切分掩盖知识库的过拟合。

4. Risk-Aware Reranking for Agentic Tool Retrieval
4.45
Relevance 5 | Novelty 4 | Practical 4 | Evidence 3 | Timely 5

Summary: 论文指出工具检索本身就是 Agent 的执行前安全边界：相关工具可能带来不必要的高风险动作。方法在冻结的首阶段检索器上增加轻量重排，分别建模 query 条件相关性与工具暴露风险，用显式参数控制安全—效用权衡，并通过 ToolGraph 平滑分数；作者在 UltraTool 和 Seal-Tools 的 6,108 个工具上做了 5 级风险标注，结果显示相较只看相关性的重排器能改善风险—相关性折中。

Key insight: 搜索 Agent 的候选召回不只是 nDCG 问题，还决定模型能否看到会写库、发帖或调用外部 API 的工具。工程上可沿用现有召回器，只在末端加入风险分数、工具关系图和规则过滤，并为不同业务设置安全—覆盖率旋钮；这样比等到工具执行后再拦截更容易审计和回滚。

5. Better Retrieval, Worse Robustness:How Multi-hop RAG Amplifies Upstream ASR Errors
4.40
Relevance 4 | Novelty 4 | Practical 4 | Evidence 5 | Timely 5

Summary: 论文研究语音查询中的上游 ASR 错误是否会被多跳 RAG 修复，比较实体图链接、迭代改写和朴素稠密检索在 HotpotQA、2WikiMultiHopQA、MuSiQue 三个数据集上的表现。结构更丰富的方案绝对 F1 更高，但在最高 WER 口音上，组合方案相对干净文本的 F1 缺口反而扩大 36%–67%；87%–96% 的损失来自查询实体被识别错误。

Key insight: 多轮改写不会自动消除 query 理解错误，错误实体会在每一跳被放大。社区短文本搜索接入语音或口语 query 时，应先做实体候选校正和置信度分流，再决定是否启动 Agentic RAG；评测必须同时报告干净文本、真实 ASR 和不同口音条件，避免只看理想输入下的多跳收益。

6. Which RAG Paradigm Wins at Scale? A Scaling Study of Retrieval-Augmented Generation Paradigms
4.15
Relevance 4 | Novelty 4 | Practical 4 | Evidence 4 | Timely 3

Summary: 论文用规模化实验比较词法、稠密、图结构和 Agentic RAG 在不同语料规模下的效果与成本。文件系统 Agent 在小规模上可接近 BM25，但在最大规模每次回答消耗约 39 倍 query token，最终落后近 20 个点；图 RAG 的构建开销最高可达每个语料 token 生成 24.6 个 token，并在覆盖约 2% 语料后停止扩展。

Key insight: Agentic 检索的优势取决于问题是否需要组合证据，而不是“更智能”就能替代基础检索。社区搜索可以采用固定检索作为默认路径，仅在 query 预测为多跳、长尾或需要跨源核验时升级到 Agent Loop，并把 token、延迟和语料覆盖率一起纳入路由阈值。

7. LongWoF-Bench: Evaluating EvoMap Genes for Verifiable Long-Workflow Tasks
4.00
Relevance 3 | Novelty 4 | Practical 4 | Evidence 5 | Timely 5

Summary: LongWoF-Bench 评估 Agent 是否能复用经验证的长工作流经验：EvoMap 将通过验证器确认的执行轨迹固化为结构化 Gene，再供后续模型调用。基准包含代码、环境构建、数学推理和规则遵循等 778 个可机器验证任务；在有 Opus 验证轨迹的 252 个任务上，Gene 在 7 个模型上都比 Skill 高 8.7–15.5 个百分点，且跨模型家族仍有效。

Key insight: 社区搜索 Agent 的失败修复不应只留在 prompt 或一次会话里。可以把成功的 query 分解、证据校验、回退路径和停止条件沉淀为带验证器的技能单元，再按任务类型检索复用；关键是保存可执行轨迹和验证结果，而不是把未经检查的思维链直接写入长期记忆。

8. MobilePA-Bench: Benchmarking Mobile Planner Agents on Complex Real-World Tasks
3.85
Relevance 3 | Novelty 4 | Practical 4 | Evidence 4 | Timely 5

Summary: MobilePA-Bench 针对移动端 Planner Agent 的真实工具调用和长程规划，避免只测界面点击或离线函数匹配。它在可执行沙盒中维护实时应用数据库，覆盖 13 个功能域和 212 个移动工具，并从子 Agent 协作、任务规划和环境反馈等维度检验 Agent 是否能在状态变化中完成目标。

9. Apodex 1.1: Scaling Agentic Intelligence for Complex Work
3.75
Relevance 3 | Novelty 4 | Practical 3 | Evidence 4 | Timely 5

Summary: Apodex 1.1 将复杂工作能力拆成环境扩展和 Agent 协同扩展：前者增加可执行、可验证的文件、搜索和代码环境，后者训练 Agent 分解长任务、并行委派、合并异步结果并重新规划。系统用共享执行框架和 AgentOS 保存任务状态与 provenance，再把环境轨迹和协同轨迹用于训练，覆盖金融、科研、数学、编码和搜索等任务。

10. Agent RAG architecture: components, control loop, and tradeoffs
3.70
Relevance 4 | Novelty 3 | Practical 4 | Evidence 2 | Timely 5

Summary: 这篇工程分析把 Agent RAG 定义为围绕检索的有界控制循环：Agent 可以决定是否检索、选择允许的数据源、改写 query、检查证据并继续检索或生成答案。文章强调生产系统必须显式管理状态、权限、证据 provenance、迭代和成本预算、全链路 trace、确定性回退与停止条件，并提醒固定单索引问题不应强行 Agent 化。

Key insight: 落地社区搜索 Agent 时，控制边界比增加 Agent 数量更重要。建议先给检索工具定义清晰 schema 和权限，再用最大步数、token 预算与证据充分性门控限制循环；对简单 query 保留固定 RAG，对跨源、多跳问题才启用 Agent，并把每次回边原因记录到 trace 便于诊断。
