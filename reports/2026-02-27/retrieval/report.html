深度解读：Semantic Search At LinkedIn

论文信息: Semantic Search At LinkedIn | arXiv:2602.07309 | 74 位作者 (LinkedIn) | 2026.02

1. 问题与动机

LinkedIn 面临的核心挑战是：如何在生产级搜索系统中真正落地 LLM 的语义理解能力，同时满足严苛的延迟和吞吐约束。

具体来说，存在三重矛盾：

  1. 语义鸿沟 vs. 关键词匹配：传统搜索依赖 term-matching，无法理解 "software engineer" 与 "full-stack developer" 的语义等价性。LinkedIn 的职位搜索和人才搜索场景中，query 和 document 之间的语义差距尤其显著（职位描述冗长、用户 profile 结构化程度不一）。
  1. 相关性 vs. 用户参与度：搜索不仅要返回语义相关的结果，还要优化点击、申请等 engagement 指标。这两个目标往往存在冲突——高相关但用户不感兴趣的结果没有商业价值。
  1. 模型能力 vs. 服务成本：8B 参数的 LLM 作为 relevance judge 效果极好，但无法直接上线服务数十万 QPS 的流量。此前业界没有成功案例证明 LLM 排序可以在效率上与传统特征工程方案（如 LinkedIn 自家的 LiRank）相媲美。

这篇论文的野心在于：不是做一个 demo 或离线评估，而是构建首个效率可比传统方案的生产级 LLM 排序系统，并在 LinkedIn 的 Job Search 和 People Search 两大核心场景全面上线。

2. 方法概述

整体框架是一个 两阶段架构：GPU 加速的语义召回 + SLM（Small Language Model）精排，核心思路是 "大模型生产知识、小模型上线服务"。

召回阶段：Embedding-based Retrieval + GPU RAR

  • 使用双塔模型做语义向量检索
  • 创新性地提出 GPU RAR（Retrieval-as-Ranking）：不再用纯 cosine similarity，而是学习一个加权打分函数 S(q,d) = w₀⟨e_q, e_d⟩ + Σwᵢfᵢ(q,d)，在召回阶段就联合优化相关性和参与度

精排阶段：三阶段 SLM 训练流水线

Stage 1 — 相关性训练：用 8B LLM 作为 oracle judge 生成 0-4 的相关性标签，训练学生 SLM（~600M），采用 soft-label 分布匹配而非 hard ordinal label

Stage 2 — 多教师蒸馏（MTD）：独立训练相关性教师和参与度教师，通过加权 KL 散度损失将两个教师的知识蒸馏到同一个学生模型，学生从 Stage 1 的相关性 SLM 热启动

Stage 3 — 特征工程：用 1.7B RL 模型压缩 member profile，将冗长职位描述压缩一个数量级，数值特征编码为描述性文本 + Boolean 标识

推理优化：模型-基础设施协同设计

  • 结构化剪枝（50% MLP + 移除末尾 8 层 transformer）
  • Text-Embedding 混合架构（MixLM）：用 encoder 将 item 压缩为 embedding token 并离线缓存
  • Prefill-only 推理 + 共享前缀摊销 + CUDA Graph 优化

3. 核心技术贡献

贡献一：Soft-Label 多教师蒸馏框架

这是方法论层面最重要的创新。关键区别在于：

  • 软标签 vs. 硬标签：传统做法是让 LLM 输出一个 ordinal label（如 "相关性=3"），学生模型学这个离散标签。LinkedIn 的方案是保留 LLM 输出的完整概率分布作为监督信号。效果差异巨大：soft-label 的 NDCG@10 为 0.8420，hard ordinal label 仅 0.7583（+11.0%）。这说明教师的不确定性信息本身就是极有价值的监督信号。
  • Relevance-aware warm-start：多教师蒸馏时，先用相关性 SLM 初始化学生，再联合蒸馏。这比从头训练多获得 +0.68% NDCG@10 和 +1.98% Click AUROC。直觉是：相关性是基础能力，在此基础上叠加 engagement 比两者从头学更容易。
  • Imbalance-aware loss masking：针对相关性和参与度标签分布不平衡的问题，设计了动态 loss mask 机制。

贡献二：MixLM — Text-Embedding 混合交互架构

这是推理效率的关键突破：

  • 核心思想：用 encoder 将 item 侧文本离线压缩为若干 learned embedding tokens，缓存在 nearline 存储中
  • 在线推理时，query 侧保留原始文本，item 侧直接用缓存的 embedding tokens，上下文长度降低数个数量级
  • 实现 ~76× 吞吐提升（相比 raw-text SLM），同时保持接近的 NDCG
  • 本质上是在 双塔模型的效率 和 cross-encoder 的效果 之间找到了一个新的帕累托最优点

贡献三：Scoring-Optimized 推理栈

不是通用 LLM serving，而是为排序任务定制的推理架构：

  • Prefill-only execution：排序只需要一次前向传播得到 score，无需自回归生成，跳过 decode/sampling 开销（+44% 吞吐）
  • Shared-prefix amortization：batch 内所有 item 共享 query prefix 的 KV cache，只计算一次（+25% 吞吐）
  • CUDA Graph + 批量 tokenization + 多进程 gRPC：绕过 Python GIL，端到端优化

这些优化层层叠加，从 750 items/s/GPU 提升到 2,200 items/s/GPU（纯文本），MixLM 变体达到 ~22,000 items/s/GPU。

贡献四：Query-Centric 召回训练

  • Policy-bucketed sampling：按语义类别和质量差距分桶采样，让训练分布对齐生产失败模式
  • 对比学习 + pairwise margin loss 联合优化：InfoNCE + margin loss 互补

5. 局限与未来方向

当前局限

  1. 依赖高质量 LLM Judge：整个框架的上限由 8B oracle LLM 的相关性判断质量决定。如果 judge 存在系统性偏差（如对某些领域/语言理解不足），bias 会通过蒸馏传播到线上模型。
  1. MixLM 的信息瓶颈：将 item 侧压缩为固定数量的 embedding tokens，必然丢失细粒度信息。对于需要 fine-grained matching 的长查询场景（如复杂技能匹配），可能存在天花板。
  1. 冷启动与长尾问题：论文主要展示了 Job Search 和 People Search 的主流场景，对于长尾 query（如极小众职位、新兴技能）的效果未充分讨论。
  1. 训练成本：多教师蒸馏框架需要分别训练 8B judge、相关性教师、engagement 教师、最终学生模型，整体训练 pipeline 复杂且资源消耗大（尽管论文提到 GPU optimization agent 节省了 256 GPU-hours）。
  1. 个性化深度有限：当前框架主要是 query-document matching，对用户长期偏好、行为序列的建模深度可能不如专门的推荐模型。

未来方向

  • 论文明确提到：更深度的个性化（利用扩展的用户上下文）、自适应/选择性计算（对简单 query 用轻量模型，复杂 query 用重模型）
  • 我的判断：

- 端到端 Retrieval-to-Ranking 联合训练：当前召回和精排是独立训练的，联合优化可能进一步提升
- 在线 LLM Judge 持续迭代：随着更强的开源/闭源模型出现，teacher 可以持续升级
- 多模态扩展：LinkedIn 有丰富的非文本信号（技能图谱、社交网络、公司关系），融合这些信号到 SLM 框架中是自然的下一步

6. 工业实践意义

这篇论文的工业价值极高，是 LLM 落地搜索排序的完整蓝图，以下几点对从业者最有参考意义：

6.1 "大模型做标注、小模型做服务" 的范式验证

这已经不是一个理论假设，而是在 LinkedIn 数十万 QPS 下被验证的生产方案。核心启示：

  • 不要试图直接上线大模型做排序，而是把大模型当成最好的数据标注器
  • Soft-label 蒸馏远优于 hard-label（+11% NDCG），这对所有做 LLM-to-production 蒸馏的团队都是重要经验

6.2 推理优化的可复制路线图

Table 12 提供的逐层优化分解极具参考价值：

  • Prefill-only 对所有"打分"类任务（排序、CTR 预估）都适用，跳过 decode 是最大的单点收益
  • Shared-prefix 在 batch ranking 场景中几乎是免费的优化
  • MixLM 思路（离线压缩 item 为 embedding + 在线只处理 query 文本）可以推广到所有 query-document matching 场景

6.3 多目标联合优化的实践方案

LinkedIn 的多教师蒸馏框架解决了一个普遍痛点：如何同时优化相关性和 engagement。关键 takeaway：

  • 先学相关性、再叠加 engagement 比联合从头学更好（warm-start 策略）
  • 独立训练各目标教师 → 蒸馏到统一学生，比直接多任务训练更灵活（可以独立迭代各教师）

LinkedIn 这篇论文证明了：LLM 排序已经从"能不能做"进入了"怎么做得又好又快"的阶段。通过模型-基础设施协同设计，LLM 排序的服务成本已经可以与传统特征工程方案相媲美，这对整个搜索/推荐行业是一个重要的拐点信号。

MAAQR: 基于 LLM 的多智能体自适应 Query 改写框架 — 深度解读

论文信息: MAAQR: An LLM-based Multi-Agent Framework for Adaptive Query Rewriting in Alipay Search, SIGIR 2025 (Industry Track, pp. 4289-4293), Zheng Q, Zhong M, Gong S, Jiang H, Wu K, Liu H, Xu J, Mo L (蚂蚁集团/支付宝)

1. 问题与动机

核心问题: 支付宝小程序搜索中的 Query 改写（Query Rewriting）。

支付宝作为超级 App，其小程序搜索面临独特挑战：

  • 词汇鸿沟（Lexical Gap）: 用户搜索词与小程序名称/描述之间存在严重的语义不匹配。例如用户搜"交电费"但小程序名称可能是"XX生活缴费"，搜"驾照"对应的可能是"交管12123"。
  • 领域知识理解不足: 现有 LLM 对支付宝生态内的 query-item 语义关系缺乏充分理解。通用大模型不了解"蚂蚁森林"是什么、"花呗"能做什么，这类领域知识需要额外注入。
  • 缺乏自适应机制: 小程序生态快速演变（新小程序不断上线、服务内容持续变化），传统的静态改写规则或一次性训练的模型无法应对新的或变化中的 query-item 关系。
  • 零结果率（ZRR）问题: 长尾 query 和新兴 query 容易命中零结果，直接影响用户体验和商业转化。

为什么重要: 小程序搜索是支付宝的核心流量入口之一，搜索质量直接影响用户使用小程序的效率和 GMV。零结果意味着用户流失，而不精确的改写会导致用户看到不相关结果同样影响体验。Query 改写作为搜索召回的前置环节，其质量对整个搜索链路有乘数效应。

2. 方法概述

MAAQR 提出了一个两阶段的框架：

阶段一：知识增强微调（Knowledge-Enhanced Fine-Tuning）

对 LLM 进行领域知识注入式的微调，提升模型对支付宝搜索场景中 query 和 item（小程序）语义的理解能力。根据同团队在 SIGIR 2024 发表的 LLMGR 工作以及业界类似实践（如淘宝搜索 BEQUE）推断，这一阶段可能包括：

  • 利用用户搜索点击/交易日志构建 query-小程序 对齐数据
  • 将小程序的名称、功能描述、类目等结构化知识融入训练数据
  • 通过 SFT（监督微调）让 LLM 学会 query 到小程序名称的语义映射关系

阶段二：多智能体协作改写架构（Multi-Agent Collaborative Rewriting）

不同于单一 LLM 直接生成改写结果，MAAQR 设计了多个 Agent 协作完成改写任务。基于论文标题中"Adaptive"和"Multi-Agent"的关键词，以及搜索结果中提到的 rewrite generator、verifier 等角色，该架构的核心思路是：

  • 分工协作: 不同 Agent 各司其职（如 query 分类/路由 Agent、改写生成 Agent、改写验证 Agent），通过协调机制完成端到端的改写流程
  • 自适应改写: 根据 query 的类型和特征，动态选择不同的改写策略，而非对所有 query 采用统一策略
  • 质量保障: 通过验证 Agent 对改写结果进行质量把关，避免低质量改写流入下游

3. 核心技术贡献

贡献一：知识增强式 LLM 微调

区别于直接使用通用 LLM 做 prompt-based 改写，MAAQR 通过知识增强微调将领域特定的 query-item 语义关系注入到模型参数中。这解决了两个关键问题：

  • 通用 LLM 不理解支付宝生态的"黑话"（如特定小程序名称、服务术语）
  • 纯 prompt 方式无法有效编码大量 query-item 映射知识

贡献二：多 Agent 协作架构（vs. 单一 LLM 改写）

这是本文最核心的创新点。与现有方法的关键区别：

对比维度传统方法 / 单 LLMMAAQR 多 Agent
改写策略统一策略处理所有 query按 query 类型自适应分发
质量控制无或依赖后置过滤Agent 间内置验证环节
可扩展性新场景需重训模型新增/调整 Agent 即可
错误传播单点失败影响全局Agent 间互相校验纠错

这种架构设计类似于 DMQR-RAG 提出的"不同 query 适合不同改写策略"的思想，但 MAAQR 通过 Agent 化的方式实现了更灵活的策略调度，而非简单的策略选择器。

贡献三：工业级部署验证

论文不仅是学术探索，而是已在支付宝小程序搜索线上部署（自 2024 年 12 月起），并通过 A/B 测试验证了效果，这为多 Agent LLM 系统在搜索场景的可行性提供了重要的工业证据。

4. 实验结果分析

根据公开信息，MAAQR 通过离线实验 + 在线 A/B 测试两个维度验证了效果：

核心指标提升

  • CTR（点击率）: 显著提升（"significantly improves"）
  • 交易量: 目标 query 的交易笔数显著增加
  • 零结果率（ZRR）: 大幅降低（"substantially reducing"）

注: 具体数值在 ACM 付费论文中，公开摘要未披露精确百分比。参考同类工作的量级：淘宝搜索 BEQUE 的 LLM query 改写在 GMV 上提升了 0.4%、订单提升 0.34%；MiniELM 在商品覆盖上提升了 54.1%。MAAQR 在小程序搜索这一相对较小的 item 库场景下，改写对 ZRR 的影响可能更为显著。

结果分析

ZRR 的大幅降低是最值得关注的指标。小程序搜索的 item 库规模远小于电商商品库，因此 query 与 item 的匹配成功率更加脆弱——一个 query 改写不当就可能导致零结果。多 Agent 协作改写通过以下机制降低了 ZRR：

  • 分类 Agent 识别出容易产生零结果的 query 类型（如长尾、口语化、新兴 query），交由专门的 Agent 处理
  • 验证 Agent 在改写结果提交前检查其是否能匹配到有效结果
  • 多策略并行尝试，提升了至少有一个有效改写的概率

5. 局限与未来方向

现有局限

  1. 推理延迟: 多 Agent 协作不可避免地引入额外延迟。搜索场景对延迟极其敏感（通常要求 <100ms），多个 Agent 串行调用 LLM 可能需要特殊的工程优化（如 Agent 并行化、模型蒸馏、缓存等）。作为 5 页的短文（pp. 4289-4293），论文可能未充分讨论延迟优化。
  1. Agent 间协调成本: Agent 数量增加带来通信和协调的复杂性。如何在 Agent 分工细粒度与系统复杂度之间取得平衡是一个开放问题。
  1. 知识更新时效: 虽然强调了"自适应"，但知识增强微调是离线过程。新上线的小程序需要等到下一轮微调才能被模型理解，实时性可能不足。
  1. 泛化性: 该框架针对支付宝小程序搜索设计，其 Agent 分工和知识增强策略是否能直接迁移到其他垂直搜索场景（如电商、内容社区）需要进一步验证。

未来方向

  • 在线强化学习: 借鉴 RL-QR 的可验证搜索奖励思路，将线上真实反馈接入 Agent 系统实现持续进化
  • 轻量化部署: 将多 Agent 协作的知识蒸馏到单一小模型中（参考 MiniELM 的知识蒸馏思路），在保持效果的同时降低推理成本
  • 动态 Agent 编排: 根据系统负载和 query 难度动态决定 Agent 参与数量和协作深度，简单 query 走快速通道，复杂 query 走完整流程

6. 工业实践意义

对搜索系统的借鉴

  1. 多 Agent 架构是 LLM 改写的工程最优解：单一 LLM 直接改写存在"一刀切"问题——同一个 prompt/模型很难同时处理好头部高频 query 和长尾 query。MAAQR 证明了通过 Agent 分工可以更好地适配不同 query 类型，这对所有面临 query 分布长尾效应的搜索系统都有参考价值。
  1. 知识增强微调 > 纯 Prompt Engineering：在垂直领域搜索中，领域知识（query-item 映射、类目体系、业务术语）是改写质量的关键。单纯依赖 prompt 注入有限的 few-shot 样例不够，需要通过微调将大量领域知识编码到模型中。
  1. 验证环节不可或缺：MAAQR 的多 Agent 架构中包含验证 Agent，这在工业系统中至关重要。LLM 改写可能产生幻觉（生成不存在的 item 名称或不合理的改写），验证环节可以在改写上线前进行兜底。

对推荐/广告系统的借鉴

  1. 小 item 库场景的 query 理解更关键：不同于电商的海量 SKU，小程序/广告的 item 库规模有限，query 理解和改写的精度直接决定用户能否找到目标。这种场景下，宁可少改不要错改，验证 Agent 的价值被放大。
  1. 多 Agent 范式可推广到其他搜索子任务：同团队在 SIGIR 2025 的另一篇论文中将类似思路应用于生成式检索的幻觉消除（使用 Decision Agent 进行后处理），说明多 Agent 模式可以系统性地应用于搜索链路的各个环节——query 理解、召回、排序、结果筛选。
  1. 渐进式 LLM 落地路径：MAAQR 展示了一条务实的 LLM 搜索落地路径：先用知识增强 SFT 打好基础模型，再用多 Agent 架构解决多样化的 query 改写需求，最后通过在线 A/B 验证效果。这种"SFT → Agent → 线上验证"的三步走策略，比一步到位的端到端方案更可控。

总结: MAAQR 最重要的贡献不在于某个单点技术创新，而在于提出了一套可落地的 LLM 多 Agent 搜索改写框架，并在支付宝这一亿级流量的工业系统中验证了其有效性。其"知识增强微调 + 多 Agent 协作"的双轮驱动架构，为搜索/推荐系统引入 LLM 提供了一个务实而有效的参考范式。

系统评估了经典文本排序方法在 Deep Research 场景下的表现，揭示了检索单元、pipeline 配置和 query 特性三个维度的关键发现。

1. 问题与动机

这篇论文讨论的不是“deep research agent 是否能搜索”，而是更底层的一个问题：当 agent 依赖搜索来完成多跳、开放域、证据密集的问题时，底层文本排序方法到底贡献了什么。现有 deep research 系统通常把搜索当成黑盒 API，agent 只看到搜索返回的网页或片段，很难判断失败来自推理、查询生成、检索召回、重排，还是上下文窗口截断。作者指出，这种黑盒化会遮蔽 IR 社区长期积累的检索单元、BM25 参数、稀疏/稠密召回、重排深度等设计经验。

动机里最关键的 gap 有三个。第一，deep research 常把网页当完整 document 返回，但网页平均长度很长，论文实验设置中返回文档会被截断到前 512 tokens；对于 130K context 的 gpt-oss-20b，若平均网页约 8K tokens，也只能容纳十几篇完整网页，因此 document-level retrieval 很容易发生信息丢失。第二，传统搜索中的重排已被证明有效，但 deep research 的“读者”是 LLM agent 而不是人，重排是否仍然提升最终 answer accuracy 并不清楚。第三，agent 生成的查询往往是 web-search-style 的关键词、短语、引号精确匹配，而许多神经检索器和重排器是在 MS MARCO 风格自然语言问题上训练的，训练-推理查询格式错配可能严重影响效果。

2. 方法详解

作者把 deep research text ranking 明确定义成 agent 的每一次 search invocation：agent 在某一轮 reasoning 后生成 search query，排序系统返回 top-ranked texts，这些 texts 再进入下一轮 reasoning。实验围绕 BrowseComp-Plus 进行，该数据集提供固定文档语料和人工验证相关性判断。因为原始数据只有 document-level corpus，作者额外构造 passage corpus，从而能比较“返回完整/截断网页”与“返回段落片段”两种检索单元。

实验使用两个本地部署 agent：gpt-oss-20b 和 GLM-4.7-Flash。gpt-oss-20b 的最大上下文窗口是 131,072 tokens，GLM-4.7-Flash 约 202,752 tokens；两者最大输出长度都设为 40,000 tokens，最大迭代次数设为 100，并用 vLLM 0.15 部署。每次 search call 返回 top-5 文档或段落，文档返回时截断到前 512 tokens，以避免网页过长耗尽 context。passage retrieval 的评估用 Max-P 策略，把命中的 passage 分数映射回 document，因为 BrowseComp-Plus 的相关性标注是 document-level。

检索器覆盖四类代表方法：BM25 作为 lexical sparse baseline；SPLADE-v3 作为 learned sparse retriever；RepLLaMA 和 Qwen3-Embed-8B 作为 single-vector dense retriever；ColBERTv2 作为 multi-vector late-interaction retriever。重排器选择三个效率-效果点：monoT5-3B，RankLLaMA-7B，以及带显式 CoT reasoning 的 Rank1-7B。monoT5 的 relevance score 来自输出 “true” token 的概率；Rank1 会生成推理 token 后再给 relevance 判断。实现上，BM25 用 Pyserini 默认参数，SPLADE/RepLLaMA/RankLLaMA/Qwen3-Embed 用 Tevatron，ColBERTv2 用 PyLate，monoT5 用 PyTerrier_t5。

为处理查询格式错配，作者提出 Query-to-Question, Q2Q。它把 agent 发出的关键词式搜索查询改写成自然语言问题，分两种：Q 只用原始 search query；Q+R 同时加入 agent 最近的 reasoning trace。例如原始查询 "61,880" football attendance，Q+R 会改写成“哪场足球比赛的 attendance 是 61,880”，比只看 query 更能恢复真实搜索意图。Q2Q 用 gpt-oss-20b 低 reasoning-effort 模式实现，并用 TREC-DL 2019 中抽样的自然语言问题作为 few-shot 示例。

3. 核心技术贡献

第一，论文把 deep research 的搜索问题拆成可复现实验，而不是只比较 end-to-end agent。它同时控制检索单元、retriever 类型、reranker 类型、rerank depth、agent 模型和 query format，能判断“搜索组件”对最终 accuracy 的影响。这比黑盒搜索 API 更接近工业搜索链路调优方式。

第二，论文证明 passage-level retrieval 在 deep research 中不是简单的 chunking trick，而是缓解 context budget 与 document length normalization 的关键设计。gpt-oss-20b 在 passage corpus 上用 BM25 达到 0.616 recall 和 0.572 accuracy，而 document corpus 上默认 BM25 只有 0.366 recall 和 0.259 accuracy。作者进一步说明，document-level BM25 对长度归一化参数敏感，截断到 512 tokens 或调大长度惩罚都能显著改善。

第三，论文重新校准了“更大的 dense retriever 一定更好”的直觉。单向量 RepLLaMA 和 Qwen3-Embed-8B 虽然参数更大，但在 agent 关键词式查询上经常不如 SPLADE-v3 和 ColBERTv2。原因是 learned sparse 和 late interaction 对关键词、短语、精确匹配更友好，而 single-vector dense 表示在新任务和新查询格式上容量受限。

第四，论文给出了 Q2Q 的边界：Q2Q+reasoning trace 对神经检索器和 reasoning reranker 有帮助，但对 BM25 可能伤害效果。也就是说，查询改写不是一律改成自然语言，而要看下游 ranker 的训练分布和匹配机制。

最强结果来自 gpt-oss-20b + BM25 passage + monoT5-3B depth 50：recall 0.716，accuracy 0.689，平均 search calls 27.57。相比无重排 BM25 passage，recall 相对提升 16.23%，accuracy 相对提升 20.45%，search calls 下降 10.98%。这个结果很有冲击力，因为它只用 20B agent、BM25 和 3B reranker，就接近论文引用的 GPT-5 agent accuracy 0.701。

消融里最重要的是三个结论。第一，retrieval unit 非常关键。document corpus 默认 BM25 因长度归一化和截断问题表现很差；只索引前 512 tokens 使 recall 从 0.366 到 0.642，accuracy 从 0.259 到 0.513，分别是 64.2% 和 98.1% 相对提升。第二，rerank depth 越深通常越好：BM25-monoT5 从 depth 10 到 20，recall/accuracy 分别增加 6.21%/6.81%，search calls 减少 3.11%；从 20 到 50 又带来 2.14%/2.23% 增益，并减少 4.80% search calls。第三，显式 reasoning reranker 不一定更好。Rank1 有失败案例：它把独立关键词 “radiation” 和 “protein” 错当成一个语义单元，给无关 passage 打出 0.999 高分，说明 reasoning 可能误读关键词式查询。

Q2Q 的结果也很细。对 SPLADE-v3，Q2Q(Q+R) 相比 raw query recall 从 0.545 到 0.585，accuracy 从 0.516 到 0.557，相对提升 7.34% 和 7.95%。对 Qwen3-Embed-8B，accuracy 从 0.417 到 0.459。对 Rank1 reranker，Q2Q(Q+R) 也把 recall/accuracy 从 0.617/0.580 提到 0.638/0.613。但 BM25 上 Q2Q 不增反降，说明原始 keyword-style query 本来就适合 lexical retrieval。

5. 局限与未来方向

作者明确限制了研究范围：实验只考察 text ranking 在 deep research 中的作用，没有扩展到更多 agent 模型规模，也没有研究所有可能的 LLM search/reasoning 策略。GLM-4.7-Flash 的实验因 GPU 资源限制排除了 Qwen3-Embed-8B、Rank1 和部分重排深度；这意味着不同 agent、不同上下文长度和不同 search policy 下的结论仍需要复验。

另一个局限是 BM25 参数调优使用了 BrowseComp-Plus 全量查询，因为没有独立 validation set。作者也提醒，调参后的 BM25 不能和其他模型做完全公平的泛化比较。对工业落地来说，这点尤其重要：如果用线上查询日志调 BM25/RRF/rerank depth，必须保留时间切分或业务分桶验证，否则很容易过拟合某批 query。

作者未来方向集中在更系统地理解 deep research 中的 ranking 行为，包括 agent-issued query 与 ranker training query 的错配、passage/document 粒度选择，以及不同 re-ranker 对最终答案质量的贡献。论文没有深入讨论线上延迟、成本、索引更新和缓存，这些是工业搜索必须补上的部分。

6. 工业实践意义

对搜索/推荐从业者，最大启发是不要把 LLM search agent 的底层检索简单等同于“换成最大 embedding 模型”。在 deep research 这类多轮搜索中，agent 查询常常像真实用户搜索一样短、碎、包含引号、数字和实体名。BM25、SPLADE、ColBERT 这种保留词面匹配能力的检索器，在这种查询分布上可能比更大的 single-vector dense 模型更稳。

对社区 UGC 短文本搜索，可以直接落地三条策略。第一，召回层保留 lexical + learned sparse + dense/multi-vector 的多路结构，用真实 query 分布而不是单一 benchmark 决定权重。第二，把文档切分粒度纳入 A/B 设计：帖子、评论、问答楼层、长图 OCR 结果都可能需要 passage-level 或 block-level index，而不是整篇内容一个向量。第三，把 query rewrite 绑定到下游 ranker：BM25 适合保留关键词式 query，神经 ranker 可以尝试 Q2Q(Q+R) 或类似“查询+用户近期行为/会话上下文”的自然语言化改写。

部署上需要注意成本。论文的最佳设置使用 depth 50 reranking，虽然减少 search calls，但 reranker 本身会带来额外 GPU/CPU 开销。工业系统可先在 top 20 或 top 50 候选上离线复现类似曲线，找到 accuracy、latency 和成本的拐点，再决定是否按 query 难度动态增加 rerank depth。对于高频短 query，可缓存 BM25/稀疏召回结果；对于长尾复杂 query，可触发更深重排或 Q2Q。整体上，这篇论文把 deep research 的经验拉回了经典 IR 工程：检索单元、词面匹配、重排深度、查询格式和长度归一化，仍然是决定最终体验的核心变量。
