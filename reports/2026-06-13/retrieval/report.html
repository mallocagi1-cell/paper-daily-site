OneRetrieval: Unifying Multi-Branch E-commerce Retrieval with an Editable Generative Model

工业电商搜索的召回阶段由倒排索引、向量召回等多路分支经人工调权融合，缺乏联合优化。论文提出 OneRetrieval，用单一生成式检索(GR)模型统一多路召回，核心是 Keyword-Aligned Encoding(KAE)：把生成标识符的每个位置绑定到一个可解释的属性词，从而在保持召回质量的同时保留倒排索引“小时级新增 term、无需重训”的实时可编辑性。倒排分支虽转化率低于平台均值，却因可被运营实时干预而难以替代，KAE 正是为补齐这一能力而设计。

OneRetrieval：用「可编辑」的生成式检索统一电商多路召回

1. 问题与动机

工业电商搜索的召回阶段通常并行三路分支，各有结构性短板：倒排索引(BM25)"词面忠实但语义盲"、稠密检索"匹配粗、对新内容周转慢"、协同过滤存在"头部偏置、压制长尾与新品曝光"。三路相互独立、靠人工调权融合，无法联合优化。生成式检索(GR)有望把这一阶段塌缩为单模型，但论文指出真正的拦路虎不是召回指标，而是实时可编辑性：倒排分支转化率低于平台均值，却几乎是唯一能让运营"小时级注入一个新 term、无需任何模型更新"的通道，任何单模型替身都必须保住这一能力。现有 GR 恰恰缺失：闭合码本方法(DSI、TIGER、LC-Rec)把标识符槽位在训练时绑定为量化 embedding，部署后无法注入新词；开放词表方法(SEAL、GLEN)又缺乏"把 term 绑定到指定 item 集合"的显式机制。OneRetrieval 的目标就是在保持召回质量的同时，恢复推理期可编辑性。

2. 方法详解

核心是 Keyword-Aligned Encoding(KAE)：给每个 item 生成长度 L=6 的语义标识符(SID)，每个位置取自该位的专属码本，且每个位置对应一个可解释的关键属性词(实体、品牌、颜色等)，而非量化向量。属性体系上，作者从生产数据(约 1.08×10⁶ 个带类型词)归纳出 18 类细粒度属性，用信息论凝聚聚类按对称条件熵 IL(X,Y)=½(H(X|Y)+H(Y|X)) 贪心合并为 6 组(实体作为单例锚点)，累计信息损失在 G=6 处出现拐点。每个码本含四类槽位：空槽(index 0)、聚类槽(尾部词 embedding 的 k-means 质心)、独占槽(高频头部词)、以及每位 10 个、共 60 个训练时不绑定的预留槽(reserved slots)，留给部署后绑定的趋势词。推荐配置 L6-D3 在前 3 个稠密位各 2048 槽、后 3 位各 1024 槽，核心 9216 + 预留 60 = 9276 个 SID token。编码时拼接标题/属性/详情页/图片 OCR，用 Aho-Corasick 自动机匹配生产属性词典、按组选代表词(主体优先 + 行为重要度 PV/CTR)，全程无需神经推理。训练用标准自回归极大似然损失，backbone 为 BART-base 扩展 9276 个 SID token，并设计四阶段 SFT：Stage 0 属性—SID 对齐(建立"词归属第 ℓ 组就在第 ℓ 位发射"的位置偏置)；Stage 1 内容对齐(检索质量主来源，约 0.8M 样本)；Stage 2 协同共现(唯一暴露 query 侧 SID、确立 query-SID→item-SID 路由，约 74.3M 样本，对可编辑性至关重要)；Stage 3 个性化检索 + 预留槽自路由(用极小辅助块教模型把 query 中的预留前缀 ⟨ℓv⟩ 原样发射到 item SID，不绑定具体词)。在线服务时 query 端用 Aho-Corasick 确定性匹配出 s_q(请求路径无神经推理)，策略用 beam size 512 的无约束 beam search 解码 top-K SID，再经查找索引 T 还原为每 SID 最多 5 个 item 送下游预排。

3. 核心技术贡献

(1) 可扩展码本的 GR 设计：通过"预留槽 + 词典绑定"实现参数无关的实时干预——新趋势词 w_new 来时只需在其属性组分配一个未用预留槽 ⟨ℓv⟩、在查找索引里把该槽映射到目标 item 集，query 编码经 Aho-Corasick 路由到 ⟨ℓv⟩，策略凭 Stage 3 自路由把它发射出来，对应 item 即进入结果。其成立靠三条性质：句法可达(无约束 beam 可发射任意码本 token)、词无关身份路由(自路由训练不绑定具体词)、编码端确定性(词典查找固定)，而闭合码本方法三条全不满足。(2) 信息论属性合并 ECOM6：用条件熵把 18 类原则性地降到 6 组，支撑稠密感知的非均匀槽位分配。(3) 四阶段 SFT 解耦：把检索质量(Stage 1)与可编辑性(Stage 2)拆到近乎不相交的阶段，由消融验证。(4) 层级编码负结果：实体条件码本虽能降密度却劣于全局编码(Table 4)。

4. 实验结果分析

离线用 31 天生产日志、5×10⁶ 训练样本、约 3 万 click + 3 万 order 测试样本、7.6M query、20.2M item。检索质量(Order HR@350)：BM25 0.2215、DPR 0.4346、LC-Rec 0.3751、OneSearch 0.5550、OneRetrieval 0.5482——在深召回(HR@350)与最强基线 OneSearch 基本持平，仅在浅 cut(HR@10)落后；但 OneSearch"几乎没有推理期可编辑性"，OneRetrieval 把它找了回来。编码范式对比(Table 5)最关键：在 IHR@350(干预命中率)上 KAE 0.0806 vs RQ-VAE/RQ-kmeans/RQ-OPQ 的 0.0021–0.0030，高出 30 倍以上，且差距是结构性的而非调参。与 BM25 比可编辑性(Table 6)：IAR@350 OneRetrieval 0.553 vs BM25 0.761，即恢复约 73% 的倒排激活率，同时把召回质量翻倍(Order HR 0.2215→0.5482)。四阶段消融(Table 7)：去掉 Stage 2 后 IHR@350 从 0.1340 崩到 0.0030，证明 Stage 2 是可编辑性的承重墙；去 Stage 1 主要伤检索质量。线上 A/B(Kuaishou 站外搜索，20% 相对流量)：仅替换倒排分支时 Order +0.711%†(p<0.05)、Buyer +0.450%；同时替换倒排+稠密分支时 Item CTR +0.821%†、转化不掉。人工 GSB：query-item 相关性 +0.82%、item 质量 +1.36%。分行业 CTR 16/20 为正、均值 +1.00%，女鞋 +3.05%、内衣 +3.00% 等属性丰富类目增益最大。

5. 局限与未来方向

作者明确指出：OneRetrieval 在浅召回(HR@10 0.1846 vs OneSearch 0.2551)与 MRR@350(0.0880 vs 0.1333)上落后，这与它定位于召回阶段(而非 top 精排)一致，作为喂给排序器的召回分支可接受；预留槽共 60 个(每位约 10 个)是按"平台周级趋势周期 + 余量"设定，换到趋势更快或类目更多的目录可能需要重新规划容量；层级/实体条件编码的劣化(Table 4)说明这条降密度路线仍有未挖掘的优化空间。整体看，把"可编辑性"作为一等约束来设计 GR，是该方向尚未充分探索的维度。

6. 工业实践意义

对社区搜索这类海量 UGC 短文本场景，OneRetrieval 给出三点可借鉴的设计：其一，别只盯召回指标，要把"运营能否小时级干预召回"当作硬约束——这正是倒排长期不可替代的原因，预留槽 + 词典绑定提供了一条在单模型里保住该能力的范式。其二，编码方式决定可编辑性上限：KAE 这种"位置↔属性词"的可解释编码相比 RQ-VAE 量化，在干预命中率上有 30 倍量级差距，说明把语义 ID 做成人可读、可干预的结构本身就是工程价值。其三，训练阶段要按目标解耦：检索质量与可编辑性由不同 SFT 阶段承载，便于分别诊断与优化。部署上它很轻量：BART-base 规模，H100 训练、RTX 4090 推理，请求路径用 Aho-Corasick 确定性编码、无神经推理，beam size 512 解码、每 SID 还原最多 5 个 item，新词干预沿用与 BM25 相同的"小时级索引刷新"机制。社区搜索若想把多路召回逐步收敛到生成式单模型，可优先在"可被运营干预的热词/活动词"这一痛点上试点，先替换语义盲的词面分支、再逐步纳入稠密分支。

The Clustering Strikes Back: Building Cost-Effective and High-Performance ANNS at Scale with Helmsman

Xiaohongshu📖 有深读 · 8 分钟

小红书(RedNote)用 ANNS 支撑搜索、推荐、广告，长期依赖内存图索引(HNSW)满足低延迟 SLA，但用户与内容规模增长导致内存占用和 CapEx/OpEx 激增。论文提出 HELMSMAN，把聚类式 ANNS 搬到全闪存(all-flash)服务器，结合面向 ANNS 的用户态存储栈、leveling-learned 剪枝模块与 GPU 加速的索引构建流水线，相比内存方案节省超过 90% 的内存与成本，同时保持高吞吐、低延迟。

INSIGHT当向量规模让内存 HNSW 的成本不可持续时，“聚类式索引 + 全闪存”重新具备竞争力，关键在于用用户态存储绕开内核 I/O 栈开销、用可学习的分层剪枝替代固定剪枝、并用 GPU 给建索引提速。对社区搜索这种 UGC 海量短文本叠加严格 SLA 的场景，这是一条在不牺牲延迟前提下大幅压低向量检索硬件成本的路线。

The Clustering Strikes Back: Helmsman ANNS (Xiaohongshu) — 深度解读

1. 问题与动机

小红书（RedNote）的搜索/推荐/广告全靠内存 HNSW 做 ANNS，到 2025 年内存 HNSW 索引消耗 PB 级 DRAM，仅搜索就吃掉数百 TB。核心矛盾是成本-性能错配：内存部署提供 100% 吞吐，但维持延迟 SLA 只需要其中 32–43%，剩下 57–68% 的 DRAM 纯粹为容量买单；而 DRAM 8 $/GB vs Gen5 SSD 0.2 $/GB，这种浪费经济上不可持续。图索引混合方案也救不了：在 96 核 + 12 块 PCIe Gen5 SSD 上实测 DiskANN/Starling/PipeANN 都无法满足 5–10ms 平均延迟 SLA，PipeANN 因串行依赖链 I/O 把 SSD-DRAM 之间 10²–10³ 的延迟差放大，吞吐只有 HNSW 的 1/10–1/25。问题落到：能否用全闪存把 DRAM 成本砍掉、又不破 SLA。

2. 方法详解

硬件底座：全闪存服务器（12×2TB PCIe Gen5 NVMe SSD + 12×96GB DDR5 + 96 核）。
在线 serving 流水线：① Router 模型按 query 预测 nprobe（探查簇数）；② DRAM 里的 Centroid Graph 定位最近簇；③ Leveling 剪枝模型进一步过滤候选；④ 经 SPDK 直接 NVMe I/O 异步加载簇 posting list；⑤ 距离计算排出 top-k。
面向 ANNS 的用户态存储栈（§4.2）：metadata 用普通文件，簇列表作为裸逻辑块存 SSD；绕过内核做 direct device I/O，固定 12KB 簇读；批量提交 NVMe 命令、每批只敲一次 PCIe doorbell；64MB 粒度的 chunk free-list 分配器管空间。profiling 发现传统 libaio/io_uring 栈占了高达 58% 的 I/O 开销，换 SPDK 才能达到每搜索线程 120–170 KIOPS 的需求。
Leveling-Learned Search Pruning（LLSP，§4.3）：GBDT router 模型按 query+top-k 预测最大搜索范围；多级剪枝模型在不依赖中间结果反馈的前提下逐 query 精修 nprobe（从而保住批量 I/O）；特征含 query 向量、top-k、质心距离分布比；离线用大 nprobe(~4096) 的非剪枝搜索近似 ground truth 训练。之所以不学 Quake/LAET/Auncel 那种迭代式 probe-compute-decide，是因为它们会串行化簇 I/O、压低带宽利用率。
GPU 加速弹性建索引（§4.4）三阶段：① GPU 粗聚类（FAISS k-means，多 GPU，对百万级向量约 10× 加速）；② 弹性细粒度均衡（分布式 CPU worker 最多 1 万核，在低峰拆分/再平衡簇，QoS 抢占保在线流量）；③ merge & finalize（多核服务器合并分片、建质心图、训剪枝模型）。

3. 核心技术贡献

① 给在线 ANNS「复活」了聚类路线：证明现代高带宽 NVMe 阵列（Gen5 约 12GB/s）让聚类方案能在满足 SLA 的同时靠批量 I/O 扩吞吐，颠覆「只有图索引才能上线」的默认。② 定制 I/O 栈：SPDK 用户态直接 device steering，Gen4 上 85%、Gen5 上 70% 带宽利用率，远高于 SPANN 的 26–59%、图基线的 <20%。③ 无中间反馈的 query 自适应剪枝：LLSP 在保持批量 I/O 友好的同时处理可变 top-k 与 query 分布，保证 >80% 的 query 达到 90% recall 目标。④ 异构弹性建索引：GPU + 弹性 CPU 池让 0.1B 向量亚小时、10B 向量小时级建完。

4. 实验结果分析

搜索性能（SIFT100M，90% recall）：吞吐比现有 DRAM-SSD ANNS 高 2–16×，达到内存 HNSW 吞吐的 85% 且始终满足平均延迟 SLA。在 RedSrch10B 上，单节点对比 10 shard 拿到 HNSW 吞吐的 47–85%，同时 CPU 核数少 3–4×、DRAM 少约 10×；P99.9 尾延迟稳定在约 10ms，而图基线尾延迟急剧恶化。
带宽利用率（RedSrch0.5B）：Helmsman Gen4 约 85%、Gen5 约 70%，SPANN Gen4 仅 55%，图基线 <20%；升级到 Gen5 后 Helmsman 吞吐提升 55–87%，基线只涨 10–30%（说明基线吃不到新硬件红利）。
剪枝效率：LLSP 比无剪枝快 1.1–1.6×，比固定剪枝策略高 5–25%；质量上固定策略对 >40% 的 query 达不到目标 recall，LLSP 保证 >80% 达 90% 目标。
建索引：GPU 加速对 0.1B 向量约 10× 提速，从 9–12 小时降到 1 小时内；10B 向量从 >16 小时降到 4–7 小时（最多借 1 万在线集群 CPU 核）。
成本效率（Table 4–5）：RedSrch0.5B 上 Helmsman 250 QPS/$，HNSW 仅 51、SPANN 88；RedSrch10B 上靠砍 90% DRAM 拿到 8.3× 成本效率（10 QPS/$ vs HNSW 1.2）。单节点 96 核 +4 GPU 建索引成本是纯 CPU HNSW 的 1.7×，但建索引时间效率更高。

5. 局限与未来方向

作者明确列出四点：① SSD die 级热点冲突——query 突发打同一批簇会引发芯片内部冲突，用冗余簇副本缓解也只有 1.5–2× 吞吐提升；② 内存带宽瓶颈——12 块 Gen5 SSD 提供约 140GB/s 但只有约 70% 可用，因为 DDR5 有效带宽 300–350GB/s 要同时服务 SSD→DRAM、DRAM→CPU、最近质心搜索，加到 20 块 SSD 收益递减；③ 原地更新——25–30 KOPS 更新与 25–30 KQPS 搜索并发已超现有大规模动态 ANNS 系统，当前用「周期重建 + 辅助内存 HNSW + tombstone 位图」的混合设计，额外吃内存与重建成本；④ top-k 评测缺口——学界惯用 recall@10，但生产要 top-k 100–1000 且 90% recall，未来 benchmark 应反映多阶段流水线。

6. 工业实践意义

这是给自建向量检索、被 DRAM 成本压制团队的一份直接施工图。落地结论：① 生产部署约 40 台全闪存服务器（每台 0.7–1.1TB DRAM + 12 SSD），承载了原先约 35000 核 + 0.35 PB DRAM 的负载，硬件成本降 >90%，已稳定运行数月，小红书计划迁移大部分内存部署、预期年省数千万美元。② 可借鉴的设计点：用 router 模型预测 nprobe，把「按 query 花预算」做成学习问题；I/O 别走内核（libaio/io_uring 能吃掉 58% 开销），上 SPDK 用户态 + 固定 12KB 簇读 + 批量 doorbell；建索引把 GPU k-means + 低峰借在线集群 CPU 核结合，能把 10B 级建索引从天级压到小时级。③ 关键认知：大规模召回瓶颈已从「召回精度」转向「内存/成本」，且内存 HNSW 有 57–68% 的 DRAM 是为容量而非吞吐买单，这部分正是全闪存能吃下的红利。④ 注意硬件天花板：SSD 加到一定数量受 DDR5 带宽限制收益递减，热点与高频更新仍是软肋，强更新场景需谨慎。代码开源于 github.com/Red-EAD/helmsman。

CoDeR: Local Constraint-Compatible Retrieval Beyond Semantic Similarity

检索系统长期把语义相似度当作相关性的代理，但对“带约束”的查询会失效——文档主题贴近 query 却支持相反的约束方向(满足了本应排除的属性、肯定了本应否定的关系)。论文称之为 constraint-violating evidence exposure，提出 CoDeR：保留标准主题编码器负责候选覆盖，另加一个双编码器实现的“兼容性打分器”，用词法极性(lexical-polarity)监督在“满足/违反”对比样本上训练。兼容性信号既可对主题候选重打分，也可单独召回一路兼容性候选，推理时无需调用外部 LLM。

INSIGHT把“主题相关”和“约束兼容”解耦，是处理否定/排除类 query 的实用思路。社区搜索中大量 query 含隐式约束(如“不辣的火锅”“非广告测评”)，纯语义向量召回容易引入违反约束的负向证据；CoDeR 用轻量双编码器在召回/重排阶段补一路极性兼容信号，推理零 LLM 调用、延迟可控，易于嵌入现有多阶段检索。

Xingkun Yin, Xuebin Tang, Hongyang Du

RCEM: Embedder Equipped with Query Rewriting Skill for Robust Conversational Search in Distributional Shift

Microsoft

会话式检索中，多轮对话里的 query 高度依赖上下文。论文提出 RCEM，把 LLM 的 query 改写能力蒸馏进 embedding 模型，让稠密检索在推理时无需显式改写就能感知上下文。与以往直接学“对话→文档”匹配不同，RCEM 让“会话 query 的 embedding”对齐“改写后 query 的 embedding”，从而在分布漂移(distributional shift)下更稳健；训练不需要昂贵且难获取的“会话 query→文档”相关性标注。在 QReCC、TopiOCQA、TREC CAsT 上一致优于强会话检索基线。
