1. Predictive Prefetching for Retrieval-Augmented Generation
4.25
Relevance 4 | Novelty 4 | Practical 4 | Evidence 4 | Timely 5

Summary: RAG 系统的同步检索会把向量检索耗时压在生成主路径上，拉高首 token 延迟。论文提出异步预取框架，由 retrieval predictor、context monitor、query generator 三个模块组成，通过监测生成过程中的语义信号，提前判断“何时该检索、检索什么”，让检索与生成重叠执行。在保持答案质量与同步 RAG 相当的前提下，端到端延迟最多降低 43.5%，首 token 时间（TTFT）改善 62.4%。已被 ICML 2026 接收。

Key insight: 把检索从生成关键路径上摘出来、用预测器判断触发时机做异步预取，是社区搜索做 RAG/生成式问答压延迟的可直接借鉴思路。三模块解耦清晰（预测器判时机、监控器读生成状态、查询生成器构造 query），不依赖改动底层检索引擎，适合叠加在现有“召回+LLM”链路上。需注意预测器误触发会带来额外检索开销，线上要权衡 prefetch 命中率。

2. Test-Time Speculation
4.15
Relevance 4 | Novelty 4 | Practical 4 | Evidence 4 | Timely 5

Summary: 投机解码靠小草稿模型批量产 token、大目标模型并行校验来提速，但论文发现“接受长度”（草稿被目标接受的 token 数）随生成推进急剧衰减——即便 DFlash、EAGLE-3 这类强草稿器，几千 token 后接受长度也跌到接近 1（几乎无加速）。作者提出 Test-Time Speculation（TTS）：推理中用目标模型已产生的校验信号在线蒸馏、持续更新草稿模型，无需额外标注。接受长度峰值最多提升 72%、平均提升 41%，且生成越长收益越大，在 Qwen-3、Qwen-3.5、Llama-3.1 上验证。

Key insight: 指出投机解码接受长度会随上下文漂移衰减，这是长输出场景（长答案、Agent 多轮）里被忽视的加速损耗点。TTS 用“免费”的目标校验信号在线蒸馏草稿器，是对现有 EAGLE 系草稿器的轻量增量改造，不改目标模型、不需离线训练数据，落地成本低。对社区搜索的长文本生成/摘要场景能稳住加速比；代价是推理时要承担在线更新草稿器的额外计算。

3. OCTOPUS: Optimized KV Cache for Transformers via Octahedral Parametrization Under Optimal Squared-error Quantization
4.05
Relevance 4 | Novelty 4 | Practical 4 | Evidence 3 | Timely 5

Summary: 长上下文自回归推理中，KV cache 主导显存占用与带宽。延续 TurboQuant、PolarQuant 的“结构化随机旋转 + 逐坐标标量量化”思路，OCTOPUS 改为对旋转后的坐标三元组做联合量化：用八面体参数化把每个三元组的方向映射到正方形，再对两个坐标和三元组模长按“实现匹配的边缘分布”做 Lloyd-Max 量化，并按总维度推导出严格非均匀的比特分配。论文称在所测试的真实 decoder 上质量最优点稳定，给出一个免训练的 KV 压缩 codec。

Key insight: 把 KV 量化从“逐坐标”推进到“旋转坐标三元组联合量化”，靠八面体参数化压低方向编码误差，是 KV cache 压缩在量化粒度上的细化。免训练 codec 可作推理侧 drop-in，对长上下文检索/RAG 服务直接省显存与带宽。需关注旋转+三元组量化在解码端的额外算子开销，以及“质量最优比特分配恒定”这一结论在不同 decoder 上的泛化边界。

4. Get Real-Time Visibility into GPU Usage Across Kubernetes Clusters
3.65
Relevance 4 | Novelty 2 | Practical 5 | Evidence 2 | Timely 5

Summary: NVIDIA 开源的 GPU Usage Monitor 把 DCGM Exporter、kube-state-metrics、Prometheus、Grafana 打包成单个 Helm chart，解决 Kubernetes 集群两类问题：一是按整卡分配却看不到真实占用（典型利用率仅 30–50%）导致硬件闲置；二是 GPU pod 卡在 Pending 却无全局感知，训练/推理任务静默停摆。仪表盘提供按 namespace/工作负载的分配趋势、单卡算力利用率、按 pod 的显存拆分、运行 vs 待调度 pod 计数，并支持按 GPU 型号（Hopper/Blackwell）过滤。需 K8s 1.19+、Helm 3.0+，三条命令部署。

Key insight: 把 GPU 可观测性做成开箱即用 Helm chart 的工程范式，对自建推理/训练集群的搜索团队有直接参考价值：用 DCGM+Prometheus+Grafana 标准栈就能拿到单卡利用率与 Pending 压力，定位 30–50% 的利用率浪费和静默排队。新颖性低（整合既有组件），但落地门槛极低、与现有 K8s 监控体系兼容，适合作为算力成本治理的起点。

5. GEM: GPU-Variability-Aware Expert to GPU Mapping for MoE Systems
3.45
Relevance 3 | Novelty 4 | Practical 3 | Evidence 3 | Timely 5

Summary: MoE 服务受制于每层同步屏障：一个 batch 内所有 token 必须处理完才进下一层，于是最慢的 straggler GPU 决定吞吐。GEM 提出感知 GPU 性能差异的专家到 GPU 映射：按专家的负载变动性分配非均匀 token 负载，并避免把“同时被激活”的专家放到同一张卡或更慢的卡上。论文把专家分为 consistent（高频常用）与 temporal（周期性共激活）两类来指导放置。相对基线映射，平均延迟改善 7.9%、最大延迟改善 16.5%。

Key insight: 把异构集群里 GPU 性能差异与专家共激活模式纳入放置决策，是 MoE 推理负载均衡的一个实用视角——区分常用专家与周期共激活专家，避免热点专家撞在慢卡上。对要在混合代际 GPU（如 Hopper/Ampere 混部）上跑 MoE 的团队有借鉴意义。改善幅度偏温和（个位数到十几个百分点），且依赖对专家激活模式的离线统计，激活分布漂移时映射可能需重算。

6. Improving Efficiency of GPU Kernel Optimization Agents using a Domain-Specific Language and Speed-of-Light Guidance
3.45
Relevance 3 | Novelty 4 | Practical 3 | Evidence 4 | Timely 4

Summary: 基于 LLM 的 GPU kernel 优化 agent 常把搜索预算浪费在低层代码上。论文提出两点：μ-CUTLASS 领域专用语言，让 agent 在更高抽象层推理、同时保留关键优化旋钮；Speed-of-Light（SOL）引导，用第一性原理的性能上界来引导和约束搜索。用 GPT-4-mini 时，从低层代码切到 DSL 把相对 PyTorch 的 0.40x 退化扭转为 1.27x 加速；加 SOL 引导达 1.56x，最佳策略 1.68x 效率增益。SOL 预算控制能保留至少 95% 的几何平均加速、同时省下 19–43% token，在 59 个 KernelBench 问题上评测。

Key insight: 给 LLM 写高性能 kernel，关键不在更强的模型而在“给对抽象层 + 给对性能锚点”：DSL 降低搜索空间维度、SOL 上界提供可计算的停止/预算信号。这对想用 LLM agent 自动调优算子的基建团队是可迁移的方法论。局限是 μ-CUTLASS 绑定 CUTLASS 生态、需要相应专业知识，且评测停留在 KernelBench 基准而非生产算子库。

7. UniEP: Unified Expert-Parallel MoE MegaKernel for LLM Training
3.35
Relevance 3 | Novelty 4 | Practical 3 | Evidence 3 | Timely 4

Summary: 算力吞吐与通信带宽的差距拉大，专家并行（EP）成为 MoE 训练扩展的关键。UniEP 把多种 EP 优化策略统一进一个抽象，通过把通信与计算融合成 MegaKernel 来降低开销，并引入确定性 token 排序机制，保证与顺序执行的数值一致性（对生产级大规模训练的精度复现很重要）。在 NVIDIA Hopper GPU 集群上，相对既有方案取得 1.03x–1.38x 加速，同时保持精度。

Key insight: 把 EP 的通信-计算融合做成 MegaKernel，并用确定性 token 排序解决“算子融合后数值不可复现”这个生产痛点，是 MoE 训练系统少见地同时兼顾性能与数值一致性的设计。对自研 MoE 训练框架的团队，确定性排序这一点尤其值得借鉴。加速幅度（1.03–1.38x）与硬件强相关（Hopper），且 MegaKernel 工程实现复杂、迁移到其他卡需重写。

8. Unlock Exascale Performance on NVIDIA GB200 NVL72 with Slurm Topology-Aware Job Scheduling
2.85
Relevance 3 | Novelty 2 | Practical 3 | Evidence 2 | Timely 5

Summary: 随着模型规模增长，能否发挥 GB200 NVL72 这类加速基础设施的全部性能，越来越取决于作业怎么放置而非单纯堆硬件。文章介绍在 NVIDIA GB200 NVL72 上用 Slurm 的拓扑感知作业调度：让调度器理解 NVLink 域、机架与网络拓扑，把强通信的作业放到带宽最优的物理位置，从而逼近 exascale 性能。属于面向超大规模训练集群的调度工程实践。

Key insight: 核心启示是大规模训练里“拓扑感知放置”和算力本身同样重要——把 all-to-all/集合通信密集的任务对齐到 NVLink 域内，能显著减少跨域通信损耗。即便没有 GB200，拓扑感知调度的思路对任何多机多卡训练集群都可迁移。作为厂商博客，缺乏严格对照实验与量化收益，且具体配置强绑定 GB200 NVL72 硬件。（因来源多样性覆盖需要纳入，分数低于阈值。）
