APEX-Searcher: Augmenting LLMs' Search Capabilities through Agentic Planning and Execution

APEX-Searcher 针对复杂多跳问题中单次检索不足的痛点，提出了一种基于 Agentic 规划与执行的搜索增强框架。该系统将搜索过程分解为规划（Planning）、执行（Execution）和验证（Verification）三阶段，允许 LLM 动态决定搜索策略和迭代轮次。在多个多跳问答基准测试（如 HotpotQA、2WikiMultiHopQA）上，APEX-Searcher 相比传统单轮 RAG 方法显著提升了答案准确率，在复杂问题上取得了约 8-12% 的性能提升。

1. 问题与动机

现有检索增强生成（RAG）系统在处理需要多跳推理的复杂问题时存在根本性缺陷。单轮 RAG 无法应对需要从多个相互依赖信息源中综合信息的问题，虽然迭代式 RAG（如 Search-o1、IRCoT）通过增加检索轮次在一定程度上缓解了问题，但这些方法本质上是「反应式」的——每次搜索都是对上一步结果的局部响应，缺乏对整个任务的全局规划。

论文作者明确指出，现有研究「忽视了 LLM 内在任务规划能力的关键重要性」。以 HotpotQA 中的典型题目「奥运金牌得主 X 的出生地的市长是谁？」为例：传统迭代 RAG 会先随机搜索 X 的相关信息，再根据检索结果决定下一步；而 APEX-Searcher 会先规划出完整解题路径「→找 X 的出生地 → 找该城市现任市长」，再按序检索执行。这种区别在 MuSiQue 等复杂多跳基准上的差距约为 7-8 个百分点 EM（精确匹配率）。

2. 方法详解

APEX-Searcher 采用两阶段层级框架，将「规划」与「执行」显式分离。

第一阶段：基于 RL 的智能规划（Agentic Planning）

规划器接受原始多跳问题，输出带显式依赖关系的子问题序列（如「#1: X 的出生地是哪里？#2: #1 结果所在城市的市长是谁？」）。使用占位符 、 引用前序子问题结果，形成可执行的依赖图。

训练使用 GRPO（Group Relative Policy Optimization）算法，而非传统的 actor-critic 方法。GRPO 直接对同批次多个生成结果进行相对优势估算，避免了额外 critic 网络带来的内存开销。关键超参数：学习率 5×10^-6，全局 batch size 512，KL 散度惩罚系数 0.01，训练 3 个 epoch，数据来自 MuSiQue 训练集 10,473 个样本。

奖励函数设计（核心创新）：不直接使用字符串匹配而采用语义对齐奖励——将生成的子问题与黄金分解结果编码为 sentence embedding，通过余弦相似度（阈值 τ=0.8）构建相似度矩阵，再使用匈牙利算法求最优二分图匹配，计算精确率与召回率的调和平均作为最终奖励。这一设计使奖励函数对语言表达的多样性具有鲁棒性，能够正确评价语义等价但表达不同的分解方案。

第二阶段：基于 SFT 的自适应探索（Agentic Exploration）

执行器针对每个子问题进行动态多轮检索：首先判断当前累积知识是否足以回答该子问题；若不足，则生成新的检索查询（避免与已尝试查询重复）；检索后更新知识库；重复直至置信度足够或达到最大跳数限制（最优为 5 跳）。

SFT 训练数据由模型自生成后经严格自动过滤获得：丢弃推理有缺陷、答案错误或格式不符的样本，最终保留 14,604 条高质量多轮检索指令样本（来源：2WikiMultiHopQA、HotpotQA、MuSiQue）。SFT 使用全参数微调，借助 DeepSpeed ZeRO Stage 3 和 Flash Attention 2，支持最大 32,768 token 的上下文窗口。

整体流程：原始问题 → Planning Agent（GRPO训练）→ 子问题序列 → Exploration Agent（SFT训练，逐子问题迭代检索）→ 答案综合。

3. 核心技术贡献

贡献1：规划优先的两阶段范式
明确将任务分解（Planning）与执行（Exploration）训练分离，每个阶段专注各自目标。对比消融实验显示，在 7B 模型上，添加 RL 训练的规划模块将组合指标从 30.39 提升到 33.82（+3.43），进一步加入 SFT 探索训练提升至 37.64（+3.82）。两阶段协同的增益超过任意单阶段。

贡献2：基于语义对齐的奖励函数
传统字符串匹配奖励对「语义正确但表达不同」的分解方案评分偏低，误导 RL 优化方向。APEX-Searcher 使用匈牙利算法的语义匹配奖励，使规划训练奖励和验证奖励均呈持续上升趋势，模型回复长度随训练进程下降（过度分解减少），证明模型在学习更精炼的规划。

贡献3：自适应探索的查询多样性约束
执行阶段引入「查询新颖性约束」，在生成新的检索查询时显式参考历史查询列表，避免重复检索相似文档。实验表明，检索文档数从 1 增加至 3 时性能显著提升，超过 3 后因噪声增加而下降，最优检索文档数为 3。

贡献4：小模型的 SFT 关键作用
消融实验揭示一个重要发现：对于 3B 小模型，规划模块单独引入反而会降低性能（EM 从 13.42 降至 12.63），因为规划任务本身超出了小模型的能力上限；而加入 SFT 探索训练后，3B 模型 EM 从 12.63 飞跃至 23.52，说明 SFT 对弱模型的能力激活至关重要。

4. 实验结果分析

在四个多跳 QA 基准（HotpotQA、2WikiMultiHopQA、MuSiQue、Bamboogle）上，以 Qwen2.5 系列作为基础模型进行评测：

基准APEX-Searcher 7BStepSearch-7B（最强基线）提升
HotpotQA40.2%约 29%+11%
2WikiMultiHopQA54.0%约 31%+23%
MuSiQue16.4%约 10%+6%
Bamboogle40.0%约 36%+4%
平均 EM37.6%29.4%+8.2%

最大提升出现在 2WikiMultiHopQA（+22.8%），该数据集需要最严格的多步骤顺序推理，与论文关于「规划对复杂多跳推理的价值」的核心主张完全一致。MuSiQue 提升最小（+7.8%），该数据集包含刻意设计的干扰跳（需要识别无关中间证据），规划层面仍有改进空间。

消融分析重要发现：规划单独使用（无 RL 训练）并不带来稳定收益；RL 训练规划至关重要，GRPO 的相对比较机制比 REINFORCE 更稳定；文档检索数量有最优值（约 3 篇）；最大推理跳数在 5 跳时最优。

5. 局限与未来方向

作者明确指出的局限：(1) 当前 Exploration 阶段仅使用 SFT 训练，作者提出未来可探索多轮 RL 持续优化执行策略；(2) 规划模块对小模型（3B）反而有害，需要额外 SFT 对齐才能发挥正向作用；(3) 当前实验基于本地检索数据库，尚未扩展到真实 Web 搜索场景；(4) 目前仅针对多跳问答任务，尚未验证在其他 agentic 任务上的泛化性。

作者未明确提及但值得关注的限制：两阶段串行设计带来额外推理延迟（Planning 阶段先完成，再进入 Exploration），对实时查询场景不够友好；SFT 数据的自生成质量依赖基础模型能力，存在质量上限。

6. 工业实践意义

对搜索系统的直接启示：APEX-Searcher 提供了一套将 LLM 从「反应型检索器」升级为「主动规划型搜索 agent」的完整技术路径。具体落地建议：

首先，查询理解层：对于社区搜索中的复杂意图（如「适合带孩子周末去的活动，距离北京两小时内，有户外体验」），引入轻量规划模块（3B 小模型或 prompt-based 分解）将查询分解为多个子意图，分别召回后综合排序。

其次，训练数据策略：论文的 SFT 数据自动生成+过滤范式可直接复用——用生产环境的复杂查询日志生成多跳检索轨迹，再经自动质量过滤（答案 EM 阈值）保留高质量样本。这是构建搜索 agent 微调数据集的低成本方案。

第三，部署成本控制：论文中 3B 模型搭配完整训练方案达到接近 7B 的效果，对于需要在成本和效果间平衡的搜索系统，可优先在规划器上部署 7B，执行器使用 3B 配合 SFT 微调，形成「大规划+小执行」的经济型架构。

延迟考量：两阶段串行带来额外延迟（规划约 0.5-1s），适合对准确率要求高的搜索场景（如专业问答、知识密集型搜索），不建议在 P99 延迟敏感的通用 UGC 搜索首链路部署，可作为第二阶段精细化搜索的补充模块。

AutoTool: Automatic Scaling of Tool-Use Capabilities in RL via Decoupled Entropy Constraints

MicrosoftHIT

AutoTool 解决了 RL 驱动的工具使用扩展中的两大核心挑战：模型对简单问题过度思考（token 浪费）和对复杂问题推理不足（搜索深度不够）。该方法引入解耦熵约束（Decoupled Entropy Constraints），在 RL 训练时分别约束简单与复杂任务的推理长度，配合热启动 SFT 使模型掌握工具调用的基本格式，再通过 RL 自动学习何时以及如何扩展工具调用深度。实验结果显示，在工具使用基准测试上比 SOTA 方法提升约 6-10 个百分点，同时减少约 30% 的 token 使用量。

INSIGHTAutoTool 的关键技术洞察是「思维长度」与「工具调用深度」需要分离控制：简单查询不应消耗大量 tokens 进行反思，而复杂查询需要足够的推理空间来设计工具调用序列。对于搜索系统中的 LLM agent（如查询改写 agent、多轮检索 agent），这一方法可直接应用于提升推理效率：通过分难度自适应控制推理长度，实现同等效果下 30% 的计算节省，具有明显的工业部署价值。微软研究院出品，代码可复现性高。

OpenClaw-RL: Train Any Agent Simply by Talking

PKUPrinceton

OpenClaw-RL 提出了一个统一的 Agent RL 训练框架，其核心观察是：任何 agent 交互都会产生「下一状态信号」（对话回复、工具输出、GUI 状态变化等），这是一种通用的在线 RL 训练信号，但现有系统从未将其系统性利用。该框架允许从对话、终端执行、GUI 操作和代码执行等多种交互中同步学习策略。在 SWE-bench、对话型 agent 和 GUI 操作等任务上均取得了优于现有专用方法的表现，展示了通用 RL 信号的强大潜力。

INSIGHTOpenClaw-RL 的革命性思路是：不需要专门设计 reward 函数，任何用户/环境对 agent 行为的反应（包括搜索结果是否被用户点击、查询是否被改写后执行）都可以作为 RL 信号。对于搜索 agent 的训练，这意味着可以利用真实用户的隐式反馈（点击、停留、满意度）作为在线学习信号，逐步优化 agent 的搜索行为。这是将搜索 agent 从离线训练迁移到在线持续学习的重要基础范式。

Why Do LLM-based Web Agents Fail? A Hierarchical Planning Perspective

GMU

本文提出了一种三层次分析框架来系统研究 LLM Web Agent 的失败模式，三层次分别为：高层规划（任务分解）、低层执行（操作与定位）和重规划（错误恢复）。研究发现，结构化 PDDL 规划比自然语言规划产生更简洁和目标导向的策略，主要失败原因集中在低层执行的「定位错误」（grounding failures）和高层规划的「目标遗漏」（goal omission），而非模型对任务本身的理解问题。在 WebArena 等基准上对多个主流 Web Agent 进行了过程级评估。

INSIGHT该论文揭示了一个重要反直觉发现：Web Agent 的主要失败不是「不理解任务」，而是「执行层的元素定位」问题（点击错误的按钮、解析错误的页面区域）。这对搜索 agent 的工程设计有直接指导意义：提升 agent 性能的重点应放在低层执行的鲁棒性（如更精确的元素识别和定位），而非仅仅优化任务规划逻辑。PDDL 结构化规划的有效性也提示了在搜索流程编排中引入形式化描述的潜力。

DOVA: Deliberation-First Multi-Agent Orchestration for Autonomous Research Automation

DOVA（Deep Orchestrated Versatile Agent）提出了深度研究自动化的多 agent 编排框架，引入三项核心创新：(1) 审议优先编排（Deliberation-First Orchestration），在调用任何工具前进行显式元推理，结合持久用户模型和实体感知上下文；(2) 混合协作推理（Hybrid Collaborative Reasoning），三阶段可组合推理流程；(3) 个性化信息综合，根据用户偏好定制研究报告输出。系统设计目标是替代或增强人工研究员在多源信息综合和对抗性验证方面的工作。

INSIGHTDOVA 的「审议优先」设计哲学对搜索系统有深远启示：在执行任何检索操作之前，agent 应先进行显式的元认知（「我需要什么信息，为什么需要，如何验证其可信度」），这与搜索引擎的被动响应模式形成对比。对于构建企业级 Deep Research 产品（类似 Perplexity、SearchGPT），DOVA 提供了一套可落地的多 agent 架构参考，特别是「持久用户模型」的引入为个性化深度研究奠定了基础。系统虽偏工程，但设计思路清晰，适合 agentic 搜索产品团队参考。

Verified Multi-Agent Orchestration: A Plan-Execute-Verify-Replan Framework for Complex Query Resolution

VMAO（Verified Multi-Agent Orchestration）提出了一套「规划-执行-验证-重规划」的四阶段多 agent 框架，用于解决需要多子问题协同的复杂查询。系统将复杂查询分解为 DAG（有向无环图）结构的子问题，通过专用 domain agent 并行执行各子问题，再由 LLM-based 验证器评估结果完整性并自适应补充缺失信息。关键技术包括：依赖感知并行执行（保证上下游子任务的信息传递正确性）和验证驱动重规划（在验证失败时自动生成补充子问题）。在复杂 QA 任务上显示出明显优于单 agent 方法的表现。

INSIGHTVMAO 的验证驱动重规划机制对搜索系统有直接参考价值：当一个复杂用户查询（如「推荐适合家庭的周末度假地，靠近上海，有儿童设施，支持宠物」）需要多维信息综合时，DAG 化分解和并行执行可以大幅降低延迟。特别是「LLM 验证器」作为 orchestration 层控制器的设计——用 LLM 来判断「是否获取了足够的信息」——提供了一种从 RAG 向 agentic 搜索演进的工程路径，适合搜索团队在复杂意图处理场景中渐进式采用。
