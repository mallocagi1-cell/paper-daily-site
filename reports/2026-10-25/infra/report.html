ATTUNE: Agentic Throughput Tuning for LLM Training

同一个大模型换一种 GPU 或换一个框架版本，原来最快的训练配方往往不再最快，配方要定的是模型怎么拆到多张 GPU 上、用哪些底层计算程序、GPU 之间的数据传输怎么和计算同时进行。ATTUNE 让一个能写代码、跑命令的智能体来调配方，给它一份能跑通的配方和一笔 GPU 小时预算，它自己反复试、自己分析瓶颈。但这篇论文真正的看点在智能体之外，一道由固定代码执行、智能体改不了的正确性闸门：模型、数据、每步处理多少条、数值精度都锁定不变，凡是会悄悄改变训练内容的改动，比如丢掉超额的训练词，在启动前就被拒绝。三个模型的微调任务换上调好的配方后，训练速度平均提高到原来的 1.7 倍，最多 3.9 倍。

训练一个大模型之前，工程师要先定一份“训练配方”：模型怎么拆到几十上百张 GPU 上、显存不够时拿多少计算去换、用哪些底层计算程序、GPU 之间的数据传输怎么和计算同时进行。同一个模型换一种 GPU 或换一个框架版本，原来最快的配方往往就不再最快。Amazon 做了一个叫 ATTUNE 的系统，让一个能写代码、跑命令的 AI 智能体来调配方：给它一份能跑通的配方和一笔 GPU 小时预算，它自己反复试、自己分析瓶颈，不需要人盯着。但这篇论文真正的看点在智能体之外：一道由固定代码执行、智能体改不了的“正确性闸门”，凡是会悄悄改变训练内容的改动，在启动前就被拒绝。Amazon 内部三个模型的微调任务换上调好的配方后，训练速度平均提高到原来的 1.7 倍，最多 3.9 倍。

1. 问题：现成的自动调优工具，要么搜不到，要么会“调坏”

训练配方里有很多可以调的“杠杆”。最重要的是模型怎么拆分：可以把每一层的矩阵切开分给几张卡，也可以把不同的层分给不同的卡像流水线一样接力，还可以把数据分成几份让几组卡各算一份。另外还有：显存不够时，要不要把中间结果丢掉、需要时再重新算一遍（用计算换显存）；要不要把一部分数据暂存到 CPU 内存里；用哪个版本的注意力计算程序。

现有的自动调优工具大致有三类。第一类按一个估算性能的公式，在事先列好的选项里挑。第二类是“黑盒”搜索，比如贝叶斯优化：不理解系统怎么工作，只是一次次试跑、根据结果决定下一次试什么，但每次试跑都很贵。第三类是最近出现的大模型调优器，比如 OptiCo，能读性能分析结果，但同样只能在一张固定的旋钮列表里调。

作者有两个观察，决定了 ATTUNE 的设计。

第一，现成配方没吃到的速度，有一部分藏在要一起改才见效的杠杆组合里，还有一部分藏在固定列表根本没列出来的杠杆里，比如换一种在多张卡之间分发数据的程序。

第二，有些配置会悄悄改变训练的内容，而训练照样跑完、不报错。举两个例子。在“混合专家”模型里，每个输入词会被分给少数几个“专家”子网络处理。有一个常用的提速参数，会限制每个专家最多处理多少个词，超出的词就直接丢掉不训练了。另一个参数看名字只是“用较低精度传梯度”，实际上还会让梯度累加也变成低精度。只检查“能不能跑起来”的调优器，会把这两种配置都当成“优化”交出去，训练出来的模型却和原来不一样。

2. 方法：智能体负责找，固定代码负责判

一次调优叫一个“战役”：固定一个模型、一个集群、固定数量的 GPU。所有候选配方训练的东西完全一样：模型、数据、每条数据的长度、每步处理多少条、数值精度都不变，每次运行还按同样顺序读同样的数据。每次试跑固定若干步，前几步用来热身、不计分，之后按平均每张 GPU 每秒处理多少个词打分。

速度测量有噪声，所以要先确定“多快才算真快”。原配方至少在不同的机器上跑 5 次，求出平均速度，以及标准差占平均值的比例 σ。噪声门槛取 3% 和 3σ 中较大的那个；新候选必须比当前最快的快出这个门槛以上，才能取而代之。这样就不会把一次碰巧跑得快当成真的改进。

智能体用的都是普通工具：读写文件（包括训练框架的源代码）、执行命令、调用集群接口。一份写好的“调优守则”给它定了六条纪律，最重要的三条是：

  • 每次启动前，先写下假设：要缓解哪个瓶颈、为什么有效、预计快多少；
  • 每次只改一个杠杆，或者一组必须一起改的拆分方式，这样结果好坏才能归因；
  • 用一个参数之前，先去框架源代码里读它的实现，看它会不会悄悄连带改掉别的参数，并把代码位置记进账本。

瓶颈不明显时，智能体会做一次性能分析：一个固定的分析程序把每一步训练的时间拆成计算、GPU 之间传数据、CPU 那边的工作和空等四部分，告诉智能体时间主要浪费在哪。

花钱由固定代码把关。记账脚本从集群分配机器那一刻算到释放为止，失败的运行和检查用的运行都算在内，预算不够就不让启动。一个失败过的配方原样重跑也会被拒绝，逼着智能体先找出原因再改。

正确性闸门分两步，这是整个系统的核心。

第一步在启动前，比较候选配方和原配方最终生效的所有参数和环境变量。要比最终值，是因为一个参数可能悄悄改掉别的参数。每一处改动都要到一张登记表里查，这张表智能体改不了。会改变训练内容的（数据、每步多少条、优化器、损失函数、路由方式、数值精度），或者会触发已知软件缺陷的，直接拒绝；只改变“怎么算”而不改变“算什么”的，比如换一种在 GPU 上摆放数据的方式，直接放行；表里没有的，先放行到第二步，并写进报告请人复核。

第二步在启动后，比较训练第一步的损失值，也就是模型在第一批数据上的错误程度。第一步时权重刚加载、还没更新，候选和原配方面对的是同一组权重、同一批数据，算出来的损失本应几乎相同。合法的改动只会因为计算顺序不同带来极小的差异；而如果权重加载错了或拆分错了，损失会成倍变化。所以规定第一步的损失必须和原配方相差不到 5%，而且整个试跑里损失不能出现无穷大或无效值。

为了真正无人值守，作者在 Claude Code 外面加了几道钩子：预算没花完、也没有带着证据写明停止理由之前，智能体不能结束；它想问人问题时，改为“取默认值并记录假设”；不认识的破坏性命令会被拦下。所有运行记录写进一个只能追加的账本，系统崩了也能从账本恢复。战役结束后智能体写下心得，经人审核后放进经验库，给下次用。

3. 结果一：比公开的最强配方还快

作者先在自己的集群上原样复现了 NVIDIA 官方的四个基准配方，其中三个和 NVIDIA 公布的速度相差不到 2%，说明起点是公平的。从这些配方出发，ATTUNE 又提速 7% 到 26%，比 NVIDIA 公布的数字高 6% 到 17%。然后作者拿四个开发时没见过的模型，从别人写好的公开配方出发调优。

能提速多少，取决于原配方和当前环境差得有多远。MiniMax-M2 的原配方本来是为 128 张卡上的强化学习写的，把优化器的数据放在 CPU 内存里来省显存；换到 64 张卡做普通训练后，这一招反而拖慢速度。ATTUNE 关掉了它，又调整了流水线的拆法，速度提到原来的 2.6 倍。GLM-4.5 的配方是为 H100 写的，到了 B200 上，诊断发现瓶颈变成了跨机器传数据和频繁启动小计算任务。ATTUNE 于是缩小专家并行的范围，让每个专家组只占一台机器上的卡。这样每个词要发去的专家都在本机，专家之间交换数据不再跨机器；路由规则和模型都没变，只是专家放在哪些卡上变了。最快的那次还把张量并行降到 1。Llama-3.1-70B 换了更快的注意力计算程序，计算时间占到每一步的 98.5%，几乎不再空等。Mixtral 和 405B 的配方本来就是厂商针对同款硬件调过的，能挖的空间很少；Mixtral 最好的候选没有超出噪声范围，所以按规则保留原配方。

4. 结果二：同样的预算，比其他调优器找得更好

作者给每种调优方法同样的预算：30 倍于一次原配方试跑的 GPU 小时，用同一道闸门和同样的发布规则，每个模型各跑 3 次。在 GLM-4.5 上，ATTUNE 平均提速 33.9%，只花了 669 GPU 小时、6.4 小时；OptiCo 一点没提升，却花了 1,407 GPU 小时；随机搜索提速 7.8%；贝叶斯优化只有 1.8%。在 MiniMax-M2 上，ATTUNE 是 164.2%，最好的对手是 55.5%。这说明 ATTUNE 不只找到了更快的配方，调优本身也花得更少。

最有意思的是 OptiCo 的失败原因。ATTUNE 在 GLM-4.5 上找到的那种拆法，其实就在 OptiCo 能调的 11 个旋钮范围之内：只用这 11 个旋钮复现这种拆法，速度和 ATTUNE 的最终配方只差 2%，但 OptiCo 没找到：它只在较浅的流水线上试过相关设置，专家之间的数据交换也一直跨机器。黑盒搜索的范围里明明有答案，可没有诊断来指路，大多数尝试要么显存爆掉，要么比当前最快的慢而被淘汰。这说明 ATTUNE 的优势主要来自“先看瓶颈再动手”，而不只是能改的东西更多。

作者还逐个拿掉 ATTUNE 的部件看影响。拿掉调优守则和经验库后，两个测试模型的提速分别从 88.0% 降到 66.9%、从 49.4% 降到 42.9%，一半的试跑没能正常启动。只允许改 OptiCo 那 11 个旋钮时，GLM-4.7-Flash 只剩 18.1%，因为它最大的收益来自关掉“把优化器数据放 CPU”，而这一项不在列表里。

5. 闸门本身靠得住吗

作者专门测试了闸门。460 次合法运行全部放行，所有配置类错误都在启动前被拒绝。作者又故意往代码里埋了 6 种错误：改变模型前向计算的 2 种，让第一步损失涨了 150% 以上，被抓住了；只在更新权重时才起作用的错误，比如漏掉一部分梯度的汇总，第一步根本看不出来；损失计算时标签错开一个词，只让损失变了 2%，和合法改动的最大差异差不多。这几种都漏了过去。

实战中闸门也立了功。在 Nemotron-3-Nano 上，配置检查拦下了 19 次“各段层数不均匀”的流水线拆法。其中一次恰好是所有试跑里最快的，但它把别的层的权重加载进了错误的层，第一步损失比正常高出 215% 到 768%。没有闸门，这个“最快配方”就会被交出去。

6. 局限与实践意义

作者列出三点局限。第一，闸门只看配置和第一步，只在权重更新时才起作用的错误查不出来，所以正式使用前还要完整训练一次做验证。第二，经验库来自过去的调优，GLM-4.5 和开发时用的模型同属一个家族，部分收益可能来自“见过类似的”。不过不用经验库时，GLM-4.5 的结果和完整版差别在噪声以内。第三，ATTUNE 只调框架开放出来的配置，不改底层计算程序和代码，也不覆盖强化学习中让模型生成样本的那一段。还有一个教训：作者回头核对经验库，发现大约五分之一的条目是错的，有的只在当初测出它的那个任务上成立。

对训练平台团队，最值得借鉴的是闸门和记账，而不是智能体本身。不管调优是人做还是智能体做，都可以先建一套检查：比较最终生效的参数差异，查一张不可修改的“哪些改动会改变训练内容”登记表，再比较第一步损失。这样就能把“丢掉超额的词”“低精度累加梯度”这类悄悄改变训练的参数挡在启动前。预算要从分到机器算到释放，失败的运行也要算。如果你的配方是从别的硬件、别的任务（比如强化学习）搬过来的，自动调优的回报最大；如果用的是厂商针对同款硬件调好的配方，预期收益要小得多，论文里这类配方只提速 0% 到 26%。经验库要定期对照原始记录核查，只留下模型自己不知道、或者能纠正它错误直觉的条目。

uGDS: A User-Space Development Kit for High-Performance GPU Direct Storage

📖 深度解读 · 11 分钟 →

用 NVIDIA 的 GDS 把数据从 SSD 直接读进 GPU 显存时，作者实测发现，异步读取 99.6% 的时间都卡在提交请求这一步。大模型推理服务会把算过的 KV cache 存到 SSD 上，下次遇到同样开头的请求就直接读回来，不用重算，这一步的速度直接影响首字延迟。uGDS 把指挥 SSD 干活这件事从操作系统内核搬到普通程序里来做。数据照样从 SSD 直达 GPU，变的是谁来下命令。uGDS 批量读的速度最高是 GDS 的 12 倍；接进开源缓存系统后，长提示的首字延迟中位数从 1.9 秒降到 0.7 秒。

Jing Wei, Guanyi Chen, Qi Chen, Chuyu Zhang, Zheng Zhou, Chutian Wang, Jian Zhang
arXiv·2026-10-22·Relevance 5 · Novelty 4 · Practical 4 · Evidence 4 · Timely 5

大模型推理服务会把算过的 KV cache 存到 SSD 上，下次遇到同样开头的请求就直接读回来，不用重算。NVIDIA 为此提供了 GPU Direct Storage（下文简称 GDS），让数据从 SSD 直接进 GPU 显存，不在主机内存里中转。可作者在开源缓存系统 LMCache 里实测发现，用 GDS 异步读数据，单条任务队列只跑出 2.36 GiB/s，不到同步读带宽的一半；99.6% 的时间都卡在“提交请求”这一步。中山大学、港科大（广州）等单位的这篇论文开源了 uGDS，把“指挥 SSD 干活”这件事从操作系统内核搬到普通程序里来做。数据照样从 SSD 直达 GPU，变的是谁来下命令。在一块 A100 显卡加一块三星 990 PRO 固态盘上，uGDS 批量读的速度最高是 GDS 的 12 倍，批量写最高 30 倍；接进 LMCache 后，长提示的首字延迟（从发出请求到看到第一个输出字的时间）中位数从 1.9 秒降到 0.7 秒。

1. 问题：数据不绕路了，命令还在绕

先说清楚“数据路径”和“控制路径”的区别。数据路径是数据本身从哪里流到哪里；控制路径是谁、通过什么步骤告诉硬件“把哪块数据搬到哪里”。

GDS 解决了数据路径：SSD 可以通过 PCIe 把数据直接 DMA 进 GPU 显存，不经 CPU 搬运。但 GDS 的控制路径每次都要进操作系统内核：一个读请求要依次经过虚拟文件系统、具体的文件系统、块设备层、内核的 SSD 驱动，NVIDIA 的内核模块还要为每 4 KiB 一页的数据查一次 GPU 地址。搬一大块数据时，这些固定开销被摊薄了，不显眼；可在 KV cache 读写、向量检索这类场景里，请求往往小而频繁，又对延迟敏感，这笔开销就成了大头。

作者还指出 GDS 的另外两个问题。

第一，排队规矩太死。GDS 的异步接口继承了 GPU 任务队列（CUDA stream）的规矩：同一队列里，每个请求都要等前一个做完。可 LMCache 读回一段缓存时，各个小块之间根本不需要先后顺序，只要模型计算开始前全部到齐就行。为了跑满带宽，应用只能把请求拆到很多条队列上，等于替 GDS 做调度。

第二，出了问题看不见。GDS 的内核部分开源，但负责批量提交、后台线程和队列衔接的用户态库只发布二进制文件。卡顿了既查不了原因，也改不了策略。

早先已经有人在普通程序里直接驱动 SSD，证明这条路走得通，但那些原型只支持 NVIDIA 显卡，假定只有一个线程在提交，也不跟踪“还在传的请求”，可能出现 SSD 还在往一块显存里写、程序就把这块显存释放了的情况。

2. 方法：CPU 下命令，SSD 搬数据，GPU 只管算

uGDS 把三件事分开。

启动时，只做一次需要特权的设置，由一个小的内核模块完成：从内核驱动手里接管这块 SSD，把 SSD 的控制寄存器和命令队列映射到程序自己能直接读写的内存里，锁定要用的 GPU 显存，记下它们在总线上的地址。

平时读写时，内核完全不参与。程序自己按 SSD 的协议（NVMe，固态盘通用的命令格式）写好一条 64 字节的命令，说明从盘上哪里读、读多少、放到显存的哪些页；然后往 SSD 的一个“门铃”寄存器里写一个数，通知它有新命令；之后去完成队列里查 SSD 有没有报告做完。整个过程都是普通的内存读写，不需要系统调用。

数据本身照旧在 SSD 和 GPU 显存之间直接传，不经过主机内存。

代价是 SSD 必须从内核驱动上解绑，交给 uGDS 独占，程序看到的是“盘上第几个字节”而不是文件。作者认为这和 LMCache、Mooncake 这类自己管理存储块的缓存引擎正好匹配；需要文件的话，可以在上面再叠一层用户态文件系统。

为了让这条路既快又安全，uGDS 做了四个设计。

一是同时支持 NVIDIA 和 AMD 显卡。显存注册时，把两家各自的显存地址统一翻译成 SSD 能认的页地址列表，上层代码不用区分是哪家的卡。

二是把命令队列分成两组。SSD 支持多组命令队列。uGDS 拿出一组深队列专门跑批量请求，其余给单个的同步请求用。这样一大批请求涌进来时，不会把单个请求挤在后面等。批量请求还会攒好多条命令后只按一次“门铃”，省掉重复的通知开销。

三是防止“边写边释放”。这是自己驱动硬件最容易出事故的地方。每发出一个请求，uGDS 就给涉及的显存记一笔“有传输在途”；在途时想释放这块显存，会直接被拒绝。每次注册还带一个递增的编号，防止旧请求误伤新分配到同一地址的显存。命令超时时，这块盘会被标记为故障并隔离，必须等硬件复位、确认 SSD 已经停手，才能回收资源。

四是完成通知可选。默认由 CPU 不停查询完成队列，响应最快，但会占满一个 CPU 核。也可以改用硬件中断，内核只负责叫醒程序，其余照样在用户态完成。

这些想法单独看都不新，在普通程序里直接驱动 SSD 的 SPDK 早就有了。uGDS 的贡献是把它们做成了一个和 GDS 接口一一对应、可以直接替换上线的 GPU 存储库：同步、批量、按队列异步三种接口都有，两家显卡共用一套抽象，安全机制补齐，从内核模块到用户态全部开源。最实用的一点是一条队列就能跑满带宽，应用不用再把请求拆到十几条队列上。

3. 实验：小请求、批量请求和首批请求

测试用的是一台装两颗 Intel 至强 CPU、一块 A100 显卡、一块三星 990 PRO 1TB 固态盘的服务器，对比 NVIDIA 当前版本的 GDS。

uGDS 启动更快：初始化中位数 42 毫秒，GDS 要 115 毫秒，几乎全花在打开 NVIDIA 的驱动会话、加载配置和探测总线拓扑上。对需要频繁拉起、回收工作进程的弹性服务，这能省不少时间。

单个小请求的提升最大。2 个线程写 4 KiB 的小块时，uGDS 的带宽是 GDS 的 6.2 倍，平均延迟从 48 微秒降到 7.7 微秒，因为每次少走了一大串内核步骤。线程多了、请求大了以后，瓶颈转到 SSD 和总线本身，差距缩小到 1.2 到 1.4 倍。在 AMD 平台上和 AMD 的同类库相比，也快约 1.2 倍。

批量请求全面领先。作者测了 36 种“请求大小 × 每批多少个”的组合，uGDS 全部胜出：读是 GDS 的 2.1 到 12.1 倍，写是 2.3 到 30.7 倍。请求越小、每批越多，差距越大。

作者顺着一个反常现象追到了 GDS 的一个问题。按道理每批请求越多应该越快，可 GDS 写 128 KiB 请求时，批量越大反而越慢。原因在第一批：每批 128 个请求时，GDS 的第一批读要 91 毫秒、写要 118 毫秒，占了整个 64 MiB 传输时间的近九成。这是因为 GDS 把显存的地址映射拖到第一次读写时才做，作者推测它还在第一次提交时才分配批量处理所需的内部状态。uGDS 在初始化时就把这些做完了，第一批和后面的批次几乎一样快。就算去掉第一批只看之后的稳态，4 KiB 请求每批 128 个时，uGDS 读仍是 GDS 的 8.8 倍，写是 23.8 倍。

轮询和中断各有用处。4 KiB 小请求时，CPU 不停查询能把延迟从 21 微秒降到 9 微秒，代价是占满一个核。1 MiB 大请求时，改用中断能让发请求的线程 CPU 占用从 100% 降到 4%，延迟只多 5.5%。所以延迟敏感的场景用轮询，大块传输用中断更划算。

5. 局限

uGDS 要独占整块 SSD：从内核驱动上解绑后，这块盘没有文件系统，也不能再给其他程序当普通盘用。目前一套 uGDS 只驱动一块本地 SSD，多盘并用和通过网络访问远端 SSD 还在计划中。同步请求按顺序分配到命令队列，并且一直占着队列直到完成，所以一个大请求会拖慢排在同一队列上的小请求，作者计划加一个按负载分配的调度器。实验只用了一块消费级固态盘、一张 A100，并关掉了 IOMMU（让设备访问内存时做地址检查的硬件），端到端也只测了 0.6B 的小模型。数据中心级 SSD、多张 GPU 共用总线交换芯片时表现如何，还有待验证。

6. 实践意义

如果你在做 KV cache 的分层存储（显存、内存、SSD 三级）或 GPU 向量检索，而且 SSD 是专用的本地盘，uGDS 值得作为 GDS 的替代品试一试。小块、高频、只用一条队列的读取，正是 GDS 最吃亏、uGDS 优势最大的场景。

上线前要确认三件事：这块 SSD 能不能独占、从内核驱动上解绑；上层是不是已经自己管理存储块的分配，像 LMCache、Mooncake 那样；服务器的 IOMMU 设置是否允许 SSD 和 GPU 直接互传。部署时可以按负载选完成通知方式：对延迟敏感的推理节点用 CPU 轮询，吞吐型或 CPU 紧张的任务用中断。

就算不换库，论文对 GDS 的两点分析也能直接用上。第一，GDS 第一次读写某块显存时会额外花几十毫秒做准备，所以服务启动后应先对每块“显存—盘”组合做一次预热读写。第二，GDS 的单条队列会被提交卡住，所以关键的读取要拆到多条队列上并行。

RACE: RoPE-Aligned Attention Compression Based on Query-Key Activation Energies

📖 深度解读 · 10 分钟 →

大模型处理长文本时存在显存里的 KV cache 越来越大，压缩它的一个方向是把每个词存的向量变短，但已有方法大多只省了存储：存的时候是短向量，真到计算时又得先还原成原来的长度，计算量反而暴涨。RACE 找到了一种不用还原的变短办法：位置编码把向量里每两个相邻的数组成一对一起旋转，只要整对保留，短向量照样能直接旋转；保留哪些对，按一小批文本上查询和键在这一对上的数值平方和挑最大的，再把这个选择直接写进模型权重。在 Llama-3.2-3B 上，向量缩短一半、输入 25.6 万个词元时，整体吞吐提高到 1.79 倍，首字延迟降 43.2%。

Irene Tenison, Abdulrahman Alabdulkareem, Daniel Karl I. Weidele, Nima Dehmamy, Dan Gutfreund
arXiv·2026-10-20·Relevance 5 · Novelty 4 · Practical 4 · Evidence 4 · Timely 4

大模型处理长文本时，要把读过的每个词留下的中间结果存在显存里，这份“记忆”叫 KV cache。文本越长，它越大，到几十万字时往往比模型本身还占地方。压缩它有三个方向：少存几个词，降低每个数的精度，或者把每个词存的向量变短。第三个方向已有方法，但大多只省了存储：存的时候是短向量，真到计算时又得先还原成原来的长度，计算量反而暴涨，最多到原来的 22 倍。这篇论文的 RACE（RoPE-Aligned Attention Compression，与旋转位置编码对齐的注意力压缩）找到了一种不用还原的变短办法：只成对地保留模型位置编码要用的坐标，再把这个选择直接写进模型权重。这样存储、位置编码和注意力计算全都在短向量上完成，不需要改推理程序。在 Llama-3.2-3B 上，向量缩短一半、输入 25.6 万个词元时，总计算量降 47.8%，整体吞吐提高到 1.79 倍，首字延迟降 43.2%。

1. 问题：省了存储，没省计算

先交代几个背景知识。注意力机制里，每个词会算出一个“查询”向量和一个“键”向量，两者做点积，得到这个词该多关注前面哪个词。KV cache 存的就是前面每个词的“键”和“值”向量。每个注意力头里这两个向量的长度叫“头维度”，常见的是 128。把头维度从 128 砍到 64，KV cache 就少一半。

难点在位置编码。现在的模型大多用 RoPE：向量里每两个相邻的数组成一对，按词的位置旋转一个角度。这样的每一对坐标，论文叫“旋转对”。

问题是，如果用一个一般的矩阵把键向量压短，这个压缩和旋转的先后顺序就不能交换：先压缩再旋转，和先旋转再压缩，结果不一样。而模型是按“先旋转”训练出来的。所以 EigenAttention、PALU（两种用矩阵压缩向量的方法）只好在每次计算前，先把短向量还原回 128 维，再做旋转。存储是省了，计算却多了一个还原步骤。论文统计，存储减半时，生成每个新词的计算量 EigenAttention 是原来的 11 倍，PALU 是 22 倍。

另外两种已有做法各缺一块。Thin Keys 不需要还原，但只压键向量、不动值向量，KV cache 只能省到 75%。同期的 RAP（一种结构化剪枝方法）也保留完整的旋转对，但它要算梯度来决定留哪些，需要反向传播，而且只看键这一边。

2. 方法：成对保留坐标，按“能量”挑

作者把目标说得很清楚：找一种把向量变短的办法，让短的查询和短的键做点积，结果尽量接近原来长向量的点积；同时这个办法必须能放在旋转之前做。由此推出两条原则。第一，查询和键要用同一种方式变短，因为点积是两个向量逐个坐标相乘再相加，两边的坐标必须对得上。第二，挑保留哪些坐标时，要同时看查询和键，因为要近似的是两者的乘积。

哪种变短的办法能放到旋转之前？论文证明了一个精确的条件。如果变短的方式是直接挑出其中一些坐标、丢掉其余的，那么它和旋转可以交换先后，当且仅当挑出来的坐标正好是若干个完整的旋转对，并且顺序不变。道理很直观：一对坐标在旋转时会互相混合，只留其中一个，就会丢掉另一个混进来的那部分。只要成对保留，在短向量上按原来的角度转，结果就和“先整体旋转、再挑坐标”完全一样。

接下来要决定留哪些对。作者在一小批通用文本上跑一遍模型，记下每个旋转对上查询和键的数值有多大，把两边数值的平方和加起来，作为这一对的“能量”。能量大，说明这一对对点积的贡献大。要把 128 维压到 64 维，就保留能量最大的 32 对。作者证明，丢掉一些对造成的误差，不会超过被丢掉的那些对能量之和的一半。所以按能量挑，正好让这个误差上限最小。作者也说明，这不等于让真实误差最小，只是一个只需跑一遍前向、计算很便宜的实用准则。

值向量不参与旋转，所以压缩起来没有这个限制。作者沿用 EigenAttention 的办法：从同一批数据里找出值向量变化最大的 64 个方向，只保留这些方向上的分量。

最后一步是把这些选择“折叠”进权重。挑坐标和找方向，本质上都是乘一个固定的矩阵，可以提前乘进模型里生成查询、键、值的那几个权重矩阵，以及最后的输出矩阵。结果就是一个普通的注意力层，只是头维度从 128 变成了 64。位置编码只对保留的旋转对做，每一对仍然用它原来的旋转角速度。之后的点积、加权求和全都在 64 维上算，用标准的 PyTorch 注意力就能跑，不需要专门写底层程序。

压缩得比较狠时，可以再做一步可选的“恢复训练”：用 100 万个词元的通用文本，让压缩后的模型去模仿原模型的输出，只更新被改过的注意力权重，其余参数不动。保留 75% 时这一步帮助不大；保留 50% 时，能找回大部分损失的效果。

论文的核心贡献在于说清了“哪些压缩是合法的”。证明只有“成对保留”这一类能直接在短向量上做之后，问题就从“怎么还原”变成了“在合法的旋转对里挑哪些”。压缩后的模型就是一个头维度更小的标准模型，现有推理框架不用做任何修改。

3. 实验一：效果能不能跟上需要还原的方法

作者在 Qwen2.5-7B、Llama-3.2-3B-Instruct、Granite-4.1-3B 三个模型上，比较 RACE 和 PALU、EigenAttention、Thin Keys、RAP。看的指标有三个：语言建模能力（困惑度，越低说明模型越能预测下一个词）、15 个不经额外训练直接测试的常识任务的平均准确率，以及 16 个长文本任务（LongBench）的平均分。

保留 75% 时，RACE 保住了原模型常识任务准确率的 96.5% 到 98.5%。各个压缩档位上，RACE 的常识和长文本分数都和 PALU 接近，但不需要计算时还原；它在所有档位都比 RAP 好，在保留 50% 和 75% 时困惑度最低。

4. 实验二：省下的存储能不能变成真实的速度

存储省了，不代表实际跑得更快，所以作者在 Llama-3.2-3B-Instruct 上实测了速度。提示长度分别是 6.4 万、12.8 万和 25.6 万个词元，每次输出 128 个词元，每组跑 10 次取平均。

提示越长，收益越大，因为文本越长，注意力在总计算里占的比例越高。25.6 万词元、保留 50% 时，读完提示的速度提高到 1.76 倍，逐词生成的速度提高到 1.90 倍，整体吞吐提高到 1.79 倍。显存只降了 28%，没有降到一半，因为显存里还有模型参数和其他中间结果，这部分不受影响。

作者还试了把 RACE 和其他压缩方法叠加：先用 RACE 保留 75%，再用 H2O 或 SnapKV 丢掉一半的词，或用 KIVI（一种降低 KV cache 数值精度的方法）把精度降一半，总共只剩 37.5%。叠加后的损失比单用 RACE 大，说明两种压缩的影响不是各算各的。三种组合里，和 KIVI 降精度叠加损失最小，困惑度尤其稳定。

另外三个发现也有参考价值。第一，用来计算“能量”的那批文本不必和下游任务相似：用通用文本和用任务数据，大多数任务的分数差距在 6% 以内。第二，同时看查询和键确实比只看一边好，近似误差更小，困惑度也最低；而且这种挑法很便宜，校准只要 2.7 秒，基于梯度的挑法要 8.3 秒。第三，作者从头训练了三个约 2.45 亿参数的小模型，总维度相同，只是头的数量和宽度不同。压缩得很狠时，头少而宽的模型保持得最好，因为每个头里可挑的旋转对更多。

5. 局限

作者自己指出了几点。按能量挑，让最小化的是误差的上限，不是真实误差。压到 50% 时需要一次恢复训练，不能完全免训练。和丢词类方法叠加时，两级压缩的损失会互相放大。论文的证明只覆盖“直接挑坐标”这一类变短方式；为了不用还原，它主动放弃了更一般的压缩矩阵，更大范围里有没有更好的办法，论文没有讨论。速度只在一个 30 亿参数的模型上测过，提示短于 25.6 万词元时收益更小；更大的模型、或多个查询头共用一组键值的架构上效果如何，论文没有给出。

6. 实践意义

对长文本推理服务，RACE 最大的好处是部署简单：输出就是一个头维度更小的标准模型文件，vLLM、SGLang 这类推理框架不用改底层程序，还能和 KIVI 这类降精度方法叠加。可以先在自己的模型上保留 75% 做试点：用三万多个词元的通用文本算能量，不做恢复训练，看长文本任务掉了多少。如果要压到 50%，就预留一次百万词元量级的恢复训练。如果你在设计新的预训练模型，并且预计部署时要做这类压缩，头更少、每个头更宽的设计，会给后面的压缩留出更多余地。

一个智能体做一道复杂任务，往往要和搜索、网页、代码执行等工具来回几百轮。每一轮，模型都要把之前所有内容的 KV cache 重新读一遍。论文统计，读这些旧缓存占了总调用费用的 82.4%，比生成新内容贵得多。常见的省钱办法是删掉或摘要旧消息，但只要改动了前面的文字，后面所有缓存都作废，得从改动处重新算一遍。清华大学团队提出换个层面来做：文字记录一个字不动，只在缓存里把选中的部分丢掉，留下的部分原样接着用。他们为此做了一个推理服务系统 AKV。在三个模型、四个智能体测试上，一个简单的策略“只保留最近 12 次工具返回的缓存”，和常用的“到长度上限就摘要”相比，平均得分高 1.7 分，平均费用低 27.7%。

1. 问题：重算太贵，一刀切又会丢信息

智能体的对话越长，缓存带来两个问题。一是费用：缓存越积越多，每轮都要读一遍，存储和读取开销很大。二是准确率：模型一次能可靠处理的长度有限，参与计算的内容超过这个范围，效果会明显变差。

现在的通行办法是改文字，也叫“上下文工程”：把旧消息删掉或换成摘要。但大模型的缓存是按顺序算出来的，每个词的缓存都依赖它前面的所有内容。改动越靠前，后面需要重算的部分就越长。所以常见的智能体框架会一直等到长度到了某个上限，再一次性把大部分历史摘要掉，只留最近几轮，这样重算的次数少一些。可这样一刀切，很容易把中间几轮的有用信息也丢了。

作者先做了一个对比。用 GPT-OSS-120B 做 BrowseComp-Plus（一个需要多轮搜索才能回答的问答测试）的前 100 题，每题做 4 次、最多 100 轮。只保留最近 12 次工具返回、每轮删文字的做法，因为反复重算，费用是不做任何处理时的 1.85 倍。到 4.8 万词元才摘要一次的做法，费用只降了约 7%，准确率却掉了 5 个百分点。而直接在缓存里丢掉旧的工具返回，准确率和费用能同时变好。

2. 方法：对缓存的三种操作

作者先区分两个长度。一个是对话记录在文字上有多长；另一个是真正参与后续计算的缓存有多长，论文叫“活跃缓存”。改文字的做法改的是前者，改缓存的做法只改后者。

在这个框架下，论文定义了三种操作：

  • 追加：这是平常的做法，读进新的词，把它的缓存接在后面，位置编号加一。
  • 丢弃：把指定的缓存条目排除在之后的计算之外。留下的条目原封不动，文字记录也不变，之后新词的位置编号照常往后数。
  • 重排位置：把留下的条目按原来的先后顺序，重新编号为 0、1、2……，下一个新词接着往后编。

为什么需要第三种操作？丢弃不会让编号变小，缓存虽然少了，编号还是一路往上涨，迟早超过模型能处理的最大位置。重排位置就是把编号压回去。对用 RoPE 的模型，这一步很便宜：把一个条目从第 p 位挪到第 q 位，只要把它的 key 再旋转 q−p 对应的角度，value 不用动，也不用重新计算。

丢哪些？作者看了模型的 attention 分布，发现两个规律：越旧的内容被关注得越少；距离差不多时，工具返回的内容又比模型自己的推理内容被关注得少。所以主策略是滚动丢弃旧的工具返回：保留所有推理内容和最近 12 次工具返回，更早的工具返回的缓存逐步丢掉。

3. 难点：同一段文字，缓存可能不一样

平常的推理服务里，只要文字开头相同，缓存就相同，所以可以按“开头相同”来复用缓存。改缓存打破了这一点：同样的文字，经过不同的操作顺序，会得到不同的缓存。

用图里的例子说明。三条路径最后都只留下 B 和 C。但 ① 里 C 是在还能看到 A 的时候算出来的，带着 A 的影响；② 里算 C 时 A 已经被丢了；③ 里连 B 自己算出来时前面都没有 A。所以三条路径里 C 的缓存各不一样。论文因此用“从空缓存开始做过的全部操作”来描述缓存状态：对同一个模型，这串操作唯一决定了当前的缓存。推理服务必须同时记住文字历史和操作历史，才能正确复用。

4. AKV：怎么把它做成一个推理服务

AKV 的接口和标准的对话接口几乎一样。客户端照常发送完整的消息列表，只多一个可选字段，写明“在第几条消息之后丢掉哪些、在哪里重排位置”。客户端不需要知道服务端还存着哪些缓存，每轮照常追加消息和操作就行。

服务内部有三个机制。

第一是复用。推理服务一般用前缀树（radix tree）做 prefix caching，前缀相同的请求共用一段缓存。AKV 在树上加了“丢弃”和“重排位置”两种节点，查找时既比文字也比操作。所以图里的 ① 和 ② 能共用 A–B 这一段，但因为丢 A 的时间不同，C 各存一份。

第二是回收。一个缓存条目只有在没有任何正在进行的计算还需要它时，才能被释放。比如 ① 和 ② 都丢掉 A 之后，A 的缓存不用等请求结束就能释放。显存紧张时，先回收已经被丢弃的缓存，再回收已结束请求的缓存，因为后者下一轮更可能被用到。

第三是恢复。缓存被挤出显存后，下次要用时得重新算出来。可普通的从头计算只能得到“什么都没丢过”的缓存，而一步步重放每个操作又要算很多遍。AKV 的做法是在每一层把要重算的内容按丢弃和重排的时间点切成几段，每段只看自己和前面各段在当时还保留着的缓存，所有段一次性算完。这样一次计算就能复原出经过丢弃和重排的准确状态。

5. 实验结果

对照组是两种“到上限就摘要”的做法。“标准”做法用模型自带的较高上限（GPT-OSS-120B 和 MiniMax-M2.7 为 9.6 万词元，MiroThinker-1.7-Mini 为 19.2 万）。“改文字”做法用同样的摘要方式，但上限统一降到 4.8 万。AKV 用“保留最近 12 次工具返回”的滚动丢弃。测试集有四个：两个多轮搜索问答（BrowseComp-Plus、xbench-DeepSearch）、GAIA 的 103 道纯文字题，以及修真实代码库漏洞的 SWE-bench Verified。费用按实际读入和生成的词元计价。为了不偏袒自己，作者让重排位置涉及的每个词元也按读缓存的价格收费，有意高估了这一步的成本。

6. 局限与实践意义

作者列出的局限是：丢哪些、什么时候丢，还需要更多探索；还没有在这套机制下专门训练智能体；对线性注意力这类新架构的模型还不支持。另外有几点值得注意。实验用的主策略是手工定的固定规则，最佳的“保留几次”可能因任务而异。被丢掉的内容仍然会通过之后算出的缓存间接留下影响，作者把这看作优点，但这也意味着结果依赖操作顺序，调试和复现时要记下完整的操作序列。

对做智能体平台和推理服务的团队，这篇论文的价值在于把“压缩上下文”从文字层挪到了缓存层。如果你的智能体有大量工具返回，比如检索结果、网页、代码运行输出，而现在靠“到上限就摘要”控制长度，可以先在自己的轨迹上看看模型对工具返回和推理内容的关注度差多少，再试“滚动丢弃旧工具返回 + 重排位置”，这是论文里最稳的组合。落地的前提是推理服务能区分操作历史：如果服务端只按“文字开头相同”复用缓存，同一段文字下不同的丢弃时间会被错误地混用。AKV 基于 SGLang 实现，代码已公开，客户端接入时只需多传一个字段。

1. 问题：top-k 丢了长尾，均匀采样又浪费预算

预算是 k 个 token，现有方法分配它的方式有三种。第一种只做检索，Quest、PQCache 用代理分数挑分数最高的 k 个，Tactic 做的是 top-p。注意力集中在少数 token 上时这很好用；可一旦分布比较散，集合之外那些 token 的注意力权重（softmax 后的概率，全部 token 加起来是 1）就全部丢了，代理分数再有一点偏差，真正重要的 token 会刚好落在边界外。第二种只做采样，MagicPig 用 LSH 近似抽样再做重要性校正，覆盖面广，但预算小时方差很大。第三种是混合，vAttention 保留 top-k，再从剩下的 token 里均匀抽样。它比前两种都好，可在激进稀疏下离稠密注意力还是有明显差距。

作者认为问题出在“均匀”。top-k 之外剩下的 token，注意力权重有大有小，差别很大，均匀抽样会把同样多的预算花在几乎没贡献的 token 上。他们先做了一个小实验：同样的预算，把稀疏近似算出的注意力输出和完整注意力的输出相减，误差的 L2​ 范数再除以完整输出的范数，这叫相对 L2​ 误差。按代理分数抽样的相对误差在各种预算比例和稀疏度下都低于均匀抽样（下图）。这就是 SSA 的出发点。

这个框架和用哪种近似检索无关。任何能给出代理分数的 top-k 方法（PQCache、Quest 等）都能直接拿来当 SSA 的提议分布，检索方法变好，SSA 也跟着变好。

3. 实现：让抽样不拖慢解码

长上下文解码受显存带宽限制，SSA 要省的是读 KV 的流量。为了跑得快，实际 kernel 没有用自适应的 λ，而是固定重集合占预算的比例 h，作者报告这样和理论版本的结果很接近。解码一步分四个阶段，前三个阶段要扫完整个上下文，但每个 token 只读几个字节。

第一阶段算代理分数。每个 key 存成 16 字节的 PQ 码（16 个子空间、256 个中心），而 head 维度 256 的 fp16 KV 对要 1 KiB，所以扫一遍 PQ 码比读 KV 便宜得多。开头 128 个 token（sink token，模型习惯把大量注意力放在这里）和最近 128 个局部 token 无论如何都会保留，它们的分数在同一个 kernel 里顺带屏蔽掉，免得再被选一次，不用再扫一遍。

第二阶段用 radix top-k 选出重集合：按分数的二进制位从高到低逐段统计落在每个桶里的 token 数，几轮就能定出第 k 大的分数门槛，不用把百万个分数整体排序。返回的下标不排序，因为上面的估计量和顺序无关。

第三阶段在残余里抽样。直接在百万个 token 上建分布、抽样太慢，所以作者分层抽：每次先选一个 1024 token 的 chunk，再在里面选一个 32 token 的子块，最后在这不到 32 个 token 里选一个；chunk 被选中的概率等于它里面所有 token 的 pi​ 之和；选定 chunk 之后，子块按它在这个 chunk 里所占的 pi​ 份额来选，token 再按它在子块里所占的份额来选。三级概率相乘，每个 token 最终被抽中的概率正好是 pi​，和直接在全部残余 token 上抽一样。同一个 query 的多次抽样可能抽到同一个 token，所以每个 query（注意力矩阵的一行）配一个哈希表去重，每个去重后的样本按 1/πi​ 重新加权。πi​ 最小截断到 10−4，防止个别权重大到失控，代价是带进一点偏差。随机数用基于计数器的 RNG，这样能兼容 CUDA graph。

第四阶段从分页 KV cache 里取出选中的 K、V，用 online softmax 算注意力：K、V 分批读入，边读边维护当前的最大分数和指数和，最大值变了就把已经累加的输出按比例缩放，读完一遍就得到归一化好的结果，不用先存下全部分数。为了多用并行度，每个 query head 拆给多个 thread block，最后用 log-sum-exp 合并。拆多少份有讲究：1M 上下文、batch 1 时，拆 64 份比 32 份快 1.58–1.71 倍，但拆到 128、256 份反而变慢，因为启动和合并的开销超过了并行带来的收益。

4. 实验：激进稀疏时优势最大，代理分数质量仍是瓶颈

对照组有三个：PQCache、vAttention（用 PQ 分数），以及 Oracle-top-k。Oracle-top-k 先算精确分数再挑 top-k，本身没法加速，只当作“确定性检索最多能做到多好”的参考。所有方法都留 128 个 sink token 和 128 个局部 token。模型有 Llama-3.1-8B、Qwen3.5-4B/9B、Ministral-3-3B/8B，LongBench 上另加 Qwen3.5-27B。

重集合比例 h 是预算里分给确定性 top-k 的份额，剩下的给抽样。同样在 AIME 2025 上、10 倍和 20 倍稀疏下做的消融说明两部分都不能少：h 在 0.2 到 0.8 之间，得分都在 61.0–64.0；全部预算拿去抽样（$h=0$）只有 40.2–42.5，全部给 top-k（$h=1$）是 49.4–53.8。

LOFT 和 LongBench 上看不出差别。LOFT 上 SSA 的注意力误差在所有设置下都是非 oracle 方法里最低的，但任务指标 subspan-EM（标准答案作为子串出现在模型输出里就算对，满分为 1）在各方法之间最多差 0.04；LongBench（Qwen3.5-27B）上所有稀疏方法都在稠密 1 分以内。也就是说，误差变小不一定变成任务分数的提升，要看任务本身对稀疏有多敏感。

速度在单张 H200 上测（16 个 query head、4 个 KV head、head 维度 256、fp16 KV）。上下文短时 SSA 反而慢，因为前三个阶段的固定开销摊不开：batch 1、128K 时，它只有 FlashInfer 速度的 0.60–0.74 倍。上下文越长越划算，到 1M 时，50 倍稀疏快 1.79 倍，20 倍快 1.39 倍，10 倍只快 1.07 倍。batch 变大收益更高，1M、batch 16、50 倍稀疏时到 2.96 倍。

kernel 优化是 batch 1 也能比稠密快的原因。不做第 3 节那些优化的参考实现，同样的算法只有 FlashInfer 的 0.37–0.47 倍，到 batch 8 才追上；优化后快了 2.95–3.80 倍。抽样这一步的对照是只按 chunk 分层：选定 1024 token 的 chunk 之后，直接在这 1024 个 token 上抽，不经过 32 token 子块这一级。加上子块这一级后，抽样快了 1.21–3.16 倍（抽的次数越多，差距越大），1M 上下文、$h=0.4$ 时抽样本身只花 0.30–1.18 ms。

5. 局限与实践意义

局限有几条。实际 kernel 用的是固定比例 h，自适应分配还没有同样高效的实现。πi​ 截断会带来少量偏差。抽样有随机性，同一个请求解码两次，注意力输出不完全一样，需要可复现时要固定随机种子。128K 以下、batch 1 时 SSA 比 FlashInfer 慢。在 Qwen3.5、LongBench 这种稀疏本来就不怎么掉点的设置下，SSA 也没有明显优势。作者提到下一步想让用户自己设定可接受的近似误差，系统保证输出不超过这个误差，但论文没有给出具体做法。

对工业界，SSA 适合的场景很明确：百万级上下文、batch 较大，而且要压到 20–50 倍以上稀疏的解码服务，比如长时程智能体的会话历史、超长文档问答、长推理链生成。如果系统里已经有 PQCache、Quest 这类 top-k 检索，接 SSA 的改动不大：检索索引原样复用，只是把一部分预算从 top-k 挪给按代理分数的抽样，再加上 1/πi​ 修正。上线前先在自己的任务上扫一遍 h，论文里 0.2–0.8 都不错，纯 top-k 和纯抽样都明显更差。如果你只需要 5–10 倍稀疏，现有的 top-k 或 vAttention 大概已经够用，SSA 的收益主要在更激进的区间。
