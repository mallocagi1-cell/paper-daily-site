ATTUNE: Agentic Throughput Tuning for LLM Training

LLM 训练吞吐取决于切分、显存-算力交换与通信重叠这套「配方」，换模型/加速器/框架就要重做；现成自动调参只在固定旋钮空间里搜、只检查能跑，常漏掉空间外杠杆，还可能悄悄改掉训练语义。Amazon ATTUNE 是编码 agent：在 GPU-小时预算内无人值守改任意能跑配方。在 H100/H200/B200 上平均吞吐 +1.7×，四条 NVIDIA AutoModel 官方基准配方被它高出 6–17%；留出模型上最高把写给别的场景的配方抬到 2.6×（MiniMax-M2）。吞吐缺口往往在固定旋钮空间之外——让 coding agent 改配方，比在预设网格里搜更对症。

LLM 训练吞吐取决于切分、显存-算力交换与通信重叠这套「配方」，换模型/加速器/框架就要重做。固定旋钮搜索只检查能跑，常漏掉空间外杠杆，还可能悄悄改训练语义。Amazon ATTUNE 是编码 agent：在 GPU-小时预算内无人值守改任意能跑配方。H100/H200/B200 上平均吞吐 +1.7×（最高约 3.9×），四条 NVIDIA AutoModel 官方基准配方被它高出 6–17%；留出模型上把写给别的场景的配方最高抬到 2.6×（MiniMax-M2）。吞吐缺口往往在固定旋钮空间之外——让 coding agent 改配方，比在预设网格里搜更对症。

1. 问题

现成自动调参在预设旋钮上贝叶斯/网格搜索，目标只是「跑得动」。真正缺口常在专家容量因子、重叠策略、内核选择等「配方文本」里。ATTUNE 把搜索改成改代码/配置的 agent 循环。

2. 方法

单 agent 做 reason–act：陈述假设 → 改一处 → 跑 profile → 诊断瓶颈。agent 外的确定性门控拒绝会改训练目标的旗标、判定测量是否有效、是否超过当前 leader；搜索结束后再做一致性检查。预算按 GPU-小时封顶，无人值守。

3. 核心贡献

把「调参」升级成「改配方」：搜索空间不再被旋钮表绑死，同时用门控防止 silent training change。可改的是配方文本，不可改的是训练语义——门控把两者拆开。

4. 实验

在多代 NVIDIA 集群上替换生产/基准配方：平均 +1.7×，峰值约 3.9×；对 NVIDIA AutoModel 已发布吞吐高 6–17%。留出模型（开发未见）上，跨场景配方迁移最高 +2.6×；vendor 已精细调过的面提升最小。同 GPU-小时预算下优于含贝叶斯优化在内的自动调参基线。

设置观察
H100/H200/B200 平均吞吐 +1.7×
峰值约 +3.9×
vs AutoModel 发布配方+6–17%
留出 MiniMax-M2最高 +2.6×

示意走查：一份 MoE 配方在 H100 上卡住通信。agent 假设 expert capacity 过大导致 token 路由不均，改一处 capacity 因子后重跑 profile；门控确认 loss 曲线未偏、吞吐上升则接纳。下一轮再动 overlap。整段搜索耗尽预算后输出最终配方与拒绝日志。

与「只搜并行度/微批」的自动调参相比，ATTUNE 能改到框架脚本里的非旋钮杠杆；代价是必须有强门控，否则 agent 可能打开会改数值结果的旗标。作者在多代集群与留出模型上验证：收益最大的往往是「别人写的配方迁到你的堆栈」，而不是在已 vendor 精调的面上再抠几个点。

5. 局限

依赖可跑的初始配方与可解析的 profile；门控规则需随框架版本维护；吞吐收益不等于收敛曲线不变，需回归 loss。

6. 实践意义

训练平台可把 ATTUNE 类 agent 挂在「新模型×新集群」接入流程；先跑门控白名单，再放 GPU-小时预算。

uGDS: A User-Space Development Kit for High-Performance GPU Direct Storage

📖 有深读 · 3 分钟

NVIDIA GDS 让 NVMe 经 PCIe P2P 直达 GPU，但仍有三条硬伤：控制面每次 I/O 穿内核、stream 路径强全序、用户态引擎闭源难诊。uGDS 做成用户态开发套件；在 Samsung 990 PRO 上批量读带宽最高达 GDS 的 12.12×、写 30.69×，两线程下 4-KiB 同步写延迟降 84.1%。GDS 单 stream 只保住同步 16-MiB 读带宽的 40.8%，提交调用可占墙钟 99.6%。GPU Direct Storage 的瓶颈常在控制面与排序语义，而不只在 DMA 带宽。

NVIDIA GDS 让 NVMe 经 PCIe P2P 直达 GPU，但仍有三条硬伤：控制面每次 I/O 穿内核、stream 路径强全序、用户态引擎闭源难诊。uGDS 做成用户态开发套件（libugds + 最小内核辅助）。Samsung 990 PRO 上批量读带宽最高达 GDS 的 12.12×、写 30.69×；两线程下 4-KiB 同步写延迟 −84.1%。单 stream 上 GDS 只保住同步 16-MiB 读带宽的 40.8%，提交调用可占墙钟 99.6%。接入 LMCache 后 TTFT 中位数最高 −62.7%，serving goodput 2.63×。GPU Direct Storage 的瓶颈常在控制面与排序语义，而不只在 DMA 带宽。

1. 问题

KV cache offload 等小 I/O 对固定每请求内核开销极敏感；GDS stream API 的全序在只需批级序时过强；闭源引擎阻碍定制调度。

2. 方法

三路径：Setup 用特权内核委托建好队列后稳态绕开 OS；Control 在用户态发 NVMe；Data 走自主 P2P DMA。硬件队列拆成延迟敏感同步请求与深批队列。提供可诊断的用户态调度钩子。

3. 核心贡献

把 GDS 的控制面搬出内核热路径，并把排序语义从「全序 stream」降到批级需求。省的是提交开销与错误排序，不是再抠 PCIe 峰值。

4. 实验

指标uGDS vs GDS
批读带宽最高 12.12×
批写带宽最高 30.69×
4-KiB 同步写延迟（2 线程）−84.1%
单 stream 相对同步带宽GDS 仅保留 40.8%
LMCache TTFT 中位最高 −62.7%
LMCache goodput2.63×
AMD vs hipFile 同步写最高 1.19×

示意走查：LMCache 把 KV 块写入 SSD。GDS 路径上每次 4-KiB 写都进内核提交，墙钟几乎耗在提交而非 DMA；换成 uGDS 后同步写走用户态队列，TTFT 中位数下降。批读场景下把请求聚到深批队列，带宽接近器件上限。

作者对比还覆盖 AMD hipFile：同一套用户态思路在非 NVIDIA 栈上仍有同步写带宽收益（最高约 1.19×），说明问题不单是某一家闭源引擎，而是「控制面是否在热路径」。对诊断，开源用户态让人能看清队列深度与顺序，而不是只拿到一个黑盒带宽数字。

5. 局限

依赖特定 NVMe/GPU/PCIe 拓扑；用户态轮询占 SM 的权衡需按负载调；安全模型与多租户隔离要额外工程。

6. 实践意义

KV offload / 训练 ZeRO-offload 路径可优先测 uGDS 类用户态直存；先看小 I/O 延迟与提交占比，再谈带宽。

03 4.30

RACE: RoPE-Aligned Attention Compression Based on Query-Key Activation Energies

📖 有深读 · 3 分钟

压 KV cache 的头维常在推理时再还原全维，解码 FLOPs 反而涨。RACE 用校准集把预训练注意力改成原生降维形式：对 Q/K 共享投影、保留 RoPE 对齐，并按 query-key 激活能量压缩，存储与注意力算力一起降。50% KV 保留、256K 上下文时，总推理 FLOPs −47.8%，吞吐 1.79×，TTFT −43.2%，解码延迟 −28.1%。头维压缩要「原生降维」而不是推理时再拼回全维，否则省下的显存会换成解码算力税。

头维压缩 KV cache 常在推理时再还原全维，解码 FLOPs 反而涨。RACE 用校准集把预训练注意力改成原生降维：对 Q/K 共享投影并保持 RoPE 对齐，按 query-key 激活能量决定保留哪些能量方向，使 KV 存储与注意力算力一起降。50% KV 保留、256K 上下文时，总推理 FLOPs −47.8%，吞吐 1.79×，TTFT −43.2%，分配显存 −28.1%。相对 EigenAttention / PALU / Thin Keys / RAP，RACE 在「保留 RoPE、共享投影、降存储、降注意力 FLOPs、免推理还原」清单上全部勾选。头维压缩要原生降维，而不是推理时再拼回全维。

1. 问题

KV 变长拖垮显存与带宽；只压 token 或量化不够时，有人压头维。若解码期重建全维 K/V，省下的显存会换成 FLOPs 税。需要校准期一次性改成降维注意力。

2. 方法

共享投影把 Q/K 映到同一低维空间，旋转位置编码在低维上仍对齐；用激活能量选主方向，V 同步压缩。校准集约一次；推理不再上投影回全维。可与 token 减少、量化叠加（文中有组合实验）。

3. 核心贡献

把「压缩」从缓存格式问题提升为注意力算子本身的降维，且不破坏 RoPE 几何。省显存的同一套投影也应省注意力算力。

4. 实验

Llama/Qwen 系列在零样本、困惑度、LongBench 上对比。50% 保留 + 256K：FLOPs −47.8%，吞吐 1.79×，TTFT −43.2%，显存 −28.1%。对照表显示竞品常在「推理重建」或「不保 RoPE」上留缺口。

设置结果
KV 保留50%
上下文256K
总推理 FLOPs−47.8%
吞吐1.79×
TTFT−43.2%
GPU 显存−28.1%

5. 局限

校准集域偏移会影响能量方向；与激进量化叠用时要重扫保留比例；超长上下文的端到端速度还受别的算子影响。

6. 实践意义

服务侧若 KV 显存紧，优先试「原生降维注意力」而非「压完再还原」；保留 50% 作为默认扫描点，看 TTFT 与 LongBench 是否可接受。

Cache Engineering for Agents

📖 有深读 · 3 分钟

Agent 长轨迹里 KV cache 读写与存储成主成本，改前缀还会让后续 cache 失效、被迫重 prefill。本文把「缓存工程」从改历史文本，转向管 cache 生命周期与驱逐策略；相对常规阈值触发摘要，简单工具响应 drop 策略平均成本 −27.7%、基准分 +1.7，配合 AKV 可达约 1.2× 输出吞吐与 1.5× P95 延迟改善；RSI 策略在留出任务上再降成本 7.1%。API 账单里 KV 读可占 82.4%。Agent 省钱的关键常是「别让 cache 失效」，而不只是把历史摘要得更短。

Agent 长轨迹里 KV 读写与存储成主成本；改历史前缀会让后续 cache 失效并重 prefill。本文提出缓存工程：agent 用 drop 排除选中 cache、用 repos 调整保留 key 的位置索引，从而直接控制活跃 KV，而不改写轨迹文本。相对阈值触发摘要，简单工具响应 drop 策略平均成本 −27.7%、基准分 +1.7；接 AKV 后输出吞吐约 1.2×、P95 延迟约 1.5× 改善；RSI 自改进策略在留出任务再降成本 7.1%。API 账单里 KV 读可占 82.4%。Agent 省钱的关键常是别让 cache 失效，而不只是把历史摘要得更短。

1. 问题

上下文工程靠修剪/摘要减长度，但改前缀使后缀 KV 作废。账单显示 KV 读可占八成以上费用。需要「动 cache、不动文本」的控制面。

2. 方法

暴露 drop / repos 原语：drop 让后续注意力看不到选中段；repos 在不改内容的前提下改位置编码索引。策略可手写（如丢工具回包），也可用递归自改进（RSI）在留出任务上搜策略。

3. 核心贡献

把优化对象从「提示词字符串」换成「活跃 KV 集合」。保留前缀字节不等于保留前缀 cache——失效一次就重付 prefill。

4. 实验

三模型×四 agent 基准：工具响应 drop 相对阈值摘要，成本 −27.7%、分数 +1.7；AKV 上吞吐 ~1.18–1.2×、P95 ~1.5×；RSI +7.1% 成本再降。阈值摘要（如 48k）可降约 7% 成本但准确率掉约 5 个百分点，说明乱摘要会伤任务。

5. 局限

依赖可写的 cache API（如 AKV）；drop 策略过猛会丢关键工具结果；RSI 搜索本身有费用。

6. 实践意义

Agent 运行时优先接「可 drop 的 KV 层」；默认先丢可重建的工具回包，再考虑摘要。

05 4.30

Stratified Sparse Attention: Reducing the Sparse-to-Dense Gap at Extreme Sparsity

📖 有深读 · 3 分钟

长上下文推理被不断增长的 KV 注意力拖住；稀疏注意力用确定性 top-k 会丢掉残余注意力质量，用采样又方差大，混合仍与稠密有明显差距。Stratified Sparse Attention（SSA）按层分层分配稀疏预算，缩小极端稀疏下的稀疏-稠密鸿沟：50× 稀疏时，相对最强实用基线，32K 从 81.8%→84.2%、128K 从 63.8%→69.3%，分别收回稠密性能的 94% 与 85%；百万上下文解码相对 FlashInfer 最高 2.96×。极端稀疏下要分层补残余注意力质量，而不是只抠 top-k。

独立页面阅读 ↗
独立页面阅读 ↗

长上下文解码被增长的 KV 注意力拖住。稀疏注意力用确定性 top-k 会丢掉残余注意力质量，用采样又方差大，混合仍与稠密有差距。Stratified Sparse Attention（SSA）按层把稀疏预算分给确定性利用与随机探索，缩小极端稀疏下的稀疏-稠密鸿沟。50× 稀疏时，相对最强实用基线，RULER 等上 32K 从 81.8%→84.2%、128K 从 63.8%→69.3%，分别收回稠密性能的 94% 与 85%；百万上下文解码相对 FlashInfer 最高 2.96×。极端稀疏下要分层补残余注意力质量，而不是只抠 top-k。

1. 问题

只取 top-k 丢残余质量；纯采样方差大；top-k+均匀采样仍有稠密缺口。需要在固定预算 k 下更好分配「必定取」与「随机探」。

2. 方法

三阶段：用代理分数把预算在 token 上分成确定段与采样段；对采样段按分层/概率抽取以覆盖残余质量；用定制 CUDA 核减少内存流量。均匀采样与纯 top-k 是特例。

3. 核心贡献

在极端稀疏比下系统性地缩小 sparse–dense gap，而不是只报加速比。加速只有在质量贴住稠密时才算数。

4. 实验

RULER / LongBench / LOFT / AIME，模型 3B–更大。50× 稀疏：32K 81.8→84.2，128K 63.8→69.3（收复 94%/85% 稠密）。H200 上 1M 上下文解码注意力层相对 FlashInfer 最高 2.96×；分片数 64 vs 32 约 1.58–1.71×。

上下文基线SSA相对稠密
32K @50×81.8%84.2%~94%
128K @50×63.8%69.3%~85%

5. 局限

代理分数质量影响分层；极端 batch 下速度优势变化；与其它稀疏核集成需工程。

6. 实践意义

长上下文服务若已上稀疏注意力，用 SSA 式预算分层做 A/B，先看 50× 稀疏下 RULER/长基准相对稠密的回收率。
