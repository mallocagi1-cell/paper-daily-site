GPUSparse: GPU-Accelerated Learned Sparse Retrieval with Parallel Inverted Indices

GPUSparse 把 SPLADE 这类学习型稀疏检索的打分从 CPU 倒排遍历（WAND/Block-Max WAND）搬到 GPU：用 block 对齐、warp 合并访存的并行倒排索引，配合批量 scatter-add 打分与融合 Triton 内核。在 MS MARCO 880 万段落上，精确打分与 Pyserini 对齐到三位小数（MRR@10=0.383，Recall@1000≥0.999），单查询 1.27ms，比 Pyserini CPU 快 235 倍；batch 500 时吞吐 787 QPS，文档并行内核达到 H100 HBM 峰值带宽的 62.6%。

TileMaxSim: IO-Aware GPU MaxSim Scoring with Dimension Tiling and Fused Product Quantization

📖 有深读 · 8 分钟

针对 ColBERT 多向量检索的 token 级 MaxSim 打分，论文先做 roofline 分析，指出朴素实现因要物化 Nq×Nd 相似度矩阵只用到 HBM 峰值带宽的 5–18%。TileMaxSim 用 IO-aware Triton 内核解决：多 query 的 SRAM tiling 让文档 embedding 只读一次、维度 tiling 支持 d>128、融合乘积量化查表把 HBM I/O 砍掉约 31 倍。H100 上达到峰值带宽 80.2%、每秒打分 8200 万文档，作为 ColBERTv2/PLAID 的 drop-in 替换把 10 万候选打分延迟从 268ms 降到 1.2ms（端到端降 98%）。

INSIGHT多向量/晚交互重排在社区搜索里常因打分太慢上不了线，TileMaxSim 说明瓶颈不在算力而在访存——别物化相似度矩阵、让 embedding 只过一次 HBM。它在 MS MARCO 和三个 BEIR 上排序与参考 MaxSim 完全一致，且 10 万到 50 万文档吞吐恒定、支持多 GPU 分片与 FP16/BF16/FP32，落地门槛低，可直接接到现有 ColBERT 检索栈。

1. 问题与动机

多向量检索（ColBERT 系）用 token 级 MaxSim 打分——对每个 query token 取它与所有 doc token 的最大 cosine 相似度，再对 query token 求和——在 MS MARCO、BEIR 上拿到 SOTA 精度，代价是 O(Nq·Nd·d) 的计算量。论文做了 roofline 分析点出真正的瓶颈：现有 GPU 实现只跑到 HBM 峰值带宽的 5–18%。以典型 ColBERT 参数（Nq=32、Nd=128、d=128、batch=10⁴）算，naive 实现的算术强度只有 16.1 FLOP/byte，而 H100 的 compute/memory 交叉点在 591 FLOP/byte——这是个深度 memory-bound 的算子。根因是 naive 实现会把 Nq×Nd 的相似度矩阵整个物化到 HBM，而这块中间数据"算一次、求完 max 就丢"，白白消耗内存流量。正因为打分慢，现有系统（如 PLAID）只能把 MaxSim 限制在 CPU 或对候选集做激进剪枝，压低了召回上限。TileMaxSim 的目标就是把这个 memory-bound 算子打到接近带宽上界。

2. 方法详解

TileMaxSim 是一族 IO-aware 的 Triton kernel，核心是三招：

(1) Multi-Query SRAM Tiling（V2-MQ）：同时对 query token 和 doc token 分块。每个 block 在寄存器里放 BQ 个 query token、在 SRAM 里放 BN 个 doc token，文档 embedding 流过共享内存的同时，per-query-token 的最大值直接在寄存器里累加。关键是把每个文档 tile 从 HBM 读的次数从 Nq 次降到 ⌈Nq/BQ⌉ 次；当 BQ=Nq=32 时达到 single-pass 最优——每条文档 embedding 只从 HBM 读一次。

(2) Dimension Tiling：把 embedding 维度切成 128 宽的块，支持 d=64~768。对 d>128（会撑爆共享内存）的 embedding 先累加各块的部分点积、再求 max。带宽利用率随维度上升：d=64 时 44%、d=768 时升到 86%。

(3) Fused PQ Decompression+Scoring（TileMaxSim-PQ）：对 product quantization 压缩的库，避免物化解压后的向量。预计算 per-query 距离表 T[i,m,k]=qi[第 m 段]ᵀ·C[m,k]，打分时直接查共享内存里的表而不读 HBM。在 B=100K、Nq=32、Nd=128 下 IO 从 6.75B 字节降到 218M 字节（31× reduction），距离表约 50MB 正好落在 L2 cache。

实验环境：2×H100 SXM 80GB（HBM3，3.35 TB/s、132 SM、每 SM 228KB 共享内存），软件栈 PyTorch 2.6、Triton 3.2、CUDA 12.4。负载 d=128、Nq=32、Nd∈{64,128,256}，batch 100~500K，模型为 ColBERTv2（128 维）。

3. 核心技术贡献

第一，把 MaxSim 重新表述成"读一次、寄存器累加最大值"的 fused kernel，从根上消掉 Nq×Nd 相似度矩阵的物化——这是相对 naive einsum/loop 实现的本质改进，理论 IO 降 2.0×，实测带宽从 18.4% 拉到 80.2%（2687 GB/s / 3350 GB/s），逼近 FlashAttention 这类 memory-bound kernel 的利用率。

第二，BQ=Nq 的 single-pass tiling 是吞吐的关键开关：ablation 显示 BQ 从 16 调到 32，带宽提升 4.5×（872→1302 GB/s，对应 26.6M→39.7M docs/s），原因正是消除了文档的重复 re-read。

第三，fused PQ 把解压和打分合并成查表，让压缩库也能高吞吐打分（B=100K 时 PyTorch PQ 直接 OOM，TileMaxSim-PQ 仍 5.8M docs/s）。这三点都不改变排序结果，是纯工程层面的吞吐/延迟收益。

4. 实验结果分析

主吞吐（Table 1，d=128、Nq=32）：B=100K 时 81.2M docs/s，对比 PyTorch loop 的 372K docs/s 提速 218×；合成均长数据上 82M docs/s，真实 MS MARCO passage 上 71.6M/s（70% 带宽利用）。对 torch.compile（Table 2），B=100K 时 1.29ms vs 10.47ms（8.1×），因为编译器无法把 matmul→max→sum 这条 reduction 链 fuse 起来。对 WARP CPU 引擎，500K 候选下 82.0M vs 175K docs/s（469×），且 WARP 的延迟 96% 花在 query 编码上。

端到端（Table 15）：作为 PLAID 打分阶段的替换，100K 候选打分从 267.4ms 降到 1.21ms（220×），把整条 pipeline 端到端延迟砍掉 98%。

精度保真：MS MARCO 200 query、187565 对上，与参考 PyTorch 的最大打分差 9×10⁻⁶，MRR@10=0.3399、nDCG@10=0.3866、Recall@1000=0.7833 与参考六位小数完全一致；BEIR 的 SciFact/NFCorpus/TREC-COVID 上 nDCG@10 也逐一相同——结论是"任何 MaxSim 实现的 drop-in 替换"。

扩展性：batch 从 1K（17.9M/s、17.5% 带宽）到 500K（83.2M/s、81.4% 带宽）吞吐趋于常数；Nd=32 时 103.1M docs/s、Nd=512 降到 22.0M/s（但达到 2881 GB/s）；FP16/BF16 吞吐几乎相同、FP32 慢 1.6×。

5. 局限与未来方向

作者明确列出两条局限：一是 fixed-Nd padding——对变长语料按固定 Nd 补齐会浪费 38% 的 token 计算，用 length-sorted batching 可回收到 70M/s；二是假设数据全部 GPU-resident（embedding 已在显存里），没处理 doc embedding 超出显存、需从 host/SSD 流式加载的场景。多 GPU 目前只做了 embarrassingly-parallel 的 data-parallel 分片，没涉及跨卡通信优化。隐含但未展开的点：评测主要在 d=128 的 ColBERTv2，更高维（如 d=768 的多向量模型）虽支持但吞吐明显下降（14.7M/s）；query 编码本身的开销（在 WARP 对比里占 96% 延迟）不在本文优化范围，端到端收益要看编码是否也被加速。

6. 工业实践意义

对做语义检索/重排的团队，最直接的结论是：多向量 late-interaction（ColBERT/PLAID）过去因打分延迟难以上线，TileMaxSim 把 100K 候选的打分压到 1.2ms，让它重新进入可用区间。三点可操作：(1) 若已在用 ColBERTv2/PLAID，TileMaxSim 是 colbert_score_packed 的 drop-in 替换，不动候选生成/解压等其他环节、排序结果逐位一致，迁移风险低；(2) 打分变快后可以放宽剪枝、直接对更大候选集精排，换取更高 recall——这对召回-精排漏斗的设计是个新自由度；(3) fused PQ 查表 + 共享内存的思路可迁移到自家 ANN/重排打分 kernel。部署上要注意：方案绑定 H100/HBM3 与 Triton，需 GPU-resident embedding；变长文档要配 length-sorted batching，否则 padding 浪费近四成算力。roofline 给出的 80.2% 带宽上界，也是评估自研 kernel 还剩多少优化空间的现成标尺。代码已开源（github.com/ashutoshuiuc/tilemaxsim）。

CAT-Q: Cost-efficient and Accurate Ternary Quantization for LLMs

Intel

CAT-Q 是面向 LLM 的后训练三值量化（PTQ），不走 BitNet 那种百亿 token 的量化感知训练。两个组件：learnable modulation（用可学习因子调制权重分布与三值阈值，降低对三值化的敏感度）与 softened ternarization（可微过渡函数稳定收敛）。1.7B–8B 模型仅用 512 条校准样本即可三值化，效果超过用 100B token 训练的 BitNet 1.58-bit v1/v2，训练 token 量降约 10 万倍；14B–235B 模型在 8 张 A100-80GB 上 8–60 小时即可量化，代码已开源（IntelChina-AI/BitTern）。

INSIGHT三值（约 1.58 bit）量化此前要从头 QAT，成本高到难以落地；CAT-Q 把它做成 PTQ，对自有排序/召回大模型的低成本压缩部署很有参考价值。关键设计是把“阈值”和“权重分布”一起当作可学习量联合优化，使权重对三值化不敏感——这是低比特 PTQ 维持精度的核心。能在 60 小时内三值化 235B 模型，说明大模型超低比特部署的算力门槛被显著拉低。

Shigeng Wang, Chao Li, Yangyuxuan Kang et al.

Information-Aware KV Cache Compression for Long Reasoning

现有 KV cache 压缩多用注意力权重估计 token 重要性，论文指出这忽略了预测不确定性等信息论信号。作者提出 Forward Influence 度量“被压缩 token 对未来上下文的影响”，分析发现注意力高分 token 主要影响临近上下文，而高预测不确定性的 token 对远处未来影响更强。据此提出 InfoKV：把 token 级预测不确定性、层间表示演化得到的熵分数与注意力分数结合。在 Llama-3.1/3.2、DeepSeek-R1 的长上下文推理基准上，长 prefill 与 decode 场景均优于基于注意力的压缩方法。

INSIGHT长推理（长 CoT）让 KV cache 成为部署瓶颈，这篇提示重要性估计不该只看注意力——熵/不确定性能捕捉对远期上下文的影响，是注意力的互补信号。对要把推理型 LLM 用到搜索 query 理解/复杂问答的团队，InfoKV 提供了一种无需重训、可叠加在现有注意力打分上的 KV 压缩思路，尤其利好长上下文场景的显存占用。

Epiphany-Aware KV Cache Eviction Without the Attention Matrix

CMU

推理模型的 CoT 动辄数万 token，KV cache 成为部署瓶颈。现有按注意力权重驱逐 token 的方法在长推理里噪声大，且要物化注意力矩阵、无法用融合内核。EpiKV 改用 epiphany score——token 引起的模型内部表示变化，直接从前向传播读取，无需注意力矩阵、几乎不增加状态。该方法免训练、无分类器、无定制内核，可直接用在 FlashAttention 推理栈，可行上下文比基于注意力的方法长 16 倍。4096-token cache 下 MATH-500 达 72%（持平最强注意力基线 ThinKV 71%、H2O 67%），lag-normalized 变体在 8192-token AIME-2024 达 37%（基线 33%），速度最高 2.8 倍。

INSIGHT这篇的工程价值在“对生产推理栈友好”：不物化注意力矩阵就能算 token 重要性，意味着可以保留 FlashAttention 的融合内核，不必为了 KV 驱逐退回慢路径。对要在线部署长推理模型的搜索/问答系统，免训练、零额外内核、即插即用的特性大幅降低落地成本，是注意力-based KV 压缩方法在生产可用性上的明显改进。

PersistentKV: Page-Aware Decode Scheduling for Long-Context LLM Serving on Commodity GPUs

自回归 LLM serving 越来越受 KV cache 搬运（而非稠密矩阵乘）限制。PersistentKV 是面向 GQA 的原生 block-table decode 注意力引擎与 page-aware 调度：按 KV-head 组分配工作、跨 grouped query head 复用 K/V tile、支持原生页表，并加一个只执行非空任务的紧凑工作队列调度。在 RTX 3060（FP16，page=16，Hq=32，Hkv=8，d=128）上，校准后的自适应策略对小 batch 选 FlashInfer、长上下文 B1/B8 选 PersistentKV，held-out trace 上 B8 同步吞吐提升 1.063–1.265 倍、B1 提升 1.399 倍，并在 B4 边界回退到 FlashInfer 避免劣化。

INSIGHT论文的洞察是“调度（工作如何分配）与注意力数学同等重要”——同一个最优内核在不同 batch/序列分布下不是最优调度。对在消费级/商用 GPU 上做长上下文 serving 的成本敏感场景，page-aware 自适应调度提供了一条不换硬件就提吞吐的路径；自适应策略能在不利场景安全回退，避免单一内核的盲区。

Moebius: Serving Mixture-of-Expert Models with Seamless Runtime Parallelism Switch

服务单个 MoE 大模型需要多 GPU 并行，张量并行（TP）在低并发更快、专家并行（EP）在高并发更优，而生产负载（突发在线请求、RL rollout 由高并发衰减为长尾）会不断跨越这个分界，固定一种布局就会在另一侧损失性能。Moebius 让引擎在运行时于 EP 与 TP 间切换，不重启、不丢在途请求。核心观察：EP 和 TP 是同一份专家权重/KV cache 的两种布局，切换只是改变哪个 rank 拥有哪片数据。在 8×H200 上服务 Qwen3-235B-A22B，Moebius 在每个工作点都追平更优的静态并行，RL rollout 上快 1.16–1.25 倍，单次切换 215–434ms，双布局常驻仅 2.4% 显存开销。

INSIGHT对要把 MoE 大模型用到检索/排序在线服务的团队，Moebius 指出“并行布局应随并发动态变化”——把 TP/EP 看成同一模型的两种 sharding 而非两个模型，用固定地址重分片+融合 GPU-to-GPU 传输内核实现 decode 步间无损切换。2.4% 显存换全工作点最优，对负载波动大（白天高峰、夜间低谷或 RL 训练）的场景很有吸引力。

Google
