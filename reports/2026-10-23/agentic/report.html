Let Agents Design How They Search: Automatic Interface Optimization for Agentic Search

韩国大学和 KAIST 让 Claude Code（Claude Opus 5.5）替搜索智能体设计检索工具：它读每道题的执行记录和得分，同时修改预先生成的索引文件、可执行的检索脚本和使用说明，循环 10 轮后选优化集上最好的版本。搜索智能体用 GPT-5.4-nano，BrowseComp-Plus 答对率从 DCI 的 71.6% 升到 78.4%，BRIGHT 四个子集平均 nDCG@10 从 45.7 升到 55.0。只优化提示词能到 75.6% 和 52.0，说明另一部分提升来自生成的索引文件和检索脚本；接口原样换给 Gemini 3.5 Flash-Lite 也比 DCI 好（73.9% 对 60.9%）。

让大模型智能体在一个文档库里查资料时，它能用哪些工具、文档库预先整理成什么样、提示词里怎么教它用这些工具，合起来叫"搜索接口"。现在的接口都是人手工设计好、对所有文档库通用的，比如 DCI 直接给智能体一个终端，让它用 grep、cat 之类的命令翻原始文档。韩国大学和 KAIST 的 SearchWeaver 让另一个编码智能体（Claude Code + Claude Opus 5.5）去自动设计这个接口：它读搜索智能体的完整执行记录和每题得分，找出失败原因，然后同时改三样东西：预先生成的索引文件、可执行的搜索脚本、给搜索智能体的使用说明；改完再跑一遍、看分数，循环 10 轮。搜索智能体用 GPT-5.4-nano，在 BrowseComp-Plus 上答对率从 DCI 的 71.6% 升到 78.4%，BRIGHT 四个子集的平均 nDCG@10 从 45.7 升到 55.0；优化出的接口直接换给 Gemini 3.5 Flash-Lite 用，也比 DCI 好。

1. 问题：同一套接口不适合所有文档库

近期的智能体检索方法都在固定接口上做文章：RAG 只给检索器返回的段落；DCI 让智能体用终端命令直接翻原始文档；DR-DCI 先用向量检索把文档拉进一个工作区再翻；RISE 圈定一个受限工作区，并给文档补上模型生成的目录。论文表 1 显示，这些方法的相对好坏随文档库变化：DR-DCI 在 BrowseComp-Plus 上比 DCI 好（73.1% 对 71.6%），在 BRIGHT 上却更差（42.1 对 45.7）。作者据此认为，接口应该针对具体的文档库和具体的模型来设计。

2. 方法：让编码智能体反复改接口

2.1 接口由哪几部分组成

一个候选接口包括三部分：

  • 预先生成的文件：在任何问题到来之前，对整个文档库做一次处理，比如生成"标题 → 文件路径"的索引表，供所有问题复用。
  • 可执行工具：Python 脚本，可以调用提供的 BM25 和向量检索，可以把检索范围限制在某个子目录，也可以把智能体对文档的判断和检索排名合并。
  • 使用说明：写给搜索智能体的指令，告诉它什么时候用哪个工具、怎么验证线索。

候选接口还可以替换搜索智能体的基础系统提示词和上下文管理策略。搜索智能体本身的模型参数不动。

2.2 优化循环

设计者是 Claude Code（Claude Opus 5.5）。每一轮它查看文档库和之前所有候选接口，写出一个新接口；新接口在优化用的题目上跑一遍，返回每题得分和完整执行记录（敲了哪些命令、工具返回了什么、最终答案）。优化题目的标准答案文档 ID 也会提供给设计者，帮助定位是"没找到"还是"找到了没认出来"。每个候选的结果不管好坏都留作后续参考。跑满 10 轮后，挑优化集平均分最高的接口，在测试题上评估，测试题从不进入设计者的反馈。

3. 实验

设置。 BrowseComp-Plus（BCP）是在固定网页库上回答多线索问题，用 GPT-4.1 判对错，30 题用于优化、800 题用于测试。BRIGHT 是需要推理的文档检索，选了生物、地球科学、经济、机器人四个子集，共 213 题优化、210 题测试，看 nDCG@10。每个文档库单独优化一个接口。提供给设计者的检索资源：BCP 上是 BM25 和 Qwen3-Embedding-4B，BRIGHT 上是 BM25 和 ReasonEmbed-Qwen3-8B 的现成排序。

3.2 工具耗时

每题工具执行时间（不含模型推理）相比 DCI 也下降了：BCP 从 42.4 秒降到 32.9 秒，BRIGHT 从 63.2 秒降到 36.6 秒。不过从图上看，RISE 和 DR-DCI 的工具耗时更低，SearchWeaver 是用更多工具时间换来了更高的分数，作者称它在评估的方法里处于帕累托前沿。

3.3 只改提示词够不够

这组实验检验提升是否来自新生成的文件和工具，而不只是更好的提示词。对比两种变体：同样的优化循环但只允许改提示词（Prompt Optimization）；以及把 SearchWeaver 最终接口里生成的文件、工具和相应说明删掉、不再重新优化。

3.4 换模型还有效吗

这组实验检验接口能否跨模型复用。把用 GPT-5.4-nano 优化出的接口原样交给 Gemini 3.5 Flash-Lite：BCP 答对率 73.9%（DCI 为 60.9%），BRIGHT 平均 nDCG@10 为 58.8（DCI 为 50.7），BRIGHT 上每题工具时间从 23.1 秒降到 15.5 秒。不重新优化也有效，说明优化出来的东西有相当一部分属于文档库本身，而不只是针对某个模型的技巧。

4. 局限

实验只在固定不变的文档库上做。文档增删后，预先生成的索引和依赖它的工具要不要更新、能不能增量更新，作者明确说没有研究。BCP 只用 30 道题做优化，接口是否对这 30 题有过拟合，正文没有分析。每轮优化都要让设计者（Claude Opus 5.5）读完整执行记录、再让搜索智能体把优化集跑一遍，这部分成本论文没有报告。

5. 实践意义

对搭建企业内部知识库问答智能体的团队，这篇给了一个可操作的流程：拿一小批带标准答案的问题，让编码智能体看着执行记录去生成索引文件和检索脚本，而不是只调提示词。消融里只改提示词也能把 BCP 答对率从 71.6% 升到 75.6%，所以资源有限时，可以先从成本低的提示词优化做起。如果文档库更新频繁，需要自己设计索引的维护方式。

MAPS: Macro-Adaptive Parallel Reasoning for Regulating Search Momentum in Retrieval-Augmented Generation

Northeastern UniversityTsinghua📖 有深读 · 8 分钟

东北大学和清华发现，边推理边检索时，后面的子查询会沿着前面子查询的移动方向继续偏离原问题，而且越往后越明显。MAPS 据此做两处改动：每轮只把提炼出的知识和一段推理摘要交给模型，不再给它看历史子查询；生成子查询前先列出几个互补方向，各写一个子查询并行检索后合并。Qwen3-32B 上六个问答集平均 Cover-EM 为 56.0，ParallelSearch 为 49.2，Search-o1 为 43.9；三个组件分别去掉后都会下降。

边推理边检索的 RAG 方法（如 Search-o1）每一步让大模型根据之前全部的推理过程和子查询，写出下一个子查询去检索。东北大学和清华的这篇论文先做了一个测量：把每个子查询编码成向量，把"相邻两步子查询向量之差"按指数加权累加起来，称为"搜索动量"，然后检验它能否预测下一个子查询偏离原问题的方向。结果是越往后预测得越准，说明后面的子查询倾向于沿着前面已经走的方向继续偏下去。据此提出的 MAPS 做了两处改动：每一轮只把检索到的知识和一段压缩后的推理状态交给模型，不再给它看历史子查询和完整推理过程；每一轮先列出几个互补的检索方向，各写一个子查询并行检索，再把结果合并。在 Qwen3-32B 上，MAPS 在六个问答数据集上的平均 Cover-EM（标准答案是否出现在回答里）为 56.0，最强基线 ParallelSearch 为 49.2，Search-o1 为 43.9。

1. 问题：子查询会沿着已有方向越偏越远

多跳问题需要的证据分散在多篇文档里，所以现在的做法是让模型一边推理一边生成子查询。问题在于第 t 步的子查询是以前面全部推理和子查询为条件生成的，早期一个跑偏的子查询会影响后面所有步骤。

论文用"搜索动量"量化这一点。具体操作：

  1. 用 E5 模型把每一步的子查询编码成向量 q_t。
  2. 动量 m_t = β_t·m_{t−1} + (1−β_t)·(q_t − q_{t−1})，即把每一步子查询的移动量按权重 β_t 累加，β_t 越大越看重历史。
  3. 对齐分数 S_t = cos(m_t, q_{t+1} − q_0)，即当前动量的方向和"下一个子查询相对原问题的偏移方向"的余弦相似度。
  4. 在训练集上用 L-BFGS-B 拟合每一步的 β_t 使 S_t 最大，在留出集上报告 S_t。
数据集β1S1β2S2β3S3β4S4
2WikiQA0.00000.40510.63520.56980.75520.64830.87610.6955
MuSiQue0.00000.31050.54000.51960.72140.64890.82520.6913
HotpotQA0.00000.44270.61610.68400.81510.77310.88360.7750

β_t 和 S_t 都随步数上升：越往后，历史移动的权重越大，下一个子查询的偏移方向也越贴近已有动量。作者的解读是，模型的推理过程并不会自己纠正早期的偏离。

2. 方法：MAPS

2.1 不让模型看历史子查询

普通做法每一步把完整轨迹（每一步的推理、子查询、检索结果）都交给模型。MAPS 只保留两样东西：

  • 知识观察集：之前每一轮从检索结果中提炼出的知识 o_1…o_{t−1}；
  • 压缩推理状态：一段每轮更新的推理摘要，不包含历史子查询。

下一轮的推理只以原问题、知识观察集和压缩推理状态为输入。知识足够或达到最大轮数时，用同样三样输入生成最终答案。

2.2 每一轮并行查几个方向

每一轮分三步，由三个角色完成：

  1. 方向提出：根据原问题、已有知识和推理状态，列出 N 个互补的检索方向；
  2. 生成子查询：为每个方向写一个子查询，各自检索 top-K 文档，合并成一个文档集；
  3. 整理：把各方向检索到的证据合并成本轮的知识观察 o_t，并更新压缩推理状态。

3. 实验

设置。 单跳问答用 NQ、PopQA，多跳用 2WikiQA、HotpotQA、MuSiQue，推理问答用 GPQA Diamond（198 题）；除 GPQA 外每个数据集随机抽 1,000 题。主干模型为 Qwen3-32B 和 Qwen3.6-35B-A3B。检索库是 2018 年 12 月的英文维基百科，检索器 E5-base-v2 + FAISS，每次返回 top-5 段落，最多 10 轮。指标是 Cover-EM（标准答案是否出现在模型回答里）。

3.1 主结果

这组实验检验 MAPS 是否在不同类型问题和两个主干模型上都比现有 RAG 方法好。

3.2 消融

这组实验检验三个组件各自是否有用：去掉"先列方向"（直接并行写子查询）、去掉并行（每轮只查一个方向）、去掉解耦（保留完整历史轨迹）。

三项去掉后平均分都下降，GPQA 上下降最大。注意消融表里 MAPS 的 GPQA 是 62.3、平均 56.1，与主表的 62.1、56.0 不一致，论文没有解释。在 Qwen3.6-35B-A3B 上，去掉解耦后 2WikiQA（64.4）和 GPQA（78.1）只比完整 MAPS 略低。

3.3 动量是否真的被压住了

这组实验检验 MAPS 的提升是否确实来自减少偏离。从所有数据集随机抽 500 个样本，计算每一轮动量和原问题的余弦相似度变化并累加。随着轮次增加，MAPS 的累计偏移比 Search-o1 和去掉解耦的版本更小、更稳定。另一项分析计算子查询和标准证据文档的相似度：Search-o1 一路下降，MAPS 前期下降、之后回升并稳定。

3.4 停止轮次

MAPS 在第 1 轮就停止的样本占 62.7%，高于 Search-o1 的 50.4% 和 ParallelSearch 的 58.5%；同时需要 5 轮及以上的样本比例也更高（14.9%，对 12.5% 和 5.1%）。作者的解释是简单问题更早查到足够证据，复杂问题则不会过早停下。

4. 局限

论文没有报告每题的模型调用次数、token 消耗或延迟。MAPS 每轮要调用方向提出、子查询生成、整理三个角色，并做 N 次检索，成本很可能高于 Search-o1，但无法从论文得知具体多少。方向数 N 取多少、对结果有多大影响，正文也没有给出。实验使用 2018 年的维基百科和 E5-base-v2 这样较弱的检索器，换成更强的检索器后差距是否保持，没有验证。

5. 实践意义

做多跳 RAG 智能体的团队可以直接试两个低成本改动：每一轮不把历史子查询喂回给模型，只给提炼后的知识和一段推理摘要；生成子查询前先让模型列出几个互补方向。消融显示这两处改动单独去掉都会损失效果。上线前需要自己测量增加的调用成本。

Signals and Queries: Token-Efficient Agentic Context Discovery

PParlant📖 有深读 · 9 分钟

Parlant 原来每轮对每条客服规则问一次大模型是否相关，36 条规则每轮约 69,000 个 token。S&Q 改为离线让大模型为每条规则写 10 条应触发的用户消息和 10 条容易混淆的反例，训练一个逻辑回归；线上每轮只需一次 embedding 和 37 微秒 CPU。在 τ²-bench 航空客服上，召回率 90% 时精确率 32%–34%，余弦阈值为 31%；从真实对话挖样例后精确率升到 43.5%，提升几乎全部来自反例。

面向客户的大模型客服通常受几十条行为规则（policy）约束，比如"只有买了旅行险才能补偿"。每一轮对话都要判断哪几条规则和当前情况相关，再放进提示词。Parlant 引擎原来的做法是每轮对每条规则问一次大模型"现在相关吗"，36 条规则每轮要 36 次调用、约 69,000 个提示词 token。Parlant 的 Signals and Queries（S&Q）把这一步换成离线训练的小分类器：对每条规则，先让大模型离线写 10 条"应当触发这条规则"的用户消息和 10 条"看起来很像、但应由相邻规则处理"的用户消息，把它们编码成向量，为这条规则单独训练一个逻辑回归；线上每轮只需一次 embedding 调用和 36 次向量点积，CPU 耗时 37 微秒。在 τ²-bench 航空客服的 254 个对话片段、36 条规则上，以大模型判定为标准，在召回率不低于 90% 时，S&Q 精确率在 Gemini embedding 上为 32%、OpenAI embedding 上为 34%，余弦阈值检索为 31%；改用真实对话中挖出的样例后，精确率升到 43.5%（Gemini）和 41.6%（OpenAI）。

1. 问题：漏一条规则是错误，多一条只是浪费

把所有规则每轮都塞进提示词，会遇到长上下文中间部分被忽视、单条指令注意力被稀释、指令越多越难全部遵守等问题，token 成本也随规则数线性增长。所以需要先筛出相关规则。

筛选的代价不对称：漏掉取消政策，客服可能做出本该拒绝的操作；多放一条无关规则，只多花几百个 token。因此 S&Q 的目标是先保证每条规则召回率至少 90%，在此前提下再提高精确率。它是一个预筛选器，筛掉的规则后面再也找不回来，留下的规则还会被客服模型自己再读一遍。

直接拿对话去和规则原文算向量相似度几乎不花钱，但对话是口语化的用户消息，规则是正式的条文，两者的向量区分度很差。

2. 方法

2.1 离线：为每条规则造正例和难负例

对每条规则，用 gemini-3.5-flash 仅根据规则原文生成：

  • signals（10 条）：应当触发这条规则的用户消息，例如取消政策对应"我想取消下周去芝加哥的航班"；
  • anti-signals（10 条）：同一话题附近、但应由别的规则处理的消息，例如"我想把航班从周二改到周四"（这属于改签规则）。

生成过程不使用任何真实对话。

2.2 每条规则一个逻辑回归

对每条规则，用这 20 条消息的 embedding 训练一个逻辑回归，输出"相关"的概率。每条规则的分类器只依赖它自己的样例，所以新增或修改一条规则，只需为它重新生成样例、训练一个分类器（约 2 毫秒），其他规则不受影响。

2.3 线上：两种对话视角取最大值

第 t 轮时，对两种向量打分并取最大值：整段对话到当前为止的 embedding，以及到当前为止每一条用户消息单独的 embedding。所有向量先减去全部规则的中心再归一化。分数超过全局阈值 θ 就保留该规则。取单条用户消息的最大值是为了在对话换话题时，前面的内容不会稀释后面话题的信号。真实对话的分数整体比生成的样例低，所以 θ 取负值（Gemini −0.45，OpenAI −0.4）。

3. 实验

设置。 50 段由 Parlant 客服和 τ²-bench 用户模拟器生成的航空客服对话，每个以用户消息结尾的前缀算一个查询状态，共 254 个。规则共 36 条：τ²-bench 航空政策的 6 节，加上作者另写的 30 条（身份验证、行李索赔、无人陪伴儿童、票价规则、欺诈处理等），其中故意放了几组近义规则。标准答案由 gemini-3.1-flash-lite 用 Parlant 线上的相关性提示词对每个（对话前缀, 规则）打 1–5 分，≥4 算相关，共 9,144 个标签。指标是在 31 条至少出现过一次的规则上做宏平均。基线四种：按规则原文或按 signals 的余弦相似度取 top-K，或按余弦阈值截断。embedding 分别用 gemini-embedding-001 和 OpenAI text-embedding-3-large 各跑一遍。

4. 局限

标准答案来自另一个大模型的判断，而不是人工标注。即使在 90% 召回下，S&Q 精确率也只有三成多，留下的规则里大部分仍是无关的，需要后续模型再筛。挖样例需要真实对话上的相关性标签；对半切分时 29 条出现过的规则中只有 22 条挖到了足够样例。长对话里一条规则一旦触发就会一直保留，保留集只增不减，作者指出部署时需要另设过期机制。

多轮 RAG 对话里，用户的问题有两种情况需要先反问再回答：一是问题本身指代不清，比如助手刚推荐了两张信用卡，用户问"这张卡有什么奖励"；二是问题本身看起来明确，但检索出的文档里有几个都说得通的答案，比如问"由共同布立吞语演变来的那种语言还有人说吗"，文档里有威尔士语、布列塔尼语、康沃尔语三种。IBM Research 构建了约 3,900 条样本的数据集 ClariEdge，其中专门包括"看起来含糊、但根据上文可以确定指代"的难负例，并用它对 3B 规模的 Granite 模型做 LoRA 微调，让同一个模型判断要不要反问，并在要反问时列出候选项。Granite-4.1-3B LoRA 的判断准确率为 96.6%，提示词方式下最好的 GPT-4o 为 79.4%，GPT-5.6 Sol 为 73.1%；去掉难负例训练后，难负例类的准确率从 87.3% 降到 35.4%（Granite-4.0-micro LoRA）。

1. 问题：什么时候该反问，反问时该说什么

已有数据集只覆盖了其中一部分。CLAMBER 评估的是没有对话上下文、没有检索文档的单句问题；AmbigQA 只要检索出多个事实答案就算含糊，但像"1922 年谁控制了意大利政府"这类问题，现在的模型会直接回答"墨索里尼和法西斯党"，并不需要反问。真实部署需要的是对话加文档一起判断。

还有一个难点：很多问题表面含糊但其实可以确定。例如上文用户说了"我在东北分部工作"，接着问"这个分部的服务什么时候开放"，"这个分部"是明确的。模型如果对这种问题也反问，就会过度打扰用户。

2. 方法

2.1 ClariEdge 数据集

对话覆盖 MTRAG 的四个领域：ClapNQ（维基百科）、Cloud（技术文档）、FiQA（金融）、Govt（政府）。数据分三类：

难负例的构造方式：让 Mistral-Large-3 在 793 段对话上生成"针对对话中出现过多个实例的实体类型"的提问，另外对 228 段更长的对话（超过 6 轮、含多种实体类型）用逐步推理加自我验证的方式生成。然后人工逐条审核：确实含糊的归入 Ambiguous，根据上文能确定的归入 CLEAR-hard。作者还补充了几种模型容易误判的模式，例如"哪一个电池续航最好"（是在比较所有候选，不是指某一个）、"价格？"这类简短追问。难负例只出现在不带检索文档的场景中。

港大等提出 BIRD-RL，用强化学习训练小模型在真实数据库上调试 SQL。难点是 SQL 会修改数据库状态，每条采样轨迹本需独立的数据库容器；BIRD-RL 按轨迹登记并复用数据库副本，在 SQLite 负载下空间效率提升 12.8 倍，不需要 Kubernetes。训练分四阶段：模仿推理、模仿多轮工具调用、强化推理、在真实数据库上交互式强化学习。7B 和 14B 模型在 BIRD-CRITIC-SQLite 上成功率 44.40% 和 48.00%，Claude-Opus-4.6 Agent 为 48.20%。

Harness Scaling for Generalizable Agentic Reinforcement Learning

IIQuest ResearchBeihang UniversityRenmin University of China

人大等发现，只在一套固定的智能体运行框架（harness）里做强化学习，模型换框架后效果会变差。Harness Scaling 把框架拆成系统提示词、工具接口、观测格式、上下文管理、工作流五个可替换部分，用正交设计挑出一小组组合训练，每个任务配两个相近的组合。在 ClawGym-Task 上训练 Qwen3-4B-Instruct，未见过的框架组合上 GRPO 平均分从 29.81 升到 39.04；迁移到 Claude Code 时平均 37.22，高于直接在 OpenClaw 上做 SFT（35.08）或 RL（33.38）。

Fei Bai, Huatong Song, Chuan Hao, Ran Tao, Jian Yang, Bryan Dai, Wayne Xin Zhao, Ji-Rong Wen

Flint-interactive: A language for creating interactive data visualizations

MicrosoftUCLA

微软研究院发布 Flint-interactive，让智能体生成可点击、筛选、缩放、跨图联动的交互式图表。做法是把交互拆成两层：编译器负责把点击、拖动等原始操作解析成"用户选中了哪些数据"这样的语义事件，并负责渲染更新；智能体只需写"某个事件触发哪个更新操作"（如高亮、加标注、平移缩放），不用写底层渲染代码。可通过 Flint-MCP 在聊天里使用，也可用编程接口接入看板和表格。博客没有给出可靠性或成本的量化数据。

Inside NVIDIA Sentry: Secure AI Agents at Runtime

NVIDIA

NVIDIA 介绍 Sentry：一套运行在 BlueField-4 DPU 上、独立于主机软件的智能体安全框架，智能体访问模型和外网的流量都必须经过它。DOCA Tower 作为透明代理解密流量，用 Open Policy Agent 按规则审批请求；DOCA Argus 直接读取主机内存，核对发起请求的进程和容器哈希是否在批准清单内。发现异常时可在毫秒级内由硬件隔离智能体，日志存在 DPU 上，智能体改不了。计划明年初推出，文中没有性能测试数据。
