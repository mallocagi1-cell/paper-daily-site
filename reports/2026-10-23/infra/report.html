Is 2:4 Sparsity Still Worth It? Semi-Structured Sparsity versus Quantization in LLM Inference

独立研究者在 Llama-3.1-8B-Instruct 和 Qwen3-8B 上，按相同存储位数（稀疏位置索引也计入）和相同标称算力档位，比较"加 2:4 稀疏"和"降一档精度"，并在 L40S、H100、RTX PRO 6000 上实测。只要还能降精度，加 2:4 就既更不准也更慢：2:4 + INT8 的存储成本等于 INT5。到 FP8 底线后，H100 上 vLLM 服务的重训 2:4 模型 prefill 吞吐比稠密 FP8 高 27%，GSM8K 相当；但重训时困惑度先恢复，推理准确率恢复得慢得多。

NVIDIA 从 Ampere 起的 GPU 都支持 2:4 稀疏：矩阵乘法里一个操作数沿累加方向每 4 个元素只保留 2 个非零值，张量核心按标称可以快一倍。它可以和量化叠加，所以部署时真正要回答的是：在当前精度上，下一步是加 2:4，还是降到更低一档精度？这篇独立研究者的论文在 Llama-3.1-8B-Instruct 和 Qwen3-8B 上，按“相同存储位数（稀疏的位置索引也算进去）”和“相同标称算力档位”两种口径比较两者。比较覆盖一层 transformer 里六类可以做成稀疏的矩阵乘法操作数（线性层的权重和输入、注意力里的 Q、K、V 和注意力概率），并且在 L40S、H100、RTX PRO 6000 三代 GPU 上实测速度，总共超过 22 万个配置。结论很干脆：只要还有更低一档精度可用，加 2:4 既更不准也更慢。只有到了硬件支持的最低精度（Ada 和 Hopper 上是 FP8），2:4 才有用武之地：H100 上用 vLLM 服务的 2:4 加 FP8 模型，prefill 吞吐比稠密 FP8 高 27%，GSM8K 准确率相当。但这个模型是在 130 亿 token 上重新训练过的，一次性剪枝的模型完全不能用。

1. 问题：硬件还在支持，软件已经放弃

一边是 NVIDIA 每一代 GPU 都保留稀疏张量核心，Blackwell 还加了稀疏 FP4；另一边，2026 年 vLLM 和 LLM Compressor 因为用的人太少，删掉了 2:4 支持。两边分歧这么大，说明缺一个在真实硬件上的直接对比。

已有的剪枝与量化对比大多按“名义压缩率”比，主要看权重，而且没有把“加 2:4”和“降一档精度”放在同一张卡上实测。作者指出四个容易被忽略的地方。第一，2:4 每个保留值旁边都要存位置索引，所以它占的位数比稠密的一半多。第二，两种做法都号称让吞吐翻倍，但数据手册不说实际能兑现多少。第三，推理时大多数操作数（激活、Q、K、V、注意力概率）是现算出来的，每次矩阵乘法前都要现场剪枝和压缩，只测矩阵乘法本身看不到这部分时间。第四，硬件规定了哪个操作数能稀疏、沿哪个方向分组，所以按整个张量统计的指标（比如峰度）反映不出 2:4 实际删掉了什么。

2. 怎样比才算公平

第一种口径是相同位数，用来比省显存。每种格式按每个原始元素实际存了多少位计费，值、索引、缩放因子都算。2:4 只保留一半元素，但每个原始元素要多 1 位索引，所以省下的位数不到一半。算下来，“2:4 加 2m 位”正好等于“稠密 m+1 位”：2:4 加 INT8 的成本等于稠密 INT5，2:4 加 INT4 等于 INT3，2:4 加 FP16 比 FP8 还贵。

所以在相同存储下，真正的选择是“丢掉一半元素、剩下的每个用 $2m$ 位存”，还是“保留全部元素、每个用 $m+1$ 位存”。

第二种口径是相同算力档位，用来比提速：按数据手册的标称吞吐配对。2 倍档是 2:4 加 FP16 对稠密 FP8 或 INT8；4 倍档是 2:4 加 FP8 对稠密 4 位浮点，后者只有 Blackwell 有。

两种口径下，精度都看算子级相对误差，也就是和 FP32 参考输出比。作者定义 R 为“最好的 2:4 配置的误差”除以“最好的量化配置的误差”，R 小于 1 表示 2:4 更好。为了不偏向任何一方，双方各自从同等投入的方法里挑最好的：2:4 一侧试三种剪枝：按权重绝对值剪（幅值剪枝）；Wanda，按权重绝对值乘对应输入的激活幅度剪；SparseGPT，剪掉后用校准数据算出的二阶信息调整剩下的权重来补偿误差。量化一侧也试三种：直接四舍五入；GPTQ，逐列量化并用二阶信息把误差摊到还没量化的列上；AWQ，先放大激活大的那些通道的权重再量化，保护重要通道。两侧都用同一批 C4 数据校准。速度用 cuSPARSELt 的稀疏矩阵乘法，现算的操作数两边都要算上在线剪枝或在线量化的时间。

3. 还能降精度时：降一档总是更好

在精度上，相同位数下，2:4 在每个存储预算、两个模型上都输。在最宽裕的预算下（稠密一侧用 8 位格式，按前面的换算 2:4 一侧保留的值可用约 14 位），误差差一个数量级以上，位数越低差距越小，但始终没有反超，最接近的一组 R 仍略高于 1。相同档位下更明显：2 倍档里，2:4 加 FP16 的误差是稠密 FP8 的 5 到 16 倍，六类操作数无一例外。在所有算力对比里，2:4 赢下的几次，对手都是较弱的格式：MXFP4（4 位浮点，每 32 个元素共用一个只能取 2 的幂的缩放系数，所以缩放很粗），以及每行只有一个缩放系数的 INT8。对上 FP8 和 NVFP4（同样是 4 位浮点，但每 16 个元素共用一个 FP8 缩放系数，再加整张量一个缩放系数，缩放细得多），一次都没赢。

算子误差不等于模型质量，所以作者又在最接近打平的 15 组配置上做了整模型测试，这是对 2:4 最有利的情形。GSM8K 上，2:4 没有一次显著好于量化，有 7 次显著更差。RULER 是长上下文基准，考的是在长文里找到并用上指定信息。2:4 在困惑度或 RULER 上显著好于对应量化格式的情形，多数出在注意力概率上：每 4 个分数只留最大的 2 个，相当于把注意力变尖，长上下文检索和困惑度会变好，但对推理从来没有帮助。

把精度和速度放在一起看，只要还有更低的稠密精度可选，每一个 2:4 配置都落在灰色区域里，总有某种稠密格式又快、误差又小好几倍。2:4 只在最右端出现在前沿上，也就是叠加在最低精度之上的时候。

在线剪枝的实现也很关键。作者写了一个融合内核，读一次输入、写一次保留值和索引，速度接近显存拷贝带宽；cuSPARSELt 自带的剪枝压缩路径和 PyTorch 的半结构化转换要慢好几倍，会把稀疏矩阵乘法省下的时间大部分吃掉。注意力概率 P 更不划算：在线剪枝压缩后，2:4 只有稠密速度的一半左右，所以不能把 P 单独当作稀疏操作数来用。

4. 为什么输：删掉的能量补不回来

原因是一个简单的不对称。量化保留每个值、只做取整，每多 1 位，误差就减半。2:4 直接删掉一半的值，删掉的那部分彻底丢了，给剩下的值再多位数也补不回来。作者把所有四元素组里被删掉的值的平方加在一起，除以整个张量所有值的平方和，称为“2:4 能量损失”。对独立高斯数据，这个比例是 13.2%，和位数无关。在高斯数据上，2:4 一侧的误差在各个预算下都在 36% 到 37%，而同位数的稠密格式从 INT8 的 0.6% 到 INT3 的 27.4%。两者要到 3 位以下才会相交，而没有任何稠密张量核心支持那么低的精度。

掩码定下以后，删掉的值只带来剪枝误差，留下的值只带来量化误差，两者落在不同的元素上，所以误差的平方和（误差能量）正好相加；下面的误差都指除以整个张量平方和之后的相对误差能量，开方才是相对误差，13.2% 的能量损失开方约是 36%。所以 2:4 一侧的误差是“能量损失 + 把留下的值量化到 $2m$ 位的误差”，稠密一侧是“全部值量化到 $m+1$ 位的误差”，两者相除再开方就是预测的 R。每一项都直接从张量算出，不拟合任何参数。它和实测 R 的排序相关系数是 0.93，区分 2:4 赢和输的 AUC 是 0.95。不过 2:4 只在 3% 的点上赢，所以这个判据能解释差距有多大、为什么，却判不准势均力敌的情况。作为对照，以前文献提出的整体峰度和结果几乎不相关。决定胜负的是张量在硬件分组方向上的局部结构，而不是它整体的分布形状。

这个分析还预测了 Hadamard 旋转的影响。低比特量化前，常先把张量乘以一个 Hadamard 矩阵（元素只有 ±1 的正交矩阵，再整体缩放），这相当于把每个值和一批邻居混合，少数特别大的离群值就被摊平到许多元素上。正因为摊平，每组 4 个元素的大小变得更接近，2:4 每组剪掉两个时丢掉的能量就更多；另一方面，离群值被摊平后量化范围变窄，量化误差变小。两头都对 2:4 不利。实测中旋转让 Q、K 和线性层输入的 R 大约翻倍，判据在 87% 的点上猜对了变化方向。实际部署大多会做旋转，所以论文未旋转的结果其实对 2:4 偏乐观。

5. 到了最低精度：真能提速，但必须重训

到了 FP8 或 NVFP4 这条底线，没有更低的稠密格式可换，2:4 只能往上叠，这时它不再有对手。作者把线性层权重做成 2:4，注意力保持 BF16，模型是 Llama-3.1-8B 基座。线性层矩阵乘法在 FP8 上加 2:4 快 1.3 到 1.7 倍，这是本文里 2:4 第一次真正赢。

6. Blackwell 的稀疏 FP4 更难用

Blackwell 的稀疏 FP4 不是逐元素 2:4，而是“成对 4:8”：每 8 个元素分成 4 对相邻的元素，保留其中 2 对。作者在 RTX PRO 6000 上验证过，逐元素的掩码在这个格式下会算出错误结果。它的内核比稠密 NVFP4 快 1.4 倍，但按对保留比按元素保留丢得更多，因为一对里的两个元素必须同进同出，没法各自挑大的留。高斯数据上它的能量损失是 20.8%，一次性剪枝后困惑度高达 108.83，是逐元素 2:4 的五倍。

已有的模型也帮不上忙。为逐元素 2:4 训练好的 Sparse-Llama 不能直接转过去，转换要丢掉三分之一已经训练好的权重，模型直接坏掉。作者在 10 亿 token 的预算下重训，GSM8K 只恢复到 0.132，而稠密 NVFP4 是 0.460，所以在这个预算下它还不可用。

7. 局限与实践意义

  • 只有两个 8B 模型。Blackwell 上的结论受限于 10 亿 token 和一套没调参的重训配方，更长的重训能不能恢复没有验证。
  • 4 位整数权重这条底线（主要用于 decode）没有测速度，因为 vLLM 已经删掉了相应的稀疏内核。decode 阶段受显存带宽限制，2:4 只省字节，在有的 GPU 上有帮助、有的反而变慢。
  • 速度对比中，稀疏矩阵乘法做了穷举调参，稠密一侧用的是库的默认策略，这对 2:4 有利，结论仍然是 2:4 输。

如果硬件还支持更低一档精度（比如 H100 从 BF16 到 FP8），先降精度，不要加 2:4。已经在 FP8 上部署、prefill 吞吐是瓶颈、并且能拿到充分重训过的 2:4 模型时，2:4 可以带来两到三成的实际提速，但 vLLM 主线已经删掉支持，需要自己维护分支。在 Blackwell 上，目前没有现成的成对 4:8 模型，自己重训的成本和效果都没有保证。评估任何重训后的稀疏模型，都不要只看困惑度。

低并发场景下，比如一个用户同时只开一两个会话的编码或智能体应用，单个请求每步要算的数据很少，延迟主要花在内核启动、内核之间的空等和多卡通信上。SGLang、NVIDIA 和 AMD 团队在这篇 LMSYS 博客里介绍了 SGLang 低延迟模式：用一个插件框架，把厂商为特定模型和硬件写的深度融合内核接进 SGLang，而不把这些代码合进 SGLang 主仓库。测试模型是 DeepSeek-V4.1-Flash 加 DSpark 投机解码（DSpark 是这套部署用的草稿方案：一个小的草稿头每步按顺序逐个提出 5 个草稿 token，再由主模型一次验证；博客称它为 Markov 头，没有进一步说明结构），在 AgentX 智能体轨迹回放上，4 张 NVIDIA GB300、1 个并发会话时，每用户 P90 生成速度从 671.2 提到 928.4 token/s（1.38 倍）；4 张 AMD MI355X、4 个并发会话时，从 331.6 提到 516.0 token/s（1.56 倍）。对照组都是同一硬件上的标准 SGLang。这是工程博客，不是论文，数字由作者团队自己测，没有第三方复现。

1. 问题：小批量时，时间不花在计算上

只有 1 个请求时，DSpark 每步只验证 6 行 token，也就是主模型一次前向只处理 6 个位置：博客没有拆开说，按 5 个草稿 token 推算，应是上一步确定的 1 个 token 加 5 个草稿 token。矩阵乘法本身很快，真正占时间的是一串小内核前后排队、每个内核启动和收尾的空档，以及张量并行每层两次跨卡归约（把各卡的部分结果加起来）时 GPU 什么都不算的等待。批量大时这些开销被大量计算摊薄，批量小时就成了主角。

针对特定模型、硬件和并发规模做深度融合可以把这些空档压掉，但每一种组合都要单独写一套。硬件有 NVIDIA 和 AMD 好几代，模型结构各不相同，并行方式也不同，全部放进 SGLang 主仓库会让代码和评审负担一直增长。所以这篇博客其实讲了两件事：两家厂商各自怎么做低延迟内核，以及 SGLang 怎么用插件把它们接进来又不背上维护负担。

2. NVIDIA：内核数量几乎没变，等待少了

NVIDIA 的实现叫 sgl-nvidia-mega。作者先在预热好的 CUDA graph 下剖析了一个解码层，1 个请求，每组约 800 次测量取中位数：

整层快了 29%，其中一半多来自注意力区段。最值得注意的是，验证一步的内核总数只从 1205 个减到 1189 个。所以提速不是靠把内核合并成更少几个，而是让前后内核重叠起来、少等一会儿。博客也提醒，剖析本身会影响计时，各区段中位数加起来也不等于整层，这张表用来说明机制，不代表线上性能。

具体做了四件事：

  1. 下一个内核提前启动。 CUDA 的 PDL（programmatic dependent launch）允许后一个内核在前一个还在跑时就开始，先准备屏障、加载权重，再等输入。SGLang 原本就用 PDL，插件做的是把“可以开始”的信号放得更早。注意力在等 query 之前先开始收集 KV，RoPE（按 token 位置旋转 query 和 key 向量的位置编码）是逐元素的计算，可以在把 query 读进来的同时算完，省掉一个单独的内核。
  2. 在矩阵乘法收尾时直接把结果发出去。 注意力输出投影后，每张卡只有部分和，需要跨卡归约。原来的做法是矩阵乘法先把结果写回显存，下一个内核再读出来发给别的卡。插件让每个线程块算完自己那一块，就直接从寄存器通过 NVLink 多播写到其他卡，不用等整个矩阵乘法结束，也省掉一次读回。
  3. 路由没结束就开始算专家。 最多 8 行时，每个专家选中的 token 刚好放进一个 8 行的块，插件用位图记下每个专家被哪些 token 选中，再数位图里有几个 1 得到每个专家的行数，据此直接把各行放进块里，不用扫描或排序。它还在路由收尾的同时提前启动第一个专家矩阵乘法，让这一步的准备工作和路由重叠。这就是 MoE 区段省下 7.9 µs 的来源。
  4. 草稿采样放进一个内核。 DSpark 的草稿头要按顺序提出 5 个 token，原来每个 token 要单独启动。插件在每张卡上一次启动完成全部 5 个，草稿阶段从 85.1 µs 降到 34.2 µs，验收逻辑不变。

测试负载固定为输入 8K、输出 1K。为了只比较插件本身，两次运行的设置相同，投机解码的平均接受长度都模拟成 3.51（每次验证平均接受 3.51 个草稿 token），唯一的区别是插件开关。结果是 1 到 8 个并发请求时，每用户解码速度提高 12% 到 38%。并发越低提速越多，这符合前面的分析：被省下的是固定的等待开销，请求越少，它占的比例越大。

这张图还有一个博客没明说的结论。插件开启、2 个请求时，每用户约 840 token/s，比插件关闭、1 个请求的约 745 token/s 还快，而每卡总吞吐从约 165 提到约 325 token/s。也就是说，对延迟有硬要求的服务，用插件后可以把并发翻倍，单用户速度仍然不比原来差。

3. AMD：每层只启动两个常驻内核

AMD 的实现叫 sgl-amd-mono，支持 MI355X 和 MI350X，走的是另一条路。作者认为 AMD 上低并发有三项主要开销：即使用了 HIP graph 免去 CPU 端的启动，每个小内核在 GPU 上仍要 2 到 4 µs；前一个内核收尾、后一个起步的空档里计算单元闲着，权重加载也停了；每层两次跨卡 all-reduce 期间没有任何计算。

插件用 FlyDSL（AMD 侧写 GPU 内核的工具）把一层的大部分工作合成两个常驻内核（persistent kernel：启动一次后一直留在 GPU 上，自己依次处理多个阶段，而不是每个小步骤各启动一个内核）。K1 做 mHC 更新（mHC 是 DeepSeek 的流形约束超连接，把残差流扩成几条并行的流，每层用一个受约束的小矩阵把它们混合；这里的更新就是这一步混合）、Q/KV 投影和写 KV cache；K2 做注意力、输出投影、MoE 和两次 all-reduce。两者之间保留一次启动边界，是为了保证 K1 写的 KV 在 K2 读之前对整张卡可见。

在一个内核内部，各阶段靠“带解码步编号的值”接力：每个阶段把算出的值和当前解码步的编号存在一起，下一个阶段不论在本卡还是别的卡，都反复读这个位置。读到的编号等于当前步，就说明这一步的值已经写好，可以开始算。这样不需要另设标志位，也不用每步清零。博客没写值和编号具体怎样一起写入。不依赖路由结果的权重提前加载，路由选出专家后再加载专家权重。all-reduce 也放进了内核：每算完一块输出就推到所有卡，各卡按固定顺序求和，其他工作组同时继续算。

这样做有一个风险：一张卡卡住，所有卡都会在内核里等。为此，每次跨卡等待都设了比 SGLang 看门狗更短的超时，超时后所有卡一起终止这次启动，而不是让整个服务挂住。

4. 插件框架：专用内核放在主仓库之外

外部内核库通过四步接入。第一步是注册，库为每种支持的模型结构声明自己的要求和构建入口。第二步是检查：在加载权重前核对硬件、精度、并行方式等是否兼容，不兼容就尽早报错，不要等到运行中才出问题。第三步是构建，在初始化时准备好权重和资源，并且在确定 KV cache 大小之前完成，所以插件占用的显存会被算进去，不会和 KV cache 抢。第四步是运行时分派：插件可以只覆盖部分步骤类型和 token 数，不覆盖的步骤回到 SGLang 原来的前向。各张卡必须对“这一步走不走插件”达成一致，否则会进入不匹配的集合通信。CUDA graph 捕获时选好的路径会被记录下来，之后回放不必再做 Python 端的判断。

这个设计的好处是厂商团队可以独立迭代，SGLang 只维护接口。代价是外部内核不经过 SGLang 常规的代码评审，正确性要靠接口层的测试来兜底，而这部分测试博客说还在计划中。

6. 局限与实践意义

  • 目前只支持 DeepSeek-V4.1-Flash 加 DSpark 这一组合，GLM-5.3、K3、MiniMax M3 等还在开发中。
  • 博客没有给出精度对比，只说明不改变投机解码的验收逻辑。融合内核可能改变浮点运算的顺序（例如跨卡求和的顺序），数值上是否和标准路径完全一致，博客没有说明。
  • 插件接口的 CI 和性能回归测试还在计划中，接口本身也处在早期，之后还会调整。
  • 收益集中在 1 到 8 个并发。大批量吞吐场景下这些开销本来就被摊薄了，博客没有给出数据。

如果你的服务是低并发、对单用户延迟敏感，并且正好用 DeepSeek-V4.1-Flash 部署在 GB300 或 MI355X 上，可以直接试这个模式。对其他模型，更有用的是方法：在小批量下先剖析每层的时间线，看时间花在计算还是等待上；如果是等待，优先做内核重叠和通信前移，而不是一味减少内核数量。用插件把专用内核隔离在主框架之外，也是一个值得参考的维护办法。

RCSD: Reinforcement and Continual Learning for Domain-Specific Speculative Decoding

投机解码的做法是：先让一个小的草稿模型连猜几个 token，再让大模型一次性并行核对，猜对几个就收下几个。每轮平均收下的 token 数叫“接受长度”，它越长，大模型需要跑的轮数越少，生成就越快。草稿模型一般用蒸馏来训，也就是让它的输出分布尽量贴近大模型。海信的这篇论文认为这个目标选错了：核对时只看草稿给的 token 是不是大模型也会选的那个，草稿把排在最前面的几个候选排对就够了，不必把整个分布学像。作者提出的 RCSD（用强化学习继续训练草稿模型的框架）先用常规方法训好草稿模型，再用 DPO 或 GRPO 继续训练，训练数据全部由大模型自己生成，不需要人工标注，也不需要额外的奖励模型。在 Qwen3-1.7B 和 Llama-3.1-8B 上，接受长度在所有测试设置中都超过基线。不过论文摘要里的“平均提高 35%”和“端到端快 1.35 倍”，用正文自己的表格核算对不上，下文会具体说明。

1. 问题：草稿模型学的东西和它要做的事不一致

这篇论文的对照组只有一个，要先交代清楚。EAGLE 的草稿模型很小，除了看已经生成的 token，还直接读大模型的隐藏状态来猜下一个词。HASS（在 EAGLE 上训练草稿模型的一种蒸馏方法）就是对照组，RCSD 也是从训好的 HASS 草稿模型接着训。

蒸馏的损失是前向 KL 散度。它的特点是“全都要”：大模型认为有一点点可能的 token，草稿模型也得分一些概率过去，否则就会被罚。问题在于草稿模型比大模型小几个数量级，没有足够的容量把整个分布学像。于是它的容量被摊到了大量根本不会被选中的低概率 token 上。

作者用下图说明这种错位。接受与否只取决于草稿最看好的 token 和大模型最看好的 token 是否一致。左下角是理想情况：分布贴得近，最高点也对上了。右下角草稿的分布和大模型差得很远，KL 损失很高，但最高点仍然对齐，所以照样被接受。上面两幅则相反，最高点错开了，不管 KL 高低都会被拒。换句话说，KL 损失只是接受率的一个间接代理，而且是不太准的那种。

由此作者把目标改了：不再要求草稿“模仿整个分布”，而是让它把概率集中到大模型最可能选的那条路上，宁可放弃分布尾部。用论文的话说，从覆盖所有峰（mode-covering）改成只抓主峰（mode-seeking）。

2. 方法：拿大模型自己的输出当正例

两种训练方式都从训好的 HASS 草稿模型出发，并把这份初始权重冻结一份作参考，防止新模型偏得太远。

DPO 版需要成对的“好”与“差”序列。好的那条完全由大模型逐个 token 生成，代表草稿理想中应该猜出来的内容。差的那条是交替生成的：大模型先写 1 个 token，然后草稿模型不经核对、连着写 k 个，再换回大模型写 1 个，如此循环（DPO 版里 k 取多少，论文没有写明）。草稿自己写的部分往往会慢慢偏离大模型会写的内容，所以这条序列自然就是反例。训练时让草稿对好序列的概率相对参考模型上升，对差序列的概率下降。

这里有一个细节很关键：差序列里由大模型写的那些 token 在计算损失时被屏蔽掉。如果不屏蔽，训练会把这些本来就正确的 token 也当成错误来压低。另外，DPO 对序列长度敏感，所以好序列上也用了同样的屏蔽位置，保证两边比较的 token 数一致。

GRPO 版不再只比一对，而是对同一个提示准备一组序列：一条由大模型直接生成，另外三条由两者交替写：大模型写 1 个 token，草稿接着不经验证连写 k 个，再轮到大模型，k 分别取 1、2、3。每条序列的得分由两部分相加，两部分都先在组内做标准化：一是大模型认为这条序列有多自然，用大模型给它的对数概率衡量，也就是每个 token 概率取对数后求和；二是这条序列里草稿写的 token 被大模型接受的比例。大模型直接生成的那条没有草稿 token，论文没有说明它这一项怎么算。组内得分高于平均的序列被加强，低于平均的被削弱。

两种方法的共同点是：正例、反例和分数全部由大模型自动给出，数据可以从线上请求或任意文本提示里批量构造。这也是标题里“持续学习”的出发点：上线后可以不断用新请求继续训练草稿。不过正文并没有做这类实验，后文会再提。

5. 论文没有回答的问题

  • 质量没有测。论文多次说“不影响生成质量”。按投机解码的标准核对规则，最终输出确实由大模型决定，理论上应该如此。但实验部分没有任何质量指标，在采样温度不为 0 或用了近似核对的部署里，这一点需要自己验证。
  • 标题里的“持续学习”和“特定领域”都没有实验。训练和测试都是通用数据集，没有做“上线后用新请求不断训练”的实验，也没有某个垂直领域的评测。
  • 方法描述前后有出入。Figure 3 左侧说正例和反例来自核对时被接受和被拒绝的 token，而方法章节写的是“大模型单独生成”对“大模型与草稿交替生成”。实验用的是后者。
  • 缺少成本数据。论文没报告构造数据和继续训练要花多少 GPU 时间，也没和其他非蒸馏的草稿训练方法比较，只和 HASS 一个基线比。
  • 吞吐只测了一组配置：一个模型、一个推理框架、一种步数，没有测不同并发下的表现。

6. 实践意义

如果你已经在线上用 EAGLE 或 HASS 类的草稿模型，这篇论文给出一个成本不高的后续步骤：用大模型对线上或离线提示生成一批回答，再按“大模型单独写”和“大模型与草稿交替写”构造正反例，对现有草稿模型做一轮 DPO。整个过程不需要标注，也不改推理代码。

预期收益要按自己的流量来估。如果训练数据和线上请求同分布，接受长度可能提高两成以上，吞吐提高一到两成。如果分布不同，按论文在 Llama 上的通用测试集结果，吞吐大约只多 7%。GRPO 比 DPO 多花一倍的生成成本，收益几乎相同，可以先不做。上线前需要自己补上论文缺的两项检查：输出是否与不开投机解码时一致，以及继续训练的 GPU 开销。

DeepSeek-V4.1-Flash、GLM-5 系列这类模型用的是按索引挑选的稀疏注意力：每步解码先由一个打分模块从全部历史里挑出一小部分位置，注意力只读这些位置的 KV cache。这样每步读的数据少了，但存储并没有省下来，因为这一步没被挑中的历史，下一步可能就会被挑中，所以全部历史都得留着。上下文一长、请求一多，显存能装下多少历史，就决定了能同时解码多少请求。Scitix.AI 的 UlaCache 把所有 GPU 的 KV 池和可选的 CPU 内存编进同一个“逻辑地址空间”：推理引擎只按逻辑地址分配和选取 KV，数据实际放在哪张卡、在 GPU 还是 CPU 上，由 UlaCache 负责搬运和改映射。它的核心不是“多用 CPU”，而是让每一份内存都存不同的历史，不再存副本。在 SGLang 上用 GLM-5.3 跑 64K–128K token 的长文摘要请求，开启投机解码、内存预算相同时，峰值吞吐比 HiSparse 高 1.16 到 2.51 倍。从论文自己的曲线看，这些收益几乎全部来自“能同时装下更多请求”，同样批大小下的单步速度并没有变快。

1. 问题：内存大多被重复的副本占掉

作者先统计了 GLM-5.3 在 8×B300 上的 KV 分配，发现现有两种做法都有大量重复存储，来源有两个。

第一个来源是跨卡重复。GLM-5.3 用 MLA，它把所有注意力头的 KV 压成一份共享的表示。常规的张量并行（TP）按注意力头把计算分到各卡，可这份共享表示没法按头切开，于是每张卡都存一份完整的。8 卡 TP 下，只有 12.5% 的空间存的是不重复的历史，其余 87.5% 都是副本。也就是说，8 张卡的显存只发挥了 1 张卡的存储容量。

第二个来源是 GPU 和 CPU 之间的重复。HiSparse 是目前用 CPU 扩展稀疏注意力 KV 的代表做法：完整历史放在 CPU，每步把被挑中的那部分搬到 GPU 并缓存起来。问题是 GPU 上缓存的每一条在 CPU 上也都还在。图中它一共用了 5330 万个物理槽，却只存了 3000 万个不同的历史位置。GPU 那 2330 万个槽只让访问变快，并没有让能存的历史变多。

HiSparse 还有一个分配上的问题：它给每个请求一块固定大小的 GPU 缓存。请求少的时候，空出来的显存别的请求也用不上。作者举的例子是 8×B300、DP 模式（数据并行：每张卡各自跑完整的模型、各自服务一批请求，后文还会细说）、开投机解码、只有 1 个请求时，GPU 本来装得下全部历史，但单个请求的缓存配额装不下，于是仍然不断从 CPU 取数据。结果它每生成一个 token 的时间（TPOT）比纯 GPU 的 SGLang 高 23.5%。

2. 统一逻辑地址：引擎只管“第几号”，不管“放在哪”

UlaCache 的做法是给每条 KV 一个固定的逻辑地址，再用一张映射表记录它当前实际在哪个 GPU 槽或 CPU 槽。数据在 GPU 和 CPU 之间搬动时只改映射表，逻辑地址不变，所以推理引擎那一侧的代码不用知道数据被挪过。这和 PagedAttention 把逻辑块映射到显存物理块是同一个思路，只是范围从一张卡扩大到了多张卡加 CPU。

在 DP 模式下，每张卡负责自己的请求，管理自己的 GPU 池和 CPU 池，一个请求可用的容量就是两者之和。这里去掉的是 GPU 和 CPU 之间的重复：一条 KV 要么在 GPU，要么在 CPU，不会两边都有。

TP 模式的变化更大。所有卡的 GPU 池合成一个分布式地址空间，每张卡只存每个请求历史的一部分：逻辑地址 t 放在第 t mod P 张卡上，P 是卡数。这样 8 张卡存的是 8 份不同的历史，而不是 8 份同样的副本。代价是计算时要从别的卡取数据，所以负责计算的卡另外留一块本地缓冲区，存最近挑中过的 KV。稀疏注意力连续几步挑中的位置重合度很高，所以缓冲区命中率高，大部分时候只需要补取少数缺的条目。

还有两个细节值得一提。GLM-5.3 里有些层共用同一次稀疏选择的结果，UlaCache 对这组层只做一次地址查找和去重，并在当前层计算时，用单独的 CUDA stream 预取后面几层要用的数据。另外，打分模块用到的索引键也按同样规则分散到各卡：每张卡只给本地的键打分，再用一次 all-gather 汇总。这一步省掉了重复打分，但在低并发时会带来额外的通信等待。

3. PB-LRU：共享的 GPU 池里先换出谁

开启 CPU 存储后，GPU 池不再按请求切块，而是所有请求共享，最近用过的留在 GPU，久没用的换到 CPU。这就需要一个替换策略。标准 LRU 要给每个槽记时间戳，选替换对象时要扫描整个池。每步解码、每一层都要做一遍，开销会落在解码的关键路径上。

PB-LRU（作者提出的并行分桶 LRU）用一个近似来避免扫描。它不再给每个槽排精确的先后，而是把同一轮调度里被访问的槽都放进同一个“桶”。每组层维护一圈最近的桶，外加一个冷桶。每轮调度当前桶往前挪一格，即将被复用的旧桶里剩下的槽归入冷桶，只改标记，不搬数据。需要腾位置时，先用空槽，再从冷桶里挑，再按从旧到新的顺序挑最近的桶。当前桶不参与挑选，因为里面的数据正要被这一步的注意力用到。

每个桶用位图表示，一位对应一个 GPU 槽。上面再叠几层汇总位图，每一位表示下面一段里有没有被占用的槽，挑选时可以直接跳过整段空白。命中检测、更新访问时间、去重都由 GPU 线程并行完成。数据搬运也有顺序要求：先把数据搬完，再更新映射表并发出完成信号，注意力等到信号才去读新位置，这样不会读到搬到一半的数据。

5. 局限与适用范围

  • 只测了一个模型、一种负载：GLM-5.3 加长文摘要。不同的稀疏选择模式（每步重合度更低的任务）会影响缓冲区和 GPU 池的命中率，论文没有覆盖。
  • 吞吐比较取的是各系统在所有批大小中的最高值，而各自的最高点出现在不同的批大小上。所以“2.51 倍”反映的是“能装下多少请求”，不是同样负载下更快。如果你的线上并发本来就到不了基线的容量上限，这个收益基本拿不到。
  • 低并发下比纯 GPU 的 SGLang 慢。对延迟敏感、并发低的服务，纯 GPU 方案仍然更合适。
  • 论文没有测精度。UlaCache 不改变注意力挑选哪些位置，理论上输出不变，但跨卡取数和换出换入的正确性只能靠实现保证，没有给出一致性验证。
  • 没有报告 CPU 与 GPU 之间的带宽占用，也没有和同期其他稀疏注意力 KV 卸载系统做对比。

6. 实践意义

如果你在 SGLang 上部署 MLA 加稀疏注意力的模型，比如 GLM-5、DeepSeek-V4.1 一类，请求上下文很长，并且瓶颈是“显存装不下更多并发”，那么这篇论文最值得借鉴的是先查重复存储。用 TP 部署 MLA 模型时，先算一下每张卡上有多少 KV 是别的卡也有的。按论文的统计，8 卡 TP 下这个比例是 87.5%，去掉它带来的容量提升比加 CPU 内存还大。

其次，用 CPU 扩容时，要让 GPU 和 CPU 存不同的东西，并让所有请求共享 GPU 池，而不是给每个请求固定配额。最后，评估这类方案时要看同样批大小下的曲线，而不只看峰值倍数。前者告诉你单步有没有变慢，后者只告诉你能多装多少请求。
