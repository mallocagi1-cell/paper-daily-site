Is 2:4 Sparsity Still Worth It? Semi-Structured Sparsity versus Quantization in LLM Inference

独立研究者在 Llama-3.1-8B-Instruct 和 Qwen3-8B 上，按相同存储位数（稀疏位置索引也计入）和相同标称算力档位，比较"加 2:4 稀疏"和"降一档精度"，并在 L40S、H100、RTX PRO 6000 上实测。只要还能降精度，加 2:4 就既更不准也更慢：2:4 + INT8 的存储成本等于 INT5。到 FP8 底线后，H100 上 vLLM 服务的重训 2:4 模型 prefill 吞吐比稠密 FP8 高 27%，GSM8K 相当；但重训时困惑度先恢复，推理准确率恢复得慢得多。

NVIDIA 从 Ampere 起的 GPU 都支持 2:4 稀疏：矩阵乘法里一个操作数沿累加方向每 4 个元素只保留 2 个非零值，张量核心按标称可以快一倍。它可以和量化叠加，于是部署时的实际问题是：在当前精度上，下一步是加 2:4，还是降到更低一档精度？这篇独立研究者的论文在 Llama-3.1-8B-Instruct 和 Qwen3-8B 上，按"相同存储位数（把稀疏的位置索引也算进去）"和"相同标称算力档位"两种口径，对一层 transformer 里全部六类矩阵乘法操作数做了比较，并在 L40S、H100、RTX PRO 6000 三代 GPU 上实测速度。结论是：只要还有更低一档精度可用，加 2:4 既更不准也更慢；到了硬件支持的最低精度（Ada/Hopper 上是 FP8）之后，2:4 才有价值，H100 上用 vLLM 服务的 2:4 + FP8 模型 prefill 吞吐比稠密 FP8 高 27%，GSM8K 准确率相当，但前提是要重新训练。

1. 问题：vLLM 已经删掉了 2:4 支持，它还值得用吗

一边是 NVIDIA 每一代 GPU 都保留稀疏张量核心，Blackwell 还加了稀疏 FP4；另一边，2026 年 vLLM 和 LLM Compressor 因为用户太少删除了 2:4 支持。已有的剪枝与量化对比大多按"名义压缩率"比较、主要看权重，没有把"加 2:4"和"降一档精度"在真实硬件上直接对比。

作者指出四个容易被忽略的点：

  • 2:4 每个保留值旁边都要存位置索引，所以占用的位数比一半多；
  • 两者都号称让吞吐翻倍，但数据手册不说实际能快多少；
  • 推理时大多数操作数（激活、Q、K、V、注意力概率）是现算出来的，每次矩阵乘法前都要现场剪枝压缩，这部分时间只测矩阵乘法时看不到；
  • 硬件规定了哪个操作数能稀疏、沿哪个方向分组，所以按整个张量统计的指标（如峰度）反映不出 2:4 实际删掉了什么。

2. 方法：在相同成本下比

2.1 相同位数

每种格式按每个原始元素实际存了多少位计费：值、索引、缩放因子都算。稠密 INTk 每 128 个元素一个 FP16 缩放因子，每元素 k + 0.125 位；2:4 只保留一半元素，但每个原始元素要多 1 位索引。结果是 2:4 + INT8 的成本等于稠密 INT5，2:4 + INT4 等于 INT3，2:4 + FP16 比 FP8 还贵。

所以在相同存储下，真正的选择是"丢掉一半元素、剩下的用两倍精度存"，还是"保留全部元素、每个多 1 位"。

2.2 相同算力档位

按数据手册的标称吞吐配对：2 倍档是 2:4 + FP16 对稠密 FP8/INT8；4 倍档是 2:4 + FP8 对稠密 4 位浮点（只有 Blackwell 有）。

2.3 怎么测

精度指标是算子级相对误差（和 FP32 参考输出比），用比值 R =（最好的 2:4 配置误差）/（最好的量化配置误差），R < 1 表示 2:4 更好。双方各自从同等努力程度的方法里挑最好的：2:4 一侧试幅值剪枝、Wanda、SparseGPT 等，量化一侧试四舍五入、GPTQ、AWQ，都用 C4 校准。速度用 cuSPARSELt 稀疏矩阵乘法，现算的操作数两边都要计入在线剪枝或在线量化的时间。总共超过 22 万个测量配置。

3. 实验

3.1 在最低精度之上：降一档精度总是更好

这组实验检验，在还能降精度时，加 2:4 是否有机会更准或更快。

精度。 相同位数下，2:4 在每个存储预算、两个模型上都输：8 位时误差差一个数量级以上，随位数降低差距缩小但不消失，在 3.1 位预算下，两者最接近的一组对比（Llama 的 K 对 INT3）R 仍略高于 1。2 倍档里，2:4 + FP16 的误差是稠密 FP8 的 5 到 16 倍，所有操作数都如此。

速度。 下表是"对手耗时 / 2:4 耗时"，大于 1 表示 2:4 更快（Llama-3.1-8B 投影层，2K–16K token 的中位数）：

W 为稀疏权重，X 为稀疏激活（含在线预处理）。在同一档位上，2:4 一侧都更慢。作者对原因的解释是：2:4 每 4 个元素丢掉的那 2 个值所占的能量（平方和），不管给剩下的值多少位都补不回来；而量化误差每多 1 位就减半。高斯数据上，逐元素 2:4 会去掉 13.2% 的能量。

3.2 在最低精度上：2:4 真能提速，但要重训

这组实验检验到了 FP8 或 NVFP4 这一底线后，2:4 能带来多少收益、代价是什么。线性层权重做 2:4，注意力保持 BF16，模型是 Llama-3.1-8B 基座。

3.3 Blackwell 的稀疏 FP4

Blackwell 的稀疏 FP4 不是逐元素 2:4，而是每 8 个元素中保留 4 对相邻元素里的 2 对。内核比稠密 NVFP4 快 1.4 倍，但在高斯数据上去掉 20.8% 的能量；一次性剪枝后困惑度 108.83，是逐元素 2:4 的五倍；为逐元素 2:4 重训过的 Sparse-Llama 也不能直接转换。在作者 1B token 的重训预算内，GSM8K 只恢复到 0.132。

4. 局限

模型只有两个 8B 模型；Blackwell 上的 4:8 结论受限于 1B token、一套未调参的重训配方，更长的重训能否恢复没有验证。4 位整数权重底线（主要用于 decode）没有测速度，因为 vLLM 已删除相应稀疏内核。实际部署常在低比特量化前加 Hadamard 旋转，作者指出这会让大多数操作数上 2:4 的劣势更大，因此本文未旋转的结果对 2:4 偏乐观。

5. 实践意义

如果硬件还支持更低一档精度（例如 H100 从 BF16 到 FP8），先降精度，不要加 2:4。已经用 FP8 部署、prefill 吞吐是瓶颈、并且能拿到充分重训过的 2:4 模型时，2:4 可以带来实际提速，但 vLLM 主线已删除支持，需要自己维护。评估重训后的稀疏模型，不要只看困惑度。

SGLang Low-Latency Mode: Kernels and Runtime

SSGLangAMDNVIDIA📖 有深读 · 6 分钟

SGLang、NVIDIA 和 AMD 团队用插件框架把专用融合内核接入 SGLang，针对低并发场景减少内核间等待和跨卡通信。DeepSeek-V4.1-Flash + DSpark 的 AgentX 回放中，4×GB300、1 个会话时每用户 P90 生成速度从 671.2 提到 928.4 token/s；4×MI355X、4 个会话时从 331.6 提到 516.0 token/s。NVIDIA 上一个解码层中位耗时从 96.8 µs 降到 68.4 µs，内核数几乎不变，提速主要来自减少内核间等待和让工作重叠。

低并发场景（例如一个用户同时只有一两个会话的智能体应用）下，单个请求每步要算的数据很少，延迟主要花在内核启动、内核之间的等待和多卡通信上。SGLang、NVIDIA 和 AMD 团队在这篇 LMSYS 博客里介绍 SGLang 低延迟模式：用一个插件框架，把厂商为特定模型和硬件写的高度融合内核接进 SGLang，而不把这些代码合进 SGLang 主仓库。测试模型是 DeepSeek-V4.1-Flash 加 DSpark 投机解码，在 AgentX 智能体轨迹回放上，4 张 NVIDIA GB300、1 个并发会话时，每用户 P90 生成速度从 671.2 提到 928.4 token/s（1.38 倍）；4 张 AMD MI355X、4 个并发会话时，从 331.6 提到 516.0 token/s（1.56 倍）。对照组都是同一硬件上的标准 SGLang。

1. 问题：小批量时时间花在哪里

在 1 个请求时，DSpark 每步只验证 6 行 token，每个内核的计算量很小，前后依赖和跨 GPU 通信占了大头。为特定模型、硬件和并发规模做深度融合能显著降延迟，但每种组合都要单独一套实现，全部放进 SGLang 主仓库会让代码和评审负担不断增大。

2. 方法

2.1 NVIDIA：让相互依赖的内核和通信重叠（sgl-nvidia-mega）

作者先在预热后的 CUDA graph 下剖析了一个解码层（1 个请求，各区段中位数）：

解码层中的区段SGLang加插件
注意力（从上一个 MoE 输出到输出投影）33.4 µs18.3 µs
注意力输出投影和张量并行归约10.9 µs9.4 µs
MoE（从路由到归约后的输出）44.4 µs36.5 µs
整层96.8 µs68.4 µs

内核总数只从 1,205 减到 1,189，延迟下降主要来自减少等待和让工作重叠，而不是减少内核数量。具体做了四件事：

  1. 下一个内核提前启动。 利用 PDL（programmatic dependent launch，允许后一个内核在前一个还在运行时就开始），把"可以开始"的信号发得更早，让后一个内核先准备屏障、加载权重。注意力在等 query 之前先开始收集 KV；RoPE 在加载 query 时顺便做掉，省掉一个单独内核。
  2. 在矩阵乘法的收尾阶段直接发送结果。 注意力输出投影之后，每张卡只有部分和，需要跨卡归约。原来是矩阵乘法写回显存、再由下一个内核读出来发给其他卡；插件让每个线程块算完自己那块就通过 NVLink 多播直接写到其他卡，不必等整个矩阵乘法结束。
  1. 路由没结束就开始专家矩阵乘法。 最多 8 行时，每个专家选中的 token 能放进一个 8 行的块，插件用位图和计数直接定位，不需要扫描或排序，并提前启动第一个专家矩阵乘法。MoE 区段中位数从 44.4 µs 降到 36.5 µs。
  2. 投机解码的草稿采样放进一个内核。 DSpark 的草稿头按顺序提出 5 个 token，插件在每张卡上用一次内核启动完成，草稿阶段耗时从 85.1 µs 降到 34.2 µs，验收逻辑不变。

2.2 AMD：每层合并成两个常驻内核（sgl-amd-mono）

在 AMD 上，作者认为三项开销最大：即使用 HIP graph，每个小内核在 GPU 上仍要 2–4 µs；内核之间有空转；每层两次跨卡 all-reduce 期间没有计算。插件用 FlyDSL 写了两个常驻内核覆盖一层的大部分工作：K1 做 mHC 更新、Q/KV 投影和写 KV cache；K2 做注意力、输出投影、MoE 和两次 all-reduce。阶段之间用"带解码步编号的值"传递，编号对上就可以开始算，不需要另外的标志位。all-reduce 放进内核内部：每算完一块输出就推到所有卡上，其他工作组同时继续算。每次跨卡等待都设了比 SGLang 看门狗更短的超时，超时则所有卡一起终止这次启动，而不是让服务挂住。

2.3 插件框架

外部内核库通过四步接入：注册（声明支持哪些模型结构）、检查（加载权重前检查硬件、精度、并行方式是否兼容，不兼容就尽早报错）、构建（初始化时准备好权重和资源，在确定 KV cache 大小之前构建，所以显存占用会被计入）、运行时分派（插件只覆盖部分步骤类型和 token 数，不覆盖的步骤回到 SGLang 原有的前向）。

3. 实验

3.1 AgentX 轨迹回放

这组实验检验插件在接近真实的智能体负载下能提速多少。设置：DeepSeek-V4.1-Flash + DSpark，TP4，每用户 P90 生成速度，只切换插件开关。

硬件1 个会话4 个会话8 个会话
4 × GB3001.38×1.28×1.20×
4 × MI355X1.50×1.56×1.45×

NVIDIA 上并发越高，提速越小；AMD 上三档都在 1.45 倍以上。

3.2 NVIDIA 固定长度负载

输入 8K、输出 1K，模拟的平均接受长度为 3.51。在 1–8 个并发请求下，NVIDIA 插件把每用户解码速度提高 12%–38%。

4. 局限

目前只支持 DeepSeek-V4.1-Flash + DSpark 这一组合，GLM-5.3、K3、MiniMax M3 等还在开发中。博客说明剖析本身会影响计时，分区段数字用于解释机制，不代表服务性能。外部内核不经过 SGLang 常规代码评审，插件接口的 CI 和性能回归测试还在计划中；接口本身也还在早期，会继续调整。博客没有给出精度对比，只说明不改变投机解码的验收逻辑。

5. 实践意义

如果你的负载是低并发、对单用户延迟敏感（例如编码或智能体会话），并且正好用 DeepSeek-V4.1-Flash 在 GB300 或 MI355X 上部署，可以试这个模式。对其他模型，更有参考价值的是方法：在小批量下先剖析等待和通信时间，再决定融合哪些内核；以及用插件方式把专用内核隔离在主框架之外。

RCSD: Reinforcement and Continual Learning for Domain-Specific Speculative Decoding

📖 有深读 · 7 分钟

投机解码用一个小的草稿模型先猜几个 token，再让大模型一次性并行验证，猜中的越多（接受长度越长）越快。草稿模型通常用蒸馏训练：让它的输出概率分布尽量贴近目标模型，包括目标模型自己也不确定的那些低概率 token。海信的作者认为这和真正目标不一致：验证时只看草稿给出的 token 能否被目标模型接受，草稿只要把最可能的几个 token 排对就够了，不必复现整个分布。他们提出 RCSD，在 EAGLE 框架里用 HASS（一种按蒸馏训练草稿模型的方法）训好的草稿模型作为起点，再用 DPO 或 GRPO 继续训练，训练信号直接来自"目标模型自己生成的序列"和"草稿模型参与生成的序列"之间的对比。在 Qwen3-1.7B 和 Llama-3.1-8B 上，接受长度在 HumanEval、MT-Bench、GSM8K、ShareGPT 四个数据集和草稿步数 3–6 的所有设置中都高于 HASS，论文报告平均提高 35%，在 ShareGPT 等实际负载上端到端快 1.35 倍。

1. 问题：蒸馏目标和接受长度不一致

蒸馏最小化的是前向 KL 散度，会迫使草稿模型把容量分给目标分布里的所有区域，包括低概率的尾部。草稿模型比目标模型小几个数量级，做不到完全复现。作者的论点是：KL 损失低不等于接受率高，KL 损失高也可能接受率很好，关键在于前几个候选 token 的排序是否和目标模型一致。

2. 方法

两种训练方式都从 HASS 训好的草稿模型出发，并以它作为冻结的参考模型。

DPO 版。 对同一个提示构造一对序列：

  • "好"的序列：完全由目标模型自回归生成；
  • "差"的序列：目标模型生成 1 个 token，草稿模型不经验证接着生成 k 个，如此交替。

然后用标准 DPO 损失训练草稿模型，让它对"好"序列的概率相对参考模型上升、对"差"序列的概率下降。"差"序列中由目标模型生成的那些 token 在计算损失时被屏蔽，避免惩罚本来就和目标模型一致的部分。

GRPO 版。 对同一个提示生成一组序列：一条由目标模型直接生成，另外几条按不同的 k（每次草稿连续生成 1、2、3 个 token）交替生成。每条序列的分数是两项标准化后相加：目标模型给这条序列的对数概率，和这条序列的接受率。再用 GRPO 的裁剪目标加 KL 约束训练。

04 4.10

UlaCache: Unified Logical Addressing for Sparse LLM Serving

📖 有深读 · 7 分钟

Scitix.AI 的 UlaCache 把各 GPU 的 KV 池和 CPU 内存编进统一逻辑地址空间，让 GPU 和 CPU 各存不同的历史，并消除 MLA 在 TP 下的跨卡重复；GPU 池由所有请求共享，用分桶并行 LRU 决定换出。SGLang + GLM-5.3、64K–128K 输入下，8×B300 TP 可同时解码的请求从 HiSparse 的 37 增到 452；开投机解码时峰值吞吐相对 HiSparse 为 1.16–2.51 倍。低并发时延迟比纯 GPU 的 SGLang 高。

Isaac Zhu, Alan Cao, Hugh Yin, Rocky Wang, Orion Wang, Hscos Zhang, Jack Li, Jason Zhao
arXiv·2026-10-21·Relevance 4 · Novelty 4 · Practical 4 · Evidence 4 · Timely 5
独立页面阅读 ↗
独立页面阅读 ↗

稀疏注意力（例如 DeepSeek-V4.1-Flash、GLM-5 系列使用的按索引选取历史 token 的注意力）让每步解码只读一部分 KV cache，但没被选中的历史以后还可能被选中，所以全部历史仍要保存。长上下文、多请求时，存这些历史的显存决定了能同时解码多少请求。Scitix.AI 的 UlaCache 把所有 GPU 的 KV 池和可选的 CPU 内存编进同一个"逻辑地址空间"：推理引擎只拿逻辑地址分配和选取 KV，数据实际放在哪张卡或 CPU 上由 UlaCache 负责搬运和更新映射。这样 GPU 和 CPU 各存不同的历史，而不是 CPU 存全量、GPU 存副本。在 SGLang 中用 GLM-5.3、输入 64K–128K token 的 Multi-LexSum 请求测试，开启投机解码、GPU 和 CPU 内存预算相同时，峰值解码吞吐相对 HiSparse 在 8×H200 上提高 1.16 倍（DP）和 1.70 倍（TP），在 8×B300 上提高 1.73 倍（DP）和 2.51 倍（TP）。

1. 问题：存储空间大多被副本占掉

作者用 GLM-5.3 在 8×B300 上统计了两种现有做法的 KV 分配：

两个来源的重复：

  • 跨卡重复。 模型使用 MLA（多头潜在注意力）时，按注意力头切分的 TP 让每张卡都存同一份 KV。8 卡 TP 下只有 12.5% 是不重复的历史。
  • GPU 与 CPU 重复。 HiSparse 把完整历史放 CPU，把选中的部分复制到 GPU。它的 5330 万个物理槽只存了 3000 万个不重复的历史位置，GPU 那部分不增加容量。

此外，HiSparse 给每个请求固定大小的 GPU 缓存配额。请求变少时，剩下的请求也用不上空出来的显存。作者给出的例子：8×B300、DP、开投机解码、批大小 1 时，GPU 本来装得下所有历史，HiSparse 的每 token 时延（TPOT）仍比纯 GPU 的 SGLang 高 23.5%。

2. 方法

统一逻辑地址。 每个 KV 条目有一个固定的逻辑地址，映射表记录它当前在哪个 GPU 槽或 CPU 槽。KV 在 GPU 和 CPU 之间移动时，只改映射，不改逻辑地址。

  • DP 模式：每张卡管理自己的 GPU 池和 CPU 池，容量是两者之和。
  • TP 模式：所有卡的 GPU 池合成一个分布式地址空间，每张卡存每个请求历史的不同部分（逻辑地址 t 放在第 t mod P 张卡上）。负责计算的卡另有一个本地 GPU 缓冲区，缓存最近选中的 KV，下一步再被选中时直接复用，只从本卡或其他卡取缺失的部分。共享同一稀疏选择的层可以在当前层计算时预取后面层需要的 KV。

PB-LRU（并行分桶 LRU）。 开启 CPU 存储后，GPU 池由所有请求共享，需要决定把哪些 KV 换出到 CPU。标准 LRU 每次都要扫描整个池，PB-LRU 把 GPU 槽按最近使用时间分成若干桶，命中检测和更新并行处理，用分层位图快速找到可替换的槽，优先替换最冷的桶，并保护当前注意力计算正要用的条目。数据先搬运，搬完再更新映射，保证后续访问读到的是已就绪的数据。

3. 实验

设置：GLM-5.3，FP8 权重和 KV cache，8×H200 和 8×B300。基线是 GPU 存全部 KV 的 SGLang 和用 CPU 存历史的 HiSparse。投机解码用 MTP，草稿 2 步。三个系统的 GPU 显存分配相同，CPU 预算为每张 H200 128 GB、每张 B300 192 GB。负载是 Multi-LexSum，输入 64K–128K token，每个请求贪心生成 2,048 个 token。

3.1 容量与可同时解码的请求数

这组实验检验统一地址能否在相同内存下装下更多历史、接纳更多请求。

3.2 吞吐与延迟

这组实验检验容量增加能否变成吞吐提升，以及低负载时多出来的查找和调度是否拖慢单请求。

  • 吞吐。 开投机解码时峰值吞吐相对 HiSparse 为 1.16×（H200 DP）、1.70×（H200 TP）、1.73×（B300 DP）、2.51×（B300 TP）。B300 TP 不开投机时，UlaCache 峰值吞吐是 SGLang 的 3.51 倍。峰值对比取各系统在所有批大小中的最高值，提升主要来自能同时解码更多请求。
  • 低负载延迟。 批大小 1–8 的八种配置下，UlaCache 的 TPOT 都低于 HiSparse，但高于 SGLang。作者认为差距来自额外的查找、调度和 TP 通信。

3.3 PB-LRU 消融

这组实验检验分桶近似会不会降低缓存命中率，以及能省多少调度时间。设置：8×H200 DP，PB-LRU 和基于时间戳的普通 LRU 回放同一组访问记录，缓存容量相同。

结果：两者 GPU 命中率相差不到 0.10 个百分点；在较大批大小下，PB-LRU 调度快约 1.5–2.3 倍。批大小小、几乎不需要替换时，普通 LRU 反而更快，因为 PB-LRU 仍要维护桶的元数据。

4. 局限

只测了一个模型（GLM-5.3）和一种负载（Multi-LexSum 长文摘要）。吞吐对比取峰值，各系统峰值出现在不同的批大小上，所以数字主要反映"能装下多少请求"，不是同一批大小下的单步速度。低并发时比纯 GPU 的 SGLang 慢。论文没有报告精度，因为 UlaCache 不改变注意力本身的选取。

5. 实践意义

如果你在 SGLang 上服务使用 MLA 和稀疏注意力的模型（GLM-5、DeepSeek-V4.1 一类）、请求上下文很长、瓶颈是显存装不下更多并发请求，尤其是用 TP 部署时，UlaCache 的思路值得关注：先消除跨卡和 GPU/CPU 之间的重复存储，再谈换入换出。若主要场景是低并发、对单请求延迟敏感，纯 GPU 的 SGLang 仍更快。
