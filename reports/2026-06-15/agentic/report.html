1. HyperTool: Beyond Step-Wise Tool Calls for Tool-Augmented Agents
4.10
Relevance 4 | Novelty 4 | Practical 4 | Evidence 4 | Timely 5

Summary: 工具增强型 LLM agent 普遍用 step-wise 原子工具调用，每次调用、观测、取值都暴露在主推理轨迹里，造成执行粒度错配：本可确定性执行的工具子流程被展开成大量模型可见的低层决策，挤占上下文。HyperTool 提出统一的可执行 MCP 风格工具接口——模型用一段代码块按工具原始 schema 调用、处理返回值、在本地传递中间结果，把确定性子流程折叠进一次外层调用。在 MCP-Universe 上 Qwen3-32B 平均准确率从 15.69% 提升到 35.29%，Qwen3-8B 从 9.93% 提升到 33.33%，超过 GPT-OSS 与 Kimi-k2.5。

Key insight: 关键不是调更多工具，而是改变模型可见的工具执行单元：把确定性的工具编排沉到代码执行层、只把高层意图留在推理轨迹，既省 token 又减少模型管理低层 dataflow 的出错机会。对搜索/RAG agent 有直接借鉴——多跳检索、过滤、重排这类固定子流程可封装成一次 HyperTool 调用，主 agent 只决策检索什么。训练数据由跨工具组合任务合成并在真实 MCP 环境验证，落地路径清晰。

独立页面阅读 ↗

1. 问题与动机

HyperTool 针对工具增强型 LLM agent 普遍采用的 step-wise 原子工具调用范式（ReAct 式）的两个结构性缺陷。第一是"上下文膨胀"（context inflation）：每次工具调用的完整观测都累积进主推理轨迹，即便后续只需要其中某几个字段。第二是"推理碎片化"（reasoning fragmentation）：模型为完成本可确定性执行的低层操作（取字段、过滤、计算、聚合），必须反复回到决策循环，把高层任务推理与过程性的状态传递交织在一起。论文用 MCP-Universe 上的实测佐证这一失败模式：Qwen3-8B 基座平均准确率仅 9.93%，即便做了 ReAct-SFT 也只有 20.92%，说明 step-wise 范式严重限制了多步工具组合能力。动机由此清晰——问题不在模型不会调工具，而在"模型可见的工具执行单元"粒度太细，把确定性子流程暴露成一连串需要 LLM 介入的决策。

2. 方法详解

核心是把原子工具调用 Call(τ, x) 替换为可执行代码块 Block(S_t)，其中 S_t 是一段在原语工具之上编写的有界可执行程序。模型写一段 Python 代码块，块内通过 call_tool(server_name, tool_name, {"param": "value"}) 按工具原始 MCP schema 调用已有工具；中间结果以局部 Python 变量保存在块内部，只有块级最终观测（赋给 result 变量）返回主轨迹。这样取字段、过滤、跨工具传值、聚合等确定性逻辑被折叠进一次外层调用，主轨迹只看到高层意图和最终结果。

训练数据合成是关键工程，分三步：(1) 组合任务构造——用 teacher 模型 GLM-5.1 与真实 MCP 环境交互，收集多源事实、归纳出彼此独立且基于真实工具输出的约束，使任务必须跨工具组合才能解；(2) HyperTool 轨迹采集——遵循三条执行规则（Reasoning Precedence 先推理后执行、Blockwise Execution 块级执行、Internal Logic 内部逻辑），并用 Context Compression（对较旧工具响应做 LLM 摘要）保持 rollout 聚焦、用 Local Repair（失败块自动修复并校验意图保持）提升成功率；(3) 轨迹验证——先做执行正确性过滤（剔除语法错误、schema 不匹配、运行时错误），再用 LLM judge 做证据一致性检查（最终答案是否被返回证据支持、中间结果解释是否正确、跨块结论是否一致、任务约束是否满足），多数投票通过才保留。

训练设置：基座 Qwen3-8B 与 Qwen3-32B；SFT 数据 10,422 条验证过的 HyperTool 轨迹（token 多在 5k–15k，长尾到 60k）；用 Ray + Megatron-LM 做长上下文训练，最大序列长 65,536；global batch 64、3 epoch、Adam(β1=0.9, β2=0.95)、峰值学习率 5e-5、cosine 衰减 + 10% warmup；8B 约 4 小时、32B 约 31 小时。注意全程是 SFT，未用 RL。

3. 核心技术贡献

(1) 把"工具执行粒度过细"明确识别为 step-wise 范式的核心瓶颈——指出原子调用暴露中间观测与工具依赖，既膨胀上下文又割裂推理，这是对 ReAct/CodeAct 一类方法的本质诊断。(2) 提出统一可执行工具接口 HyperTool：在保留原始 MCP 工具 schema 前提下，让原子调用与局部确定性多工具工作流都能用同一种代码块格式表达——相比 CodeAct 纯代码执行，它复用了 MCP 生态的工具定义，无需为工具重写接口。(3) 证明仅靠 SFT 验证轨迹即可获得稳定增益（Qwen3-8B 9.93%→33.33%），且 32B 版本无需面向代码生成的预训练即可追平商用 agent。机制上，增益来自"任务容量与上下文开销解耦"：块内编排让模型实际调用的原语工具数几乎翻倍（26.92→47.55），但模型可见调用数（26.92→20.76）和交互轮数（28.81→21.76）反而下降。

4. 实验结果分析

主结果在 MCP-Universe（4 个领域：Financial、Repository、Location、Web）。Qwen3-8B 经 HyperTool-SFT 平均准确率从 9.93% 升到 33.33%（avg score 28.75→48.42），Qwen3-32B 从 15.69% 升到 35.29%（avg score 31.99→53.18），后者超过 GPT-OSS（32.13% acc）并在 acc 上逼近 Kimi-k2.5（34.17%），但 avg score 53.18 仍低于 Kimi 的 56.96。与同基座 SFT 基线相比，HyperTool（33.33%）显著优于 ReAct-SFT(20.92%)、CodeAct(25.49%)、AgentFold(27.13%)、ReCode(19.60%)、BrowseMaster(20.91%)。

消融很有说服力。执行接口消融：纯 HyperTool 33.33% > 原子+HyperTool 混合 26.85% > ReAct 20.92%，说明"统一用块"比"混用"更好。组件消融：去掉执行正确性过滤，准确率从 33.33% 崩到 18.06%；去掉证据一致性过滤降到 21.05%——数据质量过滤是命脉。去掉 Context Compression，Web Search 通过率从 70.0% 掉到 41.0%；去掉 Local Repair，Financial Analysis 成功率从 40.0% 砍半到 20.5%。效率上，在 253 条轨迹上 HyperTool 用更少 token 拿到更高准确率（全局 816k vs ReAct 955k token，acc 33.33% vs 20.92%）；Financial Analysis 领域准确率近乎翻倍（32.5%→62.5%）同时省下 78% 以上 token（916k→199k）。但 Web Search 是反例：HyperTool token 反而更多（861k→1379k），准确率仅微升（16%→18%），说明强探索型任务里块内编排的省 token 优势会被更深的探索抵消。

5. 局限与未来方向

作者明确指出两点局限：(1) 当前设计最适合"局部确定性"的工具子流程——检索、过滤、计算、聚合这类中间结果可在块内处理、无需频繁 model 级介入的场景；对需要模型反复介入判断的高交互任务（如开放式 Web 探索）优势有限，Web Search 领域实验已印证。(2) 训练数据的多样性和规模仍可扩展，更大、覆盖更多领域/工具生态/任务结构的轨迹集合有望提升对未见工作流的泛化。可补充的是：方法依赖 teacher（GLM-5.1）与 LLM judge 做数据合成和验证，质量上限与成本受 teacher 能力约束；全程 SFT 未用 RL，是否能用 on-policy RL 进一步压缩 Web 类任务的探索冗余值得探索。

6. 工业实践意义

对搜索/推荐从业者，HyperTool 最直接的启示是：搭建检索/RAG agent 时，把"多跳检索→字段抽取→过滤→重排→聚合"这类确定性子流程封装成一次代码块调用，主 agent 只决策"检索什么/下一步查什么"，能同时降低 token 成本与出错率。对应的工程收益很具体——在 Financial 这类结构化检索任务上准确率翻倍且 token 省 78%，对延迟和成本敏感的在线搜索服务意义重大。可借鉴的设计点有三：(1) 复用现有工具 schema（MCP 风格）而非重写，迁移成本低；(2) 数据合成里"执行正确性过滤 + 证据一致性过滤"是质量命脉，消融显示去掉任一项准确率近乎腰斩，自建 agent 训练数据时务必保留这两道闸；(3) Context Compression 和 Local Repair 是低成本高收益的轨迹处理技巧，可直接移植。需要注意的边界：强探索型任务（开放 Web 搜索）里块内编排省 token 的优势会被探索深度抵消，别指望对所有搜索场景一刀切收益；另外该法目前是 SFT 蒸馏 teacher，线上部署前要评估 teacher 能力上限和 8B/32B 模型的实际延迟（最大序列 65k、长尾轨迹达 60k token，长上下文推理成本需实测）。

2. SENTINEL: Failure-Driven Reinforcement Learning for Training Tool-Using Language Model Agents
4.10
Relevance 4 | Novelty 4 | Practical 4 | Evidence 4 | Timely 5

Summary: 用 RL 训练多轮工具调用 agent 时，训练任务分布在训练前就固定，会与策略不断演化的能力错配，大量 rollout 浪费在无信息量的任务上。SENTINEL 是 failure-driven RL 框架，把 Solver 的 rollout 失败转化为针对性训练任务，采用 Controller-Proposer-Solver 流程：Controller 分析失败轨迹归纳反复出现的错误模式，Proposer 生成专门压这些弱点的可执行任务，Solver 在这些任务上训练。在 Tau2-Bench Retail 用 Qwen3-4B-Thinking-2507，Pass@1 从 66.4 提升到 74.9，并在 Pass@k 各档优于在通用合成任务上做 RL。

Key insight: 模型自身的失败是高质量、可扩展的训练信号来源——与其预先固定任务集，不如让课程随策略弱点动态生成。Controller-Proposer-Solver 的诊断-出题-训练循环可迁移到搜索 agent 的 RL：从线上失败 query 与检索轨迹中归纳错误模式，自动生成针对性训练样本，比静态数据集更贴合当前模型瓶颈，也更省 rollout。

3. Effective Reinforcement Learning for Agentic Search by Recycling Zero-Variance Queries During Training
4.00
Relevance 4 | Novelty 4 | Practical 4 | Evidence 4 | Timely 4

Summary: GRPO 类算法训练 LLM 搜索 agent 时，只有 rollout 组同时含成功和失败的 query 才贡献梯度；全对(太易)和全错(太难)的零方差组白白消耗 rollout。作者发现 query 会随策略演化在零方差与有信号之间反复翻转，提出 query recycling：把零方差组放回可变池等待后续重采样，让有效训练分布随策略共同演化。一个 1.7B 模型在合成数据上训练，7 个多跳 QA 基准平均 Pass@1 达到 66.0，追平甚至超过用基准衍生监督训练的 7B 系统；训练后期回收 query 约占有效 batch 的 3/4。

Key insight: 零方差不是 query 的静态属性而是随策略变化的动态状态，丢弃或预过滤太易太难样本其实扔掉了后期会重新变有用的训练信号。对训练搜索 agent 的启示：维护动态难度池、按当前策略能力重采样，比固定课程更省算力，且 1.7B 小模型即可逼近 7B，对资源受限团队友好。

4. SearchSwarm: Towards Delegation Intelligence in Agentic LLMs for Long-Horizon Deep Research
4.00
Relevance 4 | Novelty 4 | Practical 4 | Evidence 4 | Timely 4

Summary: 长程任务的上下文需求可无界增长，但模型上下文窗口有限。SearchSwarm 针对 deep research 提出委派智能：主 agent 分解任务、把子任务派给子 agent，子 agent 执行后只回传摘要结果，节省主 agent 的上下文预算。难点在何时委派、委派什么、如何整合返回结果——这类数据在自然文本里稀缺。作者设计 harness 引导模型做高质量任务分解与委派、并约束子 agent 规范回传；harness 引导的轨迹天然编码正确委派决策，用作 SFT 数据把委派能力内化进权重。SearchSwarm-30B-A3B 在 BrowseComp 达 68.1、BrowseComp-ZH 达 73.3，为同规模最佳，并开源 harness、权重与数据。

5. DuMate-DeepResearch: An Auditable Multi-Agent System with Recursive Search and Rubric-Grounded Reasoning
3.90

Summary: Deep Research 需要系统迭代地界定问题、获取证据、核验来源并合成长报告，但现有系统受限于欠定范围下的长程规划、单 agent 调度瓶颈、长文合成幻觉、过程不可审计四个问题。DuMate-DeepResearch 是基于百度千帆 Agent Foundry 的多 agent 框架，把负责理解/规划/调度的 Agent Core 与可扩展工具生态解耦，使每个决策和工具调用可追溯。它引入三机制：图式动态规划(由粗到细，通过反思/重规划/回溯/并行分支持续修正)、递归两层执行(把复杂子任务交给内层 Search Agent 自跑规划循环以隔离噪声检索)、基于 rubric 的测试时优化(动态生成任务专属质量标准作为证据合成与自适应停止依据)。在两个基准取得 SOTA：DeepResearch Bench 58.03%、DeepResearch Bench II 61.95%，信息召回与分析项排名第一。

6. SlimSearcher: Training Efficiency-Aware Web Agents via Adaptive Reward Gating
3.90
Relevance 4 | Novelty 4 | Practical 4 | Evidence 4 | Timely 3

Summary: Deep research agent 在准确率导向训练下普遍采用蛮力策略——盲目依赖工具、生成冗长轨迹，造成大量无谓工具调用和 token 消耗。SlimSearcher 在 SFT 与 RL 两阶段推动准确率-成本的帕累托前沿：SFT 阶段用 Pareto-efficient 过滤蒸馏既成功又经济的轨迹；RL 阶段引入 Adaptive Reward Gating，在采样 cohort 内评估相对的工具/token 效率，并与严格的正确性 gate 级联，从而避开绝对惩罚带来的过短偏置并抑制 reward hacking。在 GAIA、BrowseComp、XBenchDeepSearch 等长程基准上，平均工具调用轮数减少 17%-58%，同时维持或提升准确率。

Key insight: 搜索 agent 的成本不是只能靠砍长度硬压——用组内相对效率奖励而非绝对惩罚，能在不牺牲准确率前提下减少 17%-58% 的工具调用。对线上 deep search 服务，这意味着同等效果下推理成本和延迟显著下降；Pareto 过滤 + 相对奖励 gating 的设计可直接用于约束自家搜索 agent 的检索轮数。
