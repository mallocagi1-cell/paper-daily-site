1. Versioned Late Materialization for Ultra-Long Sequence Training in Recommendation Systems at Scale
4.35
Relevance 4 | Novelty 4 | Practical 5 | Evidence 4 | Timely 5

Summary: 针对 DLRM 超长用户行为序列训练时存储与 I/O 成为瓶颈、超过 GPU 训练算力的问题，本文提出 Versioned Late Materialization 范式：将 UIH 在归一化、不可变层中只存一份，训练时通过轻量化的版本指针即时重建序列。系统通过双协议保证流式与批量训练下的 O2O 一致性，并设计读优化的索引层支持多模型共享数据。论文报告该方案显著降低数据冗余，使数据基础设施使用率与 GPU 训练能力对齐，已在大规模工业训练中部署。

Key insight: 文章把推荐训练数据基础设施作为一等问题，跳出了把行为序列直接物化进每条样本的 Fat Row 默认范式。对推荐与社区搜索系统的启示：当用户行为长度跟着 scaling law 越拉越长时，Late Materialization + 版本化指针是控制存储爆炸、避免训练-推理一致性漂移的关键模式；多模型共用同一份用户事件流后，新模型迭代和不同序列长度试验的边际成本被显著压缩，是支撑长序列建模 scaling 的工程底座。

独立页面阅读 ↗

1. 问题与动机

工业级 DLRM 的核心 scaling 维度已经从「特征数量」迁移到「用户行为序列长度」。论文 Section 2.2 指出：在工业 ranking 场景下，user interaction history (UIH) 序列特征已经"占据训练数据总量与读带宽的大头"；当用户序列被推到 4K 以上时，他们将其形象地称为撞上 "Fat Row Wall"——基础设施的需求开始反超模型质量带来的边际收益。

「Fat Row」是指现行业界默认范式：把每个 ranking 请求对应的完整 UIH 序列，提前物化进每条训练样本。问题在于一个 lookback 窗口内同一用户的历史会被在 K 条样本中复制 K 次（论文 Figure 2 给出量化结果：当开启超长 UIH 时，"数据支撑服务的总资源消耗已经超过 GPU 训练消耗本身"）。在多租户共享 union dataset 场景下问题被放大：召回模型只需要约 100 个事件，精排模型需要 10000+ 事件，但 union dataset 必须按最大需求装载，导致小模型也被迫读取大量自己用不到的数据。

这是 HSTU、ULTRA-HSTU 等下一代 trillion-parameter sequential transducer 架构能否真正 scale 的卡点：模型能学，但数据基础设施已经先撑不住。

2. 方法详解

整体方案是把存储中心化范式翻成"compute-centric late materialization"：UIH 只在归一化、不可变的存储里存一份，训练时用版本指针即时重建序列。

Versioned Late Materialization 协议（Section 3.3）：UIH 被双协议拆成 Mutable（近期事件）+ Immutable（长期历史）两层。推理时只记录极轻量的版本元数据 (start_ts, end_ts, sequence_length, checksum)，不再写完整序列。训练时通过"Time-Travel"过程，按记录的时间边界对不可变层做有界 range scan，将近期与历史两段拼接重建出训练用的 UIH。这套双协议保证了 streaming + batch 两种训练形态下的 O2O 一致性：物理 snapshot 阻断 mutable 端的迟到写入污染，bounded range scan 在 immutable 端排除了推理时点之后的事件，checksum 校验确认重建保真度。

可扩展 UIH 存储（Section 4.1）：mutable store 用快速 merge 操作 + blind-write append，且在排序服务侧加 write-through cache；immutable store 是只读优化的归一化仓库，每天通过离线 ETL 做 offload compaction，把分区合并为按时间排序的完整序列，单层 layout（避免多层 LSM 合并放大）。Schema 走"多维度投影"：以 (user_id, feature_group, subsequence_timestamp) 复合键组织，支持两种 pushdown——序列长度投影（只读模型需要的那段 stripe）与特征组投影（只读模型需要的列）。在编码层使用 trait-aware columnar encoding，针对时间戳走 delta 编码、类别元数据走 dictionary 压缩。

训练侧物化（Section 4.2）：用 Disaggregated Data Preprocessing (DPP) 把序列重建放到独立 preprocessing 集群，监控 GPU starvation 比例自动扩容；trainer 端做 rebatching 把小 base batch 合成完整训练 batch（带来 +15% 吞吐）。Latency masking 上用 pipelined I/O prefetch（预取下一 batch，+10% 吞吐）和 partial projection pushdown 把模型对序列长度/特征组的需求显式暴露给存储层。Data-affinity 优化：在 ingestion 阶段就按用户聚簇训练样本，使得同一 session 多条样本的 UIH 检索可以摊销；同时让主训练数据与 immutable storage 做对称分片，消除跨网络 fanout——两项合计批训练读带宽 −60%、单 worker 吞吐 +28%。

3. 核心技术贡献

1）Fat Row 问题的形式化：第一次量化论证"预物化序列冗余 > GPU 训练算力"的临界点（Section 2），把推荐训练数据基础设施从"工程后端话题"提升为决定模型能力上限的一等问题。

2）版本化晚物化协议：通过物理 snapshot + 有界 range scan + checksum 三重机制，在 streaming/batch 两种训练形态下都严格保证 O2O 一致性，杜绝了"future leakage"。这是过去基于"快照视图"或"时间窗对齐"的方案做不到的。

3）多租户感知的存储工程：单层 immutable layout 配合 (user, feature_group, ts) 多维投影，把召回（短序列）、精排（长序列）这种异质租户的 I/O 需求统一在一份共享数据上，每个租户只读自己需要的部分。论文报告 immutable storage 在单位 host 资源下实现 3.4× 的读吞吐，是这一切能 scale 的物理底座。

4）端到端 deployment：不仅设计协议与存储，还落地了 disaggregated preprocessing、pipelined prefetch、data-affinity sharding 三套训练侧加速，使整个 pipeline 在工业流量下真的跑得比 Fat Row 快。

4. 实验结果分析

系统效率（Table 1，3 个模型租户共享 union dataset）：主写带宽 −46.2%；长序列模型 A 主读带宽 −70.3%；序列查找带宽相对增加 +62.7%（这一项被新增），但因 immutable storage 单位资源吞吐高 3.4×，整体仍是净收益；模型 A 单 batch loading 延迟 +9.7%，而短序列模型 B、C 反而 −26.4% ~ −36.2%。这说明长序列租户付出可控的小延迟代价，换来短序列租户的显著加速。

模型质量（Figure 4 + Table 2）：在公平基线下，把 UIH 长度从 4K 推到 64K，Platform A 的 Normalized Entropy 累计提升 ~5%，仅 4K→64K 这段就 +1.2% NE；Platform B 4K→10K 提升 +0.65% NE。同时严格验证"晚物化重建出的序列在 256–4K 范围与 Fat Row 的 NE 持平"，证明它没有引入质量损失，只是放开了上限。

线上 A/B（Table 2）：Platform A（4K→16K）topline +0.22%、消费指标 +4.1%、互动指标最高 +4.3%；Platform B（4K→10K）topline +0.14%、消费 +0.79%、互动最高 +1.7%。文章直接给出工业语境下的注解："此规模下 1% NE 提升即被认为成功，这些收益在 Fat Row 范式下根本拿不到。"

值得注意的是 ablation 隐含的关键结论：把 latency masking + data-affinity 关掉后，长序列租户 batch 延迟增加得多得多，说明 disaggregated preprocessing 不只是工程加速，而是支撑长序列训练能跑起来的必要条件。

5. 局限与未来方向

文章未单独写 Limitations 节，但隐含承认几点：

  • 整个方案严重依赖"读优化的 immutable 层吞吐显著高于主存储"，离开这种存储引擎的环境下复现需要重做底层；
  • Latency masking 复杂度上升——需要额外的 preprocessing 集群、pipelined prefetch、affinity sharding 多重机制配合，长序列租户仍有 ~10% 单 batch 延迟；
  • 每日 offload compaction pipeline 需要处理 right-to-delete（隐私合规）、schema 升级等运维问题，这些在论文里只是一笔带过；
  • 多维投影 schema 设计复杂度高，需要存储引擎层面的工作量。

未明确讨论的现实问题：当训练任务非常多样、每个租户的特征组合都不同时，多维投影的 metadata 维护本身可能成为新的瓶颈。

6. 工业实践意义

这篇文章本质上是「下一代生成式/序列化推荐系统的训练基础设施蓝图」，对任何想 scale UIH 长度的团队都是必须读的工程手册。

直接可借鉴：

  • 不要再 Fat Row。当用户序列预计要超过几千事件时，预物化范式必然撞墙，要从 day 1 就规划"用户行为只存一份"的 normalized 仓库 + 训练时 late materialization；
  • 版本指针 + bounded scan 是 O2O 一致性的关键。社区/电商场景里"未来事件泄漏"问题极隐蔽，明确 (start_ts, end_ts, checksum) 协议能避免线上踩坑；
  • 多租户共享数据集合。召回、粗排、精排原则上读一份用户事件流，通过 schema 投影 pushdown 各取所需，不要再为每个模型单独跑 ETL；
  • 训练数据 pipeline 也要 disaggregate。把 GPU starvation 当成主要监控指标，独立 preprocessing 集群按需扩容，比堆 GPU 性价比高得多。

部署考量：immutable storage 引擎是核心选择题——Meta 内部用的是与 HBase/RocksDB 类似但深度定制的列存，自建团队短期内更现实的路径是用 Iceberg + Parquet 或 Hudi + ORC 起步，先把"normalize once + range-scan reconstruction"协议跑通，再迭代到 trait-aware 编码。计算端走 Spark / Ray Data 做 disaggregated preprocessing 也都跑得通。社区平台自己的尺度通常达不到 Meta 量级，但只要 UIH 长度过千，就值得现在就把这套范式打底，否则未来任何"长序列实验"都会被基础设施先封死。

2. From Local Indices to Global Identifiers: Generative Reranking for Recommender Systems via Global Action Space
4.10
Relevance 4 | Novelty 4 | Practical 4 | Evidence 4 | Timely 5

Summary: 传统 list-wise 重排把任务建模为「从输入列表里选择本地下标」，导致同一个 logits 神经元在不同样本上代表不同物品，模型难以建立稳定的内在物品表征。论文提出 GloRank：用离散 token 序列把每个候选 item 编码成全局标识，再把重排重写成 token 生成任务。这样打分机制与可变长输入解耦，模型在所有样本上学习的是同一套物品语义。在公开数据集上 GloRank 在多项指标上明显优于传统 list-wise 重排基线。

Key insight: Reranking 的「行动空间」是一个常被忽略的设计变量，把 action space 从 local index 改成 global semantic ID 之后，模型获得跨样本可迁移的物品表征，从根上缓解了 list-wise 排序的语义不一致问题。对社区搜索 / 推荐重排的启示：当我们已经在召回侧构建了 semantic ID（OneRec / TIGER 风格），重排端也可以复用同一套 ID 体系做生成式重排，让召回-重排共享物品表征空间，减少多阶段误差累积。

独立页面阅读 ↗

1. 问题与动机

list-wise reranking 是现代推荐多阶段流水线的最后一环，决定最终曝光顺序，直接影响用户体验。Section 2 指出现有方法存在一个被长期忽视的根本缺陷：模型的 action space 是「local index」，即模型在第 i 个输出位置预测「选输入列表里的第几个 item」。问题在于同一个输出神经元（logits）在不同样本上对应的物品完全不同——一旦输入候选列表的顺序变化，第 3 号神经元代表的物品就换了。

文章用 Proposition 2.1 给出了形式化证据：在 local index 设定下，输出层梯度存在不可消除的"mapping-induced variance"，下界为 (1/N)(1−1/N)‖μⱼ‖²₂ > 0；而 Corollary 2.2 证明使用全局标签（与样本无关的 global identifier）时该方差为零。直观结果是模型很难学到稳定的物品本征效用，反而倾向于"过拟合到 index 本身的 spurious 模式"——例如学会"第 1 个位置往往被选中"，而非学会"哪个具体物品该被选中"。

这一问题在 OneRec/TIGER 等生成式召回兴起后尤为突出：召回侧已经把 item 表示为 semantic ID 序列，但重排侧仍在用 local index 范式，导致召回-重排两段建模目标空间割裂，多阶段误差累积。

2. 方法详解

GloRank 的核心是把重排重新形式化为「在全局 token vocabulary 上生成 SID 序列」。

架构：T5 风格 encoder-decoder Transformer。

Semantic ID 构造：

  • 每个 item 用 title + description 经 Qwen3-embedding-4B 编码为稠密向量；
  • 用 RQ-Kmeans（残差量化 K-means）层次量化，M=4 个 codebook，每层 vocabulary 256；
  • 每个 item 因此被表示为长度 4 的离散 token 序列。

输入构造：序列化为 S(𝒞) <sep> S(ℋ) <sep> <rank>，其中 𝒞 是当前候选集（50 项）、ℋ 是用户历史。

自回归生成：decoder 在固定全局 token vocabulary 𝒱_token 上做 softmax P(yₜ | y<t, X_input) = softmax(Wₒ · hₜ)。同一个 logits 维度在所有样本里始终代表同一个 token——这是 global action space 的关键。

两阶段训练：

  • 阶段一 Pre-training：监督式 next-token prediction，目标 list 由离线评估器从训练日志中筛出"高质量目标 list"。损失 ℒ_pre = −Σ log P(yₜ | y<t, X_input; θ)。本阶段决定模型能否真正学到稳定的物品语义。
  • 阶段二 Post-training：GRPO（Group Relative Policy Optimization），group size = 20、温度 τ=1.0、β=0（无 KL 惩罚），优化 list-wise utility 奖励。这一步把"哪个排列最好"的 list 级偏好直接灌进策略。

Inference：用 trie-based constrained decoding，把候选集 𝒞 的 SID 序列预编织成 trie，beam size = 20、输出长度 6（即重排后 top-6 from 50）。trie 同时保证生成结果都在候选集合内、不重复物品。文章指出，当候选数 N ≪ 全局 vocabulary 大小时，trie 开销可以忽略。

3. 核心技术贡献

1）理论分析（Section 2）：第一次把"list-wise reranking 输出层梯度方差不可降"这一结构性缺陷形式化，把"为什么 list-wise 模型在小变动下结果抖动"归结为 action space 的 mapping-induced variance，而非训练数据或正则化问题。

2）Global action space 形式化：把 reranking 从 "select index" 改成 "generate identifier"——一个看似只是输出维度变化的设计，实际把整个梯度更新的语义对齐了。同样的 logits 维度在所有样本里代表同一个 token，跨样本梯度是同向叠加的，模型才能学到"物品本征效用"。

3）两阶段训练 pipeline：监督式 pre-training 提供稳定的策略起点，GRPO post-training 把 list 级别奖励灌进来。Ablation 给出关键证据——去掉 pre-training 后 NDCG 从 90.08% 直接崩到 24.13%，证明纯 RL 在生成式重排上 cold start 极其困难。

4）Trie-based constrained decoding：在生成式范式下保证"输出严格在候选集合内 + 不重复"是非平凡的工程挑战，文章提出的 trie mask 在候选规模 N≪V 时开销可忽略，使得生成式重排具备落地速度。

4. 实验结果分析

数据集：MovieLens-1M（161.6K lists、3K items）、Amazon Books（311.4K lists、38.1K items）、工业数据集（589.8K lists、17K items）。

整体效果（Table 2，主表）：

  • Amazon Books：相对最强基线 GoalRank Precision +4.23%、NDCG +6.13%、MAP +9.23%；
  • MovieLens-1M：Precision +3.03%、NDCG +4.95%、MAP +6.60%；
  • 工业数据集：Precision +3.99%、NDCG +2.35%、MAP +3.39%。

Ablations（Table 3）：

  • w/o pre-training：在 Amazon NDCG 由 90.08% 跌到 24.13%，验证监督式起步必不可少；
  • w/o post-training：核心排序敏感指标普遍下降 1–2 个百分点，GRPO 提供的是 list 级精修。

冷启动鲁棒性（Figure 6）：在候选集中加入 5% 训练时未见过的 item，GoalRank 在 MAP 上崩溃 >88%，而 GloRank 仍能保持稳定——这是 global action space 的天然好处：未见过的 item 只要其 SID token 在 vocabulary 内，模型仍可生成。

超参（Figure 4）：group size G 越大效果越稳越好（GRPO 经验一致）；beam size 越大 Precision 上升但 MAP 反而下降——说明粗精度和排序排列质量之间存在权衡。

线上 A/B（Table 4，重要）：在一个 4 亿日活的内容平台上 7.8% 流量、连续 14 天测试：

  • Watch Time +0.095%、Effective Views +0.111%、Like +0.286%、Comment +0.462%、Forward +0.447%；
  • 全部 p < 0.05。

互动型指标（Comment、Forward）的提升明显大于消费型指标（Watch Time、Views），暗示 GloRank 在"识别真正与用户匹配的高质量内容"上更准——这正是 global action space 应当带来的效果。

5. 局限与未来方向

文章没有单列 Limitations 节，但有几个明显限制：

  • Trie 开销在候选 N ≪ |𝒱| 时被声称可忽略，但当候选规模放大到上千甚至更大（更早期粗排阶段），constrained decoding 的实际成本未做压力测试；
  • 依赖外部预训练 embedding（Qwen3-embedding-4B）做 SID 构造——这一步本身的质量决定整套系统的语义粒度，但 codebook 构建开销没有定量给出；
  • 选定 M=4 codebook 深度没有给出充分理由，更深的 codebook 可能进一步降低 SID 冲突但训练复杂度也涨；
  • GRPO post-training 用 β=0（无 KL 惩罚），存在策略崩溃风险，论文中没有详尽讨论训练稳定性条件。

工业落地中还会面临：物品库每天新增大量内容，SID codebook 是否要在线更新？冷启 item 进入 vocabulary 的延迟如何控制？这些都是部署时的真实挑战。

6. 工业实践意义

GloRank 给生成式推荐系统补齐了重要一块拼图——之前 OneRec/TIGER 解决了"召回阶段如何用 SID 自回归生成候选"，重排阶段依旧用判别式 list-wise 模型；GloRank 让重排端也跑在同一个 SID 表征系统上，召回-重排表征对齐，多阶段误差累积下降。

直接可借鉴的设计：

  • 重排引入 SID 比 reorder pointer-network 更稳。短期就算不上线生成式范式，把 item 的 SID 作为额外特征喂给现有 list-wise 模型也能稳定收敛；
  • 两阶段训练（pre-train 监督 + GRPO post-train）几乎是任何生成式排序任务的标配，不要直接上 RL；
  • Trie-based constrained decoding 是控制生成空间合法性的关键，对任何"生成结果必须落在限定集合"的任务（搜索 query 改写、推荐重排、广告挑库）都通用；
  • Global action space 的好处不仅是排序——它对冷启 item 提供天然鲁棒性，因为新 item 进入只需被 RQ-Kmeans 量化分配 SID 即可，模型架构无需改动。

部署考量：

  • 推理端 beam size = 20、输出 6 from 50 候选规模可控，单次预测延迟可压到几十毫秒级，关键在 trie 构建和 KV cache；
  • 在线 A/B 0.286% Like、0.462% Comment 的互动提升对社区/UGC 场景非常有吸引力（互动率往往就是社区核心指标），把现有 list-wise 重排替换为 GloRank 风格生成式重排，是在不引入额外召回阶段改造的前提下，把生成式范式收益独立拿到的最低风险路径。
  • 需要解决的工程问题：物品 SID 的离线构建 + 增量更新流水线、constrained decoding 的高 QPS 优化、热启动时与现有判别式模型的灰度切换。
