UniPinRec: Unifying Generative Retrieval and Ranking at Pinterest Scale

已录用 RecSys 2026

Pinterest 的召回模型和排序模型分开训练、分开部署，同一段用户历史在线上要编码两遍。UniPinRec 把两者合进一个 Transformer：先编码用户历史，得到的用户向量拿去做 ANN 召回；召回的候选 Pin 再接在历史后面，由同一个模型输出保存、点击、隐藏等动作的概率，候选之间不互相做注意力。历史只编码一次，算好的 KV cache 直接留给排序阶段复用。离线 Hit@3 比线上排序模型高 14.7%；在通知场景替换原召回后，沉睡用户的 push 打开提升 1.72%。

Pinterest 的推荐链路和多数公司一样分成召回和排序：召回模型 PinRec 用 ANN 从全量 Pin 里取出不到 3000 个候选，排序模型再给这些候选打分。两边现在都是 Transformer，输入也都是同一段用户行为历史，但它们分开训练、分开部署，线上每个请求要把这段历史编码两遍。UniPinRec 把两者合成一个模型：用户历史只编码一次，召回拿输出向量去查 ANN，排序直接复用编码时留下的 KV cache 给候选打分。离线上，它的召回 Recall@10 和线上召回模型持平，按“保存”预测排序的 Hit@3 比线上排序模型高 14.7%。在 Board More Ideas（按用户的某个看板推荐 Pin）和通知两个场景替换原召回后，前者场景内保存数提升 0.95%，后者 push 打开提升 0.91%。

1. 召回和排序为什么要合，又为什么一直没合

召回和排序各自训练时，两边都要从同一段行为历史里学用户表示，参数不共享，训练算力花两份，线上 GPU 也花两份。主干都换成 Transformer 以后，编码历史成了两边最贵的那部分计算，重复就更明显。

合起来有三处麻烦。第一是用法不同：召回要在毫秒级从百万量级候选里挑，只能用 ANN 点积；排序只看几百个候选，可以给每个候选做更重的交叉计算。第二是目标不同：召回用全库上的 sampled softmax，排序用曝光集合上的二分类交叉熵。第三是线上约束：合并后的模型必须比分开部署更便宜，还要能和关键词、热门等其他召回源一起用，每个阶段还要能单独做 A/B 和回滚。

已有工作只合了一部分。HSTU 用同一种 Transformer，但召回的输入是纯物品序列，排序的输入要在每个物品后面插一个动作 token，两种格式不同，只能分开训练，计算也无法共享。OneRec 这类端到端方法直接自回归生成语义 ID，整条漏斗被替换掉，很难再接入现有的其他召回源，也失去了按阶段回滚的能力。

2. 方法

2.1 起点：PinRec

PinRec 是 Pinterest 线上的生成式召回模型。每个 Pin 用预训练的 OmniSage 向量和 CLIP 多模态向量表示，经 MLP 投影成 L2 归一化的向量；用户正向行为过的 Pin 按时间排成序列，送进因果 decoder-only Transformer，每个位置预测下一个 Pin，损失是带 logQ 频率修正的 sampled softmax，负样本来自 batch 内和随机采样。UniPinRec 在这个模型上加排序能力，要解决动作信息怎么进序列、候选怎么接进序列两件事。

2.2 动作拼在特征维上，再随机遮掉

HSTU 的做法是在每个物品后插一个动作 token，序列长度翻倍，格式也和召回对不上。UniPinRec 改成 Masked Action Modeling（MAM）：把每个位置的动作 multi-hot 向量（点击、保存、隐藏等）过一个线性层，和该位置的物品向量在特征维上拼接，再一起投影到隐藏维度。动作信息放在特征维而不是序列维，序列长度和召回模型完全一样，召回的 checkpoint 可以直接拿来初始化。

训练时，历史里每个位置的动作以概率 pmask​ 独立遮掉，换成一个专门的 [MASK] 类别；候选位置的动作永远遮掉，因为线上推理时候选还没有被用户看到。[MASK] 单独占一维，模型能区分“动作未知”和“用户没有动作”。被遮掉的位置要预测自己的动作，排序监督就来自这里。

举个示意例子：用户历史是 A（保存）、B（点击）、C（无动作）。训练时 B 的动作被遮掉，模型在 B 的位置只看到 B 的内容向量、A 的内容和“保存”，要输出 B 被点击、被保存、被隐藏的概率。

2.3 候选接在历史后面，彼此不可见

ANN 召回的 k 个候选接在 n 条历史后面，组成一条序列。历史部分照常做因果注意力；每个候选能看到全部历史，但看不到其他候选，这是 M-FALCON 的掩码方式。所有候选共用同一个位置编号、场景类型和时间戳，所以一个候选的分数和同批放了哪些候选无关。注意力开销从 O((n+k)2) 降到 O(n2+nk)，实现上用 flex attention 把这种块稀疏的掩码编译成融合 kernel。

总损失是召回损失加排序损失：
L=Litem​+c=1∑C​wc​[∣Mpast​∣1​i∈Mpast​∑​ℓBCE​(hc​(zi​),ai(c)​)+k1​j=1∑k​ℓBCE​(hc​(zj′​),aj′(c)​)]
Litem​ 是历史各位置上的下一 Pin 预测损失，和 PinRec 相同；c 是动作类型，C 是动作类型总数；hc​ 是该动作的 MLP 预测头；zi​、zj′​ 是历史第 i 位、候选第 j 位的隐状态；a(c) 是该动作是否发生的 0/1 标签；Mpast​ 是历史中被遮掉的位置；wc​ 是每种动作的权重。前一项让历史位置预测被遮掉的动作，后一项让候选位置预测真实曝光后的动作。

2.4 训练样本：过去的行为加下一次请求的整屏曝光

召回模型通常只用正向行为序列训练，排序模型用曝光日志，里面有点了的也有没点的。联合训练两样都要，于是每条样本由一段过去的行为序列，加上之后某次请求的整屏曝光（论文叫 feedview）及其行为标签组成。序列每个位置是（Pin，场景，动作，时间戳）。没有任何互动的整屏曝光只保留 10%，以放大稀有的互动类别；评估集不降采样。

行为序列和曝光记录存成两张按用户 ID 分桶的 Iceberg 表，训练时由 Ray 的数据加载层在内存里按桶拼接。这样不用离线拼出一份重复的大表，序列长度、采样比例这些参数可以在训练时改。

2.5 线上：召回和排序两个进程共用一块显存

召回和排序跑在两个 Triton 节点、两个独立进程里，中间夹着 CPU 上的 Faiss 索引。Faiss 的 search_and_reconstruct 在返回候选 ID 时把索引里存的 Pin 向量一起返回，排序节点直接把这些向量当候选 token，省掉一次 embedding 计算，也保证召回和排序用的是同一份物品表示。

KV cache 的跨进程传递是关键。如果把 KV 张量序列化后从一个进程传给另一个，要走一趟 GPU→CPU→GPU，延迟会被这一趟吃掉。UniPinRec 让每个召回副本启动时预分配一块形状为 [层数, 槽位, KV 头, 历史长度, 头维度] 的显存池，用 CUDA IPC 句柄导出，排序进程把同一块物理显存映射进自己的地址空间，直接读召回写下的历史 KV。槽位按轮转复用。

3. 实验

3.1 一个模型能不能同时当召回和排序

这组实验要证明联合训练既不损失召回，又能做出不差于专用排序模型的排序。数据用 Board More Ideas 场景，召回看 Recall@10（未来那屏曝光里用户互动过的 Pin 有多少进了召回前 10），排序看 Hit@3（按保存头打分排序后，前 3 是否命中保存）。对比对象有：线上排序模型 TransAct V2 + DCNv2（长序列 Transformer 加特征交叉模块）；HSTU，按交错输入格式同时训练召回和排序，有效序列长度对齐；PinRec；PinRec 微调版，先训好召回，再冻结物品编码器加排序损失微调，冻结是为了和已建好的 Faiss 索引兼容；去掉召回损失、只训排序的 UniPinRec。两列指标在不同评估集上算。

3.3 掩码比例

pmask​ 取 0、0.1、0.2、0.3 时，Hit@3 分别是 0.09923、0.10078、0.10096、0.10075。不遮的版本最差，0.2 最好。作者另做了规模实验，层数从 2 到 24、序列长度从 256 到 2048，效果都持续变好；序列长度带来的注意力开销是平方增长，所以在延迟敏感的场景更先成为瓶颈。

3.4 线上 A/B

线上把原召回换成 UniPinRec 的“召回 + 轻排”服务：先用 ANN 多取候选（Board More Ideas 约 2 倍，通知约 3 倍），再用动作预测头排序，取前 K 个（K 小于 3000）交给下游。下游的 TransAct V2 精排模型保持不动，所以离线的排序提升会被下游稀释。对照组是 PinRec。

4. 局限

作者自己说明，UniPinRec 目前只合并了召回和上游的轻排，还没有替换 L2 精排，因为精排还依赖分数校准、训练日志、运维工具等一整套基础设施。fp8 方案吞吐更高，但因为批次形状限制增加了延迟，还没有上线。

另外，表 1 的两列在不同评估集上算，Hit@3 也只报告了“保存”这一个动作头，点击、隐藏等其他动作的排序质量论文没有给出。

5. 实践意义

  • 如果你的召回和排序都已经是吃同一段行为序列的 Transformer，最直接的收益来自共享历史编码。排序时历史部分只读 KV cache、只算候选，单次排序前向的计算从 O(n2) 量级降到 $O(nk)$，这一步不要求先改训练方式。
  • MAM 的做法可以单独拿来用：把动作拼在特征维而不是插成新 token，序列长度不变，就能给召回主干加上动作预测的监督。
  • 上线顺序可以参考 Pinterest：先替换召回加轻排，下游精排不动，A/B 归因清楚，出了问题也能单独回滚这一段。

UniRec: A Unified Expressive-Aligned Generative Recommendation Framework for E-commerce

已录用 RecSys 2026📖 有深读 · 13 分钟

Shopee 的作者统计了标准 RQ-KMeans 生成的三层语义 ID（SID）：最常曝光的前 10% 完整编码拿走了 89.62% 的曝光，生成式推荐模型的概率因此集中在少数热门编码上。UniRec 让模型先生成商品的二级、三级类目 token，再生成三层 SID，并在构建 SID 时给每个编码加一个按曝光加权的容量上限。先生成类目，后面每一层 SID 只需要在这个类目里挑。离线 HR@50 比 OneRec-V2 相对高 22.6%；线上对比原多阶段链路，订单 +4.76%，GMV +5.60%。

生成式推荐把每个商品编码成几层离散的语义 ID（SID），模型逐层生成这些 ID 来完成召回和排序。Shopee 的这篇论文指出它和判别式排序模型之间的一个差距：判别模型给候选打分时能直接看到商品的类目、店铺、品牌这些特征，和用户特征做交叉；生成模型在生成第一层 SID 之前，没有看到任何商品侧信息。UniRec 的核心做法叫 Chain-of-Attribute（CoA）：先让模型生成商品的类目，再在已知类目的条件下生成 SID，相当于在解码路径里补回判别模型能用的商品特征。配套的还有按曝光量限制码本负载的 SID 构造、给解码过程注入场景和组合特征的 CDC，以及 RFT 加 DPO 的业务对齐。离线 HR@50 比最强基线 OneRec-V2 相对高 22.6%；在 Shopee 主 feed 和落地页上线，订单 +4.76%，GMV +5.60%，端到端延迟 110ms，原多阶段链路是 266ms。

论文在 arXiv 上的标题是 “UniRec: Bridging the Expressive Gap between Generative and Discriminative Recommendation via Chain-of-Attribute”，本文按 arXiv 全文解读。

1. 生成式推荐差在哪里

判别式排序模型估计 p(y∣f,u)，也就是给定用户 u 和商品特征 f，用户产生互动 y 的概率，商品特征在打分时全部可见。生成式模型按 ∏l​p(sl​∣s<l​,u) 逐层生成 SID，生成第一层时只看用户，不看任何商品特征。

作者用贝叶斯公式说明这个差距从哪里来：
p(y∣f,u)∝p(f∣y,u)p(y∣u),p(f∣y,u)=k=1∏n​p(fk​∣f<k​,y,u)
p(y∣u) 不随商品变化，所以按判别分排序等价于按 p(f∣y,u) 排序，而后者按链式法则展开正好是逐个生成商品特征。结论是：如果生成模型逐个生成商品的全部特征，它和判别模型的排序能力一样。实际系统做不到逐个生成全部特征，延迟太高，所以用几层 SID 压缩商品语义。类目、店铺、品牌这些判别模型直接拿来交叉的结构化属性，在压缩时被揉进了 SID，解码时不再显式出现，差距就出在这里。

2. 方法

2.1 Chain-of-Attribute：先生成类目，再生成 SID

CoA 在 SID 序列前面加 m 个属性 token a，生成顺序变成先属性、后 SID：
p(s∣u)=p(a∣u)⋅l=0∏L−1​p(sl​∣a,s<l​,u)
线上配置里，属性是商品的二级类目和三级类目（类目分 L1、L2、L3 三级，越往下越细），所以一个商品的解码路径是“二级类目 → 三级类目 → s0​ → s1​ → s2​”，比原来多两步。

先生成类目为什么有用：同类目的商品在 SID 空间里挨得近，知道类目以后，下一层 SID 的候选范围变小。作者把这一点写成条件熵的减少量 ΔHl​=H(sl​∣s<l​,u)−H(sl​∣a,s<l​,u)，它等于属性和该层 SID 之间的条件互信息，只要两者相关就大于 0。每层出错的概率降下来，整条路径全对的概率就提高，beam search 也更稳。

2.2 带容量约束的 SID：按曝光量而不是商品数平衡码本

已有的平衡量化（如 OneRec 用的 RQ-KMeans）让每个码字分到的商品数接近，但商品热度是长尾的，商品数平均不代表曝光量平均。作者在 Shopee 线上数据上统计：按曝光量排序，前 10% 的第一层码字拿走 33.24% 的曝光；前 10% 的（s0​,s1​）组合拿走 87.90%；前 10% 的三层组合拿走 89.62%。

训练数据里高曝光的 token 路径出现得多，模型在 beam search 时就反复生成这几条路径，作者称之为逐层继承的马太效应。容量约束 SID 的做法是在每一层残差聚类里加一条约束：每个簇里商品的曝光权重之和 Vk​ 不能超过平均负载的 τ 倍。
{zi​},{μk​}min​i=1∑N​∥xi​−μzi​​∥22​s.t.Vk​=i:zi​=k∑​wi​≤τCcap​
xi​ 是第 i 个商品在当前层的残差向量，zi​ 是它被分到的簇，μk​ 是簇中心，wi​ 是它的历史曝光次数，Ccap​ 是总曝光除以簇数，线上 τ=1.05。精确求解是 NP 难，实际用两步贪心：先把每个商品分到最近的簇，再把超载簇里的商品挪到最近的未满簇，重复到重构误差不再变化。

2.3 CDC：告诉模型当前是什么任务，再补上组合特征

一个生成模型要同时服务点击、购买、加购、跨境等目标，以及主 feed、搜索、相似推荐、秒杀等场景。Task-Conditioned BOS 把固定的起始 token 换成按“目标 × 场景”查表得到的可学习向量，从第一步开始就把解码引向该场景的分布。

Content Summary 处理 token 之间的组合含义：同一个 s1​ 跟在不同类目后面，代表的商品可能完全不同。直接给每对 token 组合建一个 embedding，两个 4000 词表的层就有约 1600 万个组合。CDC 改用 3 个哈希函数（$x+y$、x⋅y、p1​x+p2​y，p1​、p2​ 为质数）把（二级类目, s0​）、（三级类目, s1​）、（s0​, s1​）等组合映射到一张共享的哈希 embedding 表，拼成每一步的组合特征 ct​。

2.4 解码器和业务对齐

解码侧序列是 [BOS, 属性 token, SID token]，作为 Q；用户最近 200 条点击行为的商品向量，再接上 100 个由多层 SID embedding 融合成的多模态向量，一起作为 K、V，经过 3 层带可学习门控系数的交叉注意力和 MMoE-FFN。每一步有一个独立的 Rank Head，把注意力输出、已生成前缀的 embedding、ct​ 和用户聚合表示拼起来，经 SENet 和 MaskNet 输出该步的 token 分布。

下一 token 预测只拟合曝光分布，不直接优化 GMV。RFT 给每条样本算一个业务奖励，在 batch 内减均值、除以均方根、截断后得到 A~i​，把样本的损失权重乘上 (1+λA~i​)。DPO 按同一请求下的曝光商品构造偏好对，购买 > 点击 > 仅曝光，并且只对最后一层 SID 回传梯度，前面各层的预测保持不动，免得对齐过程打乱前缀。两者合起来训练：
L=LRFT​+λDPO​LDPO​
线上 RFT 和 DPO 的损失权重比是 20:3，DPO 的 β=0.1。

A Framework for Value-Aligned Modeling and Robust Experimentation

Google Discover 广告团队发现，转化预估模型（pConvs）的离线 Poisson Loss 和线上广告主价值（Delivered Value，每次点击的转化数乘广告主目标单次转化出价 tCPA 再求和）之间的相关系数只有 0.1，离线变好的模型上线后经常不涨。作者把损失里每次点击按 tCPA 加权，并给所有低流量实验配一个同样流量、重新训练的生产模型作对照。按 tCPA 加权后，离线损失衡量的就是广告主真正愿意付钱的那部分转化。离线与线上的相关系数升到 0.65，低流量与高流量实验的相关系数从 0.53 升到 0.93。

Google Discover 广告团队的模型迭代分三步：离线比较新旧模型的损失，小流量 A/B 看广告主获得的价值，最后把通过的改动打包上大流量。过去的问题是这三步之间对不上：转化模型（pConvs）离线泊松损失的变化和线上价值的相关系数只有 0.1，大量离线变好的改动在小流量阶段失败；小流量和大流量结果的相关系数也只有 0.53。这篇论文（RecSys 2026 最佳工业论文）从两头修：离线损失按每次点击对广告主值多少钱加权，让损失下降对应到价值上升；实验流程上逐项消掉系统偏差和噪声。改完以后，离线到线上的相关系数升到 0.65，小流量到大流量升到 0.93，两类模型换用新目标后线上价值合计提升 4.7%，作者估计研发效率约翻倍。

1. 三个阶段、三类误差

拍卖排序阶段有两个模型：pCTR 预测一次展示后的点击，pConvs 预测一次点击后的转化数，两者和广告主出价一起算出拍卖分，进行第二价格拍卖。上线决策看的业务指标是交付价值（Delivered Value，DV）：
DV=i∈Clicks∑​Ti​⋅Ci​
Ti​ 是广告主为一次转化愿意付的目标单价（tCPA），Ci​ 是第 i 次点击带来的转化数。一次 1000 美元床垫的购买，价值超过一百次对商家网站的浏览，而普通的转化预测损失把两者当成同等的转化来算。

每个阶段的耗时依次是 O(X)、O(Y)、O(Z)，X 远小于 Y、Y 远小于 Z，所以前面阶段每做错一次判断，都会浪费后面更贵的资源。作者把测量误差分成三类：目标不对齐（前一阶段测的东西不能预示后一阶段的结果）、系统误差（实验设置带来的偏差）、随机误差（系统噪声带来的方差）。

2. 让离线损失对齐交付价值

2.1 pConvs：泊松损失按 tCPA 加权

pConvs 原来按泊松分布做最大似然，损失是 PL=∑i​Pi​−Ci​logPi​，Pi​ 是第 i 次点击的预测转化数。作者把预测目标从“点击后的转化数”换成“点击后的交付价值”，损失变成加权泊松损失（WPL）：
WPL=i∈Clicks∑​Ti​[Pi​−Ci​logPi​]
为什么加权是对的，论文给了一个推导。设广告主真实获得的价值 v=Ti​Ci​，出价 b=Ti​Pi​，第二价格（广告主实际付的钱）s 的密度为 $f(s)$，单次拍卖的期望收益是赢下拍卖时“价值减成本”的积分 ∫0b​(v−s)f(s)ds。如果 f(s)∝1/s，积分结果是 vlnb−b 加常数，最大化收益等价于最小化 b−vlnb，把 b、v 代回去，去掉与参数无关的常数，就是 WPL。泊松回归在这里有效，不是因为转化数真服从泊松分布，而是因为 1/s 的成本分布近似成立。

2.2 pCTR：从“是否点击”改成“点击几次”

pCTR 原来预测一次展示至少被点一次的概率，用对数损失训练、用 AUCLoss（1 减 AUC）评估。轮播广告一次展示常有多次点击，每多一次点击都有价值，于是团队把目标改成一次展示的期望点击数，线上 DV 提升 1.2%。

3. 离线阶段：系统误差和随机误差

模型都是连续在线训练，每条数据只过一遍，离线评估用渐进验证：每条数据先预测、记损失，再拿来训练。

系统误差有两个来源。一是标签成熟度偏差：转化标签会延迟到达，实验模型比对照模型启动得晚，追历史数据时看到的转化标签更全，同一时间段上的损失看起来更好，其实只是信息更多；解决办法是只在两个模型训练数据质量相同的时间段上比较。二是优化器带来的假象：二阶优化器和 DLRM 这类把特征分组做交互的结构，加一个常数特征就可能改变分组，把需要交互的重要特征分到不同组里。修掉这两类问题后，两个等价模型之间的离线差异稳定在 0.02% 以内，以前这种情况下经常测出显著差异。

4. 线上阶段：小流量对照组要和实验组一样小

4.1 系统误差来自流量大小不同

常见做法是拿小流量的实验模型和大流量的线上模型比，这样一定有偏。原因有三：小流量模型在连续训练里看到的自己的流量少，没法修正自己的预测偏差，这是赢家诅咒；广告主预算是固定的，小流量下预算约束不明显，价值会被高估；大流量下的反馈控制会把预测偏差拉回目标约束，小流量没有这层修正。

作者的做法是定一个标准的小流量规模，把线上模型按这个流量重新训练一份，作为同规模所有实验共用的对照组。需要其他流量规模时，再单独训一个对应规模的对照。改完后，两个完全相同的重训模型之间的 DV 差异接近 0%，以前常超过 1%。

这组对比用 7 个历史实验（旧设置）和 8 个新实验（新设置），小流量到大流量的相关系数从 0.53 升到 0.93。样本少是因为大流量实验成本高，但每个大流量实验跑得久、流量大，单次测量本身很准。两组评估的是同一批模型，两者之间有约 0.75 的相关，作者用考虑这种相关的 Williams t 检验，得到 p<0.05。

4.2 随机误差：截断和期望值

DV 依赖稀疏的转化，置信区间很宽。对单次点击的大额价值做截断，置信区间宽度缩小 40%，偏差小于 3%；用期望 DV（用 pConvs 预测代替实际转化）代替实际 DV，宽度再缩小 70%，偏差约 5%。两者叠加约缩小 82%，2% 流量的实验现在能达到原来 30% 流量实验的精度，同样的流量可以并行跑更多实验。

5. 为什么相关系数决定效率

作者假设离线和线上的结果服从相关的二元正态分布，把离线判断和下一阶段方向一致的概率、小流量判断和大流量方向一致的概率相乘，就是两次判断都正确的概率：
Pgood​=[21​+πarcsin(ρoff​)​]⋅[21​+πarcsin(ρon​)​]
ρoff​ 是离线到小流量的相关系数，ρon​ 是小流量到大流量的相关系数。改进前 0.1 和 0.53，概率约 0.36；改进后约 0.69 和 0.93，概率约 0.65。

正文写的是改进后离线相关系数 0.65，图上标的是 0.69；按公式算，0.69 对应约 0.65 的概率，0.65 对应约 0.64。论文的效率证据是 3 年里 100 多个实验改动：pConvs 每次打包上线包含的成功改动数，以及每位贡献者的改动数，都持续上升，作者估计整体效率约翻倍，具体数字因保密没有公开。

6. 局限

作者承认，所有证据都来自 Google Discover 广告这一个连续训练的线上环境。WPL 的推导依赖成本服从 $1/s$ 分布，作者在附录里说明实际的第二名出价分布衰减更快、尾部更轻，更贴近实际的成本分布留作以后的工作。

另外，DV 本身是论文为了说明问题做的简化指标，实际上线还要看多个相互依赖的指标；小流量到大流量的相关系数只基于 7 个和 8 个实验。

7. 实践意义

  • 如果你的模型服务于按出价排序的拍卖，离线评估损失可以先试着乘上每个样本的业务价值，再看它和线上结果的相关系数有没有提高；不需要改训练，就能判断现有离线指标是否在测错的东西。
  • 小流量实验的对照组应该和实验组同样规模、同样重训方式。拿小流量实验组去比大流量线上模型，测出的差异里混着赢家诅咒、预算和反馈控制的偏差，A/A 实验就能先检查出来。

Lequn Wang, Jiangwei Pan, Linas Baltrunas

Netflix 首页由多行组成，每行是一个主题（比如“韩国电视剧”），行内横排若干部影片。原来的首页由多阶段推荐系统拼出来：先召回候选行和候选影片，再分别排序，最后组页。GenPage 用一个 decoder-only Transformer 直接生成整页：用户历史、账号属性和请求信息编码成 prompt，模型按从左到右、从上到下的顺序逐个生成行 token 和影片 token，每行、每部影片都只占一个 token。训练照搬大模型的流程，先在线上获得正反馈的首页上做下一 token 预测预训练，再用加权二分类（WBC）或强化学习做后训练。约 2 亿参数的 WBC 版本在 14 天 A/B 中把 Netflix 上线决策用的核心互动指标提升 0.24%，端到端延迟降低 20%；强化学习版本还没有上线。

1. 为什么要整页生成

多阶段系统里，召回、排序、组页各有各的模型和目标，特征工程也分散在各阶段。整页生成想解决三件事。第一，一个模型从原始输入直接出页面，要维护的模型少，各阶段目标不一致的问题也随之消失。第二，逐个生成的页面可以用强化学习按整页奖励优化，把行与行之间的相互影响算进去：比如“继续观看”行放在顶部时，用户多半直接续看已经开始的剧，不再往下浏览，论文把这种吸住注意力、让用户停止浏览的能力叫 stopping power。第三，模型质量可以靠加数据、加参数继续提高，不必反复改系统结构。

落到线上有四个约束：首页要实时生成，延迟是第一位的；片库每天都有新片，要处理冷启动；用户兴趣和热点在变，模型要保持新鲜；页面还要满足大量业务规则。

2. 数据怎么变成 token

每条训练样本对应一次首页曝光，包含三部分：上下文（用户历史、账号属性、请求信息）、页面（按版面顺序排列的行和影片）、反馈（播放、点赞、放弃等）。只有上下文和页面被 token 化作为模型的输入输出，反馈经过奖励系统转成监督信号。

团队没有用现成的文本分词器，而是为首页数据定制了 token。“用户 30 天前看了 50 分钟《女子监狱》”这件事，GPT-5 的分词器要 16 个 token，GenPage 只要 4 个：影片 ID、行为类型、行为时间分桶、观看时长分桶。一个影片、一行各对应一个 token，序列更短、推理更便宜，业务规则也能直接写成对某些 token 的屏蔽。行和影片的词表每天更新。

首页通常分几次请求、每次生成几行。每次翻页前，已经生成的行和用户在这些行上的最新行为会追加到 prompt 里，下一批推荐就能同时用上长期偏好和本次会话的行为。

3. 奖励与模型

奖励来自 Netflix 已有的奖励系统，它经过线上 A/B 调校，和用户的长期满意度对齐。系统给页面上每个曝光的影片一个标量奖励：一晚上刷完的剧奖励高，只看了 10 分钟的电影奖励低，曝光后用户放弃的影片得负奖励。整页奖励是所有曝光影片的奖励之和。

模型是标准 decoder-only Transformer，只有一处改动：输入 embedding 和输出投影不共享权重。预训练优化整个词表上的 softmax，WBC 后训练优化每个 token 各自的 sigmoid，两者需要的 logit 数值范围差别很大，拆开权重让模型能同时适应两种目标。线上 A/B 用的是约 2 亿参数的模型，为的是守住延迟预算。

4. 训练

4.1 预训练：模仿线上系统

预训练用线上获得正反馈的首页曝光，给定上下文和已生成的前几个页面 token，预测下一个页面 token。模型从零开始训，不从现成的大模型初始化。这一步让模型学会生成和线上系统相似的页面，但它只是模仿，不直接优化奖励大小；GenPage 上线后，如果反复用自己生成的页面再训练，模型还有退化的风险。

4.2 WBC 后训练：把生成变成逐 token 估值

WBC 让模型在给定上下文和已生成前缀时，估计生成每一个候选行或影片的价值。每个曝光影片的标签取奖励的正负（正向互动为 1，放弃为 0），权重取奖励的绝对值，行的奖励由行内影片奖励汇总得到。按论文的描述，损失写成：
LWBC​=−t∑​∣rt​∣[yt​logσ(zt​)+(1−yt​)log(1−σ(zt​))],yt​=1[rt​>0]
t 是页面上一个曝光的行或影片，rt​ 是它的奖励，zt​ 是模型在该位置给这个 token 的 logit，σ 是 sigmoid。每个曝光目标之外，还随机抽一些 token 当负样本。很少被曝光的影片作为随机负样本被抽中的次数远多于作为正样本出现的次数，于是模型给冷门影片的估值天然偏低，这相当于一个热度先验，避免模型因为少量噪声样本把冷门影片排得很高。

生成时，模型在每一步对所有候选 token 算 logit，贪心选最大的那个，追加到前缀，再生成下一个。在线上排序模型的标准离线评估集上，WBC 模型在加权 AUC 等影片级指标上超过了线上排序模型。

4.3 强化学习后训练：按整页奖励优化

WBC 优化的是单个影片，强化学习优化整页。做法参照大模型的 RLHF：先训一个奖励模型，输入任意一页生成结果，预测这一页的整页奖励（监督目标是奖励系统给出的影片奖励之和），再用 Dr. GRPO（GRPO 的一个修正目标偏差的变体）优化生成策略，训练框架是 verl，推理引擎是 vLLM。策略、参考模型和奖励模型都从预训练 checkpoint 初始化。奖励模型的训练数据来自线上策略，只在和线上相似的页面上可靠，所以策略用 KL 惩罚约束在参考模型附近，防止策略生成那些奖励模型会误判为高分的页面。另有规则奖励，比如页面必须是一行一行的结构，业务上关键的行不能排得太靠下。

5. 上线要解决的工程问题

冷启动有两个办法。一是把新片或直播等时效内容的元数据直接写进上下文 token。二是语义 embedding 融合：每部影片的输入 embedding 由 ID embedding 和基于简介、演员、字幕、类型、视频内容的内容 embedding 融合而成，新片即使交互很少也有可用的表示。

保持新鲜靠多节奏增量训练：隔一段时间在较长的历史窗口上完整做一遍预训练和后训练；两次之间每天从前一天的 checkpoint 继续后训练，数据是最近一天加一部分抽样的历史数据，既跟上新片和热点，又不忘掉旧知识。新行、新影片先用对应类型的兜底 token 初始化，训练时还随机把一小部分已知 token 换成兜底 token，让模型学会处理没见过的 token。

业务规则用约束解码保证：每一步按适用的规则算出可选 token 的掩码，乘到输出 logit 上，只允许合规的 token 被生成。比如要把“热门游戏”行固定在第 2 行，就在第 2 行的位置屏蔽其他所有行 token。规则因请求而异，所以掩码要按请求、按位置动态构造，团队为此改了推理引擎。

每行只自回归生成前几部影片，因为前几部最受注意、最能决定这一行给人的印象；剩下的位置在这个前缀条件下做一次前向，按 logit 取分数最高的合规影片，这叫混合行解码，用来减少解码步数。

6.1 预训练有没有用

Entity AUC 从 0.91 到 0.92 看起来很小，作者换了一种说法：不考虑样本加权时，随机抽一对曝光影片（一个正样本、一个负样本），模型排错的概率从 9% 降到 8%。在成熟的线上系统上，单个改动很少能带来这么大的提升。

6.2 加参数还是加上下文

这组实验要比较两种提升方式的收益：模型从约 1.2 亿参数扩到 9 亿参数，以及模型大小不变、逐步丰富 prompt 的内容和 token 化方式。

模型扩大约 7.5 倍，WBC 损失只降约 1.3%；丰富上下文累计降约 6.9%，好几次单独一项上下文改进的收益就超过整个参数扩大的收益。作者的判断是，当前阶段个性化质量先受限于模型能拿到的信息和表示方式，然后才受限于容量。两组实验的轴不同，上下文的每一步也是在不同数据快照上测相对上一步的改进再连乘出来的，只能做相对比较。

6.3 强化学习是不是在优化整页

这组实验要说明强化学习学到的是整页层面的策略，而不是逐个 token 贪心。奖励在训练中稳步上升，但这是用策略正在优化的同一个奖励模型算的，只能算验证。更有说服力的是多样性：用页面上影片两两之间的 embedding 距离衡量，它不在训练目标里，却也随训练上升。

6.4 线上 A/B

线上对照组是现有的多阶段首页推荐系统，实验组是约 2 亿参数的 WBC 模型。为了沿用资格审核等业务规则，GenPage 在现有系统给出的候选行和候选影片集合里解码。共 5 个实验组，区别在随机负样本的数量和训练时纳入哪些线上曝光。

上线后还观察到两件事。一是会话内的最新行为会很快影响后续推荐，一两天后回落到长期偏好，说明模型确实在使用行为时间戳，原系统做到这一点要靠大量手工特征。二是曝光内容的构成发生了意料之外的变化，比如新片和老片、剧集和电影、高质量和低质量互动的比例都变了。作者推测这是因为 GenPage 的个性化更精准，暴露出从原系统继承来的奖励系统等组件和生成式范式还没对齐，后续会调这些组件。

7. 局限

作者列出的未完成部分有三项：强化学习后训练还没有上线；长上下文仍然靠手工设计的摘要；文本、多模态和推理能力还没有接入。强化学习还有两个开放问题：离线评估依赖策略正在优化的奖励模型，结论是循环的；WBC 完全按影片拆分、整页强化学习完全不拆，两者之间如何利用部分结构还没有答案。

另外，线上实验是在原系统给出的候选集合上解码，召回阶段并没有被替换，所以这次 A/B 验证的是排序和组页，不是完全端到端的生成。

8. 实践意义

  • 如果你在做生成式推荐，可以先检查 token 化方式：一个物品、一个版面单元对应一个 token，序列短，业务规则也能直接写成 logit 掩码，不需要在多 token 的文本词表上维护复杂的约束。
  • 在加大模型之前先丰富上下文。Netflix 的数据里，上下文改进累计带来的损失下降约为 7.5 倍参数扩大的 5 倍。

Generating Personalized Images for Sparse-Interaction Users with Uncertainty-Aware Retrieval and Dense Knowledge Guidance

已录用 RecSys 2026

个性化图像生成通常把用户交互过的图片特征注入扩散模型。用户只有 1–3 次交互时，这几张图未必和目标物品语义相关，注入后会带进无关的风格。UDSIG 先为目标物品找一批语义相近的候选图，再用预训练推荐模型给出该用户对每张候选图的偏好分，挑分高的作参考图；另用活跃用户的密集交互训练一个奖励模型，指导稀疏用户的生成。参考图从全库里挑，就不受用户自己那几次交互的限制。在 POG、SER、MovieLens 三个数据集上，50 人参与的人工评测中，个性化排名最多提升 25.12%。
