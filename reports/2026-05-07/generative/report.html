Beyond Similarity Search: A Unified Data Layer for Production RAG Systems

针对生产环境 RAG 系统中「原型干净/线上掉链子」的鸿沟，论文将根因归结到三处：数据陈旧、租户数据泄露、查询组合爆炸；都来自传统的「向量库+元数据库」分裂式数据层。作者提出基于 PostgreSQL+pgvector+HNSW 的统一数据层，并在 5 万文档基准上：日期过滤查询延迟 -92%、租户隔离查询 -74%、零同步不一致、零跨租户泄露，同步代码量 -93%。还讨论了热-温-冷三层混合架构。

OpenSeeker-v2: Pushing the Limits of Search Agents with Informative and High-Difficulty Trajectories

📖 有深读 · 8 分钟

工业界训练前沿搜索 Agent 的「标准菜谱」是 PT→CPT→SFT→RL 的重资源管线。本文反其道而行之，证明只要用「高信息量+高难度」轨迹，纯 SFT 也能达到 SOTA。三个简单的数据合成改动是关键：扩大知识图谱以丰富探索、扩大工具集、严格过滤低步数轨迹。仅 10.6k 数据上训练 30B 规模 ReAct agent，BrowseComp 46.0%、BrowseComp-ZH 58.1%、HLE 34.6%、xbench-DeepSearch 76.0%，全面 SOTA。

INSIGHT对于生成式搜索/Agent 落地，本工作把「复杂 RL pipeline」破除为可复用的工程问题——重点不在 RL，而在轨迹质量。社区/UGC 搜索若想做 DeepSearch 风格的复杂查询分解，可以先按本文的三条数据合成原则建一条 SFT-only 基线：(1) 知识图谱越大召回越多样；(2) 工具集大小决定 agent 行动空间；(3) 严格过滤低步数轨迹避免 shortcut。这是一条比「先 PT 再 CPT 再 RL」低 10x 成本的复制路径。

1. 问题与动机

OpenSeeker-v2 直面"前沿搜索 Agent 训练被工业巨头垄断"这一现实：训练一个 SOTA 的 Deep Search agent 通常意味着 PT→CPT→SFT→RL 的重资源管线，学术与中小团队无法复现。论文的核心立论是："这条管线真的必要吗，还是数据质量足够时纯 SFT 就够？"作者指出，OpenSeeker-v1 等先前工作虽然探索过 SFT 路径，但它们使用的合成轨迹要么太短、要么知识图覆盖太窄，给模型"shortcut 解题"留下了空间——很多问题靠简单关键词匹配就能解，导致模型学不到长程多步推理。在 BrowseComp / BrowseComp-ZH / Humanity's Last Exam / xbench 这种需要"持续在网页上探索"的 benchmark 上，先前 SFT 模型与重 RL 流程之间存在显著差距。本文要回答的具体问题是：在不引入 CPT 与 RL 的情况下，仅通过提升合成数据的"难度+信息量"，能否让 SFT 训出 SOTA 的搜索 Agent？这一问题对学术界与企业内部"复制工业级搜索 Agent"都有直接意义。

2. 方法详解

Base 模型与运行范式：基于 Qwen3-30B-A3B-Thinking-2507（总参 30B、激活 3B 的 MoE），256k 上下文，运行在 ReAct 范式下，单条轨迹最多允许 200 次工具调用。这一选择本身就反映了团队的核心判断——选 thinking-friendly + 长上下文的 base，让模型能"想深+查多"。

数据合成的三个关键改动（核心方法贡献）：

  1. Scaling Knowledge Graph Size：把每条合成数据所依托的知识子图从 k 个节点放大到 K 个节点，让证据图拓扑更丰富、强制模型做多跳推理而非单跳查找；
  2. Expanding Tool Set：在 v1 工具集基础上扩张工具种类，使 agent 能学到更灵活、功能更丰富的解题模式（搜索、浏览、抽取、对比等组合）；
  3. Strict Low-Step Filtering：硬过滤掉工具调用次数低于 T_min 的"直接命中型"轨迹——这些"shortcut 数据"看起来是正例其实在教模型偷懒。

训练设置：仅 10.6k SFT 样本，无 CPT、无 RL。论文未给出 optimizer/学习率/batch size/硬件的具体数字（这是论文实证披露层面的薄弱点）。

轨迹统计佐证设计动机：合成轨迹平均工具调用步数 64.67（v2）vs 46.97（v1）vs 36.01（RedSearcher），直接量化"任务难度上升"。这是三条改动的最直观体现：扩图+扩工具+过滤短轨迹，自然产出更长、信息更密的训练样本。

3. 核心技术贡献

  1. 数据难度替代 RL：把"复杂的 RL pipeline"问题降维成"高质量数据合成"问题。前者技术栈深、需要 reward model + rollout，后者只需把图扩大、工具加多、滤掉简单样本。这是一条让学术团队也能跑出 SOTA Agent 的实操路径。
  2. 三条简单可复现的合成原则：图大小、工具数量、最小步数，每一条都对应一个在 v1 上做不到的"长尾难度"，且互为正交。任何团队都可以单独 ablate 验证。
  3. Trajectory Length 作为难度指标：用平均工具步数定量衡量数据难度，给后续工作提供了可比较的标尺。
  4. 挑战 Scaling 假设：在 30B 参数下，10.6k SFT 数据居然能击败 671B DeepSeek-V3.1（BrowseComp 46.0% vs 30.0%）和 Claude-4.5-Sonnet（24.1%）——证明对于 deep search 这类任务，"训练数据轨迹质量"的影响可能远大于参数规模。

最显著的提升在 BrowseComp-ZH（+11.4）——中文长程搜索本身是行业弱点，论文的"扩图+严格过滤"在中文知识图上效果尤为突出，说明数据难度论对低资源语种提升更大。

与 v1 对比（同 base 系列）：BrowseComp 29.5%→46.0%（+16.5），BrowseComp-ZH 48.4%→58.1%（+9.7），xbench 74.0%→78.0%（+4.0）。增益不是来自 base 模型升级，而是来自数据合成改造——这是论文最有说服力的对照。

惊人发现：OpenSeeker-v2 在 BrowseComp 上以 30B 击败 671B DeepSeek-V3.1（30.0%）与 Claude-4.5-Sonnet（24.1%），说明在"网页深度搜索"这类高度依赖工具使用模式的任务上，参数规模并非主导因素，反而是"是否在长程多步轨迹上充分训练过"决定上限。

实验局限：论文没有给出三条数据合成改动各自的 ablation（图扩大单独贡献多少、工具扩张单独贡献多少、低步过滤单独贡献多少），这是它的方法学短板。

5. 局限与未来方向

论文未设独立"限制"章节，但隐含约束清晰：

  1. 模型规模仅 30B：未尝试 70B/100B+，扩到更大规模数据是否仍 SOTA 未知；
  2. 基准只 4 个：BrowseComp 系列+HLE+xbench 都是"网页深搜"型，不能覆盖代码搜索、企业知识库搜索、垂直领域多模态搜索等长尾场景；
  3. 训练超参未披露：无 learning rate / batch / 训练步数等关键数字，复现门槛高于论文宣称；
  4. 缺少线上 A/B：所有结果都是离线 benchmark，没有真实搜索产品线上对比；
  5. 三条数据改动未做 ablation：哪一条贡献多少不清楚，给后续优化方向留了未解的空白。

6. 工业实践意义

对社区/UGC 搜索做"DeepSearch 风格复杂查询分解"的实践有三条直接启示：

  1. 先建一条 SFT-only 基线：不要急着上 RL。按 OpenSeeker-v2 的三条原则合成 1 万条轨迹（扩大业务知识图 → 扩工具集 → 过滤短轨迹），用 30B 级 thinking 模型 SFT，作为"DeepSearch v1"。论文证明这条路径在多个公开 benchmark 上能击败 RL 重型方案——对中小团队是 10x 成本下降。
  1. 数据质量比数据量重要：10.6k 数据胜过百万级 RL rollout，背后是"每条轨迹都强制走多步推理 + 多工具组合"。社区搜索可以模仿：把热门帖、问答、评论组成的"业务知识图"作为合成基底，强制每条轨迹必须跨 5 个以上节点+至少 3 种工具，过滤掉"直接搜关键词找答案"的简单样本。
  1. 部署考量：30B-A3B 激活 3B 的 MoE 推理对工业部署相对友好（A3B vs Dense 70B+ 显存压力差很多），但 64 步以上的工具调用链对延迟影响显著（每步 1-2s 网页 fetch+LLM 推理），社区搜索若要做实时 DeepSearch，需要分级触发（仅高复杂度 query 走 64 步链路，简单 query 走 1-step 兜底）。论文未给延迟数字，落地团队需要自测。

可借鉴的"避免坑"：论文未做三项数据合成改动的 ablation，落地团队应该在自己业务上做 ablation——某些场景下"扩工具集"提升很小（业务工具天然有限），重点应放在"扩图+过滤短轨迹"。

Revisiting General Map Search via Generative Point-of-Interest Retrieval

Tencent

针对地图搜索中 query 模糊、上下文异构的痛点，论文从「生成式」视角提出 GenPOI：把异构搜索上下文与 POI 统一序列化为结构化 token 序列，借 LLM 的上下文建模能力做生成式 POI 召回。两个核心组件：(1) Geo-Semantic POI Tokenization，把每个 POI 编码为含语义+地理信息的紧凑 token 序列，给 LLM 注入空间感知；(2) Proximity-Aware Constrained Generation，限制解码空间确保生成的 POI 地理上有效。在 Tencent 地图 1000 万级 POI 工业数据上验证。

INSIGHTGenPOI 给社区/UGC 搜索的启示是：当 query 高度上下文依赖且语义浅匹配失效时，「把候选 ID 编码成可解码的 token 序列+约束解码」是比「两阶段召回排序」更自然的范式——尤其适合短文本帖子搜索这种「用户表达模糊+上下文丰富」的场景。可借鉴的设计：semantic ID 时同时注入位置/类目等结构化属性、用 trie/约束解码兜底候选合法性，避免 LLM 幻觉出不存在的 item。

Sparse Memory Finetuning as a Low-Forgetting Alternative to LoRA and Full Finetuning

针对 LLM 适配新任务时的灾难性遗忘问题，作者复现 Sparse Memory Finetuning (SMF)：给模型加 key-value memory 层，每步只更新当前 batch 读取最多的少量 memory 行。在 Qwen-2.5-0.5B-Instruct 上对比 LoRA 与全量微调：SMF 在 MedMCQA 提升 +2.5pp，同时 WikiText perplexity / TriviaQA 仅漂移约 1pp，遗忘明显小于 LoRA / 全微调。比较了两种行选择策略：KL 散度 vs TF-IDF，前者更平衡两类遗忘指标。

INSIGHT对于在线推荐/搜索的「持续微调」场景这是一条值得关注的路径：传统 LoRA 在领域漂移下会让模型「知识穿仓」，SMF 通过显式存储+稀疏写入把「通用能力 vs 领域特化」解耦。社区 UGC 搜索如果走 LLM 排序+周更微调，可以试 SMF：每周只更新少量 memory 行而不是全 LoRA 矩阵，能在追新热点的同时保住 base model 的通用语义匹配能力。

RAG over Thinking Traces Can Improve Reasoning Tasks

通行观点认为 RAG 对推理任务收益有限。本文挑战这一假设，指出问题出在语料而非 RAG 本身：与其检索文档，不如检索「思考轨迹」——即模型在求解过程中产生的中间推理片段。作者提出 T3 离线方法把这些 trace 转成结构化、检索友好的形式。在 AIME 2025-2026、LiveCodeBench、GPQA-Diamond 上验证：retrieve-then-generate 的简单管线就能稳定优于无 RAG 基线和检索静态文档的 RAG。

INSIGHT把「思考轨迹」作为可检索语料，对于做「复杂查询理解」的搜索系统是一条新思路。社区搜索里很多 query 是带推理（A 和 B 哪个更适合 C 场景），可以离线让 LLM 跑大量类似 query 的思考过程并结构化入库；线上检索这些 trace 比检索原始帖子更直接命中「如何回答这类问题」，相当于把推理能力外置到检索语料里——比 fine-tune 推理模型成本低很多。

SURE-RAG: Sufficiency and Uncertainty-Aware Evidence Verification for Selective Retrieval-Augmented Generation

RAG 把答案锚到检索段落里，但「检索 ≠ 验证」——一段证据可以话题相关却不足以支撑结论。作者把这个 gap 形式化为「证据充分性验证」：给定问题、候选答案、检索证据，预测证据是 supports / refutes / insufficient，并默认拒答。SURE-RAG 用一个共享的 pair 级 claim-evidence verifier 产出局部关系分布，在 set-level 聚合出 coverage、relation strength、disagreement、conflict、retrieval uncertainty 五维信号，给出可审计的三分类决策。

INSIGHT对生成式搜索/问答场景的核心启示：单段打分永远抓不到「缺关键跳」和「未消解冲突」，必须做集合级证据聚合。社区搜索里很多问题答案分布在多帖里，SURE-RAG 那五维聚合信号（coverage / 冲突 / 不确定）正好可作为生成式答案的「敢不敢回」开关——拒答其实是一项有质量护栏价值的产品决策。

Rethinking Reasoning-Intensive Retrieval: Evaluating and Advancing Retrievers in Agentic Search Systems

推理密集型检索的目标不是找话题相关而是找下游推理可用的证据。现有 BRIGHT 等基准 gold 集窄、隔离评估，合成训练语料只优化单段相关性。作者推出 BRIGHT-Pro 专家标注基准：每个 query 扩展为多面 gold 证据，并在 static + agentic 双协议下评估检索器；同时构建 RTriever-Synth 合成语料，用 aspect 分解生成「互补正例 + 正例条件硬负」，LoRA 微调出更强的 RTriever。

INSIGHT对生成式搜索的启示：当下游是 agent 多步推理时，检索器要被当作「证据组合器」而非「段落匹配器」训练——硬负应是「话题相关但推理不充分」的诱饵。社区搜索如果接 agent 链路，可以把帖子按「信息面」拆，按 aspect 合成互补正/硬负，用 LoRA 增量微调 reranker；这比直接用通用 embedding 在 agent loop 里反复捞重复内容性价比高得多。

Revisiting Graph-Tokenizing Large Language Models: A Systematic Evaluation of Graph Token Understanding

Graph-Tokenizing LLMs (GTokenLLMs) 把图压成「图 token」作为 LLM 前缀输入。作者反问：LLM 真的理解这些 token 吗？他们形式化统一框架，提出 GTEval 评估管线，通过格式与内容两层 instruction 变换探查图 token 理解。在 6 个代表性 GTokenLLMs 上的实验得出三条结论：(1) 现有 GTokenLLMs 并未充分理解图 token；(2) 不同模型在格式 vs 内容扰动下表现不对称；(3) 微调不一定能修复语义理解缺陷。

INSIGHT把这条结论搬到生成式推荐/检索：semantic ID 这类把 item 压成离散 token 给 LLM 用的范式，可能存在和 GTokenLLM 一样的「形式可见、语义未通」问题。落地建议：在用 RQ-VAE/codebook 把 item 编码进 LLM 时，必须设计像 GTEval 这样的「穿透式」探针，验证 LLM 真的理解这些 token 的语义而非只是当作位置占位符——否则 scaling law 会被「模型其实没看懂 ID」拖后腿。

A Benchmark for Interactive World Models with a Unified Action Generation Framework

实现 AGI 需要能自适应交互的 agent，交互式世界模型为感知-推理-行动提供可扩展环境。论文提出 iWorld-Bench：33 万视频片段中筛 2.1k 高质量样本，覆盖多视角/天气/场景；针对世界模型行动模态差异，设计 Action Generation Framework 统一评估，含 6 类任务、4.9k 测试样本，联合评估视觉生成、轨迹跟随、记忆。在 14 个代表性世界模型上识别出关键能力 gap。

INSIGHT对生成式搜推：交互式世界模型本质上是「action 序列的生成模型」，与生成式推荐里「用户行为序列的生成模型」在数学结构上是同源的。本文的 Action Generation Framework 把多模态行动统一进同一 token 空间评估，这一思路可借鉴：把推荐里的「曝光/点击/收藏/分享/停留」等多类型行为统一编码成 action token，让生成式推荐模型既学序列又学行为分布。

STORM: A Spatio-Temporal Factor Model Based on Dual Vector Quantized Variational Autoencoders for Financial Trading

STORM 提出基于双 VQ-VAE 的时空因子模型，用于量化金融交易。两个 VQ-VAE 分别从时间维度（同一资产历史）和空间维度（跨资产横截面）学习离散潜在因子码本，在统一时空潜空间内表达资产状态；下游基于这些离散因子做收益预测和组合优化。WSDM 2026 接收。

INSIGHTSTORM 把 VQ-VAE 双码本拆「时间×空间」二维这一架构对生成式推荐有迁移价值：推荐里同样存在「用户历史时序 vs 跨用户横截面行为」的双向结构，用两个码本分别压时序和分布、再交叉融合，比单一 RQ-VAE 更能捕获「群体行为」信息。该思路可作为下一代 semantic ID 设计参考。
