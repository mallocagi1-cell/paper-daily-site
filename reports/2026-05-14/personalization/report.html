Make It Long, Keep It Fast: End-to-End 10k-Sequence Modeling at Billion Scale on Douyin Recommendation

本文提出一套生产级长序列建模方案，将抖音推荐系统的用户历史序列扩展到 10k 长度同时维持线上延迟与成本预算。核心包含三项创新：Stacked Target-to-History Cross Attention (STCA) 用目标对历史的堆叠交叉注意力替代历史自注意力，将复杂度从二次降到线性；Request Level Batching (RLB) 在同一用户/请求内聚合多个目标共享 user 侧编码，大幅降低序列相关的存储、通信与计算；长度外推训练策略 (短窗训练、长窗推理) 使模型泛化到生产长度。系统已在抖音亿级 DAU 推荐场景全量上线，离线 AUC 与在线核心指标均有显著提升。

Make It Long, Keep It Fast: 抖音 10k 长序列端到端建模深度解读

1. 问题与动机

工业短视频推荐的核心矛盾是：用户行为历史动辄数千条，但主流系统沿用两段式架构 (检索 + 排序) 截断序列、牺牲端到端优化。Douyin 的目标是让模型直接吃 10k 长度的用户历史，同时不打破生产环境的延迟与算力预算。作者强调 standard Transformer self-attention 的 O(L²) 复杂度让 L=10k 几乎不可行：他们测得 self-attention 在 L=10k 需要 236.26 GFLOPs，而本文方法只需 21.06 GFLOPs——大约 11 倍差距。

更本质的洞察是：与 NLP/CV 的 scaling law 不同，推荐系统受 user-generated data 制约，扩 token 数最直接的来源就是用更长的历史。作者通过实验确认了推荐场景下 "性能随序列长度可预测放大" 的 scaling 行为，因此长序列是一条值得投入工程力的扩展轴。这一动机区别于以往工业长序列方案 (SIM/ETA/TWIN) 主要走 "检索精简" 路线——本文要的是 end-to-end 建模整段历史。

2. 方法详解

整套方案由三块组合而成：STCA + RLB + 长度外推训练。

STCA (Stacked Target-to-History Cross Attention)

核心是把 history 内部的 self-attention 替换为 target-only 的 cross-attention：target 作为唯一 query 去 attend 历史序列。复杂度从 O(L²·d_h) 降为 O(L·d_h)。多头公式：

α^(i,j) = softmax((q^(i) W_Q^(i,j) (X̃^(i) W_K^(i,j))^T) / √d_h)
o^(i,j) = α^(i,j) (X̃^(i) W_V^(i,j))

层间通过 target-conditioned fusion 堆叠——每层输出拼上 target embedding 再用一个可学习投影压回固定维度，从而能堆深做多层信息聚合。一个关键工程优化是先算 attention 权重再扩展 value，避免实例化长度 L 的中间 K/V 张量。

RLB (Request Level Batching)

传统训练每个 (user, target, label) 是独立样本；RLB 把同一用户的 m 个目标合成一个 micro-batch，user/history 编码 Φ_user(ℋ) 只算一次被全部目标复用。Loss 写成 ℒ_u = (1/m) Σ_k ℒ_BCE(ŷ(u, t_k), y_k)，根据期望线性性它依然是经验风险的无偏估计。系统侧收益：L=512–2k 时序列相关带宽下降 77–84%，端到端训练吞吐提升 2.2×，结合 kernel 优化达到 5.1×；可训练最大序列长度提升约 8×；Parameter Server CPU 与通信带宽各降 50%。

长度外推训练 (Train Sparsely, Infer Densely)

训练平均长度 L_train^avg ≈ 2k、推理 L_infer = 10k，外推比 ρ_extra = 5。引入 Sequence Sparsity 指标 SS = L_train^avg / L_train^max（2k/10k ≈ 20%）。训练时按 U 形 Beta 分布在 [L_min, L_max] 内随机截断序列，构造长短混合 curriculum。截断策略对比表明 "保留最近交互" (temporal suffix) 显著优于随机采样。还实现了 ragged 计算 + index-based target-attention kernel，处理变长序列时不引入 padding 浪费。

训练 curriculum：先在 L=512 预训稳收敛，再切到 L=2048 继续训。模型架构 4 层 STCA、d=256、h=8、FFN expansion ratio r=4、SwiGLU 激活；RLB micro-batch m=8。

3. 核心技术贡献

  1. STCA 把推荐长序列的 attention 从 O(L²) 降到 O(L)：通过用 target 替代 history-token 作 query，避免了 history 内部的二次注意力。该取舍背后的假设是——推荐场景下我们只关心 "history 中哪段对预测当前 target 重要"，并不需要让 history 自己彼此交叉注意。
  2. RLB 给出了一条 user-tower 摊薄的训练范式：传统训练把 (u, t, y) 当独立样本浪费了大量 user 侧重复计算；RLB 用统计上的无偏聚合解锁了 ~8× 的最大可训长度上限，同时显著减少 PS 通信和 GPU 显存。
  3. U-shaped sparsity + 短训长推：对比 α=10 (skewed)、α=0.5、α=0.02 (U-shaped)，U-shaped 在 +0.21% AUC 上最优，说明 curriculum 里要同时保留 "很短" 和 "很长" 两个尾巴。最重要的是 L_train^avg=2k 时已能拿到全量 10k 训练增益的 ~80%。

5. 局限与未来方向

作者明确提到的约束：

  1. 训练稳定性问题：直接在 L=2048 训练不稳定，必须先 L=512 预训。
  2. 总成本权衡：取消 TWIN(10k) 检索后 GPU +33%、CPU −16%，净成本 +17%——作者称 "在在线增益面前可接受" 但仍是真实开销。
  3. 位置编码细节未充分披露，长序列外推超过 10k 的行为未讨论。
  4. RLB 的同 user 内 target 相关性虽不破坏期望无偏性，但对方差/收敛速度的影响未深入分析。
  5. 实验完全在 Douyin 短视频场景，e-commerce/news 等其它领域适用性未验证。

6. 工业实践意义

对国内做工业搜推的团队，这篇论文有几个高 ROI 借鉴点：

  • STCA 是 SIM/ETA/TWIN 之后值得新尝试的长序列范式：不再做先检索后排序的两段拆分，而是端到端用 target-to-history 的 cross-attention 一把建模全段历史。落地时主要风险点是 RPC/显存——RLB 的 m=8 micro-batch 给出了一条务实工程路径。
  • RLB 的思想可独立复用：即便不上 STCA，把推荐训练样本按 user 聚合、user-tower 计算共享，是低风险的训练吞吐优化。对召回/粗排/精排几乎都通用。
  • 短训长推：建议工业团队不要直接在 L=10k 训练（不稳且慢），先 L=512 预训、再切 2k 继续训、推理时跑 10k 即可拿到 ~80% 全量增益。U 形 sparsity 是关键细节。
  • 部署成本约束很硬：方案虽强但还是要 +17% 总成本买在线 +3.3% Finish。要去说服业务 trade-off 时这是真实数据点。
  • 对社区/UGC 场景：UGC 用户行为同样长尾稀疏、低活占多数，本文 "低中活提升最大" 的结论高度可迁移——长序列建模对低活用户的收益可能是最值得期待的方向。

LEAPS: An LLM-Empowered Adaptive Plugin in Taobao AI Search 深度解读

1. 问题与动机

LLM 时代用户搜索行为正从离散关键词转向自然语言多约束 query。典型案例：『我想买亚麻男士西装，500-800 元，适合海滩婚礼，不要纯黑、不要大花纹』——5 个并列约束。现有电商搜索面临两难：精确 NL query 频繁触发零结果，强行简化 query 又会返回大量噪声逼用户自己筛。LEAPS 一个月线上 A/B 显示 Sufficient Result Rate (首屏≥10 个相关 item 的概率) 从 77.0% 提升到 91.4%——也就是说基线状态下接近 1/4 的搜索请求其实首页相关内容不足。该问题在淘宝月活数亿的规模下意味着大量用户被劣质结果劝退。

业界已有方案如 Query2Doc (查询扩展)、MiniELM (端到端语义召回)、ICL LLM Pipeline (上下文学习重写) 等都尝试过用 LLM 改造搜索，但要么对复杂多约束 query 仍乏力，要么改造主搜引擎成本过高。LEAPS 选择走 "non-intrusive" 路线——把现有搜索引擎当黑盒，只在两端各挂一个 LLM 插件。

2. 方法详解

整体框架是 Broaden-and-Refine：上游 Query Expander 把单 query 扩展为多个互补 query 子集合并到候选池，下游 Relevance Verifier 用多源信号 + CoT 推理逐条裁剪。

Query Expander (ℰ) 三阶段训练

Stage 1 - Inverse Data Augmentation：从精选商品 title 反向生成口语化 query（用 DeepSeek-R1 合成符合淘宝真实用户语料的表达），按标准 NLL warmup 模型：
ℒ_align(θ) = -E_(x,y)~D_align Σ log π(y_i | y_0:i-1, x; θ)
作用是给模型注入电商 query 的领域语言。

Stage 2 - Posterior-Knowledge SFT：假设 query 的多个属性有层次重要性，并非每个都是核心约束。系统对原 query 做属性置换生成多个 candidate 重写、提交给搜索引擎、用 Verifier 度量每个重写返回的相关商品占比，取 top-k=4 个最佳作为 SFT 目标 (Algorithm 1)。500-query 审计显示 mocked 与真实 user-profile 排名的 Spearman ρ≈0.96，表明用户侧特征对 "重写质量评估" 几乎正交，证明该 posterior 信号可信。

Stage 3 - Diversity-Aware RL (GRPO)：单条 SFT 只能优化单个重写，无法刻画 "一组重写的集合覆盖力"。Effective Relevance reward 通过去重直接惩罚冗余：
R_eff = |I_r| / N，其中 N=100 是每个 query 的检索预算，I_r 是 Verifier 判定相关且去重后的商品集合。RL 训练限制 R_eff ∈ [0.1, 0.9] 以稳定，group size 8，KL β=0.04。

Relevance Verifier (𝒱)

多源数据融合：商品页 OCR 文本、精选高质量评论、价格、销量、店铺/品牌信誉、用户地理位置——一起组装成 "重构粒度上下文"。

CoT 推理内化：多指令 SFT 用 ~800k query-item pair（按四档复杂度分层采样）训练 Verifier 预测二分类 relevance + 简短理由。双标 + 分歧裁定 (分歧率 ~8%) 在 2000 对审计上达到 Cohen's κ=0.81。CoT rationales 由 DeepSeek-R1 在不暴露 ground-truth label 的情况下生成，保留的 rationale 中 ≥92% 与 label 一致。一个 5000 对的审计显示 Verifier 与人工标注的一致性 ~95%，κ=0.88。

3. 核心技术贡献

  1. Posterior-Knowledge SFT 替代传统 RL 探索冷启动：用引擎+Verifier 反馈替代昂贵的 RL 试错冷启动，ablation 显示这是 Expander 三阶段中最关键 (去掉 -0.14 F1，是单点最大下降)。
  2. Effective Relevance reward 强迫覆盖：相比按重写单独算 reward，去重后归一化的 R_eff 强制 RL 优化 query 集合的边际信息增益，与传统 GRPO 在 LLM RLHF 中的范式不同。
  3. 黑盒搜索引擎假设的工程价值：LEAPS 只通过 query 提交 + 结果聚合与底层引擎交互，整个方案 plug-and-play，跨不同 backend (BM25/embedding/hybrid) 均可适配——这对任何想给现有大型搜索系统加 LLM 增强的团队是关键设计决策。
  4. 多源 + CoT 的 Verifier：相比 raw LLM-as-judge 直接打分，融入价格/销量/OCR/评论 + CoT rationale 让 verifier 在工业混杂噪声下大幅提升精度 (去掉 multi-source 降 0.10 F1，去掉 CoT 降 0.09 F1)。

  • 全部 p<0.001。200 个多约束 query 的 production 审计：LEAPS 在 84% 的 case 上首页完全合规 (vs 控制组 41%)。

5. 局限与未来方向

作者明确指出：

  1. 重写权重平均化：N=100 检索预算在多个重写间均等分配，未来应做 confidence-aware allocation——置信度高的重写分配更多 slot。
  2. 稀有实体兜底：在含罕见实体的 idiosyncratic query 上仍有 low-result 残留，建议联合 retrieval-side 的 index expansion。
  3. （未深入披露）调用 LLM 的成本：双 Qwen3-14B 推理叠加在每次搜索请求上，对长尾 QPS 与冷启动延迟的影响有限说明。
  4. 在 ESCI 这种英文公开集与 Taobao 中文电商之间的迁移性未充分实验。

6. 工业实践意义

对要把 LLM 引入工业搜索/推荐的团队：

  • Plug-in 思路比改主搜引擎更落地：LEAPS 的 Broaden-and-Refine 是低风险高 ROI 范式，搜索引擎几乎不动，所有 LLM 创新都在两端插件里——可独立迭代、独立回滚、独立扩缩容。对老牌成熟系统尤为友好。
  • Posterior-Knowledge SFT 是个被低估的范式：与其纯 RL 探索，不如先用既有 ranker/Verifier 的反馈做 SFT 冷启，再切 RL 提升 ceiling。这套两段范式对 query rewrite、生成式 retrieval、relevance modeling 都通用。
  • 多源 + CoT Verifier 工业可复用：直接照搬到内容/UGC 平台——价格/销量换成内容质量分、收藏数、作者权威度等，CoT rationale 既提精度又可日志化便于人工 debug。
  • 生产部署细节：双 14B 模型 INT8 + TP=2，P99 ~290ms，峰值 QPS ~150——给团队部署 LLM-in-the-loop 搜索一组实参考。Verifier 用 ~800k 高质量人工标注数据是关键投入，没这个数据规模性能掉得很厉害。
  • 对社区/UGC 搜索：UGC query 经常更口语化、约束更分散，LEAPS 在 Heavy≥4 约束上 0.32→0.70 的提升暗示这套范式恰恰击中 UGC 搜索的痛点。Verifier 的多源信号在 UGC 场景可换成内容质量、互动数据、作者画像等，迁移直接。
